#### 我的答案
A1: 此时Pod不一定起来了，要用kubectl get pods XXXX 查看确认。k8s会在每次reconcile loop检查期望状态是不是等于实际状态，不一致的话，会尝试让实际状态变成期望状态。在apply depoyment后，k8s在下一次reconcile loop里会检查到当前状态不等于期望状态（有个新pod或更新过的pod），这时候会去重启pod。

A2：不应该比较事件里的old/new，永远看spec和实际的状态，如果不一致，要把实际状态调成期望状态。漏掉事件会导致实际状态无法更新到期望状态，reconcile loop这种模式就没这个问题，因为它总是会“”时不时地“看一眼集群状态和期望状态是否一致。

A3：worker 会 reconcile一次，worker会去重。worker拿到key后，去etcd缓存里重新拿最新的状态定义。

A4：当``obj``不是``*corev1.Pod``的时候，应该用``pod, ok := obj.(*corev1.Pod) if ok {xxx}``来判断。

A5: 有乐观锁机制，2个进程里有一个会更新失败：进程A和B都读到``resourceVersion=470``，假设B先完成更新，这时候在k8s里resourceVersion被更新到471，然后进程A再尝试去更新，k8s看到请求里resourceVersion还是470，低于当前实际版本471，所以更新失败。

A6: 这3个annotation分别定义了:
1. hook的执行时机：pre-install,pre-upgrade（在helm install/update执行前）
2. 执行顺序的权重，数字越小排名越靠前
3. hook的删除策略

A7: 会读不到这个config map，因为pre-upgrade hook是在upgrade前执行的，而这个config map是在upgrade后创建的。‘

A8：drop table会导致多次跑helm结果不一样，因为之前的数据会被删掉。应该用"migration"机制来完成表的更新/失败回滚(up/down)

A9：第一段有问题，没有``{{ - ``会导致缩进多了空格（语法没错，但是难看），另外``indent``不会换行，会导致模版里后面一行的内容会接着这一行。

A10: 在执行helm install或者upgrade的时候，要加上``set XXXX=YYYY``，才能在模板里用``.Values.XXX``。`required`相当于做了空值校验，没值的话helm install/upgrade会失败，不会带着错误的数据去执行。

### 小题 B · 设计题（可以查文档，要写理由）

**B1.** 巡检 CLI 用 `List`，controller 用 `informer`。
如果把巡检 CLI 做成每 5 分钟跑一次的 CronJob，该换成 informer 吗？为什么？

**B2.** api 的 `/healthz` 会 Ping 数据库。

**B3.** ⭐ 讲义 §2.3 说「spec 是别人的，status 是你的」。
你的 operator（D20）管理一个 `Order` 自定义资源，reconcile 时发现订单已支付，
想把 `spec.status` 改成 `paid` 方便下次判断。这样做有什么问题？应该写在哪？

**B4.** Helm 的 `--set image.tag=$GIT_SHA` 和把 tag 写进 `values-prod.yaml` 提交，
各在什么场景下合理？「线上到底跑的是哪个版本」这个问题两种方式各怎么回答？

**B5.** chart 里的 dev Postgres 用了 emptyDir。
有人提议「加个 `persistence.enabled` 开关，prod 也用这个 Postgres 模板」。
你同意吗？从「chart 的职责边界」角度说理由。

#### 我的答案

B1: “5 分钟跑一次的 CronJob”也不一定要用informer，当集群里面pod不是很多，只是`list`也不会有什么性能问题。当集群很大，并且需要很频繁去查询状态的时候，要考虑用informer

B2: 数据库挂了会导致`/healthz`接口不能返回成功的response，readinessProbe 和 livenessProbe会失败，重启pod也不能解决问题，因为是数据库的问题。readinessProbe 的实现最好不要依赖外部系统，只看这个container本身有没有起动成功，不然的话，在这个case里，会导致pod最终启动失败，因为readinessProbe 失败了，但其实问题根本不在这个pod，会误导人。

B3: 如果有人在`Order` 这个自定义资源在status改成paid之前把订单取消了，那么在下次reconcile loop里，订单状态还是会被改成"paid"，这就不对了。reconcile loop不知道实际业务逻辑，只是无脑改状态，这类业务逻辑不应该依赖k8s的资源状态，应该控制在业务代码里。

B4: 用`--set image.tag=$GIT_SHA`更合理，这样避免每次提交代码，都更新一下`values-prod.yaml`，这样相当于helm chart的定义也比啊换了，要bumpup chart的version了（其实不需要）

B5： 我认为不应该这样。prod的数据库配置，应该和dev严格分开，prod有严格的安全要求，dev配置我们可以把用户名，密码之类写在里面，prod绝对不允许。

**A1 ⚠️** —— 「不一定起来了」对，reconcile 的描述也对。但「**会去重启 pod**」不对：
apply 一个新 Deployment 时没有 Pod 可重启。真实链条是**一串 controller 接力**：
Deployment controller 建 ReplicaSet → ReplicaSet controller 建 Pod → scheduler 填 `nodeName`
→ kubelet 起容器。每一环都是一个独立的 reconcile loop，各管一层。
「谁」的答案不是「k8s」，是这四个。

**A2 ✅** —— 「时不时看一眼」就是 informer 的 resync，说到点上了。

**A3 ⚠️ 两个词用错** —— 结论对（1 次）。但去重的是 **workqueue** 不是 worker；
拿对象是从 **informer 的本地缓存（Indexer/Lister）** 拿，不是「etcd 缓存」——
etcd 在 API server 后面，controller 永远碰不到它。§4.4 那张图：worker → Lister.Get → 缓存。

**A4 ⚠️ 只答了一半** —— comma-ok 是对的，但**什么时候会不是 Pod**没答：
watch 断线重连期间对象被删了，informer 塞给你的是 `cache.DeletedFinalStateUnknown`（墓碑）。
而且你的修法 `if ok { ... }` 会**把墓碑静默丢掉**——那个 Pod 的删除事件就丢了，
缓存里它还在。正解是拆墓碑：

```go
if tomb, ok := obj.(cache.DeletedFinalStateUnknown); ok {
    obj = tomb.Obj
}
```

或者直接用 `cache.DeletionHandlingMetaNamespaceKeyFunc`（§5.1 的示例就是）。
⭐ 「断言失败就跳过」和「错误就 return nil」是同一种懒：把一个明确的信号当成没发生。

**A5 ⚠️ 第二问没答，第一问一个词错** —— 乐观锁的流程对。但「470 **低于** 471」不对：
§3.3 强调过 `resourceVersion` **只能比相等，不能比大小**——它是 etcd 修订号，
跨对象、跨压缩后没有序关系，API server 也只做 `==` 判断。
「和 `RowsAffected` 的共同点」漏答了：都是**不加锁、靠版本号在写入时检测冲突、
判断由存储层做、冲突了重读重试**——JPA `@Version` 的 `UPDATE ... WHERE version=?` 同一个东西。

**A6 ⚠️ 第三个没展开，「少了会怎样」没答** —— 前两个对。第三个的两个值各是什么：
`before-hook-creation` = 下次跑之前先删掉上次的同名资源；`hook-succeeded` = 成功后删。
少了整行的话 Helm 默认给 `before-hook-creation`，所以**不会坏**——
但跑成功的 Job 会一直留在集群里（`kubectl get jobs` 永远有一个 Completed），
而且 `helm uninstall` 不删 hook 资源，你今天亲手删过一次。
⭐ 你实验里还学到了第二个 annotation 的真正用途：**hook 之间有依赖时，weight 是唯一可靠的排序手段**。

**A7 ✅** —— 「普通资源在 hook 之后才创建」，对。你在 Secret 上又撞了一次同一个坑。

**A8 ✅** —— 「不幂等 → 用迁移工具」，方向对。补一句：迁移工具的核心不是 up/down，
是**版本表**——记录哪些跑过，只跑没跑过的。幂等由工具保证，SQL 本身不用幂等。

**A9 ❌** —— 这题在讲义 §6.4 有实测输出，答反了。
第一段（`indent`）**不是「多了空格但语法没错」，是直接 YAML 解析失败**：
模板行自己有 2 格缩进，`indent 2` 又给每行加 2 格，结果**第一行 4 格、后面各行 2 格**，
`did not find expected key`。第二段（`{{-` + `nindent`）才是对的。
「indent 不换行导致后面一行接着这一行」也不是实际现象。
你 `deployment.yaml` 里写的是对的（`{{- toYaml .Values.resources | nindent 12 }}`），
但说不出 `indent` 为什么错——**知道怎么写，不知道为什么**。

**A10 ❌** —— 题目问的是「值是什么：报错、nil、还是空字符串」，答的是「要 `--set`」。
正确答案：**空字符串**。`values-prod.yaml` 没有 `secrets` 段，但 `values.yaml` 有
`secrets.DATABASE_URL: ""`——§6.5 讲的**按 key 深度合并**，缺的 key 从默认值来。
如果连 `values.yaml` 都没定义，那就是 **nil**（模板里渲染成空，不报错）。
两种情况 `required` 都会拦住（nil 和 "" 它都当「没给」）——这才是它存在的理由：
**Helm 对缺失的 value 默认是沉默的，`required` 是你唯一能让它开口的地方。**

**B1 ⚠️ 判据用错了** —— 「集群大、查得频繁才用 informer」是 §4.5 的表面。
真正的判据是**进程是不是长跑的**：informer 的收益来自「List 一次，之后靠 watch 增量」，
一个每 5 分钟启动一次的 CronJob 进程每次都要**重新 List 全量**才能建缓存——
成本和直接 List 一样，watch 那部分永远享受不到。所以 CronJob **无论集群多大都不该用 informer**。
「什么信号让你改」：巡检从「定时跑」变成「常驻、对变化实时反应」的那一刻——
也就是它变成一个 controller 的时候。

**B2 ⚠️ liveness 对，readiness 反了，而且和你的模板矛盾** ——
「重启解决不了数据库的问题，所以 liveness 不该依赖数据库」✅，这是核心。
但 readiness 的职责恰恰是「**这个 Pod 现在能不能接流量**」——数据库挂了它确实接不了，
从 Service 摘掉是对的（客户端拿到 503 而不是一堆 500）。
「会导致 pod 启动失败」也不对：readiness 失败 Pod 不会失败，只是 NotReady、不进 endpoints。

标准分工：**liveness = 进程还活着（不查依赖，越便宜越好）；readiness = 现在能服务（可以查依赖）**。
⚠️ 你 `deployment.yaml` 里两个探针都是 `/healthz`——和你自己 B2 的结论相反。
改法：api 加一个不碰数据库的 `/livez`（或者 liveness 用 `tcpSocket`），readiness 保留 `/healthz`。

**B3 ❌ 答的不是这道题** —— 题目考 §2.3 ④「spec 是别人的，status 是你的」。
controller 往 `spec` 里写 `paid` 的问题：① `spec` 是用户意图，用户下次 `kubectl apply`
（或 GitOps 同步）会把它**覆盖回去**，controller 再改回来——两边打架；
② 真相来源混了：读 `spec.status` 时分不清是用户要求的还是 controller 观察到的；
③ `status` 是子资源，有独立的 update 端点和 RBAC，专门为 controller 写而设计。
正确位置：`status.phase = paid`。你的答案讲的是「业务逻辑不该在 reconcile 里」——
但 D20 要写的 operator **就是**管 Order 生命周期的 controller，那是它的业务。

**B4 ⚠️ 只答了一边，理由有误** —— 「不用每次提交都改 values-prod.yaml」对。
但「改 values 文件要 bump chart version」不对——`values-prod.yaml` 不是 chart 的一部分
（`Chart.yaml` 的 version 管的是 `templates/` 和 `values.yaml`）。
题目要的是**两边各自的场景 + 各怎么回答「线上跑的什么」**：

| | 合理场景 | 「线上是哪个版本」 |
|---|---|---|
| `--set image.tag=$GIT_SHA` | CI 每次构建自动部署 | `helm get values golearn` —— 存在 release 里 |
| tag 写进 git 的 values 文件 | GitOps（ArgoCD 之类），部署 = 改文件 + review | 看 git —— 可审计、回滚 = revert |

两者都对，取决于「部署的真相来源」是 CI 还是 git。

**B5 ⚠️ 理由答偏了** —— 结论对（不同意），但「密码安全」不是这道题的点，
密码已经由 Secret 和 `required` 隔开了。题目问的是**chart 的职责边界**：
这个 chart 的职责是「部署 golearn-api」，**不是「运营一个生产数据库」**——
备份、HA、版本升级、存储类、监控，每一项都是独立的工程，一个 `persistence.enabled` 开关
给不了这些，只会给人「prod 也能用」的错觉。生产库要么是托管服务，要么是专门的
Postgres operator / chart。⭐ 判据：**一个开关打开后，值不值得为它的行为负责。**
