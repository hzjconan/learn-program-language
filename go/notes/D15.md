### 小题 A · 推理题（先想，别跑代码）

**A1.** 下面这个 helper 在数据库没起时会让 `go test ./...` 输出什么？

if err := db.PingContext(ctx); err != nil {

`ordersvc` 和 `api` 的单元测试**都**抓不到？

**A3.** 反过来：D14 的 bug 4（`List` 没走 DTO，返回 Go 字段名）

**A5.** 下面的 `TestMain` 有个 bug，容器不会被清理。在哪？

```go
func TestMain(m *testing.M) {
    pg, err := postgres.Run(ctx, "postgres:17-alpine", ...)
    if err != nil {
        log.Fatal(err)
    }
    defer pg.Terminate(ctx)

    os.Exit(m.Run())

```

**A6.** fuzz 测试为什么通常断言的是「不会 panic」「错误类型是 Invalid」，
而不是「输入 X 应该得到输出 Y」？

**A7.** golden file 测试里，如果响应体带 `created_at`（当前时间），
会发生什么？两种解决办法各是什么？

**A8.** `go test ./...` 和 `go test -tags=integration ./...` 都通过了。
但同事说「集成测试在 CI 上从来没跑过」。
CI 配置里最可能少了什么？这个问题和 A1 是不是同一类？

#### 我的答案
A1: 会skip掉用到这段代码的test case，go test不会报错，误以为全绿。

A2: 因为这些单元测试"fake"了各自的依赖：api层用到fake的service的实现，service层用到了fake的repository的实现。fake的实现里面反而“正确”得返回了status。"fake"的测试没法抓到被fake的实现本身不正确带来的问题。

A3：因为repository层的集成测试压根管不到最后序列化出去的结果。

A4：因为实际上postgres只有第二次输出了“ready to accept connections”才表示它真的就绪了。只等一次的话，可能还没ready就跑test case导致出错。

A5：log.Fatal(err)会导致这条goroutine退出，执行不到defer语句。

A6: 因为我们不能预知Fuzz测试的输入是什么，所以只能测一些不管输入如何，都一定不会变的场景，比如，不应该panic，或者出错时候的error code是某个固定值之类。

A7: 会导致两次golden test的时间不一致导致测试失败。解决方案是把时间写死。

A8: 可能CI里少配了“go test -race -tags=integration”这一步。和A1不是同一类问题，A1是测试代码开始跑了，但没有跑到实际测试逻辑部分就被skip了，并且会误以为全通过，因为go test没报错。这里是压根没跑。

### 小题 B · 设计题（可以查文档，要写理由）

**B1.** 实测 testcontainers 起一个 Postgres 要 **24 秒**。
你会怎么组织测试，让日常开发的反馈循环保持在秒级，同时保证集成测试真的会被跑？
（说清楚：本地怎么跑、CI 怎么跑、谁保证它不被忘掉。）

**B2.** 讲义 §2.2 说「fake 体现的是你**以为**真实现在做什么」。
既然 fake 有这个根本缺陷，为什么不干脆全部用真库测？
给出**两条**理由，并说明你会在什么情况下真的这么做。

**B3.** 你的 `fakeRepo` 现在既是 fake、又是 stub（`err` 字段）、又是 spy
（`created`/`updateCalled`）。
这样混着好不好？什么时候应该拆开？

**B4.** 假设你要给 `ordersvc.Place` 加一条规则「同一个客户 1 分钟内不能下超过 3 单」
（就是 D14 B2 那条）。
这条规则的测试该写在哪一层？需要 fake 还是真库？为什么？
⚠️ 想想它的并发正确性怎么测。

**B5.** 团队里有人说：「覆盖率要求 90%，低于这个不许合并。」
结合你 D6 学的东西和这两周的实际经历，你同意吗？
如果你要给团队定一条**比覆盖率更有用**的测试规则，你会定什么？

#### 我的答案
B1: 把启动Postgres的部分放在TestMain里面，并且同时包含销毁它的逻辑。可以在这些需要实际用到Postgres的test case里面加上编译标签，比如"//go:build integration"，这样在本地只跑"go test xxx"命令不会执行到这些，在CI上，应该还要加上跑“go test -tags=integration xxx”来执行这些需要postgres的case。这个规则可以写在github action里面，保证每次有代码提交，都会执行普通单元测试和费时间的集成测试。

B2:
用fake的理由：1.为了执行单元测试少费些时间 2.为了更快速地编写测试 case，只focus被测的这一层的逻辑，不关系它的依赖本身实现得是否正确。fake测试和带实际依赖的integration测试应该都是必要的，integration在fake测试之上 - 首先fake测试得通过，保证自己这一层实现得没问题，再去看和别人集成的时候有没有问题。

B3: 我认为并没有大问题，fake, stub, spy本身都是合理的测试手段。混在一起唯一的问题是表意性和可维护性略有欠缺，无法直接知道用的测试手段是什么，只能看代码。

B4: 这个逻辑本身加在的service层，首先应该利用fake做单元测试。其次，使用真实postgres做integration测试也是必要的，在有并发的情况下，我们可以测出对数据库操作时，事务是不是正确。

B5：我认为测试覆盖率达到多少多少并不能一概而论，即使100%的覆盖率，也有可能是假的 - 代码分支都被执行到了，但可能压根没做任何断言。比数字更重要的，我认为有两点：
1. code review的时候看测试是不是都合理覆盖了改动的逻辑
2. 日后出了bug，修复的时候要带上相关的测试

**A1 ✅** —— 补一个细节：输出是 **`ok`**，`SKIP` 这个字只在 `-v` 下才看得见。
所以「误以为全绿」不是「可能」，是默认就会。

**A2 ✅** —— 「抓不到被 fake 的实现本身的问题」和讲义那句
「fake 体现的是你以为真实现在做什么」是同一个意思，表述过关。

**A3 ✅** —— 可以再具体一点：**序列化发生在 api 层的 `toResponse`/`json.Marshal`**，
repository 测试的调用栈根本不经过那里。

**A4 ⚠️ 结论对，机制说反了** —— 不是「第一次还没 ready」。
第一次那个实例**真的 ready 了**，只是它是官方镜像 entrypoint 起来跑 init 脚本的
**临时实例**，跑完就关，然后再起正式的那个。
所以只等一次的后果不是「连不上」，是**连上了一个马上要关掉的实例**——
表现为随机的 `connection reset`，比连不上更难查（时好时坏）。
⭐ 差别在于：「还没 ready」你会去加等待；「连上了临时实例」你得知道它有两个。

**A5 ❌ 找错了地方，而且对 `log.Fatal` 的理解有误** ——

题目里的 bug 是 **`os.Exit(m.Run())` 跳过了 `defer pg.Terminate(ctx)`**。
讲义 §3.2 的例子和 `main_test.go` 脚手架注释里「四个坑」的第 4 条都是这一句，
而且你自己在 D15 代码里就是按这个写的（`code := m.Run(); terminate(pg); os.Exit(code)`）。
⚠️ **代码写对了，读别人代码却没认出同一个坑** —— 和 #22 #23 #27 是同一个模式，
这是第四次。

另外「`log.Fatal` 会导致这条 goroutine 退出」是错的：
`log.Fatal` = 打日志 + `os.Exit(1)`，**整个进程**退出，不是 goroutine。
goroutine 级别的退出是 `runtime.Goexit()`（`t.FailNow` 用的那个），两者不要混——
QA #20 刚讲过 `t.Fatal` 和 `panic` 走两条路，这是第三条。

**A6 ✅**

**A7 ⚠️ 只答了一半** —— 现象对。「两种解决办法」只给了一种（样本用固定时间）。
第二种是**比较前把不稳定字段归一化**：
把 `created_at` 替换成占位符（或从 map 里删掉）再比。
两种的取舍：固定时间**测试数据必须可控**（`toResponse(sample)` 可以，
真走 HTTP 拿到的响应就不行——服务端用的是 `time.Now()`）；
归一化**什么来源都行**，但要多写几行、且那个字段等于没测。
⭐ 更根本的一种：**把时钟做成依赖注入**（`now func() time.Time`），D19 B4 会用到。

**A8 ⚠️ 原因对，分类判断值得商榷** —— CI 少了带标签那一步，✅。
但你说「和 A1 不是同一类」——机制上你分得对（一个跑了但跳过，一个压根没编译），
讲义 §3.5 却明确写了「否则又变成了另一种 skip」。
**分类的标准是「后果」不是「机制」**：两者都是**信号是绿的、实际没测**，
排查时你面对的是同一个问题——「绿灯不可信」。
⭐ 会分机制是好事，但别让机制差异掩盖了「它们要用同一种手段防」：
让集成测试的输出**可见**（CI 日志里能看到 `ok internal/orders 5.7s`，而不只是一个绿勾）。

**B1 ✅** —— 三问都答了，和你实际做的一致。「谁保证它不被忘掉」可以再进一步：
CI 配了也会被忘（步骤被注释掉、标签拼错）。你 Makefile 里
`check` 默认跑全量并写了理由「默认不该悄悄少跑一批」——那条才是**机制层面**的保证，
比「写在 CI 里」更硬。再加一条：仓库设 required status check，绿不了不许合并。

**B2 ⚠️ 两条理由偏弱，第三问没答** ——
「省时间」「写得快」都对但不是最有力的。最有力的一条是：
**fake 能制造真库很难制造的情况** —— 让 `repo.Create` 返回一个 error、
让 `Get` 返回 `NotFound`、模拟超时——真库上要造这些得改数据、改网络、改权限。
D14 的 `TestAPI_PayWhenReloadFails` 就是例子：真库上怎么让「支付成功但紧接着的 Get 失败」？
⭐ **fake 测错误路径，真库测正确路径**，这是分工的核心。

「什么情况下真的全用真库」你没答。答案：**这一层的职责就是 SQL 时**（repository 层，
你已经这么做了），或者 service 薄到只是转发时。判据是「fake 掉依赖之后还剩多少逻辑可测」。

**B3 ⚠️ 「什么时候拆」没答到点上** —— 混着确实没大问题，讲义也说三十行不需要框架。
但「什么时候该拆」有具体信号，不是「可维护性略欠」：
① fake 上的**配置字段开始按方法分**（`createErr`、`getErr`、`updateErr`…）——
说明接口太大，该拆的是**接口**不是 fake；
② spy 记录的调用开始被断言**次数和顺序**——讲义 §1 那句「频繁断言调用次数是设计信号」；
③ 多个测试文件各有一份 fake 且开始不一致——D15 §2.2 的两个 fake 就是（`ordersvc_test` 和
`api_test` 各一份，都「帮忙」填了 pending）。

**B4 ⚠️ 方向对，最关键的并发点没想透** ——
「用真库测事务是不是正确」太笼统。把问题拆开：

规则本身（`count < 3` 放行、`= 3` 拒绝、窗口边界 59s/61s）→ **service 层 + fake**，
fake 的 `CountRecent` 返回预设值。⚠️ 时间要**注入**（`now func() time.Time`），
否则窗口边界测不了——A7 那条的延伸。

并发正确性是另一回事：两个请求**同时**读到 count=2 → 都放行 → 4 单。
这是 check-then-act 竞态，**service 层无论怎么写都防不住**，只能靠数据库：
`SELECT ... FOR UPDATE` 锁住客户行 / 事务隔离级别 / advisory lock。
所以它的测试**必须在真库上**：起 10 个 goroutine 同时 `Place`，最后 `count(*)` 断言 ≤ 3。
⭐ 这题的题眼：**「事务对不对」不是一个测试，是两个不同层的测试；
而且并发那个 fake 上永远是绿的**——D15 §2.2 又一次。

**B5 ✅** —— 「覆盖率可以是假的（跑到了但没断言）」是关键洞察。
你定的两条都好。再给一条可以自动化的：**修 bug 的 PR 必须先有一个能复现它的红测试**
（你 D14 补的两个测试就是这么来的），这条能进 PR 模板，比「review 时看一眼」更硬。
