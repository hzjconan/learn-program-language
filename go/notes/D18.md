### 小题 A · 读代码找问题（先想，别跑代码）

**A1.** 下面这条构建命令执行成功了，程序跑起来以后 `/version` 返回的还是 `"dev"`。为什么？

```bash
go build -ldflags "-X buildinfo.Version=v1.4.0" -o api ./cmd/api
```

**A2.** 同事把 Dockerfile 构建阶段的基础镜像从 `golang:1.26-alpine` 换成了 `golang:1.26`（Debian 版，说是「工具更全」），
构建命令是 `RUN go build -o /out/api ./cmd/api`（没写 `CGO_ENABLED=0`），运行阶段还是 `FROM gcr.io/distroless/static-debian12`。
构建成功，但容器一启动就退出，报 `exec /api: no such file or directory`。文件明明在那里，为什么说找不到？仅凭原来使用 Alpine，能保证原产物是静态链接的吗？

**A3.** 某个 Pod 的 `securityContext` 写了 `runAsNonRoot: true`，镜像的 Dockerfile 最后是 `USER nonroot`。Pod 起不来，事件里写着
`container has runAsNonRoot and image has non-numeric user (nonroot), cannot verify user is non-root`。为什么？怎么改？

**A4.** 下面这段 CI，每次都是绿的。它测了什么？没测什么？

```yaml
defaults:
  run:
    working-directory: go
jobs:
  test:
    steps:
      - uses: actions/checkout@v4
      - run: go test ./...
```

仓库结构：`go/go.mod`、`go/operator/go.mod`、`go/operator/internal/controller/*_test.go`。

**A5.** 有人改了 `api/v1alpha1/webapp_types.go`，给 `WebAppSpec` 加了一个字段，测试全绿，合并了。部署以后 `kubectl apply` 带这个新字段的 WebApp，
字段被**静悄悄地丢掉**了（`kubectl get wa -o yaml` 里看不到）。漏了哪一步？CI 里怎么防？

### 小题 B · 设计题（可以查文档，要写理由）

**B1.** 版本号从哪来？给出一个方案：本机 `make build`、CI 的每次提交、正式发布（打 git tag）三种情况下，`buildinfo.Version` 分别是什么，由谁、在哪一步注入。

**B2.** 镜像 tag 用提交号（`golearn-api:1824697`）还是语义化版本（`golearn-api:v1.4.0`）？还是两个都打？各自解决什么问题？`latest` 为什么不行（D19 讲过一半）？

**B3.** `make deploy` 会改写 `config/manager/kustomization.yaml`（§5.2）。团队里每个人都在本机跑它，会出什么问题？你会怎么改这个流程？

#### 我的答案

- A1：因为 `-X` 后面要写完整的 import path。
- A2：可能缺少了某个系统库，因为没写 `CGO_ENABLED=0`。
- A3：不知道，已跟随讲解学习数字 UID 的校验方式。
- A4：不会，不在一个模块。
- A3 复习后：写数字 UID 是为了让 Pod 能知道当前不是 root 用户。
- A5 复习后：只改结构体的话，K8s 并不知道 CRD 的定义变化了。
- B1：本机开发有未提交修改时用 dev；CI 构建用 commit hash；正式发布用与 tag 相同的版本号。
- B2：两个都打。commit hash 用于追溯对应提交，v1.4.0 更适合对外发布。
- B2 补答 latest：认为默认只在镜像不存在时拉取，latest 对 K8s 来说没变化，所以不会拉。
- B3：将 kustomization.yaml 里和构建有关的信息（如版本号）改成从环境变量读取。

### Claude 的批改

- A1 ✅：必须写完整包路径；路径写错可能不报错，需运行验证注入结果。
- A2 方向正确：更精确地说，缺少 ELF 动态加载器可能导致文件存在却报 no such file。Debian/cgo 可能产生 glibc 动态依赖；Alpine/cgo 也可能依赖 musl，不能保证原来就能运行，已修正题目前提。显式关闭 cgo，并检查实际 Linux 产物。
- A3 已讲解：用户名本身不能证明 UID 非零，kubelet 不会通过镜像 /etc/passwd 解析名字来完成此检查。distroless 可改 USER 65532:65532，或 Pod 明确配置 runAsUser: 65532。
- A4 ✅：operator 有独立 go.mod，是嵌套模块；主模块的 go test ./... 不会进入它，所以需要独立 CI job。
- A3 复习通过 ✅：更准确的主体是 kubelet，它用数字 UID 验证非 root 运行要求；用户名本身不足以完成该检查。
- A5 复习通过 ✅：Go 类型、仓库生成的 CRD、集群安装的 CRD 要一致。先 make manifests generate 并提交生成物，再更新集群 CRD；CI 重新生成后用 git diff --exit-code 检查漏交产物。
- B1 方案成立 ✅，补充注入责任：本机可 make build VERSION=dev（直接 go build 则保留默认 dev）；CI 从构建提交读取 hash；发布流程从 tag 读取版本。统一经构建命令的 -ldflags -X 注入，Docker 构建先经 --build-arg 传入。当前本机 make build 默认采用 hash-dirty，这是另一种更便于区分开发产物的选择；dev 本身不区分不同开发构建，需结合 revision/modified 排查。
- B2 核心通过 ✅：hash 便于关联源码，语义化版本便于发布沟通；同一次发布应构建一次，让两个 tag 指向同一镜像 digest。tag 本身可被覆盖，hash 名字不自动保证不可变。latest 不表示固定版本，且更新同名 tag 不会自动改变 Deployment 的 Pod template；latest 部分待用户补答。
- B2 latest 补答纠正：抓住了 Pod template 没变的原因；但首次创建对象时未显式配置策略，latest 通常默认 Always。滚动更新与拉取策略是两件事：没有新 Pod，就不会因拉取策略检查镜像；Always 也不会让旧 Pod 定期更新。已讲解，尚未再次复述确认。
- B3 方向正确，补充机制：Kustomize 不会自动展开 YAML 中的 ${IMAGE_TAG}。由部署脚本读取变量，在临时配置副本中设置镜像后渲染，或沿用 Helm --set image.tag。共享文件反复被部署命令改写会弄脏工作区，带来误提交个人 tag 和无意义冲突。已讲解，尚未实现流程改造。
