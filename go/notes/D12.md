#### 我的答案
A1: 打印出来9007199254740992，因为json里面数字是float64，精度丢了。变量m的类型改成map[string]int64就行了

A2：没有区别。c2虽然是从一个空json字符串反序列化过来的，但因为port是int类型，零值就是0，即使json字符串里压根没这个字段，反序列化后也是0。要解决这个问题，应该再定义一个用来做反序列化的struct，里面的port字段用指针类型，比如
```go
type C2 struct {
	Port *int `json:"port"`
}
```

A3: 输出
{
	A: []
	B: {
		X: 0
	}
}
A和B后面都带了omitempty。用S{}直接创建一个结构体，里面的字段都是对应类型的零值。A因为是切片，不是nil，B是Inner{}，Inner里面的X是int类型，零值是0

A4：②和③会打印出实际的值。
②能打出来是因为“%#v”底层就是会打印，是go本身的设计
③能打出来因为json.Marshal不吃类型的String函数，要复写对应类型的MarshalJSON函数。

A5: ①不会，②会。因为1里面调用的Info函数不使用context作为函数参数，其实走不到上面写的“Handle(ctx context.Context, r slog.Record)”函数。

A6：这里的err如果不是**apperr.Error**而是其他的error的话，这里的ok也是true, 但e.Kind是没有的，会返回nil

A7: 客户端会看到内网数据“10.0.0.5:5432”。返回给客户端看的东西不应该直接拿底层error里的描述。

A8：这样定义会让“KindInternal”变成“Kind”这个枚举的默认值，万一有地方忘了显示设置某个“Kind”的error，会用“KindInternal”，总比用别的好。

#### 实际跑完的验证结果（对了/错在哪）

**A1 ⚠️ 部分对** —— 数值和原因都对，但问的是 `out` 的**内容**，实际是：

```
out = 9.007199254740992e+15 float64
```

不是 `9007199254740992`。⭐ **`%v` 对 `float64` 用的是 `%g`**，大数会变科学计数法。
demo 里看到的整数形式是用 `%.0f` 打的。

独立知识点：**`%v` 不是「原样打印」，它对每种类型有各自的默认动词。**
`float64` 的默认是 `%g`，所以 `1e21` 和 `0.000001` 都会变指数形式 —— 日志里打浮点要注意。

修法（改成 `map[string]int64`）✅。

**A2 ✅ 全对** —— 结论、原因、修法都对。
特别是「再定义一个用来做反序列化的 struct」，等于自己推出了讲义 §1.2 那条
「请求体的类型和存储的类型必须分开」。

**A3 ❌ 错** —— 实际输出 `{"b":{"X":0}}`，**`a` 被省掉了**。

```
S{} 的 A 字段: []int(nil)  (nil? true)
```

⭐ **切片的零值是 `nil`，不是空切片。** `[]int{}` 要显式写才有。
`nil` 在 `omitempty` 的空值列表里，所以 `a` 被省略。`B` 判断对了（struct 不在列表里）。

顺带：`[]int(nil)` 和 `[]int{}` 序列化结果也不同 —— `null` vs `[]`，经常坑前端。

**A4 ✅ 全对** —— ②③ 泄漏，理由准确。

**A5 ✅ 全对** —— 补一点更精确的：`Info` **也会**调到 `Handle`，
只是传进去的 ctx 是 `context.Background()`，`ctx.Value` 拿不到东西。
**函数走到了，值没了**，不是「走不到」。

**A6 ❌ 错** —— 两处机制说反了，而且没答到真正的点。

**① 「这里的 ok 也是 true」—— 不是。**

```
errors.New("boom").(*Error)  →  e = <nil>, ok = false
```

comma-ok 形式的类型断言，**类型不匹配时 `ok` 就是 `false`**，`e` 是 `*Error` 的零值。
这正是 comma-ok 的意义 —— 把「断言失败」变成可判断的布尔值。
（单值形式 `err.(*Error)` 才会 panic。）

**② 「会返回 nil」—— 返回不了。** `Kind` 是 `int`，签名是 `(Kind, bool)`，
走到最后一行返回的是 `(KindInternal, false)`。

**③ 真正的答案：包装之后就失效。**

```
err                              KindOfBad     KindOfGood
没包装（repository 直接返回）        (1, true)     (1, true)
service 用 %w 包了一层              (0, false)    (1, true)   ⚠️ 不一致
普通 error（不是 *Error）           (0, false)    (0, false)
nil                              (0, false)    (0, false)
```

**只有第二行不一样，而第二行正是真实架构里最常见的情况** ——
service 层写 `fmt.Errorf("购买 %s: %w", id, err)` 加上下文。
加了这一层，类型断言就找不到 `*Error` 了，一个本该 404 的错误变成 500。

⚠️ 阴险之处：**单元测试很容易测不出来**。直接构造 `apperr.NotFound(...)` 传进去
就是第一行，过。只有测试里也包一层 `fmt.Errorf` 才暴露 —— 所以
`TestAppErr_KindOfSeesThroughWrapping` 特意包了一层、三层、还有 `errors.Join`。

> ⭐ 代码里写对了（用的 `errors.As`），但这题说明当时是照着脚手架注释写的，
> 没真正理解为什么。**这正是「代码对了、理解没跟上」的典型。**

**A7 ✅ 对** —— 补一层机制：`e.Error()` **按设计就包含 `Err.Error()`**，
那一份是给日志/开发者看的，带全细节是对的。
错的是**把它当成给用户的消息返回了**，正确写法是返回 `e.Message`。

这就是「两个消息」设计的全部意义：不是「要不要脱敏」，
而是**两份消息从一开始就分开存，各走各的出口**。

**A8 ✅ 对** —— 「总比用别的好」对，但可以更狠。
如果 `KindNotFound` 是零值，`&Error{Message: "x"}`（忘了写 Kind）会变成 **404**：

1. **骗客户端** —— 数据库挂了，却告诉对方「资源不存在」
2. ⭐ **告警不会响** —— 404 是 4xx，通常不计入服务端错误率，故障**在监控上完全隐形**

第 2 条才是要命的。选零值的原则：**默认必须落在「最吵闹」的那一档，不是最安静的那一档。**

### 小题 B · 设计题（可以查文档，要写理由）

**B1.** 你的服务要返回一个订单列表，订单号是雪花 ID（`int64`，19 位）。

**B3.** 你要给 `Logging` 中间件换成 slog，并且让**每条**业务日志都自动带上 request ID。
有两种做法：

- (a) 中间件把 `logger.With("request_id", id)` 放进 ctx，业务代码从 ctx 里取 logger
- (b) 自定义 `slog.Handler`，从 ctx 里提取 request ID（讲义 §3 那种）

各自的优缺点是什么？你选哪个？
（提示：想想「业务代码忘了从 ctx 取 logger」和「业务代码忘了用 `InfoContext`」这两种失误分别会怎样）

**B4.** 十二要素说「配置放环境变量」。但你的服务有一份 200 行的路由规则配置，
显然不适合塞进环境变量。你会怎么处理？环境变量和配置文件的分工是什么？

**B5.** `Validate()` 里我要求校验 `WriteTimeout > ReadTimeout`。
结合 D11 §8 讲的四个超时，说明为什么这个约束是必要的，
以及如果配反了（`WriteTimeout` 更短），线上会观察到什么现象。

#### 我的答案

B1: 转成string类型。因为javascript里面的number也是float64，从int64转过去可能会丢精度。
示例代码：
```go
type OrderDTO struct {
	ID string `json:"id"`
}
```

B2: 判断`context.Canceled` / `DeadlineExceeded`在链上找 `*Error`的前面。
在context发出了“取消”或者“超时”的信号的时候，应该优先响应。比如在你给的repository的例子里，如果超时了，调用repository的这层自己应该取消后续所有的操作，至于repository那边返回什么error不重要了。

B3: 我选方案B。把logger放到context里似乎不妥，logger应该服务于整个进程的生命周期，而不是一次请求。B方案的代价是需要强迫记log的人使用“XxxContext”方法，而不是Info/Error这种，需要在文档里说明。

B4：环境变量里放这个配置文件的路径，代码里去读这个文件。环境变量的值不应该太大，要一眼能看明白的那种。

B5: 因为WriteTimeout是从读完**请求头**开始的，所以它包含了读完**请求体**的时间，所以如果它小于ReadTimeout（比如ReadTimeout是1000，WriteTimeout是10），很有可能**请求体**读完后（花费100）啥事还没做就已经超时了。假如配置反了，线上可能会看到不应该发生的timeout。

### 改造 httpx 的设计决策

**请求头兜底那条路：去掉，不补回来。**

改造前 `Logging` 里有两个 request ID 来源：① ctx，② 拿不到就读 `r.Header` 的
`X-Request-ID`，用来覆盖「没装 `RequestID` 中间件、但上游网关注入了 ID」的场景。
换成 `ctxHandler` 之后只剩 ①。

**刻意不补**，三个理由：

1. `RequestID` 中间件本身就会**复用上游请求头里的 ID**（见它的实现），
   只要装了它，②能覆盖的场景①全都覆盖到了
2. 唯一剩下的场景是「**根本没装 `RequestID` 中间件**」—— 那是**配置错误**。
   此时日志里没有 `request_id` 是个**有用的信号**，兜底反而把错误藏起来
3. 而且 `Handle` 只拿得到 `ctx`，拿不到 `*http.Request`。要兜底就得让 request ID
   重新变成两个来源，和「统一由 Handler 注入」的设计打架

> ⭐ 一般原则：**兜底要看它藏起来的是什么。藏「偶发的缺失」值得，藏「配置错误」不值得**
> —— 后者你希望它尽早暴露。

这和 D11 当时排除来源②（从**响应头**读）的理由是同一条 —— 那次也是
「② 说明中间件顺序配错了，日志留空是有用的信号」。**同一个判据用了两次。**

理由同时写进了 `middleware.go` 的 `WithRequestID` 文档注释里。

#### 小题 B

**B1 ✅ 全对**

**B2 ✅ 选择对，理由有一处要修**

> ~~至于 repository 那边返回什么 error 不重要了~~

**不是不重要，是「不影响状态码映射」。** repository 那个
`apperr.Internal("查库失败", ctx.Err())` 仍然会被 `writeError` 完整记进日志 ——
`Message` 和整条 `%w` 链都在。只有**给客户端的状态码**听 ctx 的。

更有力的理由是**监控**：超时被包装成 `Internal` 后若按 500 返回，
会污染错误率指标、触发不该触发的告警；而 504（网关超时）和 499（客户端断开）
是完全不同的故障类别，应该分开看。

**B3 ✅ 选择对，理由可以更硬**

原答案说 (b) 的代价是「需要在文档里说明」—— ⭐ **其实可以让 lint 强制**：

```yaml
linters:
  enable:
    - sloglint
linters-settings:
  sloglint:
    context: all       # 强制 InfoContext / ErrorContext
    static-msg: true   # msg 必须是常量，方便聚合
```

这比文档强得多，也正是 (b) 相对 (a) 的**决定性优势**：
**(b) 的纪律是机器可检查的，(a) 的「记得从 ctx 取 logger」没法用 lint 检查。**
（本仓库目前没配 sloglint，可以加。）

另外「logger 应该服务于整个进程而不是一次请求」这个直觉要小心：
`logger.With(...)` 造出来的**就是**请求级 logger，这本身没问题（讲义 §3 推荐）。
(a) 的真正问题是**传递方式** —— 塞进 ctx 意味着每个函数都要 `LoggerFrom(ctx)`，
忘一次就静默降级成全局 logger。

**B4 ✅ 全对**

「环境变量的值不应该太大，要一眼能看明白的那种」这个判据很好。
补一条：**密钥仍然留在环境变量（或密钥管理服务），不要进配置文件** ——
文件容易被误提交进 git。

**B5 ✅ 对，观察现象可以更具体**

机制说对了。「线上可能会看到不应该发生的 timeout」再具体一层，真实现象是：

- **响应被截断**或**连接被 reset** —— 服务端已经开始写了才超时，改不了状态码了
- 故障**和请求体大小相关**，而不和 handler 快慢相关 ——
  上传大文件的接口挂，普通接口好好的
- 看起来「随机」，因为取决于客户端网速

⚠️ 最难查的是：**服务端日志里可能记的是 200**。
`Logging` 记的是 `responseRecorder` 看到的状态码，而写失败发生在更下层。
