#### 我的答案

A1: 没有跑make generate manifests，会造成在k8s里的CRD还是旧的，不包含新的字段。这会导致新的代码（controller）在用到env的时候会出错或者执行逻辑不是预期的。

A2: ``deploy.Spec = desiredDeployment(&app).Spec``把spec一整个覆盖了，代价是如果acutal state和desired state起时没区别，但是每次 reconcile 还会白发一个 PUT，日志和指标里全是 updated。

A3: 不忽略不存在的webapp的实例的话，每次reconcile都会有error，会看到很多error log，只要k8s还活着就一直持续下去

A4：没有设置“webapp”“owns”这个"deployment"的时候，webapp的controller不会把replica改回2。设置之后会改。
在启动的时候：
informer负责把key放入队列 - [default/api-a, default/api-b, team2/api-a]
worker 逐个取出 → Reconcile(api-a) → Reconcile(api-b) → Reconcile(team2/api-a)
之后，某个webapp的实例的CRD信息变了，只有它的 key 入队， 只 reconcile 它。某个 Deployment 变了 → Owns 找到父 → 只有父的 key 入队

A5: 不是bug。`r.Get`内部的`k8sClient`做读操作是从缓存读的，所以肯能还没读到最新的“2”。测试的时候`r`内部的`k8sClient`是读操作不做缓存的。

A6: `r.Update`更新的是`spec/metadata`，`r.Status().Update()`更新的是运行时的状态，比如 `Available`状态。如果去掉`+kubebuilder:subresource:status`，不会报错，但是跑`kubectl get webapp`的时候不会显示出来"状态"

A7: `meta.SetStatusCondition`会去重（同 Type 只留一条），`LastTransitionTime`不会变化（Status 没变就不更新时间）

A8: 不知道

A9：envtest里因为没有GC Controller的关系，不能测级联删除。kind是个完整的k8s环境，会有级联删除。

A10：应该是稍加了一行权限的"marker"，本机跑`make run`的时候用的是"admin"，有所有权限。

### 小题 B · 设计题（可以查文档，要写理由）

**B1.** WebApp 的 `spec.replicas` 和 Deployment 的 `spec.replicas`，谁是真相来源？
如果用户给 WebApp 配了 HPA（自动扩缩 Deployment），你的 controller 会和 HPA 打架。怎么设计能共存？
（提示：Deployment 自己对 `replicas` 字段就有这个问题，看看它是怎么留口子的。）

**B2.** §4.5 说「有 K8s 之外的东西要清才用 finalizer」。
假设 WebApp 加一个 `spec.dnsName`，controller 要去外部 DNS 服务商创建记录。
画出删除时的完整流程（用户 delete → … → 对象消失），标出哪一步没有 finalizer 就会漏。

**B3.** 你的 `Reconcile` 每次都 `Status().Update`，哪怕 status 没变。
这有什么后果？（提示：§3.5 的事件流，以及 status 更新会不会触发 `For` 的事件。）怎么改？

**B4.** D19 的 Helm chart 和今天的 operator 都能把 golearn-api 部署出来。
一个团队什么时候该用 chart、什么时候该写 operator？给出一条判据，并说出 operator 多付的成本是什么。

**B5.** controller-runtime 默认一个 controller 只有 1 个 worker（`MaxConcurrentReconciles: 1`）。
把它调成 10 之前要确认什么？（提示：同一个 key 会不会被两个 worker 同时处理？不同 key 之间呢？）

#### 我的答案

（写在这里）
B1: Deployment 的 `spec.replicas`是通过解读WebApp 的 `spec.replicas` 来更新的。最终起效的是Deployment里的。如果配置了HPA，在自己写的web app的controller里面应该以HPA为准，动态修改replicas的数目。

B2: 用户delete web app -> 在web app对象上挂一个标记`deletionTimestamp != nil`，不真的删除 → 下一次reconcile会看到这个标记，清理外部资源(DNS记录) → 摘掉 finalizer → 删除web app

B3: 不知道

B4: 如果被部署的应用只需要依赖k8s原生的功能就能完成所有业务要求，那就不需要引入operator。反之，如果k8s原生的功能没法满足需求，比如上面说的给web app引入HPA，我需要实现在扩容或者缩减的时候发出email通知，就只能靠operator来实现了。

**A1 ⚠️ 只答了一种** —— 题目问「**两种**不同的失败，各是漏了哪一步」。你答的是漏 `manifests`：
CRD schema 还是旧的 → API server 以 `unknown field "env"` **拒绝创建**，`kubectl apply` 当场报错。
另一种是漏 `generate`：`zz_generated.deepcopy.go` 里的 `DeepCopyInto` 还是旧的，**不拷贝 Env 字段**。
⚠️ 症状完全不同——apply 成功、controller 不报错，但 informer 缓存里的对象 DeepCopy 出来 `Env` 是 nil，
容器起来一个环境变量都没有。**「明明 apply 了怎么没生效」**，比第一种难查得多。
⭐ 两步各管一边：`manifests` 管**服务端**认不认这个字段，`generate` 管**客户端**拷不拷这个字段。

**A2 ✅** —— 「服务端 no-op、代价是日志失真」，准确。可以再补一句真正会死循环的那种（desired 不确定）。

**A3 ⚠️ 少了最关键的一半** —— 「一直报错」对，但漏了**退避**这个机制：
controller-runtime 对返回 err 的 key 做**指数退避**重入队（5ms → 10ms → 20ms → … → 16 分钟上限），
所以不是「疯狂刷日志」，是「越来越慢地一直重试」，而且这个 key **永远不会被 Forget**。
后果：日志里永远有一条 ERROR 在周期性出现，你以为有东西坏了，其实是个已经删掉的对象；
真正的问题被噪音盖住。⭐ 这就是「正常情况不该返回 error」的理由——
`error` 在 controller 里的语义是「**可重试的失败**」，不是「发生了一件事」。

**A4 ✅** —— 连启动 resync 和事件路由都说全了。

**A5 ✅** —— 缓存 vs 直连，对。

#### 小题 B

| B1 | B2 | B3 | B4 | B5 |
|---|---|---|---|---|
| ⚠️ | ⚠️ | ❌ | ⚠️ | ⚠️ |

**B1 ⚠️ 「以 HPA 为准，动态修改 replicas」做不到** —— 你的 controller **看不到** HPA 的意图，
只看到「Deployment 的 replicas 是 5，我的 spec 说 2」，于是改回 2；HPA 下一秒又调到 5。
**两个 controller 对同一个字段各有真相，就是死循环**，谁也不会让步。

提示里说的「Deployment 自己怎么留口子」——三种真实解法：

1. ⭐ **spec.replicas 做成可选指针，nil 时不管这个字段**（mutateFn 里 `if app.Spec.Replicas != nil` 才赋值）。
   用了 HPA 就别在 WebApp 里写 replicas —— **交出所有权**。最简单、最常见。
2. **`scale` 子资源**：给 CRD 加 `+kubebuilder:subresource:scale`，让 HPA 直接伸缩 **WebApp** 而不是 Deployment，
   你的 controller 再把它同步下去 —— 真相来源只有一个（WebApp），HPA 也满意。
3. Server-Side Apply 的字段所有权：谁 apply 过某字段谁拥有它，别人改了不抢回来。

⭐ 一般规律：**同一个字段不能有两个 controller 认为自己是真相来源**。
设计 CRD 时要想「这个字段会不会被别人也改」，会 → 要么别管，要么把它变成你的子资源。

**B2 ⚠️ 流程对，「哪一步没有 finalizer 就会漏」没标出来** —— 你写的四步是**有** finalizer 的流程。
题目要的是对比：

```
没有 finalizer:  用户 delete → API server 立刻从 etcd 删掉对象 → 你的 reconcile 收到事件、
                 r.Get 返回 NotFound → 你【什么都不知道】→ DNS 记录永久泄漏 ⚠️
                 （对象已经没了，你连 dnsName 是什么都读不到）

有 finalizer:    用户 delete → API server 只设 deletionTimestamp（对象还在）
                 → reconcile 看到 deletionTimestamp != nil → 删 DNS 记录 → 摘掉 finalizer
                 → API server 发现 finalizers 空了 → 这才真删
```

⭐ 漏的那一步是**「读不到对象」**：没有 finalizer，你失去了最后一次读 spec 的机会。
finalizer 的本质是**「我还没清理完，别删」的一票否决**。
⚠️ 代价：你的 controller 挂了或者清理永远失败 → finalizer 摘不掉 → 对象卡在 Terminating **删不掉**
（生产事故常见来源，只能手动 `kubectl patch` 清空 finalizers）。

**B3 ❌（答了不知道）** —— 后果是**自触发的空转循环**：
`Status().Update` 成功 → WebApp 对象变了 → `For(&WebApp{})` 的 informer 收到 MODIFIED
→ 入队 → reconcile → 又无条件 `Status().Update` → 又一个事件……

⚠️ 它**不会**无限刷：`meta.SetStatusCondition` 的 `LastTransitionTime` 不变、
其它字段也一样，所以第二次 Update 的内容和服务端一致，API server **no-op**（和 A2 一个道理），
resourceVersion 不变 → 不产生新事件 → 停下来。所以现在的代码**能收敛**，代价是每次 reconcile 多一次白写。

但一旦 status 里掺进**每次都不同**的东西（`LastProbeTime: time.Now()`、随机顺序的列表），
它就变成真的无限循环 —— 而且是**自己触发自己**，最难查的那种。

怎么改：`meta.SetStatusCondition` 返回 `changed bool`，加上 readyReplicas / observedGeneration 的比较，
**有变化才写**：

```go
changed := meta.SetStatusCondition(&app.Status.Conditions, cond)
if changed || app.Status.ReadyReplicas != ready || app.Status.ObservedGeneration != app.Generation {
    ...赋值...
    if err := r.Status().Update(ctx, &app); err != nil { return ctrl.Result{}, err }
}
```

⭐ 通用原则：**controller 写自己 watch 的对象时，必须先判断有没有变化**——否则就是给自己发事件。

**B4 ⚠️ 判据太宽，成本没答** —— 「原生功能满足不了就上 operator」这句话对但不可操作：
Helm 也能部署 HPA、也能配 Job。更锐的判据（讲义 §1 那段问答）：

> **reconcile 里装的是「渲染 + apply」→ 用 Helm；
> 装的是「看到现状 X 就做 Y」的运维判断 → 才是 operator。**

你举的「扩缩容时发邮件」是对的例子 ✅——它是「观察到事件后做动作」，模板表达不了。

「多付的成本」完全没答，这是这题的一半：
一个**长期运行的进程**要你负责（升级、监控、leader election、OOM、日志）；
CRD 是**公开 API**，加字段容易、删字段要走废弃流程；
RBAC、版本兼容（`v1alpha1` → `v1`）、conversion webhook；
出 bug 的影响面是**所有**用这个 CRD 的团队。⭐ **写 operator = 从「写应用」变成「维护一个平台组件」。**

**B5 ⚠️ 结论对，缺了关键的两条保证** ——
「避免一个卡住阻塞其它」对，「同一个 key 不会被并行」也对。但**为什么**不会：
workqueue 保证同一个 key **处理中就不会被再次交出**（D19 §5.2 那个 `defer c.queue.Done(key)`），
不是靠 worker 之间协调。

「调大之前要确认什么」你没答具体项：
① **Reconcile 里没有跨 key 的共享可变状态**（map、计数器）——有就要加锁，或者干脆别有；
② **不同 key 的资源不重叠**——两个 WebApp 如果会写同一个 Deployment（名字撞了），并行就有竞态；
③ **下游扛得住**——10 个 worker 同时打 API server 或外部 API，注意限流；
④ 幂等（本来就要）。
⭐ 调大 worker 数是**性能手段**，前提是 reconcile 之间**除了 API server 没有任何共享**。
