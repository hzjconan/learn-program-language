**B4.** 线上 golearn-api 的内存每天涨 200MB，一周重启一次。你只能碰生产环境的 `kubectl`。
写出排查步骤：抓什么、抓几次、间隔多久、怎么对比，以及拿到结果以后下一步做什么。
⚠️ 要考虑到 pprof 端口只监听 localhost（讲义 §5.2）。

**B5.** CPU profile 显示 `runtime.mallocgc` 和 `runtime.gcBgMarkWorker` 加起来占了 40%。
这说明什么？下一步该抓哪个 profile、看哪个 `sample_index`？（这题是 D17 的预告）

#### 我的答案

B1:
**延迟：**
``histogram_quantile ( 0.95 , rate (http_request_duration_seconds_bucket{job="golearn-api" }[5m])) > 500 for 5m``
为什么选这个阈值：95% 的请求在 500ms 内完成，超过 500ms, 持续5分钟就认为是异常请求。

**流量：**
``rate (http_requests_total{job="golearn-api"}[5m]) < 1 for 15m``
5分钟窗口平均 QPS 低于 1，持续15分钟，这意味着服务几乎没收到请求，有可能上游的网络问题（load balance, ingress）导致没有流量进来，或者pod卡住了（readiness接口也许还能正常返回）

**错误：**
``sum by ( status ) (rate(http_requests_total{job= "golearn-api" , status =~ "5.." }[ 5 m])) / sum by ( status ) (rate(http_requests_total{job= "golearn-api" }[ 5 m])) > 0.01``
5xx 比例持续超过 1%

**内存占用：**
``container_memory_working_set_bytes{container= "golearn-api" } /container_spec_memory_limit_bytes{container= "golearn-api" }> 0.85 for 15m``
超过内存 limit 的 85%，持续15分钟

B2:
`child_ops_total{op="updated"}` 稳态时应该是：趋近 0，这意味着没有任何人/系统在改 WebApp spec、Deployment status 也不触发 reconcile。
抓"desired 不确定导致无限滚动"的告警：
```go
rate(golearn_webapp_child_ops_total{kind="Deployment", op="updated"}[1m])
/
rate(controller_runtime_reconcile_total{controller="webapp", result="success"}[1m])
> 0.1
for 5m
```
和``TestReconcile_IsIdempotent``相比，这条告警是在线上环境跑，``TestReconcile_IsIdempotent``是在CI环境

B3:
trace_id 是给服务端排障用的（跨服务链路），request_id 是给客户端+服务端一起排障用的（单次请求定位）。
OTel 里 trace 因为采样率可能会丢失，但 request_id 在日志里 100% 留着——这是两套独立的可观测性手段，不能互相替代。

B4:
pprof 只监听 localhost（`6061` ） → 必须用`kubectl port-forward` 把端口转到本地。
### 排查步骤
第1步， port forward
```bash
kubectl port-forward -n golearn-system pod/golearn-api-xxxxx 6061:6061
```

第2步，抓heap profile（做两次，在强制GC后）
```bash
# 第一次：现在抓，加 gc=1 强制先 GC 再抓
curl -sS http://localhost:6061/debug/pprof/heap?gc=1 -o heap-before.pb.gz

# 记下 top 分配，然后等 1 小时
# 第二次：1 小时后同样方式再抓一次
curl -sS http://localhost:6061/debug/pprof/heap?gc=1 -o heap-after.pb.gz
```

第3步，用-base做对比
```bash
go tool pprof -top -base heap-before.pb.gz heap-after.pb.gz
```

第4步，分析结果
- 如果是 goroutine 相关的泄漏（类似 leakdemo 那种），补抓`goroutine?debug=1` 看有没有数量稳定增长的那组
- 如果是 Go 运行时本身的增长（`runtime.mallocgc` flat 高），补抓 CPU profile 看分配热点
- 如果想抓分配趋势（"到底是哪种对象一直在被创建、没人释放"），查`alloc_space` 或`inuse_space` 的 sample_index

B5:
这说明内存分配和频繁，GC也很频繁地跟着跑。下一步应该看heap profile 的 alloc_space

**A1 ✅** 每个不同的 URL 一条序列，订单号无上界 → 一周累积到 OOM。改成路由模板对。补两点：
- Go 1.22 的模板写法是 `"GET /orders/{id}"`，用 `r.Pattern` 取
- ⚠️ `r.Pattern` 是 mux 路由时**原地写进** `*Request` 的。这个中间件在 `next.ServeHTTP` **之后**才读，看起来没问题；
  但如果它和 mux 之间有别的中间件调用过 `r.WithContext`（比如你的 `RequestID`），mux 改的是复制出来的那份，这里读到的还是空字符串（讲义 §2.4）

**A2 ⚠️** 你的主线是「Reconcile 没被触发」。但题目说的是「等好几分钟**才生效**」，最后生效了 → 说明**确实被触发了**，只是很晚。

- 慢在哪：reconcile 本身 P99 只有 8ms，所以时间花在**进入 reconcile 之前**，也就是 key 在队列里排队
- 关键：`reconcile_time_seconds` **只统计 reconcile 本身**，不含排队时间（QA #21 末尾那条，P99 要先弄清统计范围）
- 证实用的指标：
  - ⭐ `workqueue_queue_duration_seconds`（key 在队列里等了多久）：它的 P99 是几分钟，就坐实了
  - `workqueue_depth` 持续不为 0（你提到了 ✅）
  - `controller_runtime_active_workers` 一直等于 `max_concurrent_reconciles`：worker 全忙
- 常见原因：`MaxConcurrentReconciles` 默认 1，集群里 WebApp 很多，或者有某个 key 的 reconcile 特别慢（调外部 API）把唯一的 worker 占住了
- 你提的 `GenerationChangedPredicate` 解释不了这个现象：改 spec 会让 generation +1，这个 predicate 放行的**正是** spec 的变化，只丢 status 和 annotation 的。而且它的效果是「永远不触发」，不是「晚几分钟」
- 这就是讲义 §3.1 的饱和度信号，以及 ① 黄金信号表里「饱和度」那一行要看的东西

**B1 ⚠️**

- ❌ **单位**：histogram 是秒，`> 500` 是 500 秒。要写 `> 0.5`（讲义 §2.3：名字带 `_seconds`，用基本单位）
- ❌ **错误率用了 `sum by (status)`**：分子 `{status="500"}` 除以分母 `{status="500"}`，PromQL 按相同 label 配对相除 → 结果永远是 1，只要有一个 5xx 就告警。去掉 `by (status)`，两边都 `sum()`
- ⚠️ **没跨 Pod 汇总**：延迟要 `histogram_quantile(0.95, sum by (le) (rate(..._bucket[5m])))`（先 rate、再按 `le` 加、最后算分位数）；流量 `rate(...) < 1` 不加 `sum()` 的话，**任意一个 Pod** 流量低就告警
- ⚠️ **阈值的理由是循环论证**：「95% 在 500ms 内，超过就异常」只是把式子复述了一遍。阈值要来自 **SLO** 或**历史基线**（比如平时 P95 是 50ms）。更好的写法是直接算达标比例 `le="0.5"` 的桶 / 总数（QA #21）
- 错误那条缺 `for`；低流量时 3 个请求错 1 个就是 33%，要加一个最低流量条件（`and sum(rate(...)) > 0.1`）
- 内存占 limit 85% 作为饱和度 ✅（USE）。golearn-api 更贴身的饱和度是**数据库连接池**：`InUse / MaxOpen`（D13）
- **「哪一条最容易误报」没答**：是**流量那条**。半夜、周末流量本来就低，「QPS < 1」会天天响。降误报：和上周同一时刻比（`offset 1w`），或者看「比平时下降了多少」；或者干脆用外部探活（blackbox）代替

**B2 ⚠️**

- 稳态趋近 0 ✅。但理由「Deployment status 也不触发 reconcile」不对：① 里亲眼看到 Deployment controller 写 status 会触发 reconcile（scale 一次 7 个事件）。
  准确的说法：**reconcile 照样发生，只是 desired 没变，结果是 `unchanged`**；`updated` 只在真有 spec 变化或有人改了子资源时出现
- 告警式子用 `updated / reconcile_success` 做比例 ✅，比看绝对值好：用户正常改一次镜像，只有一两次 `updated`，比例很低。窗口用 `[5m]` 比 `[1m]` 稳（抓取间隔 15–30 秒，1 分钟窗口只有两三个点）
- **「各自的盲区」没答**，只说了「一个线上一个 CI」。两者抓的是**同一类**问题（reconcile 不幂等），盲区不同：

| | `TestReconcile_IsIdempotent` | 这条告警 |
|---|---|---|
| 抓到的时机 | 合并前 ✅ | 上线后，用户已经受影响 |
| 盲区 | 只覆盖测试里的输入：测试的 WebApp 只有 0～1 个 env，**map 顺序问题根本不会触发**；envtest 没有 Deployment controller，看不到滚动 | 依赖 `updated` 的含义。② 修复**之前**，白写也报 `updated`，比例永远是 1 → 这条告警会**一直响**，变成噪音 |

  ⭐ 指标的语义（`updated` 是「发出了 Update」还是「真改了」）决定了告警能不能用。② 把它修干净之后，这条告警才成立
- 另一个不依赖 operator 自身指标的抓法：kube-state-metrics 的 `changes(kube_deployment_metadata_generation[10m]) > 5`（generation 一直在涨 = 一直在滚动）

**B3 ✅** 采样和客户端两个角度都对。补：

- **谁生成**（没单独答）：`trace_id` 由 OTel SDK 生成，或从上游 `traceparent` 沿用。上游如果是浏览器、移动端或者不支持 OTel 的老服务，每一跳都会新开 trace；`X-Request-ID` 是最简单的约定，网关（ingress、nginx）、客户端都能在进来之前就生成好
- **客户端能拿到**：你的 `RequestID` 中间件把它写进了**响应头**；`otelhttp` 默认不会把 `traceparent` 返回给客户端。用户报错时能报给客服的是 `request_id`
- ⚠️ 一处细节：「trace 因为采样可能丢失，request_id 在日志里 100% 留着」——不采样时 **`trace_id` 在日志里其实也 100% 都在**：SDK 照样生成 SpanContext，只是不记录、不导出。问题在于**拿着日志里的 trace_id 去后端查，查不到任何东西**

**B4 ⚠️** 骨架对：port-forward（转发进 Pod 网络里的 localhost 端口，所以只监听 localhost 也能用）、`gc=1`、两次快照、`-base` ✅。补：

- ⚠️ **第 0 步：golearn-api 根本没开 pprof**（只有 leakdemo 和 operator 开了）。要先改部署加上管理端口，而**重新部署会重启进程，泄漏归零**，得等它重新涨起来再抓。这是真实排查里最常卡住的地方
- 抓 pprof 之前先看**便宜的指标**：`go_goroutines` 是不是一直涨（goroutine 泄漏，⑤ 那种）；`go_memstats_heap_inuse_bytes` 和容器 RSS 是不是一起涨（不一起涨说明不是 Go 堆，可能是 goroutine 栈、cgo、page cache）；Pod 重启原因是不是 `OOMKilled`
- 间隔 1 小时偏短：200MB/天 ≈ 8MB/小时，容易被正常波动淹没。抓**三次**、间隔几小时，确认是**单调**增长再下结论
- 第 4 步混了：查泄漏看 **`inuse_space`**（还活着的）；`alloc_space` 是查 GC 压力的（B5）。`runtime.mallocgc` flat 高也不是该去抓 CPU profile 的信号
- ⭐ **缺了最关键的一步**：`-base` 指到分配位置以后，`-list` 看是哪一行，然后**读代码找谁拿着它**（讲义 §5.4，⑤ 里 `order` 拿着 `buf[:16]` 就是这一步）。之后：写回归测试 → 修 → 用同样的方法再抓两次，确认不涨了

**B5 ✅** 分配多 → GC 跟着跑。下一步看分配：`/debug/pprof/allocs`（或 heap 切 `sample_index`）✅。补：GC 的开销主要跟**对象个数**（和指针）有关，不只是字节数。大量小对象时 **`alloc_objects`** 比 `alloc_space` 更能指出问题。D17 会讲逃逸分析和怎么减少分配。
