### Claude 的批改

#### 小题 A（A1 见「我的答案」里的逐题对照）

| 题 | 结果 | 一句话 |
|---|---|---|
| A2 | ⚠️ | 说出了「缓存会过时」，但 80% 不可信的**主要原因**和并发问题都没答 |
| A3 | ✅ | 两个问题都找到了。补修法 |
| A4 | ❌ | 把「存活堆太大」当成了「分配太多」，D16 和 D17 的问题混了；GOGC 那问没答 |
| A5 | ⚠️ | 说「sec/op 不靠谱」对，但没读懂 benchstat 里的 `~` 和 p 值，那才是这题的关键 |

**A2 ⚠️**

- 你说的「`Add` 之后缓存就过时了」是一个真问题 ✅（缓存要在 `Add` 时失效）
- 但 **80% 不可信的主要原因**不是这个：`BenchmarkFormat` 每轮用**同一个** `rpt`，只有第一轮真排序，后面全部命中缓存。真实使用（`cmd/loganalyze`）每次只 Format 一次，享受不到（讲义 §4.4，练习 ② 你做方案选择时已经遇到过）
- **上线后还可能出的问题**漏了最重要的：`Percentile` 会写 `r.sorted`，一个只读方法变成了**写共享状态**。两个 goroutine 同时 `Format` 同一个 Report → **数据竞争**（`-race` 能抓到）。这正是你在练习 ② 选方案 2 的理由

**A3 ✅**

- 没 `Reset`：`bytes.Buffer` 是**追加写**，下一个调用方的 JSON 会接在上一次后面，**确定会**拿到错误数据 ✅
- `return buf.Bytes()` 之后 `defer Put`：返回的切片和池子里的 buffer 共享底层数组，另一个 goroutine 拿走后一写，调用方手里的数据**悄悄变了** ✅（④ 里 `Bytes()` / Pool 第 3 个坑的同一件事）
- 修法：`Get` 之后先 `buf.Reset()`；返回前复制一份 `out := bytes.Clone(buf.Bytes())` 再 `Put`。顺带：`Encode` 的错误被丢掉了
- 两个都会给出错误数据：第一个**每次都会**，第二个只在**并发**时偶尔出现，更难查

**A4 ❌**

- 你的答案：GC 太频繁、分配太多，去看 `B/op`、`allocs/op`
- 问题在于：`->480 MB` 是**存活堆**，就是 GC 之后**还活着**的数据。它比 `GOMEMLIMIT`（460MiB）还大，说明问题不是「分配得多」，而是「**留着的太多**」。
  这是**你上午刚问过的 D16 和 D17 的区别**：查存活数据要看 `inuse_space`，查分配压力才看 `alloc_*`、`B/op`
- 发生了什么：存活数据超过软上限，GC 拼命跑也压不下去，runtime 把 GC 限制在约 50% CPU（讲义 §3.4，就是你看到的 50%）防止死亡螺旋，然后**允许内存继续超过上限**。离容器上限 512Mi 只剩约 30MB，**马上要 OOMKill**。练习 ③ 的 `GOMEMLIMIT=100MiB` 就是这个场景的缩小版
- **调大 GOGC 有用吗**（没答）：**没用**。接近 `GOMEMLIMIT` 时 GC 由上限驱动，`GOGC` 设多大都一样，`GOGC=off` 也一样
- **应该先查什么**：heap profile 的 `inuse_space`（加 `gc=1`），看是谁留着这 480MB。是泄漏（D16 ⑤ 那种）就修；是业务确实需要这么多（比如缓存设计就是这么大）就调大容器内存、或者限制缓存大小
- 已记进 [MISTAKES #33](../MISTAKES.md)

**A5 ⚠️**

- 「sec/op 受环境影响，要结合 B/op、allocs/op」✅ 方向对，④ 里你亲眼见过
- 但这题的关键是**读懂 benchstat 已经给出的结论**：
  - `~` 就是 benchstat 在说「**没有显著差别**」
  - `p=0.393`：差别是噪音的概率约 39%，远大于 0.05
  - 两边的波动是 `± 9%`、`± 11%`，比那 5% 还大
- 回复同事：「benchstat 显示 `~`，p=0.39，这 5% 在噪音范围内，不能说快了。要么关掉干扰、多跑几轮或交替运行再测；要么拿 `allocs/op` 这类稳定的指标来证明」

**A 组总评**：A3 最好，是练习 ④ 亲手踩过的坑。A4 是 D16/D17 的区别（存活 vs 分配）在新场景里没认出来；A2、A5 是题目问的东西（主要原因、`~` 的含义）没答到。

#### 小题 B

**B1 ⚠️ 方向对，只说了一半**（详细推理见 [D17/4-sync-pool.md](D17/4-sync-pool.md)「思考题」）

- ✅ 说对的：`order` 里的切片都指向 Pool 里同一块缓冲区，每个新请求都覆盖它，所有签名的内容都变成最近一次请求的数据
- ❌ 没答的：题目问的是「**会出什么错、什么时候暴露**」，要接着推数据变了以后 `dedup` 的行为：
  - **前 5 万条看起来完全正常**：查重靠 `set`，key 是 `string(sig)`，存入时复制了一份，是对的；`order` 这阶段没人读
  - **第 50001 条起悄悄出错**：淘汰时 `delete(d.set, string(d.order[d.next]))` 读的是被覆盖后的数据 →
    该删的老签名没删，`set` 超过上限一直涨（**换了个方式的内存泄漏**）；删掉的是最近请求的签名，同一签名再来时**去重失效**
  - 至少 5 万个不同签名才暴露，单测和本地调试到不了；不报错，只是偶尔漏掉重复上报 + 内存慢慢涨
- ⭐ 同样少一行 `bytes.Clone`：没有 Pool 时是**内存泄漏**（每条钉住 64KB，涨得快、容易发现）；有 Pool 时是**数据悄悄出错**（内存不涨，更隐蔽）。优化改变了 bug 的表现形式
- 答题习惯：和 D16 的 A2、A8、B1～B3 一样，**说出了现象，没推到题目要的结论**。交之前对照题目逐问检查

**B2 ⚠️ 方向对（会 OOM、大数据量用近似算法），没估算，有一处说错**

- **估算**（用练习 ③ 的数据）：100 万行存活约 190MB → 每行约 190 字节 → **1 亿行约 19GB**，是 6GB 输入的 3 倍多（`time.Time`、两个字符串头、切片扩容余量）
- ❌「Percentile 只需要保留那几条」：精确分位数**必须**知道所有耗时。只需要几条的是 `TopSlowest`

| 报告内容 | 边读边算需要存什么 |
|---|---|
| 总数、按级别/服务计数 | 几个计数器，常数内存 |
| `TopSlowest(10)` | 最多 10 条（练习 ② 的写法挪到 `Add` 里） |
| 精确分位数 | 所有耗时，但只存 `int64`：1 亿 × 8B = **800MB**，比存 Entry 少 20 多倍 |
| 近似分位数 | 固定大小：histogram、t-digest |
| `Failed []error` | ⚠️ 也会无限增长，要设上限 |

- 取舍不只是精度：**只能回答事先定好的问题**（N 要读之前定；想换维度得重读文件）；`Report` 的 API 会变（不能再随时 `TopSlowest(任意 n)`）

**B3 ⚠️ 90% 的规则用对了，数字的依据不对**

- ❌「根据之前做过的 benchmark，256 足够了」：没有测过 golearn-api 的内存。benchmark 测的是单个函数**每次操作的分配量**，不是整个服务**占了多少内存**。
  要看线上或压测**高峰时**的 `container_memory_working_set_bytes` / `go_memstats_heap_inuse_bytes`，再加余量（比如 1.5 倍）。
  golearn-api 的大头大概是 DB 连接池（`MaxOpenConns=100`）、连接和请求的 goroutine 栈、请求体缓冲区。没数据时先给保守值，**再用指标验证、调整**。答题要说「依据什么来定」，不是给一个数
- ⚠️ 单位：K8s 的 `256M` 是 10⁶，`256Mi` 是 2²⁰，差约 5%。容器写 `256Mi`、`GOMEMLIMIT` 写 `230MiB` 才对得上
- ✅ `GOMEMLIMIT` = 容器上限的 90%
- ✅ `GOGC` 150～200：有 `GOMEMLIMIT` 兜底，用内存换 CPU。前提是平时存活堆远小于上限（平时 30MB、`GOGC=200` 目标 90MB，离 230MiB 很远；快到上限时 `GOMEMLIMIT` 接管）。调完要验证 GC CPU 有没有降
