## 1. `database/sql` 的模型

Go 的数据库访问分两层：

```
你的代码
   ↓
database/sql          标准库：连接池 + 通用接口，【不懂任何具体数据库】
   ↓  driver.Driver
pgx / mysql / sqlite  驱动：懂协议、懂类型
   ↓
数据库
```

这和 Java 的 JDBC 是同一个思路，但有个**关键差别**：

> ⭐ **`*sql.DB` 不是一个连接，是一个连接池。**

| | Java | Go |
|---|---|---|
| 连接 | `Connection`（你自己管） | 藏在 `*sql.DB` 里，你**看不到** |
| 池 | HikariCP 等第三方 | **标准库自带**，就是 `*sql.DB` |
| 生命周期 | try-with-resources 关连接 | 关的是 **`Rows`/`Tx`**，不是连接 |

所以：

- **`*sql.DB` 是长生命周期对象**，整个进程一个，启动时建、退出时关
- **不要**每次查询 `sql.Open` 一次——那是新建一个池
- 它**并发安全**，多个 goroutine 直接共用

### ⚠️ `sql.Open` 不连接数据库

```
sql.Open("pgx", "postgres://nobody:nope@127.0.0.1:1/nodb")   → err = <nil>   ⚠️
```

一个**完全连不上**的 DSN，`sql.Open` 照样返回 `nil` 错误——它只解析 DSN、准备好池，**一个包都不发**。

```go
db, err := sql.Open("pgx", dsn)
if err != nil { ... }                 // 只能抓到 DSN 语法错误

if err := db.PingContext(ctx); err != nil {   // ⭐ 这一步才真连
	return fmt.Errorf("连接数据库: %w", err)
}
```

**启动时一定要 Ping**，否则第一个真实请求才发现连不上，而那时用户已经在等了。

## 2. 驱动：为什么是 pgx

Postgres 的 Go 驱动有两个：`lib/pq`（老牌，已进入维护模式）和 **`pgx`（现在的默认选择）**。

`pgx` 有两种用法：

```go
// 用法 A：走 database/sql 标准接口（本课用这个）
import _ "github.com/jackc/pgx/v5/stdlib"
db, err := sql.Open("pgx", dsn)

// 用法 B：pgx 原生接口，性能更好、支持 Postgres 独有特性
import "github.com/jackc/pgx/v5/pgxpool"
pool, err := pgxpool.New(ctx, dsn)
```

**先学 A**：`database/sql` 的知识可以迁移到任何数据库，而且绝大多数项目够用。等你确实需要 `COPY`、`LISTEN/NOTIFY`、自定义类型时再上 B。

> ⚠️ 注意那个 `_` 空白导入。驱动是靠 `init()` 里调 `sql.Register("pgx", ...)` 注册的，
> 你不直接用它的任何符号，所以必须用 `_` 导入——否则编译器报「imported and not used」。
> 这是 Go 里少数几个「副作用导入」的合理场景。

## 3. 三种查询方法

```go
// ① 多行
rows, err := db.QueryContext(ctx, `SELECT id, name FROM items WHERE price > $1`, 100)

// ② 单行
err := db.QueryRowContext(ctx, `SELECT name FROM items WHERE id = $1`, id).Scan(&name)

// ③ 不返回行（INSERT/UPDATE/DELETE）
res, err := db.ExecContext(ctx, `UPDATE items SET price = $1 WHERE id = $2`, p, id)
n, _ := res.RowsAffected()
```

三条通用规则：

1. **一律用 `XxxContext` 版本**，别用 `db.Query`/`db.Exec`（D10：取消要能贯穿整条链）
2. **占位符是 `$1 $2`**（Postgres 风格；MySQL 是 `?`）——**永远不要用 `fmt.Sprintf` 拼 SQL**，那是 SQL 注入
3. 参数**不需要**引号：`WHERE name = $1` 不是 `WHERE name = '$1'`

### ⚠️ `QueryRow` 的错误延迟到 `Scan`

```go
row := db.QueryRowContext(ctx, ...)   // ← 这里【不返回 error】
err := row.Scan(&name)                // ← 错误在这里出现
```

```
查不到时 Scan 返回: sql: no rows in result set
errors.Is(err, sql.ErrNoRows) = true
```

⭐ **`sql.ErrNoRows` 通常不是「错误」，是「没找到」**——正是 D12 §5 那个要翻译成 `apperr.NotFound` 的东西：

```go
err := db.QueryRowContext(ctx, q, id).Scan(&o.ID, &o.Customer)
if errors.Is(err, sql.ErrNoRows) {
	return nil, apperr.NotFound("订单不存在", err)     // ⭐ 在 repository 层翻译
}
if err != nil {
	return nil, apperr.Internal("查询订单失败", err)
}
```

## 4. ⭐ `rows` 的生命周期 —— 今天的题眼

`Query` 返回的 `*sql.Rows` **占住了池里的一条连接**，直到它被关闭。

### 4.1 读到底会自动关，中途退出不会

实测（池里就这一条连接）：

```
Next() 返回 false 之后（没调 Close）:  InUse=0 Idle=1     ✅ 自动关了
只读一行就不管了:                      InUse=1 Idle=0     ⚠️ 连接被占住
```

**`Next()` 返回 `false` 时（数据读完或出错）`Rows` 会自动 `Close`。** 所以「正常读完」的路径不写 `Close` 也没事——这正是**危险的地方**：happy path 测试全绿，你以为没问题。

真正泄漏的是**提前退出**：

```go
for rows.Next() {
	var o Order
	if err := rows.Scan(&o.ID, &o.Customer); err != nil {
		return nil, err        // ⚠️ 这里走掉，rows 永远不会关
	}
	if o.Customer == target {
		break                  // ⚠️ 同样泄漏
	}
}
```

**所以 `defer rows.Close()` 不是可选的**——它保护的正是这些你不会去测的路径。

```go
rows, err := db.QueryContext(ctx, q)
if err != nil {
	return nil, err
}
defer rows.Close()             // ⭐ 紧跟着 err 检查，中间不要插任何东西
```

> `Close` 可以重复调用，自动关过之后再 `defer` 关一次是安全的。

### 4.2 ⚠️ 泄漏没有 GC 兜底

「反正 `rows` 变量出了作用域就没人引用了，GC 会收掉吧？」——**不会。**

```
三次查询后（未 GC）:   InUse=3 Open=3
两次 runtime.GC() 后:  InUse=3 Open=3        ⚠️ 纹丝不动
```

`database/sql` **没有为 `Rows` 设置 finalizer**。连接被永久占住，直到进程退出。

（唯一的救星是 ctx 取消：取消传给 `Query` 的 context 会关掉 `Rows` 并归还连接。但**别指望它**——你不一定有 `cancel`，也不一定会调。）

### 4.3 后果：整个服务挂住

池上限设成 2，连续查三次都不关：

```
第 1 次: ok（11ms）      InUse=1 Open=1
第 2 次: ok（10ms）      InUse=2 Open=2
第 3 次: ok（1.496s）    ← ⚠️ 阻塞了一秒半
```

第 3 次**没有报错，它在等**——等池里有连接还回来。生产环境里 `MaxOpenConns` 通常是 25 或 50，泄漏几十次之后，**所有**请求都开始排队，然后一起超时。

⭐ **这类故障的特征**：不是某个接口报错，是**整个服务同时变慢再挂死**，而且日志里往往什么都没有（大家都在等，没人报错）。查的时候看 `db.Stats()`：

```go
st := db.Stats()
// WaitCount 一直涨 + InUse 顶到 MaxOpenConns = 有人在泄漏连接
```

**把这几个指标暴露成 Prometheus metric**（D16），比事后翻代码快一百倍。

## 5. ⚠️ 忘记 `rows.Err()`：静默丢数据

`for rows.Next()` 结束有**两种**可能：读完了，或者**出错了**。循环本身分不出来。

实测——查 6 万行，让除零发生在**第 5 万行**：

```sql
SELECT 1/(50000-i) FROM generate_series(1,60000) i
```

```
想读 60000 行，循环「正常」结束，实际读到 49999 行
循环体里的 Scan 错误: <nil>                              ⚠️ 一个都没有
rows.Err()          : ERROR: division by zero (22012)   ← 只有它知道
```

**`Scan` 全部成功，`Next()` 安静地返回 `false`。** 不查 `rows.Err()` 的话，你会拿着这 49999 行当成全部 60000 行继续往下跑——没有 panic、没有错误日志、没有任何征兆。

> ⚠️ **对比**：如果让除零发生在**第 1 行**，`Query` 阶段就直接报错了，压根进不到循环：
>
> ```
> 错误在第 1 行     Query 阶段就报错: ERROR: division by zero
> 错误在第 5 万行   读到 49999 行, Scan 错误=<nil>, rows.Err()=division by zero
> ```
>
> 差别在于**第一批数据有没有成功返回**。真实世界里「迭代中途才失败」的原因是
> **连接断了 / 上游超时 / 网络抖动**——而这些在测试里几乎不会发生。
> **所以这个 bug 极难被测出来，只能靠代码习惯挡住。**

标准写法就三行，一个都不能少：

```go
rows, err := db.QueryContext(ctx, q, args...)
if err != nil {
	return nil, err
}
defer rows.Close()          // ① 提前退出也要关

for rows.Next() {
	...
}
if err := rows.Err(); err != nil {   // ② 循环结束必须查
	return nil, err
}
return out, nil
```

⭐ **`rows.Err()` 是 Go 数据库代码里最常被忘的一行。** review 时我会专门看。

## 6. NULL 怎么办

Go 的 `string` / `int64` 没有「空」这个状态，而 SQL 有。实测四种写法：

```
扫进 string          → err = converting NULL to string is unsupported    ⚠️ 直接失败
扫进 sql.NullString  → err=<nil>, Valid=false, String=""
扫进 *string         → err=<nil>, p=<nil>
SQL 里 COALESCE      → err=<nil>, c=""
```

| 方案 | 什么时候用 |
|---|---|
| `sql.NullString` / `NullInt64` / `NullTime` | 需要区分「NULL」和「空值」，且要显式处理 |
| `*string`（指针） | 同上，但你已经在用指针表达可选（D12 §1.2 那套） |
| `COALESCE(col, '')` | **不需要**区分 NULL 和零值时——最省事 |

⭐ **推荐顺序：能在 SQL 里 `COALESCE` 就 `COALESCE`。** 把「可选」这个复杂度挡在数据库边界，Go 这边的结构体就能保持干净的值类型。只有当「NULL」和「空字符串」**语义不同**时，才让它渗进 Go 类型里。

> 这和 D12 §1.2 是同一个判断：**只在真的需要区分时才用指针。**
> 区别是那边区分的是「没传」，这边是「没值」。

## 7. 事务：`defer` + 命名返回值

```go
func (r *Repo) Create(ctx context.Context, o *Order) (err error) {   // ⭐ 命名返回值
	tx, err := r.db.BeginTx(ctx, nil)
	if err != nil {
		return apperr.Internal("开启事务失败", err)
	}
	// ⭐ 无脑 Rollback —— 已经 Commit 过的话它返回 ErrTxDone，忽略即可
	defer func() {
		if rbErr := tx.Rollback(); rbErr != nil && !errors.Is(rbErr, sql.ErrTxDone) {
			// 回滚失败是真问题，但不能盖掉原始错误
			err = errors.Join(err, rbErr)
		}
	}()

	if err := tx.QueryRowContext(ctx, insertOrder, ...).Scan(&o.ID); err != nil {
		return apperr.Internal("插入订单失败", err)
	}
	for _, it := range o.Items {
		if _, err := tx.ExecContext(ctx, insertItem, o.ID, it.SKU, ...); err != nil {
			return apperr.Internal("插入订单项失败", err)
		}
	}
	return tx.Commit()
}
```

四个要点：

1. **`defer tx.Rollback()` 放在 `BeginTx` 成功之后立刻写**——之后任何路径 return 都自动回滚
2. **`Commit` 之后 `Rollback` 返回 `sql.ErrTxDone`**，这是正常的，要忽略
3. **命名返回值 `(err error)`** 才能让 defer 修改返回的错误（D2 §5）
4. **事务里所有操作都用 `tx.`**，不能用 `db.`——`db.` 会从池里另拿一条连接，**不在这个事务里**

> ⚠️ 第 4 条是最隐蔽的 bug：代码能跑、测试能过，但那条语句根本没在事务里，
> 回滚的时候它不会被撤销。**在 repository 里传 `tx` 而不是 `db` 是硬要求。**

### `Tx` 独占一条连接

事务期间那条连接**不回池子**。所以：

- **事务要短**。别在事务里调 HTTP、别在事务里 sleep
- 长事务 + 小连接池 = 又一种池耗尽

## 8. 把数据库错误翻译成领域错误

D12 §5 说 repository 的职责是**翻译**。Postgres 的错误码在 `pgconn.PgError` 里：

```go
import "github.com/jackc/pgx/v5/pgconn"

var pgErr *pgconn.PgError
if errors.As(err, &pgErr) {           // ⭐ 又是 errors.As（MISTAKES #22）
	switch pgErr.Code {
	case "23505":                      // unique_violation
		return apperr.Conflict("这个 SKU 已经在订单里了", err)
	case "23503":                      // foreign_key_violation
		return apperr.Invalid("引用的订单不存在", err)
	case "23514":                      // check_violation
		return apperr.Invalid("数量必须大于 0", err)
	}
}
```

⭐ **别把 `pgErr.Message` 直接返回给用户**——它包含表名、列名、约束名，是内部结构信息（D12 §5 的「两个消息」）。

## 9. 迁移

### 9.1 迁移：工具是最简单的部分

**永远不要手工在生产库上跑 DDL。** 迁移要版本化、可重放、可审计。

工具选型基本没有争议，随便挑一个都行：

| 工具 | 特点 |
|---|---|
| **`golang-migrate`** | 最通用，支持一堆数据库，有 CLI 也有库 |
| **`goose`** | 更简单，支持用 Go 写迁移（需要数据回填时有用） |
| **`atlas`** | 声明式：你描述目标 schema，它算 diff |

**真正的难点不在工具，在下面四条。**

### 9.2 ⭐ 迁移在哪里跑：别放在应用启动时

这是生产上第一个要决定的事。

```go
func main() {
	db := mustConnect()
	migrate.Up(db)          // ⚠️ 别这么干
	startServer(db)
}
```

三个问题：

1. **多副本竞争**——K8s 滚动更新时 5 个 Pod 同时启动，5 个进程同时跑迁移
2. **回滚变成灾难**——应用回滚到旧版本，但 schema 已经是新的了
3. **启动被拖慢甚至卡死**——一个大迁移让所有 Pod 的健康检查超时，然后被杀掉重启，再跑一次迁移

> `golang-migrate` 用 Postgres 的**咨询锁**（`pg_advisory_lock`）解决第 1 条，
> 所以并发跑是安全的——但第 2、3 条它解决不了。

**主流做法：迁移是一个独立的、在部署之前完成的步骤。**

```
CI/CD 流水线：
  ① 构建镜像
  ② 跑迁移        ← 独立的 job，成功了才继续
  ③ 滚动更新应用
```

K8s 上的具体形态：

| 方式 | 说明 |
|---|---|
| **Helm `pre-install`/`pre-upgrade` Hook** | 最常见。一个 Job，跑完才开始更新 Deployment |
| **`initContainer`** | 简单，但每个 Pod 都会跑一次（靠咨询锁去重） |
| **独立的 `Job` + 流水线编排** | 控制最细，也最啰嗦 |

⭐ **不管哪种，迁移用的数据库账号应该和应用的账号分开**——应用的账号不该有 DDL 权限。这样「代码里误加一句 `DROP TABLE`」就跑不起来。

### 9.3 ⭐⭐ expand-contract：零停机的唯一办法

这是生产迁移里**最重要**的一条，也是最反直觉的。

问题：滚动更新期间，**旧代码和新代码同时在跑**。所以任何「一步到位」的 schema 变更都会挂掉其中一半。

想把 `note` 列改名成 `remark`，一步改的话：

```
迁移执行 → 旧 Pod 还在跑 → 旧代码 SELECT note → 列不存在 → 全部 500
```

正确做法是**拆成多次部署**，每一步都保证新旧代码都能跑：

| 阶段 | 迁移 | 代码 |
|---|---|---|
| **1. expand** | `ADD COLUMN remark`（可空） | 不变 |
| **2. 双写** | 无 | 同时写 `note` 和 `remark`，仍读 `note` |
| **3. 回填** | `UPDATE ... SET remark = note`（分批） | 不变 |
| **4. 切读** | 无 | 读 `remark` |
| **5. contract** | `DROP COLUMN note` | 不再引用 `note` |

**五次部署改一个列名。** 第一次做会觉得荒谬，但这是零停机的代价。

> ⭐ 由此得到一条硬规则：**每个迁移都必须和「当前正在线上跑的代码」兼容。**
>
> 推论——这些操作**永远不能**单独出现在一次部署里：
> 改列名、改列类型、加 `NOT NULL`、删列、加没有默认值的必填列。

### 9.4 ⚠️ 锁：一个 10ms 的迁移能让表停摆 30 秒

**实测**（200 万行、516MB 的表）：

```
会话①  一个跑 8 秒的查询（持有 ACCESS SHARE 锁）
会话②  ALTER TABLE ADD COLUMN     → 需要 ACCESS EXCLUSIVE，排队等①
会话③  SELECT 1 FROM big LIMIT 1  → 只要 ACCESS SHARE
```

会话③和会话①的锁**完全兼容**，按理说不该等任何人。结果：

```
→ ALTER 完成，等了 7371ms
→ SELECT 完成，等了 6372ms   ⚠️
```

⭐ **Postgres 的锁是排队的**：一个在等 `ACCESS EXCLUSIVE` 的请求会**挡住它后面所有人**，哪怕后面那些请求彼此完全兼容。

所以：**迁移本身多快不重要，重要的是它前面有没有长查询。** 一条跑 30 秒的报表查询，能让一个 10ms 的 `ADD COLUMN` 把整张表堵死 30 秒。

**解药：`lock_timeout`。** 让迁移拿不到锁就快速失败，而不是排队堵住所有人：

```sql
SET lock_timeout = '3s';
ALTER TABLE orders ADD COLUMN remark text;
```

同样的场景，加上 `lock_timeout = '1s'` 之后实测：

```
ALTER:       等了 1280ms → 超时失败
普通 SELECT: 等了 255ms   ✅ 完全没被连累
```

迁移失败了没关系——**重试就行**，反正它还没开始改任何东西。而堵死整张表是要发故障报告的。

> 配套的还有 `statement_timeout`（限制语句总时长）。两个都设上，
> 是生产迁移脚本的标配开头。

### 9.5 Postgres 特有的几个陷阱

**① `ADD COLUMN` 的默认值决定它是毫秒还是分钟**

实测同一张 200 万行的表：

```sql
ALTER TABLE big ADD COLUMN status text NOT NULL DEFAULT 'pending';
--  7.8ms      ← 常量默认值，PG11+ 只改元数据

ALTER TABLE big ADD COLUMN seen_at timestamptz NOT NULL DEFAULT clock_timestamp();
--  2884ms     ← 易变默认值，必须重写整表（370 倍）
```

差别在于默认值是不是**常量**。非常量（`now()`、`clock_timestamp()`、`random()`、`gen_random_uuid()`）都会触发全表重写，而重写期间**整张表锁死**。

⭐ 需要「每行不同的默认值」时：先加可空列 → 分批回填 → 再加约束。

**② `CREATE INDEX` 会锁写，用 `CONCURRENTLY`**

```sql
CREATE INDEX idx ON orders (customer);              -- ⚠️ 建索引期间【写入全部阻塞】
CREATE INDEX CONCURRENTLY idx ON orders (customer); -- ✅ 不阻塞
```

`CONCURRENTLY` 的代价：慢一倍、**不能在事务里跑**（所以迁移工具要配置成不包事务）、失败会留下一个无效索引需要手工清理。

**③ 加 `NOT NULL` 要分两步**

直接 `SET NOT NULL` 会全表扫描并锁表。正确做法：

```sql
-- 步骤 1：加一个 NOT VALID 的约束（不检查存量数据，瞬间完成）
ALTER TABLE orders ADD CONSTRAINT note_nn CHECK (note IS NOT NULL) NOT VALID;
-- 步骤 2：单独校验（只加 SHARE UPDATE EXCLUSIVE 锁，不阻塞读写）
ALTER TABLE orders VALIDATE CONSTRAINT note_nn;
```

### 9.6 迁移文件长什么样

两种主流风格。

**`golang-migrate`：一个变更两个文件**

```
migrations/
├── 000001_create_orders.up.sql
├── 000001_create_orders.down.sql
├── 000002_add_remark.up.sql
└── 000002_add_remark.down.sql
```

```sql
-- 000002_add_remark.up.sql
ALTER TABLE orders ADD COLUMN remark text;

-- 000002_add_remark.down.sql
ALTER TABLE orders DROP COLUMN remark;
```

**`goose`：一个文件，用注释分段**

```sql
-- migrations/00002_add_remark.sql
-- +goose Up
ALTER TABLE orders ADD COLUMN remark text;

-- +goose Down
ALTER TABLE orders DROP COLUMN remark;
```

两者都靠数据库里的一张版本表（`schema_migrations` / `goose_db_version`）记住「跑到第几号了」，所以重复执行是安全的。

> ⚠️ 本课的 `migrations/001_orders.sql` **不是真正的迁移**——它开头是
> `DROP TABLE IF EXISTS`，每次执行都把表重建一遍。这在教学里方便（随时 `make db-migrate`
> 回到干净状态），但**生产上这么写等于删库**。真正的迁移只做增量变更，从不重建。

### 9.7 它们怎么被执行

**工具全包了，你不写调用代码。** 三个部分：

**① 文件名就是元数据。** `000002_add_color.up.sql` 被解析成
`版本=2 / 名字=add_color / 方向=up`。工具扫目录，按版本号排序。

**② 数据库里有一张版本表**，就一行：

```
schema_migrations 表:  version=2  dirty=false
```

所有决策都基于它——「跑到第几号了」。

**③ 你只调三个方法**（或对应的 CLI 命令）：

```go
m, _ := migrate.New("file://migrations", dsn)
m.Up()        // 把所有 version > 当前 的 up 按序跑完
m.Down()      // 全部回退
m.Steps(-1)   // 回退一步
```

实测的完整循环：

```
初始           版本=<无>   widgets 表：不存在
m.Up()         版本=2      列：[id name color]
m.Steps(-1)    版本=1      列：[id name]        ← 执行了 000002 的 down
m.Up()         版本=2      列：[id name color]
m.Up() 再来    → "no change"                     ⭐ 幂等，不会重复执行
m.Down()       版本=<无>   widgets 表：不存在
```

> 顺带一提，这里有**三个空白导入**（§2 那个 `_`）：
>
> ```go
> _ "github.com/golang-migrate/migrate/v4/database/postgres"  // 注册数据库后端
> _ "github.com/golang-migrate/migrate/v4/source/file"        // 注册 file:// 源
> _ "github.com/jackc/pgx/v5/stdlib"                          // 注册 pgx 驱动
> ```
>
> 所以 `migrate.New("file://migrations", "postgres://...")` 里那两个 scheme
> 才认得出来。**和 `database/sql` 是同一个注册表模式。**

#### ⚠️ 失败了会怎样：`dirty` 标记

这是生产上最需要提前知道的一环。让一个迁移中途失败：

```
Up 失败: Dirty database version 3. Fix and force version.
版本=3  dirty=true   ⚠️

再想跑迁移 → 同样的错误
⭐ 工具【拒绝继续】，必须人工介入
```

**`dirty=true` 的意思是「有个迁移跑到一半，我不知道库现在是什么状态」。**
之后所有迁移操作全部拒绝——这是对的，盲目继续可能把数据搞乱。

修复只能人工：**先去库里确认真实状态**，再告诉工具「实际到了第几号」：

```go
m.Force(2)   // → 版本=2 dirty=false
```

```bash
migrate -path migrations -database "$DSN" force 2
```

⭐ 这就是 §9.2 说「迁移要作为独立部署前步骤」的另一个理由：
如果它跑在应用启动里，一次失败会让**所有 Pod 卡在启动阶段反复重试**，
而且没人会去看那个 dirty 标记。

> **实践：每个迁移文件只做一件事。** 一个文件里两条语句、第一条成功第二条失败的话
> （Postgres 会把它们一起回滚，但工具不保证所有数据库都这样），
> 你得去查才知道库到底什么状态。一个文件一件事，dirty 时状态就是确定的。

#### CLI 和库是同一套

日常更常用 CLI，CI/CD 里就是跑这几行，不需要写任何 Go 代码：

```bash
migrate -path migrations -database "$DSN" up
migrate -path migrations -database "$DSN" down 1
migrate -path migrations -database "$DSN" version
migrate -path migrations -database "$DSN" force 2
```

### 9.8 `down` 长什么样，以及它为什么不可靠

先看**能写对**的情况：

| up | down | 可逆吗 |
|---|---|---|
| `ADD COLUMN remark text` | `DROP COLUMN remark` | ✅ 真可逆（列是空的） |
| `CREATE INDEX idx_x` | `DROP INDEX idx_x` | ✅ 真可逆 |
| `CREATE TABLE foo` | `DROP TABLE foo` | ✅ 真可逆（如果还没数据） |

再看**写不对**的情况——这才是重点：

```sql
-- up：把 note 改名成 remark
ALTER TABLE orders RENAME COLUMN note TO remark;
-- down：看起来完美对称
ALTER TABLE orders RENAME COLUMN remark TO note;
```

⚠️ **这个 down 语法上没问题，但救不了你**。因为回滚的时机是「新代码已经上线、已经往 `remark` 里写了一小时数据」，你把列名改回去，**那一小时里旧代码不认识的新数据格式还在里面**。schema 回去了，数据没有。

更直接的例子：

```sql
-- up
ALTER TABLE orders DROP COLUMN legacy_code;

-- down —— 唯一能写的形式
ALTER TABLE orders ADD COLUMN legacy_code text;
```

**列回来了，数据永远回不来了。** 这个 down 能跑通、能通过测试、看起来一切正常——直到你真的用它。

⭐ **所以 `down` 的可靠性和它「看起来对不对」无关，只和「有没有丢信息」有关。**
凡是 up 里有 `DROP` / `RENAME` / 改类型 / 删数据的，它的 down 都是**假的**。

#### 生产上的实际做法

几乎所有工具都支持 `down`，教程也都教你写。**但生产上很少真的执行它。**

三个原因：

- **多数 down 是假的**（上面那条）
- **`down` 几乎从不被测试**——CI 只跑 up，真出事时 down 自己也是坏的
- **真实的回滚是往前修**：写 `000003_revert_remark.up.sql`，而不是倒着执行 002

> ⭐ **迁移永远向前。** 出了问题就写下一个迁移修复它。
> 靠 §9.3 的 expand-contract 保证「回滚**应用代码**」永远是安全的——
> **能回滚的是代码，不是 schema。**

`down` 还是要写，两个用途：

1. **本地开发**：来回切分支时把库还原
2. **它逼你想清楚这次变更是不是可逆的**——如果 down 写不出来，说明这是个
   不可逆变更，就该走 §9.3 的多次部署流程，而不是一把梭

第 2 条才是写 `down` 的真正价值：**它是个思考工具，不是回滚工具。**

### 9.9 迁移文件放哪、怎么打包

推荐用 `embed` 把迁移嵌进二进制：

```go
import "embed"

//go:embed migrations/*.sql
var migrationsFS embed.FS
```

好处是**版本和代码强绑定**——不会出现「镜像是 v2、迁移文件是 v1」这种事，也不用往容器里额外挂文件。`golang-migrate` 和 `goose` 都支持 `fs.FS`。

### 9.10 一份生产迁移的检查清单

每个迁移合并前问自己：

- [ ] 它和**当前线上正在跑的代码**兼容吗？（§9.3）
- [ ] 有没有 `lock_timeout` / `statement_timeout`？（§9.4）
- [ ] `ADD COLUMN` 的默认值是常量吗？（§9.5①）
- [ ] `CREATE INDEX` 加 `CONCURRENTLY` 了吗？（§9.5②）
- [ ] 大表的数据回填**分批**了吗？一条 `UPDATE` 改 200 万行会长时间持锁、撑爆 WAL
- [ ] 它在**和生产同量级**的数据上跑过吗？（10 行的测试库上什么都是毫秒级）

## 10. 查询层：手写 SQL vs sqlc vs GORM

| 方案 | 怎么工作 | 代价 |
|---|---|---|
| **手写 SQL + `Scan`**（本课） | 你写 SQL，手动扫描到结构体 | 啰嗦，字段多了容易错位 |
| **`sqlc`** ⭐ | 你写 SQL，它**生成**类型安全的 Go 代码 | 需要构建步骤 |
| **`GORM`** | ORM，用方法链生成 SQL | 见下 |

⚠️ **给 Java 背景的人一句话**：`GORM` 看起来像 Hibernate，会让你觉得亲切——但这份亲切是陷阱。Go 社区的主流做法是**离 SQL 更近**，因为：

- 生成的 SQL 不可预测，性能问题难查（N+1 在 ORM 里是常态）
- Go 没有 JPA 那样的运行时代理，ORM 要靠大量反射，类型安全弱
- **`sqlc` 拿到了 ORM 想要的东西（类型安全、不手写扫描）却不放弃 SQL 的可预测性**

**建议：先手写（理解底层），生产上用 `sqlc`。** 除非团队已经全员 GORM。

## 11. ⭐ 取关联数据：JOIN、两次查询、还是拉回 Go

「查一批订单，每张要带上它的 items」——每个后端都会遇到，也是最容易做错的地方。

### 11.1 三种做法，实测

500 张订单 × 每张 10 个 item（共 5000 条明细）：

| 做法 | 耗时 | SQL 条数 |
|---|---|---|
| ① **N+1**（每张订单查一次 items） | **437ms** | 501 |
| ② **两次查询**（`= ANY`） | **13.9ms** ⭐ | 2 |
| ③ 一次 `LEFT JOIN` | 28.7ms | 1 |

⚠️ **「两次查询」和「N+1」是完全不同的两件事**，别混——差 31 倍。

### 11.2 两次查询：永远是 2 次，和 N 无关

关键在第二次用 **`= ANY($1)`** 一次把所有子记录取回来，再在 Go 里分组：

```go
// 第 1 次：拿订单
orders := listOrders(ctx, db, filter)     // 500 张

ids := make([]int64, len(orders))
byID := make(map[int64]*Order, len(orders))
for i := range orders {
	ids[i] = orders[i].ID
	byID[orders[i].ID] = &orders[i]        // ⭐ 取地址，后面往里 append
}

// 第 2 次：一条 SQL 拿回全部明细
rows, err := db.QueryContext(ctx,
	`SELECT order_id, id, sku, qty, price_cents FROM order_items
	 WHERE order_id = ANY($1) ORDER BY order_id, id`, ids)
...
for rows.Next() {
	var oid int64
	var it Item
	rows.Scan(&oid, &it.ID, &it.SKU, &it.Qty, &it.PriceCents)
	byID[oid].Items = append(byID[oid].Items, it)      // 内存里分组
}
```

⭐ **`= ANY($1)` 传的是一个数组参数，不是拼出来的 `IN (1,2,3,…)`。**
pgx 会把 Go 的 `[]int64` 编码成 Postgres 数组，所以它仍然是**一个占位符**：
不用担心注入，也不会因为 id 太多撑爆语句长度或让语句缓存失效。

> 这个模式不是 Go 特有的。Hibernate 的 `@BatchSize`、GraphQL 的 **DataLoader**、
> Rails 的 `includes`——**全是同一个东西**：批量加载 + 内存分组。

### 11.3 为什么 JOIN 在这个场景反而慢

JOIN 只发一次 SQL、只有一次往返，直觉上该更快。实测却慢一倍。

原因是**冗余传输**：JOIN 返回 5000 行，每行都带着完整的订单字段（`customer`、`note`、`status`、`created_at`）。**订单数据被重复传了 10 遍**，5000 行里 4500 份是冗余。

耗时分解（同一份数据）：

| | 服务端执行 | 端到端 |
|---|---|---|
| 一次 LEFT JOIN | 4.09ms | 27.2ms |
| 两次查询 | 0.13 + 1.78 = **1.91ms** | **13.4ms** |

两个口径比例一致，所以结论和测量方式无关。

> 顺带两个观察：
>
> - **Go 侧的 `Scan` 几乎不花钱**。「查完就丢」和「完整扫描+分组」耗时差不到 1ms，
>   大头是网络往返和协议开销。
> - **pgx 在 `database/sql` 模式下会缓冲整个结果集** ——
>   `QueryContext` 返回时数据已全部到客户端。这也解释了 §5 里
>   「除零发生在第 1 行时 `Query` 阶段就报错」的现象。

> ⚠️ **别把「两次查询更快」当普适定律。** 这里数据库在本机 Docker 里，往返几乎为零。
> 生产上一次 RTT 可能 0.5–2ms，那时「多一次往返」和「冗余传输」谁更贵，
> 取决于**父对象多宽、子对象平均几个**。
>
> ⭐ 真正普适的是下面两条**结构性**理由，性能只是顺带的。

### 11.4 ⚠️ 结构性理由一：JOIN 让 `LIMIT` 失效

```sql
SELECT ... FROM orders o LEFT JOIN order_items oi ON ... LIMIT 50
```

`LIMIT 50` 限的是**连接后的行数**，不是订单数。一张有 50 个 item 的订单就把配额吃光——**你以为拿了 50 张订单，实际只有 1 张。**

⚠️ 这是**正确性问题，不是性能问题**。而且测试数据里每张订单只有 1–2 个 item 的话，**完全测不出来**。

要用 JOIN 又要分页，只能先在子查询里 `LIMIT` 再 JOIN：

```sql
FROM (SELECT * FROM orders ORDER BY id DESC LIMIT $1) o
LEFT JOIN order_items oi ON oi.order_id = o.id
```

——已经比两次查询复杂了。

### 11.5 结构性理由二：NULL 处理

`LEFT JOIN` 时**没有 item 的订单**那几列全是 NULL，`Scan` 进 `int64`/`string` 直接报错。要么每列 `COALESCE`，要么用 `sql.Null*`：

```sql
COALESCE(oi.id, 0), COALESCE(oi.sku, ''), COALESCE(oi.qty, 0), COALESCE(oi.price_cents, 0)
```

```go
if item.ID != 0 {                    // 0 是安全哨兵：bigserial 从 1 开始
	o.Items = append(o.Items, item)
}
```

⚠️ 用 `0` 当哨兵**只在那个值不可能自然出现时才成立**。这和 D12 §1.2 是同一个判断：

| | in-band 哨兵 | out-of-band |
|---|---|---|
| JSON | `Port int`，用 0 表示「没传」 | `Port *int`，`nil` |
| SQL | `COALESCE(id,0)`，用 0 表示「没有」 | `sql.NullInt64` 的 `Valid` |

**先问「那个哨兵值在真实数据里可能出现吗」**——`Port` 可能真是 0（要指针），
`id` 是 `bigserial` 最小值 1（`COALESCE` 就够）。用 in-band 哨兵时
**务必写注释说明为什么它安全**，否则下一个人会以为你在赌运气。

⭐ 两次查询**完全不需要这一段**：查不到 item 就是零行，天然得到空切片。

### 11.6 那 JOIN 什么时候用

JOIN 没有作废，只是用途和「拼装对象图」无关：

| 你要什么 | 用什么 |
|---|---|
| **子表的列出现在结果里**（报表、平铺数据） | `JOIN` |
| 只是**按子表条件筛父表** | `EXISTS` / `IN`（半连接） |
| **父对象 + 子集合** | **两次查询 + 内存分组** |
| 聚合统计 | `GROUP BY`，别拉回来算 |

#### ⚠️ 筛选场景别用 `JOIN + DISTINCT`

```sql
-- ⚠️ naive 写法：先产生重复行，再去重
SELECT DISTINCT o.* FROM orders o
JOIN order_items oi ON oi.order_id = o.id
WHERE oi.sku = $1;

-- ✅ 半连接：找到第一个匹配就停，不产生重复行
SELECT o.* FROM orders o
WHERE EXISTS (SELECT 1 FROM order_items oi
              WHERE oi.order_id = o.id AND oi.sku = $1);
```

一张订单里有 3 个 item 都匹配时，`JOIN` 要产生 3 行再压成 1 行，`EXISTS` 一行都不多产生。

### 11.7 ⭐ 什么时候可以拉回 Go 里算

**能，只是通常不该。** 实测（同样 5000 条明细）：

| 场景 | 在 SQL 里做 | 拉回 Go 里做 |
|---|---|---|
| 按子表条件筛选 | **1.04ms**（返回 1 行） | 5.15ms（传 5000 行） |
| 按客户聚合 | **2.09ms**（返回 500 行） | 6.71ms（传 5000 行） |

差的不是「Go 比 SQL 慢」——§11.3 量过，`Scan` 几乎不花钱。**差的是传输量**：

```
SQL 里筛选：数据库扫 5000 行 → 返回 1 行    → 传 1 行
Go 里筛选： 数据库扫 5000 行 → 返回 5000 行 → 传 5000 行 → Go 扔掉 4999 行
```

而且这还是**没有索引**的情况。给 `sku` 加索引后 SQL 那边变成「索引直接定位」，
Go 那边**一点变化都没有**——它永远要传 5000 行。表涨到 500 万行时，
SQL 还是毫秒级，Go 那边直接 OOM。

⭐ **数据库在数据旁边，Go 在网络另一头。搬计算比搬数据便宜得多。**

什么时候拉回 Go 是合理的：

- **数据量小且有界**——配置表、字典表，几百行，还能缓存
- **逻辑 SQL 表达不了**——复杂业务规则、要调外部服务、要用 Go 的库
- **数据已经在内存里**——本来就因为别的原因加载了，再遍历一遍不花钱

判据是**「筛选/聚合之后剩多少」**：5000 行里只要 1 行 → 让数据库做；
5000 行里要 4800 行 → 反正都要传，在哪做无所谓。

> ⭐ **别把数据库当成「取数据的地方」，它是「算数据的地方」。**
> 这也是 §10 讲「离 SQL 更近」的理由——ORM 容易让人忘记数据库会算东西，
> 于是把筛选和聚合都搬进应用层，然后抱怨数据库慢。

## 12. 连接池参数

```go
db.SetMaxOpenConns(25)                  // 池上限（含使用中 + 空闲）
db.SetMaxIdleConns(25)                  // 空闲上限
db.SetConnMaxLifetime(30 * time.Minute) // 连接最长存活
db.SetConnMaxIdleTime(5 * time.Minute)  // 空闲多久被回收
```

实测（`MaxOpen=3`，6 个并发查询）：

```
进行中:  OpenConnections=3  InUse=3  Idle=0  WaitCount=3
结束后:  Open=1  Idle=1  WaitCount=3  WaitDuration=490ms
```

`WaitCount=3` 就是「有 3 次查询排过队」，`WaitDuration` 是累计等待时间。**这两个指标涨得快就是池不够用（或者有人泄漏）。**

四条经验：

1. **`MaxIdleConns` 要等于 `MaxOpenConns`**。默认只有 2——超出的连接**用完就关**，高并发下反复建连（上面那次结束后 `Open=1` 就是因为我把 Idle 设成了 1）
2. **`MaxOpenConns` 不是越大越好**。Postgres 每条连接是一个进程，几百条就把数据库拖垮了。先算：`实例数 × MaxOpenConns ≤ 数据库的 max_connections × 0.8`
3. **`ConnMaxLifetime` 一定要设**。云上的负载均衡器会静默掐掉长连接，不设的话你会拿到一堆已死的连接
4. **`0` 表示无限制**，不是「禁用」——`SetMaxOpenConns(0)` 是不限量，别写错

## 附录 A · 怎么确认 Postgres 在跑

练习期间最常问的一件事。**分三个层次查，它们能骗过你的方式各不相同。**

### 四条常用命令

```bash
# ① 容器状态 —— 最常用
docker ps --filter name=golearn-pg

# ② 端口有没有被监听（不依赖 docker，能看出是不是别的东西占着）
lsof -nP -iTCP:5433 -sTCP:LISTEN

# ③ 数据库能不能接受连接 —— 最可靠
docker exec golearn-pg pg_isready -U devuser -d golearn

# ④ 直接连进去看
make db-psql
```

正常时 ① 的输出：

```
NAMES        STATUS                PORTS
golearn-pg   Up 3 days (healthy)   0.0.0.0:5433->5432/tcp
```

⭐ `(healthy)` 来自 `deploy/docker-compose.yml` 里配的 healthcheck，它每 2 秒跑一次
`pg_isready`。**这个字段本身就是「数据库活着」的证据，比 `Up` 有信息量得多。**

### ⚠️ 三个层次骗你的方式不一样

| 查什么 | 命令 | 什么情况下会骗你 |
|---|---|---|
| 容器进程活着 | `docker ps` | 容器在跑，但里面的 Postgres 挂了 |
| 端口被监听 | `lsof -iTCP:5433` | 端口开着，但数据库还没准备好接受查询 |
| **真能查询** | `pg_isready` / 真连一次 | —— |

⭐ 这正是 §1 那条的现实版：**`sql.Open` 不连接数据库，`Ping` 才连。**
前两层相当于 `sql.Open`（看起来没问题），第三层才是 `Ping`。

所以测试里的 `openDB` 才要 `PingContext` 而不是只 `sql.Open`。

### 顺带：一个 SQL 的 NULL 坑

查端口时我写过这么一句，输出是**空的**：

```sql
select 'db=' || current_database() || ' port=' || inet_server_port();
```

因为 `docker exec psql` 走的是 **Unix socket**，`inet_server_port()` 返回 `NULL`，
而 SQL 里 **`NULL || 任何东西 = NULL`** —— 整个字符串没了，不报错、不警告。

```sql
-- 加上 coalesce 就好了
coalesce(inet_server_port()::text, 'unix-socket')
```

这和 §6 是同一件事的两面：

| | 表现 |
|---|---|
| NULL 扫进 Go 的 `string` | **报错**（`converting NULL to string is unsupported`） |
| NULL 在 SQL 里参与运算 | **静默传染** |

⚠️ **SQL 的 NULL 比 Go 的零值危险得多**，因为它安静：

```sql
WHERE x = NULL      -- 永远是假（要用 IS NULL）
SUM(col)            -- 跳过 NULL，不报错
'a' || NULL         -- 整个变 NULL
count(col)          -- 不数 NULL 行，和 count(*) 结果不同
```

全都不报错。**从数据库读出来的每一列，先问一句「它可能是 NULL 吗」。**
