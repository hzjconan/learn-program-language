## 1. 为什么 Go 的测试长这样

Java 有 JUnit + AssertJ + Mockito + Spring Test。Go 什么都没有——**标准库的 `testing` 包只有大约 20 个常用 API，没有断言函数，没有 mock 框架，没有注解。**

```go
func TestAdd(t *testing.T) {
	if got := Add(1, 2); got != 3 {
		t.Errorf("Add(1,2) = %d, want 3", got)
	}
}
```

就是 `if` + `t.Errorf`。这是刻意的：

| | JUnit | Go |
|---|---|---|
| 断言 | `assertEquals(3, got)` | `if got != want { t.Errorf(...) }` |
| 失败信息 | 框架生成 | **你自己写** |
| Mock | Mockito 生成 | **手写一个 struct 实现接口**（D5 那些替身） |
| 参数化 | `@ParameterizedTest` | **表驱动，普通 slice** |

**代价是啰嗦，收益是没有魔法。** 测试就是普通 Go 代码，不需要学第二套 DSL，出问题时用普通调试手段就能查。

### `t.Error` vs `t.Fatal`

| | 行为 | 什么时候用 |
|---|---|---|
| `t.Errorf` | 记录失败，**继续执行** | 默认用这个。一次跑出所有问题 |
| `t.Fatalf` | 记录失败，**立即结束这个测试** | 后续代码依赖这一步（比如 `err != nil` 就没法继续） |

```go
got, err := Parse(input)
if err != nil {
	t.Fatalf("Parse 失败: %v", err)   // ← 必须 Fatal，否则下一行会 panic
}
if got.Name != "x" {
	t.Errorf("Name = %q, want %q", got.Name, "x")   // ← Error 就够
}
```

> ⚠️ `t.Fatal` **只能在测试的主 goroutine 里调用**。在子 goroutine 里调用它不会终止测试（`runtime.Goexit` 只结束那个 goroutine），行为是错的。子 goroutine 里只能 `t.Errorf`。

### ⭐ 失败信息的格式

Go 社区有一个近乎强制的惯例：

```
函数名(输入) = 实际值, want 期望值
```

```go
t.Errorf("Split(%q, %q) = %v, want %v", s, sep, got, want)
```

**为什么重要**：失败信息是这个 bug 唯一留给你的线索。`t.Error("failed")` 这种写法，等价于线上只打一句「出错了」——我们 D4/D5 review 反复说的可观测性，在测试里同样适用。

用 `%q` 打字符串（能看见空格和不可见字符），`%v` 打结构体，`%#v` 打带类型的完整表示。

## 2. `go test` 的基本盘

```bash
go test ./...                      # 跑全部
go test -v ./internal/store        # 显示每个测试的名字和 t.Log
go test -run 'TestGet'             # 只跑名字匹配【正则】的
go test -run 'TestGet/不存在'       # 子测试用 / 分隔，也是正则
go test -count=1 ./...             # ⭐ 禁用缓存，强制重跑
go test -race ./...                # 竞态检测
go test -cover ./...               # 覆盖率
go test -failfast ./...            # 第一个失败就停
go test -timeout 30s ./...         # 默认 10 分钟
```

**两个容易踩的：**

1. **`-run` 是正则不是字符串**。`-run TestGet` 会同时匹配 `TestGetAll`、`TestGetter`。要精确匹配写 `-run '^TestGet$'`。
2. **测试结果会被缓存**。代码没变时第二次跑直接输出 `(cached)`。这通常是好事，但如果你的测试依赖外部状态（文件、环境变量、时间），缓存会骗你——用 `-count=1` 强制重跑。

### 文件与函数的规则（编译器强制）

- 文件名必须以 `_test.go` 结尾，**这些文件不会被编译进正式产物**
- `Xxx` 只是占位符，意思是「这里接你自己起的名字」——有意义的是**前缀词**

| 前缀 | 签名 | 干什么 | 什么时候跑 |
|---|---|---|---|
| `TestXxx` | `(t *testing.T)` | 验证**正确性** | `go test` 默认跑 |
| `BenchmarkXxx` | `(b *testing.B)` | 测量**性能** | **只有加 `-bench` 才跑** |
| `ExampleXxx` | `()` 无参数 | 既是**文档**也是测试 | 默认跑（前提是有 `// Output:`） |
| `FuzzXxx` | `(f *testing.F)` | **自动生成输入**找崩溃 | 默认只跑种子；加 `-fuzz` 才真正模糊 |

实测（同一个包，三条命令）：

```
go test -v                    → Test / Fuzz(仅种子) / Example        ⚠️ Benchmark 不出现
go test -bench=. -v           → 上面三个 + BenchmarkUpper-10 ... 20.13 ns/op
go test -fuzz=FuzzUpper       → 3 秒生成并试了 50 万个输入
```

**这就是基准测试不会拖慢日常 `go test` 的原因**——它默认根本不执行。而 `Fuzz` 有两副面孔：平时是普通回归测试（只跑 `f.Add` 的种子），只有显式 `-fuzz` 时才变成模糊测试引擎。

### 名字的硬规则

`Xxx` 部分**必须大写开头或非小写字符**，而且这条是**强制**的：

```
four_test.go:39:6: TestupperLowercase has malformed name:
    first letter after 'Test' must not be lowercase
```

`go test` 会自动跑 `go vet`，所以写错名字**直接构建失败**，不会静默跳过。（真正会被静默忽略的是前缀就不对的函数，比如 `func checkUpper(t *testing.T)`——那在 Go 看来只是个普通函数。）

## 3. 表驱动测试 + 子测试

你已经写过很多次了，这里补上你可能没注意的细节。

```go
func TestValidate(t *testing.T) {
	tests := []struct {
		name string       // ⭐ 必须有，它是失败时唯一的定位信息
		in   Record
		want string
	}{
		{name: "合法", in: Record{ID: "u1"}, want: ""},
		{name: "ID 为空", in: Record{}, want: "ID"},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {   // ⭐ 子测试
			...
		})
	}
}
```

### 为什么一定要 `t.Run`

不用 `t.Run` 也能跑，但你会失去三样东西：

1. **失败时能定位**：输出里显示 `--- FAIL: TestValidate/ID_为空`，而不是一堆没上下文的 Errorf
2. **能单独跑一条**：`go test -run 'TestValidate/ID_为空'`
3. **一条失败不影响其他条**：子测试里的 `t.Fatal` 只结束那一条

> 子测试名里的**空格会被替换成下划线**，所以 `-run` 时要写 `ID_为空`。这也是为什么很多人用不带空格的 name。

### 并行子测试

```go
for _, tt := range tests {
	t.Run(tt.name, func(t *testing.T) {
		t.Parallel()        // ← 这条与其他并行子测试同时跑
		...
	})
}
```

`t.Parallel()` 的语义很绕：调用它的子测试会**暂停**，等父测试的函数体跑完，然后所有标记了 `Parallel` 的子测试一起放行。

> **Go 1.22 之前**这里有个著名的循环变量陷阱（所有子测试拿到同一个 `tt`），必须写 `tt := tt`。**Go 1.22 起循环变量每轮都是新的**，不再需要。我们的 lint 开了 `copyloopvar`，你要是写了 `tt := tt` 它会提醒你删掉。

## 4. `t.Helper` / `t.Cleanup` / `t.TempDir`

这三个你还没用过，但都很常用。

### `t.Helper()`：让失败行号指向调用处

```go
func assertNoErr(t *testing.T, err error) {
	t.Helper()          // ← 关键
	if err != nil {
		t.Fatalf("意外的错误: %v", err)
	}
}
```

不加 `t.Helper()`，失败信息会指向 `assertNoErr` **内部**那一行——所有调用点的失败看起来都在同一个位置。加了之后，行号指向**调用它的那一行**。

**任何被测试调用的辅助函数，第一行都写 `t.Helper()`。**

### `t.Cleanup()`：比 `defer` 更适合测试的清理

```go
func newTestStore(t *testing.T) *MemStore {
	t.Helper()
	s := &MemStore{}
	t.Cleanup(func() { s.Close() })    // 测试结束时自动调用
	return s
}
```

和 `defer` 的区别：

| | `defer` | `t.Cleanup` |
|---|---|---|
| 何时执行 | **当前函数**返回时 | **当前测试**（含子测试）结束时 |
| 能不能写在辅助函数里 | ❌ 辅助函数一返回就执行了 | ✅ 等测试结束才执行 |
| 顺序 | LIFO | LIFO |

**上面那个 `newTestStore` 用 `defer` 是写不出来的**——`defer s.Close()` 会在 `newTestStore` 返回时立刻执行。这就是 `t.Cleanup` 存在的理由。

### `t.TempDir()`：自动清理的临时目录

```go
dir := t.TempDir()        // 每个测试一个独立目录，结束自动删除
path := filepath.Join(dir, "config.txt")
```

比 `os.MkdirTemp` + `defer os.RemoveAll` 干净，而且**每个子测试拿到的是不同目录**，天然支持并行。

### `TestMain`：整个包的 setup/teardown

```go
func TestMain(m *testing.M) {
	// setup：起数据库容器、加载 fixture……
	code := m.Run()
	// teardown
	os.Exit(code)
}
```

**一个包只能有一个。** 用得不多，但连接真实数据库的集成测试离不开它。

## 5. ⭐ 覆盖率的真相 —— 今天的题眼

```bash
go test -cover ./...
go test -coverprofile=cover.out ./... && go tool cover -html=cover.out   # 浏览器里看
go tool cover -func=cover.out                                            # 命令行按函数看
make cover                                                               # 我们的 Makefile 里配好了
```

### 覆盖率量的是「这行代码被执行过」，不是「这行代码是对的」

```go
func Get(k string) (V, bool) {
	it, ok := c.items[k]
	if !ok {
		return zero, false
	}
	return it.val, true          // ← 忘了检查过期
}

// 测试：
func TestGet(t *testing.T) {
	c.Set("a", 1)
	v, ok := c.Get("a")          // ← 每一行都执行到了
	if !ok || v != 1 { t.Error(...) }
}
```

**覆盖率 100%，bug 完好无损。** 因为测试从来没让时间往前走过。

再看一个更狠的：

```go
func TestEverything(t *testing.T) {
	Add(1, 2)         // 调用了，但【一个断言都没有】
	Sub(5, 3)
	Mul(2, 4)
}
```

**这个测试文件能把覆盖率刷到 100%，并且永远不会失败。**

### 所以覆盖率该怎么用

| 怎么用 | 说明 |
|---|---|
| ✅ **找没测到的分支** | 打开 HTML 报告，红色的部分是你完全没想到的路径 |
| ✅ **作为下限指标** | 低于 60% 大概率有整块功能没测 |
| ❌ **作为目标** | 「把覆盖率刷到 90%」会逼出一堆没断言的垃圾测试 |
| ❌ **作为质量证明** | 100% 覆盖的代码库照样能到处是 bug |

> **一句话**：覆盖率能告诉你**哪里肯定没测**，不能告诉你**哪里测好了**。它是排除法工具，不是质量指标。

### 怎么判断测试是不是真的有用

问自己一个问题：**「如果我把这行代码改坏，测试会红吗？」**

这就是**变异测试（mutation testing）**的思路——把 `>` 改成 `>=`、把 `return err` 改成 `return nil`、把边界 `+1` 改成 `-1`，看测试抓不抓得住。Go 有 `go-mutesting` 之类的工具，但**你手动改两行试试，效果就够了**。今天的练习就是这个方法的实战。

### ⭐⭐ 那怎么知道该写什么测试

这是做今天练习时最容易卡住的地方：**「我盯着代码看了半天，没看出问题，那我要写什么测试？」**

思路反了：

> **别读实现去找 bug，读文档去写断言。**

测试的来源是**规格**，不是代码。把文档里每句话都变成断言，bug 会自己掉出来——**你事先根本不需要知道它在哪**。下面五个方法，前四个是产出测试，第五个是检验测试。

#### 方法一：把文档逐句拆成断言

拿 `cache.Set` 的文档做示范：

```go
// Set 写入一个键值对，并把它的过期时刻重置为「现在 + ttl」。
//
// 同 key 覆盖，命中计数（见 Hits）随之清零。
```

| 文档里的句子 | 对应的断言 |
|---|---|
| 「写入一个键值对」 | `Set("a",1)` 后 `Get("a")` 得到 1 |
| 「过期时刻重置为**现在 + ttl**」 | 时钟推进 ttl-1 后仍能 Get；推进 ttl 后 Get 不到 |
| 「同 key **覆盖**」 | `Set("a",1); Set("a",2)` → 得到 2，且 `Len()==1` |
| 「**重置**过期时刻」 | 快过期时再 `Set` 一次，应重新获得完整 ttl |
| 「命中计数**随之清零**」 | `Get` 三次后 `Set`，`Hits` 应回到 0 |

**一句话一个断言。** 文档里有五句，就该有五个断言——不管你觉不觉得那句话「显然成立」。

#### 方法二：找出现有测试「从来没变化过的维度」

很机械，但特别有效。看任何一份测试，列出它固定不变的输入维度：

| 维度 | 弱测试里永远是 | 该试的其他取值 |
|---|---|---|
| **时间** | 「刚写入，立刻读」 | 未到期 / **正好到期** / 已过期 |
| **状态组合** | 「缓存里全是新鲜项」 | 全过期 / **新鲜和过期混在一起** / 空 |
| **并发** | 「单 goroutine」 | 多 goroutine 同时读 / 同时读写 |

**bug 不长在被测过的维度上。** 你不需要知道 bug 是什么，沿着没被覆盖的维度各推一把就行。**边界值优先**——`正好到期` 这类临界点是 off-by-one 的老巢。

#### 方法三：跨方法的不变量

「一个方法一个测试」的结构，永远发现不了**「两个方法各自看起来对，但互相矛盾」**。

所以额外写一类断言：同时调用多个方法，检查它们说法一致。

```go
// 不变量：Len() 应该等于「实际能被 Get 到的键的数量」
count := 0
for _, k := range allKeys {
	if _, ok := c.Get(k); ok {
		count++
	}
}
if count != c.Len() {
	t.Errorf("Len()=%d 但实际能取到 %d 个", c.Len(), count)
}
```

**这个断言不要求你知道谁错了**——它只要求两者一致，谁不一致就暴露谁。关键是要在**有意思的状态**下跑它（比如「部分数据已过期」），而不是在全新鲜的状态下。

#### 方法四：并发测试是纯机械动作

文档写了「并发安全」，就无脑加这个，然后 `go test -race`：

```go
var wg sync.WaitGroup
for range 8 {
	wg.Add(1)
	go func() { defer wg.Done(); /* 调各个方法 */ }()
}
wg.Wait()
```

**你不需要理解代码**——竞态检测器替你判断。这是唯一一类「不动脑也能找 bug」的测试，所以**凡是文档承诺并发安全的类型，都该有一个**。

> 让不同 goroutine 调**不同的方法组合**，别全都调同一个。竞态只有在两个 goroutine 真的碰到同一块内存时才会被发现（§7）。

#### 方法五：写完之后反向验证

用上面那个变异测试的问题检验你的成果：**把某一行改坏，测试红了吗？** 没红就说明那行目前没有任何保护。改完记得改回来。

#### 那什么时候才读实现

读代码有用，但它是**第二遍**的事，目标也不同：

- **第一遍读文档** → 产出断言清单（此时你还不知道 bug 在哪，也不需要知道）
- **第二遍读实现** → 只扫几类高危信号：**比较符号是 `<` 还是 `<=`**、**这行在读锁还是写锁里**、**这个分支返回零值还是错误**、**循环里有没有重复计算**

## 6. 基准测试

```go
func BenchmarkFilter(b *testing.B) {
	data := make([]int, 10000)
	b.ResetTimer()              // ⭐ 排除上面准备数据的耗时

	for b.Loop() {              // Go 1.24+ 的新写法
		_ = Filter(data, isEven)
	}
}
```

```bash
go test -bench=. -benchmem ./internal/genx
go test -bench=BenchmarkFilter -benchtime=10s ./internal/genx
go test -bench=. -count=10 ./... > new.txt && benchstat old.txt new.txt   # 统计显著性
```

输出长这样：

```
BenchmarkFilter-10    	  145238	      8203 ns/op	   81920 B/op	       1 allocs/op
                          ^^^^^^        ^^^^^^^^^        ^^^^^^^^^          ^^^^^^^^^
                        跑了多少轮      每轮耗时        每轮分配字节      每轮分配次数
```

**`-benchmem` 一定要加。** `allocs/op` 往往比 `ns/op` 更能说明问题——Go 的性能问题十有八九是分配太多，而分配次数是个稳定的、跨机器可比的指标，`ns/op` 则受机器状态影响很大。

### `b.Loop()` vs 老写法 `for i := 0; i < b.N; i++`

Go 1.24 加了 `b.Loop()`，**新代码一律用它**：

| | `for i := 0; i < b.N; i++` | `for b.Loop()` |
|---|---|---|
| 计时器 | 要手动 `b.ResetTimer()` | **自动排除循环外的准备工作** |
| 编译器优化 | 循环体可能被**整个删掉**，要手动防 | **调用本身不会被删掉** |
| 执行次数 | 每次 benchmark 重跑整个循环 | 同上，但语义更清楚 |

老写法的经典坑：编译器发现结果没被使用，把整个调用优化没了，于是你测出一个 `0.3 ns/op` 的假结果。`b.Loop()` 保证调用一定会发生。

### ⚠️ 但 `b.Loop()` 挡不住逃逸分析（实测）

`b.Loop()` 保证**调用不被删掉**，但**不保证结果被分配到堆上**。丢弃返回值时，编译器仍可能把本该在堆上的东西放栈上：

```go
for b.Loop() { BuildPrealloc(1000) }          // → 582 ns/op  0 B/op  0 allocs/op  ❌ 假的
```

`BuildPrealloc` 里明明 `make` 了 8000 字节。内联后编译器发现这块内存逃不出去，就放栈上了——**栈分配不计入 `B/op`**。

加一个包级 sink 逼它逃逸：

```go
var sinkSlice []int
for b.Loop() { sinkSlice = BuildPrealloc(1000) }   // → 1271 ns/op  8192 B/op  1 allocs/op  ✅
```

**规则：基准测试里的返回值必须有去处**（赋给包级变量），否则你测的可能是个和生产环境完全不同的东西。看到 `0 allocs/op` 时先怀疑自己。

### 三个指标怎么读

| 指标 | 含义 | 稳定性 |
|---|---|---|
| `ns/op` | 每次操作的**墙上时间** | 差——受机器、负载影响 |
| `B/op` | 每次操作**在堆上分配的字节总数** | 好 |
| `allocs/op` | 每次操作**调用了多少次堆分配** | **最好**——整数，跨机器可比 |

`B/op` 的两个易错点：**它是累计分配量不是峰值占用**（衡量的其实是 GC 压力），**它只算堆**（栈上的不计，见 QA #10 逃逸分析）。

**优化顺序：先降 `allocs/op`，`ns/op` 通常自己跟着降。** 实测一组数据（构造 1000 个元素 / 拼 1000 个字符串）：

```
预分配 make([]T,0,n)      1271 ns/op       8192 B/op        1 allocs/op
不预分配 var s []T        2896 ns/op      25208 B/op       12 allocs/op   ← 12 次扩容
strings.Builder           6861 ns/op      34296 B/op       15 allocs/op
字符串 += 拼接          467698 ns/op    4273915 B/op      999 allocs/op   ← O(n²)
```

最后一行：为了产出一个 8KB 的字符串分配了 4.2MB。string 不可变，每次 `+=` 都要新分配并拷贝全部已有内容。**循环里拼字符串一律用 `strings.Builder`。**

## 7. `-race` 竞态检测器

```bash
go test -race ./...
```

**这是 Go 最有价值的工具，没有之一。** 我们的 `make check` 里已经默认开了。

- **原理**：运行时记录每次内存访问的 happens-before 关系，发现两个 goroutine 无同步地访问同一地址、且至少一个是写，就报告
- **代价**：内存 ×5～10，速度 ×2～20。所以只在测试和预发环境开，生产不开
- ⚠️ **它只能发现「代码真的被执行到」的竞态**。测试没让两个 goroutine 走到那条路径，它就沉默——**不报警不等于没有竞态**

### ⭐ 它不靠「撞上」，靠 happens-before（实测）

常见误解：以为要两个 goroutine 在时间上重叠访问才能被抓到，所以要拼命加循环次数碰运气。**不是这样。**

实测一个无保护的 `b.n++`，两个 goroutine 各只调用**一次**：

```
第 1 次：只跑一次的版本 → 报告竞态    |   8×500 轮的版本 → 报告竞态
第 2 次：只跑一次的版本 → 报告竞态    |   8×500 轮的版本 → 报告竞态
第 3 次：只跑一次的版本 → 报告竞态    |   8×500 轮的版本 → 报告竞态
```

**每次都抓到了。** 因为检测器记录的是「这次访问属于哪个 goroutine、有没有被 mutex/channel 排过序」，而不是「两次访问的时间戳挨得近不近」。只要两个 goroutine 之间没有同步原语建立先后顺序，哪怕执行完全错开也会被判定为竞态。

**所以写并发测试的关键不是循环次数，而是：**

> **让两个 goroutine 都真的「执行到」那段代码。**

如果你的并发调用在第一个 `if` 就返回了（比如 `Get` 一个不存在的键），后面的代码根本没跑，检测器自然什么都看不到。**先把状态准备好，再并发访问。**

（多跑几轮仍然值得——成本几乎为零，还能覆盖更多的路径组合。只是它不是成败关键。）

D5 那个 `Set.Has` 的竞态就是它抓出来的：

```
WARNING: DATA RACE
Write at 0x00c000102088 by goroutine 12:
  genx.(*Set[...]).Has()  genx.go:154
Previous read at 0x00c000102088 by goroutine 9:
  genx.(*Set[...]).Has()  genx.go:153
```

**要让它有机会开口，你得写并发的测试**——这是今天练习里的一条。

## 8. 模糊测试（Fuzz）

Go 1.18 起内置。适合**输入是字节/字符串、且有明确不变量**的函数——解析器、编解码器。

```go
func FuzzParse(f *testing.F) {
	f.Add("key=value")              // 种子语料
	f.Add("")

	f.Fuzz(func(t *testing.T, s string) {
		got, err := Parse(s)
		if err != nil {
			return                   // 报错是合法结果，不是 bug
		}
		// 不变量：解析成功的东西，序列化回去应该还能解析
		if _, err := Parse(got.String()); err != nil {
			t.Errorf("往返失败: %q → %q", s, got.String())
		}
	})
}
```

```bash
go test -fuzz=FuzzParse ./internal/kvconf      # 持续跑，Ctrl-C 停
```

**关键在于「找什么」**：fuzz 不知道什么是正确答案，它只能找**崩溃**和**你写出来的不变量**。常用不变量：

- 不 panic（最低要求，什么都不写就有）
- 往返一致：`Decode(Encode(x)) == x`
- 与朴素实现结果相同（差分测试）

发现的失败用例会自动存进 `testdata/fuzz/`，**要提交进 git**——它会变成一个永久的回归测试。

## 9. `Example` 函数：测试和文档是同一份东西

```go
func ExampleSum() {
	fmt.Println(Sum([]int{1, 2, 3}))
	// Output: 6
}
```

**这既是文档也是测试**：

- `go doc` / pkg.go.dev 上会显示成这个函数的示例代码
- `go test` 会**真的运行它**，比对 stdout 和 `// Output:` 后面的内容，不一致就失败

> **文档不会过期**——这是 Go 里最优雅的设计之一。Java 的 `@code` 注释里的示例代码烂掉了没人知道。

命名规则决定它挂在哪儿：

| 函数名 | 显示位置 |
|---|---|
| `ExampleSum` | `Sum` 函数的文档下 |
| `ExampleCache_Get` | `Cache` 类型的 `Get` 方法下 |
| `ExampleSum_negative` | `Sum` 的第二个示例（小写后缀是变体名） |
| `Example` | 整个包的文档下 |

顺序不确定的输出用 `// Unordered output:`。没有 `// Output:` 注释的 Example **只编译不运行**。

## 10. 黑盒测试 vs 白盒测试

Go 允许测试文件用**两个包名之一**：

```go
package store        // 白盒：和被测代码同包，能访问私有成员
package store_test   // 黑盒：外部包，只能用导出的 API
```

**这是 Go 独有的设计**——`store_test` 是唯一允许和目录名不一致的包名。

| | 白盒 `package store` | 黑盒 `package store_test` |
|---|---|---|
| 能测私有函数 | ✅ | ❌ |
| 能替换私有字段（注入假时钟） | ✅ | ❌ |
| 强迫你从**使用方视角**设计 API | ❌ | ✅ |
| 会不会造成循环导入 | 可能 | **不会** |

**实践**：默认写黑盒（`_test` 后缀），需要注入内部状态时才用白盒。**两种可以在同一个目录里共存**——`cache_test.go` 写 `package cache_test`，`cache_bugs_test.go` 写 `package cache`，完全合法。

> 循环导入那条很实用：如果包 A 的测试需要用包 B，而 B 又导入 A，白盒测试会循环导入编译失败，黑盒不会。

### 第三条路：`export_test.go`

标准库大量使用的折中方案——**主测试保持黑盒，只开一个可控的后门**：

```go
// export_test.go —— 文件名以 _test.go 结尾，所以只在测试时编译，不进正式产物
package cache

// SetClock 把私有的 now 字段暴露给外部测试包。
func (c *Cache[K, V]) SetClock(f func() time.Time) { c.now = f }
```

黑盒测试包 `cache_test` 就能调 `c.SetClock(...)`，而正式用户看不到这个方法。代价是多一个文件。

### ⚠️ 我自己没做到这一点（实测审计）

写完这份讲义我回头量了一下前五天的测试：**11 个测试文件全是白盒**。然后我把 9 个 `internal/` 包的测试逐个改成黑盒（`package X_test` + dot import）编译：

```
✅ cache  ✅ genx  ✅ kvconf  ✅ mathx  ✅ payroll
✅ slicex ✅ store ✅ stringx ✅ units      ← 全部编译通过
```

**全都能改成黑盒，也就是说白盒的权限我一次都没用上。** 没有设计理由，纯粹是省事：同包不用写 import，标识符不用加前缀。

代码本身没问题——能编译成黑盒恰恰证明这些包的导出 API 是完整的。但我丢掉了一个信号：

> **黑盒测试能「证明」API 完整，白盒测试永远证明不了**——它可以随时伸手进去拿私有成员，你不会发现 API 少了什么。

假如 `MemStore` 忘了导出 `Len()`：黑盒测试里 `dst.Len()` 会**编译失败**，逼你立刻补上；白盒测试则会去读 `len(m.records)`，测试照样绿，而外部用户拿到的是个残废的 API。

### 顺带：`cache` 需要白盒，这本身是个设计信号

今天的练习里你**必须**用白盒（要替换 `c.now`）。但换个角度：**「必须伸手进结构体才能控制时间」说明 API 不完整**。更干净的做法是把时钟做成导出选项——D4 §5 的功能选项模式：

```go
func New[K, V](ttl time.Duration, opts ...Option[K, V]) *Cache[K, V]
func WithClock[K, V](f func() time.Time) Option[K, V]
```

我故意没这么设计，因为今天要教的正是「白盒注入内部状态」这个场景。**但这是取舍，不是唯一解。**

## 11. 项目布局：`cmd/` `internal/` `pkg/`

这三个目录里，**只有 `internal/` 是编译器认的**，其余是社区惯例。

### `internal/` —— 唯一有强制力的

```
github.com/you/proj/
├── internal/secret/     ← 只有 github.com/you/proj/... 下面的包能导入
└── pkg/api/
```

**规则**：`internal/` 目录下的包，只能被 `internal/` 的**父目录所在的模块子树**导入。别人 `import "github.com/you/proj/internal/secret"` 会**编译失败**：

```
use of internal package github.com/you/proj/internal/secret not allowed
```

这是 Java `package-private` 在模块层面的对应物，但更强：**它跨模块生效**，任何人都绕不过去。

> **实践建议：新项目默认把所有东西放 `internal/`。** 一旦某个包被外部导入了，你就再也不能改它的 API（语义化版本约束）。`internal/` 保留了你随时重构的自由。我们这个仓库就是这么组织的。

### `cmd/` —— 惯例，一个子目录一个可执行文件

```
cmd/hello/main.go     → go build ./cmd/hello  产出名为 hello 的二进制
cmd/ifacedemo/main.go → go run ./cmd/ifacedemo
```

**`main` 包应该尽可能薄**——只做参数解析和依赖装配，逻辑全在 `internal/`。理由就是测试：

```go
func main() {
	cfg := parseFlags()
	if err := app.Run(cfg); err != nil {      // 逻辑在 app 包，可测
		fmt.Fprintln(os.Stderr, "错误:", err)
		os.Exit(1)
	}
}
```

**这也是为什么我们仓库里 `cmd/*` 覆盖率是 0% 而我不打算管它**：那些是教学演示程序，本身就是「输出给人看」的，没有可断言的逻辑。真实项目里 `main` 应该薄到不值得测。

### `pkg/` —— 纯惯例，而且有争议

意思是「这些是给外部用的」。**Go 官方从不用它**（标准库、`golang.org/x/...` 都没有 `pkg/`），很多人认为是多余的一层。**我们不用。**

## 12. `go.mod` / `go.sum` / MVS

```
module github.com/hzjconan/learn-program-language/go

go 1.26.6

require (
    github.com/google/go-cmp v0.6.0          // 直接依赖
    golang.org/x/sys v0.20.0 // indirect     // 间接依赖
)
```

| 文件 | 作用 | 要不要提交 |
|---|---|---|
| `go.mod` | 模块名、Go 版本、依赖及其**最低版本** | ✅ 必须 |
| `go.sum` | 每个依赖的**校验和**（含间接依赖的所有历史版本） | ✅ 必须 |

`go.sum` 不是锁文件（版本已经锁在 `go.mod` 里了），它是**防篡改校验**。有人偷偷改了某个 tag 指向的代码，`go.sum` 会让构建失败。

### ⭐ MVS：Go 和所有其他语言都不一样的地方

**Minimal Version Selection（最小版本选择）**：当多个依赖要求同一个包的不同版本时，Go 选**满足所有要求的最低版本**。

```
你的模块  → 要求 lib v1.2.0
依赖 A    → 要求 lib v1.5.0
依赖 B    → 要求 lib v1.3.0
                            ⇒ Go 选 v1.5.0（最大的那个"最低要求"）
```

注意别被名字骗了：**「最小」指的是「不会自作主张升级到更新的版本」**，而不是选最老的。npm/Maven 的策略是「装能装的最新版」，所以同样的 `package.json` 今天和明天装出来的东西可能不一样。**Go 的构建是可复现的**：`go.mod` 不变，构建结果就不变，不需要 lockfile。

升级要显式：

```bash
go get -u ./...              # 升级所有依赖到最新的次版本/补丁版本
go get pkg@v1.5.0            # 升到指定版本
go get pkg@latest
go list -m -u all            # 只看看有哪些能升，不动手
```

### 常用命令

```bash
go mod tidy       # ⭐ 加上缺的、删掉没用的。改完 import 就跑一次
go mod download   # 下载到本地模块缓存（CI 里常用）
go mod verify     # 校验缓存里的模块没被改过
go mod why pkg    # 这个依赖到底是谁引进来的
go mod graph      # 完整依赖图
go mod vendor     # 把依赖拷进 ./vendor/
```

**`go mod tidy` 要养成习惯**：改完 import 就跑，提交前再跑一次。它是唯一能保证 `go.mod` 和真实代码一致的手段。

> **vendor 现在还要用吗**：多数情况不用。模块代理（`proxy.golang.org`）+ `go.sum` 已经解决了可用性和完整性。只在「离线构建」「审计要求所有代码进仓库」时才用。一旦存在 `vendor/` 目录，Go 会**默认从它构建**（`-mod=vendor`），忘了跑 `go mod vendor` 就会出现「改了 go.mod 但构建行为没变」的怪事。

## 13. `gofmt` / `go vet` / `golangci-lint`

### `gofmt`：不可协商

**Go 没有代码风格之争，因为格式是工具定的。** 缩进用 tab、大括号必须在行尾、import 分组——全部自动。

```bash
gofmt -l .          # 列出格式不对的文件
go fmt ./...        # 直接改
```

> 你从 Java/TS 过来会觉得少了很多自由（比如没法把短函数写成一行）。**这是特性不是缺陷**：所有 Go 代码看起来都一样，读别人代码时零适应成本，code review 里永远不会讨论格式。

`goimports` 是 `gofmt` 的超集，额外会自动增删 import 并分组。我们的 `.golangci.yml` 里配了 `local-prefixes`，让本模块的 import 单独成组。

### `go vet`：编译器不管但肯定是错的

```bash
go vet ./...
```

它抓的是**语法正确但语义几乎必错**的东西：

- `fmt.Printf("%d", "hello")`——格式动词和参数类型对不上
- 拷贝了含 `sync.Mutex` 的结构体（`copylocks`）
- `struct` tag 写错格式
- 不可达代码、自赋值、可疑的移位

写 D5 演示时它就抓过我一次：

```
cmd/ifacedemo/main.go:71: fmt.Println call has possible Printf formatting directive %v
```

**`go test` 会自动跑一部分 vet 检查**，所以你可能已经在无意中用它了。

### `golangci-lint`：把几十个 linter 打包

我们的 `.golangci.yml` 已经配好了（`internal` 之外还开了 `errcheck`、`staticcheck`、`revive`、`gocritic` 等）。这五天它替我们抓到过：

| 检查 | 抓到的问题 | 在哪天 |
|---|---|---|
| `SA4005` | 值接收者上的赋值无效 | D4 |
| `SA4023` | 函数永远不返回 nil 接口 | D5 |
| `%v` in `Println` | vet 的 printf 检查 | D5 |

**这就是我一直说的「有工具兜底」**。规则还是要记，但工具能把你从 80% 的低级错误里捞出来。

`//nolint:linter // 理由` 可以局部关闭——**必须写理由**，否则它会变成垃圾场。

   | 预分配 | 一次 80KB | **cap=10000 → 一直占着 80KB** |
   | 不预分配 | 多次扩容，累计更多 | cap≈1～2，几乎不占 |

   所以你还得单独报告 `cap(result)`（用普通 `Test` + `t.Logf` 就行）。跑三档命中率（100% / 50% / 0.01%），然后回答：**`genx.Filter` 该不该改？改成什么？** 这问没有标准答案，要的是用数据支撑一个判断，并说清适用条件。
3. **给 `genx.Sum` 和 `store.Record` 各写一个 `Example` 函数**，跑 `go test` 确认 `// Output:` 真的被校验了（故意写错一个字符看看）。
