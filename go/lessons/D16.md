## 1. 三根支柱，以及 Go 和 Java 最大的不同

| | 回答什么 | 典型问题 | 成本 |
|---|---|---|---|
| **日志** | 某一件事的细节 | 「订单 42 为什么支付失败」 | 按条数计，量大就贵 |
| **指标** | 聚合后的数字，随时间变化 | 「过去 5 分钟错误率多少、P99 延迟多少」 | 按**时间序列条数**计，和流量无关 |
| **trace** | 一个请求穿过哪些服务、每段花多久 | 「这个慢请求慢在 API 还是数据库」 | 按 span 数计，生产上要采样 |
| **profile** | 进程内部的 CPU / 内存 / goroutine 花在哪 | 「内存为什么一直涨」 | 按需抓，平时几乎为零 |

日志你 D12 已经做过（slog + request_id）。今天补另外三样。

### 1.1 ⭐ Java 靠 agent 自动埋点，Go 必须显式传 ctx

| | Java | Node/TS | Go |
|---|---|---|---|
| 指标 | Micrometer + Actuator `/actuator/prometheus` | prom-client | `prometheus/client_golang` |
| profile | JFR、async-profiler、`jstack`、`jmap` | `--inspect`、clinic | **`net/http/pprof`，标准库自带** |
| trace 怎么埋点 | `-javaagent:opentelemetry-javaagent.jar` **改字节码**，零代码 | `@opentelemetry/auto-instrumentations-node`，monkey-patch `require` | **没有 agent**，每个库显式包一层 |
| trace 上下文放哪 | `ThreadLocal` | `AsyncLocalStorage` | **`context.Context`，一路手传** |

Java 里「当前 span」挂在线程上，框架看不见也能自动续上。Go 没有 goroutine-local 存储，这是故意的设计。
所以 trace 上下文**只能**放在 `ctx` 里一路往下传。

⭐ 推论：**在 Go 里忘了传 ctx，trace 就断了。** 这和 D10 讲的「忘了传 ctx，取消就失效」是同一个原因。
`context.Background()` 出现在业务代码中间，就是一个断点：取消传不过去，deadline 传不过去，trace 也传不过去。

⭐ 另一个推论：Go 里很多埋点要你**自己挑位置**。好处是没有魔法，看代码就知道哪里有 span。
代价是漏了就是漏了，没有任何工具替你兜底。

## 2. Prometheus 的指标模型

### 2.1 pull 模型和文本格式

Prometheus 每隔 15–30 秒来**拉**一次你的 `/metrics`。你的进程只负责在内存里维护数字，不负责发送。

```
# HELP controller_runtime_reconcile_total Total number of reconciliations per controller
# TYPE controller_runtime_reconcile_total counter
controller_runtime_reconcile_total{controller="webapp",result="success"} 17
controller_runtime_reconcile_total{controller="webapp",result="error"} 0
controller_runtime_reconcile_total{controller="webapp",result="requeue"} 0
```

每一行是一条**时间序列**：指标名加上一组 label 值唯一确定一条。上面这段是 3 条序列。

对比 Java：Micrometer 的 `Counter.builder("x").tag("k","v").register(registry)` 和这里的 `CounterVec.WithLabelValues("v")` 是同一个东西。
Micrometer 的 tag 就是 Prometheus 的 label。

### 2.2 四种类型

| 类型 | 语义 | 例子 | 查询时 |
|---|---|---|---|
| **Counter** | 只增不减（进程重启归零） | 请求总数、错误总数、reconcile 次数 | ⚠️ **永远套 `rate()`**，看绝对值没意义 |
| **Gauge** | 可增可减的当前值 | 队列深度、goroutine 数、ready 副本数 | 直接看 |
| **Histogram** | 按预设桶计数 + 总和 + 总数 | 请求耗时、reconcile 耗时 | `histogram_quantile(0.99, …)` |
| Summary | 客户端算好的分位数 | — | ⚠️ **不能跨实例聚合**，新代码别用 |

⭐ **为什么用 histogram 不用 summary**：3 个 Pod 各自算出 P99，你没法从这三个数得到「整体 P99」，分位数不能相加。
histogram 存的是每个桶的计数，桶计数可以相加，加完再算分位数。所以你横向扩容以后，只有 histogram 还能用。

### 2.3 命名约定（不遵守的话 PromQL 写起来别扭，review 会被提）

- 前缀是你的系统名：`golearn_`。controller-runtime 用的是 `controller_runtime_`，client-go 用的是 `rest_client_`
- counter 以 `_total` 结尾
- 单位写进名字，并且用**基本单位**：`_seconds` 不用 `_milliseconds`，`_bytes` 不用 `_kb`
- label 名用 snake_case，label 值用有限的枚举

### 2.4 ⚠️ 基数（cardinality）：指标系统最常见的事故

**每一种 label 值组合都是一条独立的时间序列**，Prometheus 为每条都要占内存和磁盘。

```go
httpRequests.WithLabelValues(r.Method, r.URL.Path, status)   // ⚠️
```

`/orders/1`、`/orders/2`……每个订单号都多出一条序列。一百万个订单就有一百万条，Prometheus OOM。
这不是理论上的风险，是 Prometheus 最常见的线上事故。

正确做法是用**路由模板**做 label，不用实际路径。Go 1.22 起可以用 `r.Pattern` 取到它：

```go
httpRequests.WithLabelValues(r.Method, r.Pattern, status)   // "GET /orders/{id}" —— 有限个
```

⚠️ `r.Pattern` 是 mux 在路由时**原地写进它收到的那个 `*Request`** 的（`net/http/server.go`：`h, r.Pattern, … = mux.findHandler(r)`）。
所以外层中间件能不能读到它，分两种情况：
- 在 `next.ServeHTTP` **之前**读：还没路由，是空字符串
- 在 `next.ServeHTTP` **之后**读：要看中间有没有别的中间件调用过 `r.WithContext`。
  调用过的话，mux 改的是**复制出来的那份**，外层手里那份还是空的。你的 `RequestID` 就会复制请求（D11 §4）

最稳的做法是把打指标的中间件放在 `RequestID` **里面**，或者直接包在 mux 外面紧贴着它。这和 D11 §4 讲的中间件顺序是同一个问题。

**判据**：label 的取值个数必须有上界，而且这个上界和流量无关。

| label | 行不行 |
|---|---|
| method、status code、路由模板、controller 名、`op`（created/updated/unchanged） | ✅ 有限的枚举 |
| namespace + CR 名 | ✅ 一般可以：上界是集群里的对象数。kube-state-metrics 就是这么做的 |
| user_id、order_id、request_id、完整 URL、错误消息原文 | ❌ 这些信息放进日志或 trace 里 |

### 2.5 ⚠️ 僵尸序列

`gauge.WithLabelValues("default", "golearn-api").Set(2)` 之后，WebApp 被删了。
**这条序列会一直停在 2，直到进程重启。** 看板上显示一个已经不存在的应用「2 个副本就绪」。

对象消失的时候，要主动删掉它的序列：`gauge.DeleteLabelValues("default", "golearn-api")`。
在 reconcile 里，「对象消失」对应的就是 NotFound 那条路径。D20 你在那里写的是 `return ctrl.Result{}, nil`，现在它多了一件要做的事。

## 3. 四个黄金信号

Google SRE 书里的说法是：如果只能监控四样东西，就监控这四样。

| 信号 | 含义 | ⚠️ 常见的错 |
|---|---|---|
| **延迟 Latency** | 处理一个请求要多久 | 成功和失败**分开算**。快速失败的 500 会把平均延迟拉低，看起来反而「变快了」 |
| **流量 Traffic** | 需求有多大（QPS、reconcile/s） | — |
| **错误 Errors** | 失败的比例 | 不只看 5xx，「返回 200 但内容是错的」也算错误 |
| **饱和度 Saturation** | 离满载还有多远 | 最难定义，也最有用。**排队时间**通常是最好的饱和度信号 |

两个衍生的说法：面向请求的服务用 **RED**（Rate / Errors / Duration），面向资源（CPU、磁盘、连接池）用 **USE**（Utilization / Saturation / Errors）。

### 3.1 落到你的 operator 上

controller-runtime **已经替你暴露了**这些指标：

| 信号 | 指标 | PromQL |
|---|---|---|
| 流量 | `controller_runtime_reconcile_total{controller,result}` | `sum by (result) (rate(controller_runtime_reconcile_total{controller="webapp"}[5m]))` |
| 错误 | 同上 `result="error"`，另有 `controller_runtime_reconcile_errors_total` | `rate(…{result="error"}[5m]) / rate(…[5m])` |
| 延迟 | `controller_runtime_reconcile_time_seconds`（histogram） | `histogram_quantile(0.99, sum by (le) (rate(controller_runtime_reconcile_time_seconds_bucket[5m])))` |
| ⭐ 饱和度 | `workqueue_depth{name}`、`workqueue_queue_duration_seconds`（在队列里等了多久）、`controller_runtime_active_workers` | 队列持续不为空、排队时间在涨 → worker 不够用，或者 reconcile 太慢 |
| 重试 | `workqueue_retries_total` | 在涨说明有 key 在退避重试，也就是 D20 §3.4 说的 `AddRateLimited` |
| 下游 | `rest_client_requests_total{code,method}` | 你对 API server 的调用：429 多了说明你被限流了。⚠️ 默认**只有计数**，耗时（`rest_client_request_duration_seconds`）等要在 main 里调 `metrics.RegisterRESTClientMetrics(metrics.MetricRequestLatency, …)` 才会注册（`pkg/metrics/client_go_adapter.go`） |

⭐ **饱和度的例子**：reconcile 本身每次 5ms 很快，但 `workqueue_queue_duration_seconds` 的 P99 是 30 秒。
说明 key 在队列里等了 30 秒才轮到。这时候问题不在 reconcile 的代码，在 worker 数，也就是 D20 小题 B5 的 `MaxConcurrentReconciles`。
**只看 reconcile 耗时会得出「一切正常」的结论。**

### 3.2 内置指标覆盖不到的东西

内置指标能回答「controller 忙不忙、快不快、有没有报错」。
它们**回答不了**「每一趟 reconcile 写了什么」。

D20 的两个 bug，放在内置指标里**看起来完全正常**：
- desired 算得不确定（map 顺序）：reconcile 全部 `success`，耗时正常。但 Deployment 每一趟都 `updated`，Pod 一直在滚动
- 无条件的 `Status().Update`（D20 小题 B3）：同样全部 `success`。但每一趟都多一次写

这两件事要靠**你自己定义的指标**才看得见（练习 ②）。这也是自定义指标的一般用途：**把你代码里的不变量变成线上可以观察的数字**。

## 4. operator 的指标实操

### 4.1 打开指标端口

`cmd/main.go` 里 `--metrics-bind-address` 默认是 `"0"`，意思是**关闭**。这是 kubebuilder 的安全默认值。
`--metrics-secure` 默认是 `true`：走 HTTPS，并且要求请求带 K8s token、通过 RBAC 鉴权（`filters.WithAuthenticationAndAuthorization`）。

- **集群里**：`config/default/manager_metrics_patch.yaml` 已经加了 `--metrics-bind-address=:8443`，所以线上的 operator 其实**一直在暴露**指标，只是要鉴权才能读
- **本机调试**：关掉 TLS 和鉴权，换一个不冲突的端口

```bash
cd go/operator
go run ./cmd/main.go --metrics-bind-address=:8090 --metrics-secure=false
curl -s --noproxy '*' localhost:8090/metrics | grep -E '^(controller_runtime|workqueue)_' | head -40
```

⚠️ 你的 shell 里有 `HTTP_PROXY`，curl 本机服务要加 `--noproxy '*'`。
⚠️ 集群里那份 operator 也在 reconcile 同一批对象。两份同时跑不会打架，因为 desired 相同。
但**日志和指标会各记各的**，看的时候别混。想看得清楚，就先 `kubectl -n golearn-operator-system scale deploy --all --replicas=0`，做完再改回 1。

### 4.2 ⭐ 用 workqueue 指标再验一次 informer

开着 operator，按顺序做下面的操作，每步之后看这三个数：

```bash
m() { curl -s --noproxy '*' localhost:8090/metrics | grep -E 'workqueue_adds_total\{.*webapp|reconcile_total\{.*webapp.*success'; }
```

1. 什么都不做，等 1 分钟。数字变不变？
2. `kubectl scale deploy golearn-api --replicas=5`：`adds_total` 涨了几？
3. `kubectl annotate wa golearn-api foo=bar`：涨了几？
4. `kubectl annotate svc golearn-api foo=bar`：涨了几？

把结果写进笔记。能用 D20 §3.2 的 `For` / `Owns` 解释每个数，informer 就算懂了。
⚠️ 第 2 步涨的次数可能**多于 1**，想一想为什么。提示：scale 之后，除了你以外，还有谁在改这个 Deployment？

### 4.3 自定义指标：注册到哪

```go
import (
    "github.com/prometheus/client_golang/prometheus"
    "sigs.k8s.io/controller-runtime/pkg/metrics"
)

var childOps = prometheus.NewCounterVec(
    prometheus.CounterOpts{
        Name: "golearn_webapp_child_ops_total",
        Help: "CreateOrUpdate results for WebApp child resources.",
    },
    []string{"kind", "op"},
)

func init() {
    metrics.Registry.MustRegister(childOps)
}

// Reconcile 里：
childOps.WithLabelValues("Deployment", string(op)).Inc()
```

⚠️ 两个坑：
- **注册到 `metrics.Registry`**（controller-runtime 的），不是 `prometheus.DefaultRegisterer`。
  Manager 的 metrics server 只 serve 自己那个 registry。注册错了不会报错，`/metrics` 里就是**看不到**
- `MustRegister` 对同名指标注册两次会 **panic**。放在 `init()` 里，保证只执行一次

对比 Java：Spring 里 `MeterRegistry` 是注入进来的 bean。Go 生态的惯例是**包级变量加 `init()` 注册**。
这是 Go 里少数被广泛接受的全局状态，因为 registry 本来就是整个进程共享的。
它的代价在测试里：counter 在所有测试之间共享，而且只增不减，所以测试只能断言**差值**。

### 4.4 测指标

```go
import "github.com/prometheus/client_golang/prometheus/testutil"

before := testutil.ToFloat64(childOps.WithLabelValues("Deployment", "unchanged"))
reconcile(t, app)
after := testutil.ToFloat64(childOps.WithLabelValues("Deployment", "unchanged"))
if after-before != 1 { … }
```

`testutil` 在 `client_golang` 模块里。这个模块 operator 已经间接依赖了，import 之后跑一次 `go mod tidy`，它就会从 indirect 变成直接依赖。

## 5. pprof

### 5.1 有哪些 profile

| 名字 | 是什么 | 怎么采 | ⚠️ |
|---|---|---|---|
| `profile` | **CPU**：每秒 100 次采样，记下当时在跑的栈 | `?seconds=30`，会阻塞 30 秒 | 只看得到**在跑**的代码，看不到在等锁、等 IO 的 |
| `heap` | **还活着**的内存是在哪一行分配的 | 即时 | 默认显示 `inuse_space`。用 `-sample_index` 可以切到另外三种 |
| `allocs` | 同一份数据，默认显示「累计分配了多少」 | 即时 | 找 GC 压力来源用这个（D17） |
| `goroutine` | 所有 goroutine 的栈 | `?debug=1` 按栈分组计数，`?debug=2` 格式和 panic 输出一样 | ⭐ 查泄漏最常用的就是它 |
| `block` / `mutex` | 在 channel/锁上等了多久 | 要先调 `runtime.SetBlockProfileRate` / `SetMutexProfileFraction` | **默认关闭**，不开的话抓到的是空的 |
| `trace` | 执行追踪：调度、GC、系统调用的时间线 | `?seconds=5`，然后用 `go tool trace` 看 | 和 OTel 的 trace 不是一回事，名字撞了 |
| `goroutineleak` | **Go 1.26 新增**，见 §5.6 | 构建时要加 `GOEXPERIMENT=goroutineleakprofile` | 实验特性 |

heap 的四种 `sample_index`：

| | 一次快照里「还活着」的 | 从进程启动起「累计分配过」的 |
|---|---|---|
| 字节数 | `inuse_space` ← **查内存泄漏** | `alloc_space` ← **查 GC 压力** |
| 对象个数 | `inuse_objects` | `alloc_objects` |

### 5.2 ⚠️ 怎么暴露：两个安全问题

**第一个：副作用 import。**

```go
import _ "net/http/pprof"
```

这一行会往 `http.DefaultServeMux` 注册 `/debug/pprof/*`。如果你的业务服务写的是 `http.ListenAndServe(addr, nil)`，
第二个参数 `nil` 就表示用 `DefaultServeMux`，**pprof 就跟着业务一起暴露到公网了**。
这和 D13 讲的 `_ "github.com/jackc/pgx/v5/stdlib"` 是同一种机制：import 带来了你没写的代码。

**第二个：pprof 能看到什么。**
heap profile 带着栈和分配位置，goroutine profile 带着每个 goroutine 的参数指针，`cmdline` 会返回**进程的命令行参数**。
如果你把密码写在 flag 里，访问 `/debug/pprof/cmdline` 就能直接看到。

正确的做法（`cmd/leakdemo/main.go` 就是这么写的）：
- pprof 用**单独的 mux、单独的端口**
- 端口**只监听 `localhost`**
- 集群里要看的时候用 `kubectl port-forward pod/xxx 6060`，不通过 Service 暴露

controller-runtime 已经做好了这件事：`ctrl.Options{PprofBindAddress: "localhost:6061"}`，Manager 会单独起一个只挂 pprof 的 server（练习 ④）。

### 5.3 `go tool pprof` 的用法

它是 profile 文件的**分析器**：不管数据来自 HTTP 端点、`go test -cpuprofile` 还是存下来的 `.pb.gz`，它都能读，然后用不同的视图展示。

```bash
go tool pprof [参数] <数据来源>
```

**数据来源**两种写法：
- **文件**：`profile/d16/heap-after.pb.gz`
- **URL**：`http://localhost:6060/debug/pprof/heap`。当场抓一份，并自动在 `~/pprof/` 存副本（屏幕上会提示 `Saved profile in ...`）

#### 输出方式：选一种

不加输出参数时进入**交互模式**（`(pprof)` 提示符）；加了下面这些就直接打印然后退出：

| 参数 | 作用 | 什么时候用 |
|---|---|---|
| `-top` | 按函数排序的表格 | **最常用**，先看谁占得最多 |
| `-list <正则>` | 函数源码，每行标出数值 | 从函数定位到**具体哪一行** |
| `-peek <正则>` | 这个函数的调用者和被调用者 | 想知道「谁调用了它」 |
| `-traces` | 每一条完整调用栈 | 看原始数据 |
| `-http=localhost:0` | 浏览器 Web UI，`:0` = 随机空闲端口 | **看图、看火焰图**，交互最方便 |
| `-png` / `-svg` + `-output 文件` | 把调用图画成图片 | 贴进文档或报告 |

`-list`、`-peek` 的参数是**正则**，`-list 'Foo'` 会匹配所有名字里带 `Foo` 的函数。

⚠️ 方法名长这样：`main.(*T).Foo`。其中 `(`、`*`、`)`、`.` 都是正则的特殊字符，原样写进去会报
`missing argument to repetition operator: *`。引号只防 shell，防不了正则。两种写法：
- **推荐**：只写一个足够独特的片段，`-list 'Foo'`
- 完整名字就逐个转义：`-list 'main\.\(\*T\)\.Foo'`

`-http`、`-png`、`-svg` 的**调用图**要靠 graphviz 的 `dot` 来画（`brew install graphviz`，2026-09-29 已装）。没装的话只有 Graph 视图和这几个参数会报错，其它视图不受影响。

#### 数据选择：看哪一项、看哪一部分

| 参数 | 作用 |
|---|---|
| `-sample_index=<名字>` | 同一份 profile 有多种数值时选哪种。heap 有四种（§5.1 那张 2×2 表） |
| `-base <旧文件>` | **从新数据里减去旧数据**，只剩「这段时间新增的」。⭐ **查泄漏用这个** |
| `-diff_base <旧文件>` | 也是对比，显示相对变化。用来比较**两个版本**的代码（优化前后） |
| `-focus=<正则>` / `-ignore=<正则>` | 只保留 / 去掉经过匹配函数的调用栈 |
| `-nodecount=N` | `-top` 只显示前 N 行（默认 80） |
| `-cum` | 按 cum 排序，不按 flat |
| `-lines` | 按**行**汇总，不按函数。一个函数里有好几处分配时有用 |
| `-seconds=N` | 数据来源是 CPU profile 的 URL 时，采集多少秒 |

⚠️ `-base` 和 `-diff_base` 别混：**同一个进程**两个时间点「多了什么」→ `-base`；**两个版本**的程序「哪里快了慢了」→ `-diff_base`。

#### 怎么读 `-top`

```
Showing nodes accounting for 93MB, 100% of 93MB total
      flat  flat%   sum%        cum   cum%
   86.17MB 92.66% 92.66%    86.17MB 92.66%  main.(*T).Foo
    2.82MB  3.03% 95.69%     2.82MB  3.03%  main.newBar
```

| 列 | 含义 |
|---|---|
| **flat** | 这个函数**自己**分配的（CPU profile 里是自己在跑的时间） |
| flat% | flat 占总量的百分比 |
| sum% | 从第一行累加到这一行的 flat%，看前几名一共占多少 |
| **cum** | 这个函数**加上它调用的所有函数**一共的量 |
| cum% | cum 占总量的百分比 |

#### flat 和 cum

**cum = cumulative（累计）**：函数**自己**的量，加上它**调用的所有函数**（一层层往下）的量。**flat** 只算自己。
你用过的工具里有同一个概念：

| | 只算自己 | 自己加下游 |
|---|---|---|
| pprof | **flat** | **cum** |
| Chrome DevTools / IntelliJ Profiler | Self Time | Total Time |

一份 heap profile 的 `-top` 里有这样几行：

```
      flat  flat%   sum%        cum   cum%
   37.2MB 84.47% 84.47%     37.2MB 84.47%  main.(*T).Handle
    3.3MB  7.55%   100%      3.3MB  7.55%  main.newCache (inline)
        0     0%   100%      3.3MB  7.55%  main.main
        0     0%   100%     37.2MB 84.47%  net/http.(*ServeMux).ServeHTTP
```

把调用关系画出来：

```
main.main                    flat 0       cum 3.3MB    ← 自己没分配，调用链往下有人分配
 └ run → newServer
    └ newCache               flat 3.3MB   cum 3.3MB    ← 真正分配的地方

ServeMux.ServeHTTP           flat 0       cum 37.2MB   ← 自己只负责路由
 └ (*T).Handle               flat 37.2MB  cum 37.2MB   ← 真正分配的地方
```

- `main.main` 一个字节都没分配，但 `run → newServer → newCache` 分配的全部算进它的 cum
- `ServeMux.ServeHTTP` 只是把请求转给 handler，cum 包含 handler 的全部
- `Handle` 和 `newCache` 的 **flat = cum**：内存是它们**自己**分配的，下游没再分配

怎么用：
- **flat 高**：问题就在这个函数**里面**，直接 `-list` 它
- **flat 低、cum 高**：它自己没做什么，顺着调用往下找，直到找到 flat 高的那个
- **越靠近调用链顶端，cum 越大**：`main` 的 cum 几乎总接近 100%，不说明 `main` 有问题

⭐ 排查时先按 **flat** 找「真正花掉资源的地方」（`-top` 默认就按 flat 排）；
想知道「这份开销是从哪条调用路径来的」，再看 **cum**（`-top -cum`）。

### 5.4 ⭐ 和 Java heap dump 的根本区别

| | Java `jmap -dump` + MAT | Go heap profile |
|---|---|---|
| 内容 | **整个堆的对象图**：谁引用了谁 | **采样**：平均每分配 512KB 记一次，记下**分配时的调用栈** |
| 能回答 | 「这个对象为什么没被回收？」，看它的 GC root 路径 | 「这些还活着的内存，**是在哪一行代码分配的？**」 |
| 回答不了 | — | ⚠️ 「**谁**还拿着它」 |

所以 Go 查内存泄漏**分两步**：
1. profile 告诉你**分配位置**，比如 `server.go:71: make([]byte, 64KB)`
2. **你自己读代码**，推断这块内存之后被谁拿住了

第 2 步没有工具可以代劳。练习 ⑤ 就会遇到：profile 指向的那一行本身完全没问题，问题在几十行以外。

### 5.4b ⚠️ heap profile 是「上一次 GC 时」的快照：`?gc=1`

`runtime/pprof` 的文档原文：

> The heap profile reports statistics as of the most recently completed garbage collection;
> it elides more recent allocation to avoid skewing the profile away from live data and toward garbage.

**`inuse_*` 的数字是最近一次 GC 结束时的状态**，那次 GC 之后新分配的都不算。

为什么这样设计：刚分配的对象里很多马上就会变成垃圾，经过一次 GC 还活着的才确定是「活的」。
把新分配的也算进去，`inuse` 就会混进一堆即将被回收的垃圾。

后果是 **profile 可能落后于真实情况**。默认 `GOGC=100`，堆长到上次 GC 后存活量的约 2 倍才触发下一次 GC。
如果最后一次 GC 发生在压测进行到一半，之后分配的就都不在 profile 里。
你手算「请求数 × 每次分配大小」和 profile 对不上时，先想到这一点，别急着下结论。

**`?gc=1`**：heap 端点先跑一次 GC 再生成 profile，数字就是此刻的真实状态。

```bash
curl -s --noproxy '*' -o heap.pb.gz 'localhost:6060/debug/pprof/heap?gc=1'
```

| | 不加 `gc=1` | 加 `gc=1` |
|---|---|---|
| 反映的时刻 | 上一次 GC 结束时 | 此刻（刚 GC 完） |
| 对进程的影响 | 无 | 多一次 GC。堆很大时有 CPU 开销，线上别频繁抓 |
| 什么时候用 | 日常看个大概 | **要和手算对账、要用 `-base` 比较前后两次时**：两次都加，才是在比同一种状态 |

⚠️ 只有 `inuse_*` 受这个影响。`alloc_*`（累计分配）只增不减，不存在「被 GC 掉」的问题。

⭐ 排查方法上的一点：「profile 比手算少」有两种可能的解释，**只留住了一部分**，或者**全留住了但 profile 滞后**。
不要凭感觉选，设计一个两种解释**预测结果不同**的实验：加 `gc=1` 再抓一次。

### 5.5 怎么读 goroutine profile

`?debug=1` 的输出按「完全相同的栈」分组，每组前面是数量：

```
goroutine profile: total 724
717 @ 0x... 0x... 0x...
#	0x...	main.xxx+0x37	/path/to/file.go:20
```

**判断一组 goroutine 是不是泄漏**：
- 数量**随流量单调上升**，流量停了也不回落。所以要**压测前后各抓一次**
- 栈顶停在 `chan send`、`chan receive`、`select`、`sync.(*Mutex).Lock`、`semacquire` 这类**等待别人**的地方

**正常的 goroutine 长什么样**：数量稳定，栈顶在 `netpoll`（等网络）、`Accept`（等新连接）、worker 循环里等任务的 `select`。
一个 operator 空闲时有 50 个左右的 goroutine 是**正常**的（练习 ④ 你会亲手数一遍）。

⭐ **要看数量的变化，不要只看数量**。500 个 goroutine 可能完全正常，从 50 涨到 51 再涨到 52 反而值得警惕。
指标 `go_goroutines`（Prometheus client 默认就会暴露）加上告警规则，就是生产上发现泄漏的第一道防线。
pprof 是第二步：告警响了之后，去找是哪一组在涨。

### 5.6 Go 1.26 新增：`goroutineleak` profile

普通的 goroutine profile 只能告诉你「有 717 个 goroutine 卡在 `chan send`」。
**它们会不会被唤醒，要你自己判断。**

Go 1.26 加了一个实验性的 profile 来回答这个问题。
它借助 GC 的可达性分析：如果一个 goroutine 阻塞在某个 channel 上，而**其它所有还能运行的 goroutine 都已经引用不到这个 channel**，
那就没有人能再唤醒它。这时它就被**判定**为泄漏，不再只是「看起来像泄漏」。

```bash
GOEXPERIMENT=goroutineleakprofile go run ./cmd/leakdemo
curl -s --noproxy '*' 'localhost:6060/debug/pprof/goroutineleak?debug=1'
```

⚠️ 它能抓到的范围：
- ✅ channel、`sync.Mutex`、`sync.WaitGroup`、`sync.Cond` 上的**永久阻塞**，而且这个同步对象已经没有人能访问
- ❌ 如果 channel 还被某个全局变量或者长寿对象引用着，GC 认为它仍然可达，就**判断不了**
- ❌ 在 `time.Sleep`、网络 IO、系统调用上阻塞的 goroutine。这些终究会醒，不算泄漏

它仍然是实验特性，所以练习里拿它**对照验证**用，主要手段还是普通的 goroutine profile。

### 5.7 在测试里抓 goroutine 泄漏

线上用 profile 抓到泄漏以后，还要**写一个测试把它锁住**，防止以后又有人写回去。有两种工具：

**`testing/synctest`**（Go 1.25 起正式可用）：测试函数跑在一个「气泡」里，气泡内的时间是**假的**，只在所有 goroutine 都阻塞时才向前跳。
测试函数返回时，如果气泡里**还有 goroutine 永久阻塞着**，就 panic：

```
panic: deadlock: main bubble goroutine has exited but blocked goroutines remain
goroutine 8 [chan send (durable), synctest bubble 1]:
```

这就是一个现成的泄漏检测器。而且因为时间是假的，「等 100ms 超时」在测试里**不花真实时间**。

**`go.uber.org/goleak`**：第三方库，`defer goleak.VerifyNone(t)`，在测试结束时对比前后的 goroutine。
在 synctest 出现之前这是标准做法，很多开源项目还在用。

⚠️ synctest 的一个细节，练习 ⑤ 会遇到：**`time.Sleep` 里的 goroutine 也算「阻塞」**。
测试函数返回的时候，如果某个 goroutine 还在睡，synctest 同样会报 deadlock，尽管它其实迟早会醒。
所以测试要**先让时间走够**，让所有该结束的 goroutine 都结束，然后再返回。

## 7. OpenTelemetry trace

### 7.1 概念

```
trace  4bf92f3577b34da6a3ce929d0e0e4736                     ← 一次请求的全过程
 └─ span  "POST /orders/{id}/pay"      api          38ms     ← 根 span
     ├─ span  "ordersvc.Pay"           api          35ms
     │   ├─ span  "SELECT orders"      api→pg        3ms
     │   └─ span  "UPDATE orders"      api→pg       30ms    ⚠️ 慢在这里
     └─ …
```

- **span**：一段有开始和结束的操作。它带着 name、attributes（键值对）、events（时间点）、status（Ok/Error）
- **span context**：`trace_id` + `span_id`，也就是在服务之间传递的那部分
- **父子关系**：通过 `ctx` 建立。`tracer.Start(ctx, "x")` 会把 ctx 里已有的 span 当作父 span，然后返回一个**新的 ctx**，里面放的是这个新 span

```go
ctx, span := otel.Tracer("ordersvc").Start(ctx, "ordersvc.Pay")
defer span.End()
// ⚠️ 往下传的是这个新的 ctx，不是函数参数里原来的那个
if err := s.repo.UpdateStatus(ctx, id, "paid"); err != nil {
    span.RecordError(err)
    span.SetStatus(codes.Error, "update status")
    return fmt.Errorf("pay order %d: %w", id, err)
}
```

⚠️ `ctx, span := ...Start(ctx, ...)` 这里**覆盖**了 ctx 变量。如果写成 `_, span :=`，或者新 ctx 换了个名字但往下传的仍是旧的，
子 span 就会挂到**爷爷 span** 下面。trace 图不会报错，只是结构错了，很难发现。

### 7.2 ⭐ API 和 SDK 分离：Go 版的 SLF4J

| | 日志（Java） | 日志（Go） | trace（OTel） |
|---|---|---|---|
| 库依赖的门面 | SLF4J API | `log/slog` | `go.opentelemetry.io/otel`（API） |
| 进程启动时装的实现 | logback / log4j2 | `slog.New(handler)` | `go.opentelemetry.io/otel/sdk` |
| 没装实现时 | NOP | 默认 handler | **no-op**：`Start` 返回一个什么都不做的 span |

所以 **`ordersvc` 只 import API 包**，它不知道 span 最后导出到哪里。
导出到哪里只在 `main` 里（也就是 `obs.SetupTracing`）决定一次：stdout、Jaeger 还是 OTel Collector。
测试里不装 SDK，span 全是 no-op，没有任何开销。

### 7.3 ⚠️ 跨服务传播和空 propagator

跨服务时，trace context 放在 HTTP 头里传，这是 W3C 标准：

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             版本  trace_id（16 字节）              父 span_id      采样标志
```

- 服务端：`otelhttp.NewHandler` 从请求头**提取**它
- 客户端：`otelhttp.NewTransport` 往请求头**注入**它

⚠️ **全局 propagator 默认是空的**。不调用 `otel.SetTextMapPropagator(propagation.TraceContext{})` 的话，
提取和注入**都不会发生**。每个服务各自开始一条新的 trace，跨服务的链路就断了。
这个过程**不报任何错误**，只有你打开 trace 后端时才会发现每个服务的 trace 都是孤立的。

这和 D12 §5 讲的原则是一回事：**默认值应该是最吵闹的那一种**。OTel 在这里选了最安静的默认值，所以你必须记住手动设置。

### 7.4 在 golearn-api 上接入

```go
// server.NewHandler 的最外层
return otelhttp.NewHandler(
    httpx.Chain(mux, httpx.RequestID, …),
    "golearn-api",
)
```

⭐ 放在**最外层**，这样后面所有中间件（包括 Logging）拿到的 ctx 里都已经有 span 了。

然后是**日志和 trace 的关联**。这是今天和你 review 关注点（「凌晨三点只靠一条消息能不能定位」）直接相关的部分：

```go
// httpx.ctxHandler.Handle 里，和 request_id 并列
if sc := trace.SpanContextFromContext(ctx); sc.IsValid() {
    r.AddAttrs(slog.String("trace_id", sc.TraceID().String()))
}
```

有了这个字段，看到一条 ERROR 日志时可以拿着 `trace_id` 直接找到整条 trace，看到这个请求在每一层分别花了多少时间。
反过来，在 trace 里看到一个慢 span，也能按 trace_id 查到那次请求的所有日志。

⚠️ 想一想：有了 `trace_id` 之后，`request_id` 还需要吗？把你的答案写进小题 B3。

### 7.5 metrics：OTel 还是 Prometheus client？

OTel 同样有 metrics API。它的 SDK 可以导出成 Prometheus 格式，也可以通过 OTLP 推给 collector。

- **K8s 生态**（controller-runtime、client-go、kube-state-metrics）**全都直接用 `prometheus/client_golang`**，所以 operator 继续用它
- **新写的业务服务**：两种都常见。已经全面接入 OTel 的团队会用 OTel metrics，让三种信号共用一套 SDK 和 resource 属性

今天的分工是：**operator 的指标用 Prometheus client，API 的 trace 用 OTel**。这也是你在大多数现有代码库里会看到的样子。

### 7.6 采样（知道就行）

生产环境很少 100% 采样，span 的数量和存储成本都受不了。
常用的是 `sdktrace.ParentBased(sdktrace.TraceIDRatioBased(0.1))`：
**上游已经决定采样的，跟着采样**；自己是根 span 时，按 10% 的概率决定。
⚠️ 如果每个服务独立按 10% 采样，一条跨 3 个服务的 trace 完整保留下来的概率就只有 0.1%。`ParentBased` 就是为了避免这个问题。

更高级的做法是在 collector 里做 **tail sampling**：整条 trace 结束之后再决定留不留，比如「出错的和慢的全部保留」。
