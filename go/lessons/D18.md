## 1. 和 Java 比：Go 交付的是一个文件

| | Java | Go |
|---|---|---|
| 产物 | `.jar` + 一个 JVM | **一个静态链接的可执行文件** |
| 运行时依赖 | JRE（几百 MB）、`-Xmx` 等参数 | 几乎没有：不需要 Go 装在目标机器上 |
| 镜像 | `eclipse-temurin` 基础镜像约 200MB+ | distroless/static 约 2MB + 你的二进制 |
| 换平台 | 「一次编译到处运行」靠 JVM | **在本机编译出别的平台的二进制**（§2.1） |
| 启动 | JVM 启动 + JIT 预热 | 直接运行，毫秒级 |

Go 把「运行时」编译进了二进制。代价是**每个平台要单独编一份**，好处是编出来以后什么都不用装。

## 2. `go build` 的几个开关

### 2.1 交叉编译

```bash
GOOS=linux GOARCH=amd64 go build -o profile/d18/bin/api-linux-amd64 ./cmd/api
GOOS=linux GOARCH=arm64 go build -o profile/d18/bin/api-linux-arm64 ./cmd/api
go tool dist list          # Go 支持的所有平台组合
```

两个环境变量就够了，**不需要安装任何交叉编译工具链**。前提是 `CGO_ENABLED=0`（§2.2）：一旦用了 cgo，就要有目标平台的 C 编译器。

### 2.2 `CGO_ENABLED=0` 和静态链接

```bash
file profile/d18/bin/api-linux-amd64
# ELF 64-bit LSB executable, x86-64, ... statically linked
```

- `CGO_ENABLED=0`：不链接任何 C 库，产物是**静态链接**的，可以直接放进连 libc 都没有的 distroless/static 或 scratch 里
- cgo 可能**悄悄**被启用：在 Linux 上本机编译、又用到了 `net`（DNS 解析）、`os/user` 时，默认会走 cgo 版本。交叉编译时 cgo 默认关闭，所以本机编译和交叉编译的结果可能不一样
- **规则**：要放进 distroless/static 的二进制，**显式写上 `CGO_ENABLED=0`**，不依赖默认值（D14 的 Dockerfile 就是这样做的）

### 2.3 `-ldflags "-s -w"`：去掉符号表

实测（一个最小的程序）：

| | 大小 | panic 时的堆栈 |
|---|---|---|
| 默认 | 1.75MB | `main.boom(...)` + `/完整/的/本机/路径/main.go:3` |
| `-ldflags "-s -w"` | **1.16MB（−33%）** | **一样能看到函数名和行号** |
| 再加 `-trimpath` | 1.16MB | `main.boom(...)` + **`sw/main.go:3`** |

- `-s` 去掉符号表，`-w` 去掉 DWARF 调试信息。**panic 堆栈和 pprof 不受影响**：Go 运行时有自己的一份函数表（pclntab），不依赖它们
- 代价：`dlv` 这类调试器没法调试这个二进制了。生产镜像通常可以接受

### 2.4 `-trimpath`：去掉本机路径

不加的话，二进制里记着**你本机的绝对路径**（`/Users/hzjconan/workspace/...`），panic 和日志里都会出现。

- **隐私**：别人能从你发布的二进制里看到你的用户名和目录结构
- **可重复构建**：同样的代码在两台机器上编，路径不同，二进制就不同。加了 `-trimpath`，路径变成模块路径，两边一样

生产构建一律加 `-trimpath`。

## 3. ⭐ 版本信息：线上跑的是哪个版本

凌晨三点出事，第一个问题永远是「**线上跑的是哪个版本？**」。D19 你用提交号当镜像 tag，已经解决了一半：`kubectl get pod -o yaml` 能看到镜像 tag。但进程自己说不出自己是谁：日志里没有、接口里也查不到。

### 3.1 来源一：Go 自动记录的 VCS 信息（Go 1.18+）

```bash
go build -o profile/d18/bin/api ./cmd/api
go version -m profile/d18/bin/api | grep vcs
#   build  vcs=git
#   build  vcs.revision=18246974b9ec93732cc9a6c23e0aecdd50a250ff
#   build  vcs.time=2026-10-17T08:59:05Z
#   build  vcs.modified=false
```

`go build` 在 git 仓库里编译时，会**自动**把提交号、提交时间、工作区有没有未提交的改动写进二进制。运行时用 `runtime/debug.ReadBuildInfo()` 读出来。不用改任何构建命令。

⚠️ **但在 Docker 里构建时，它是空的。** D14 的 Dockerfile 用 `go/` 当构建上下文，`.git` 在上一层，而且 `.dockerignore` 也排除了它。`go build` 找不到 `.git`，就**什么都不写**，也不报错。

### 3.2 来源二：`-ldflags -X`，从外面注入

```bash
go build -ldflags "-X github.com/hzjconan/learn-program-language/go/internal/buildinfo.Version=v1.2.3" ./cmd/api
```

`-X 包路径.变量名=值`：在**链接时**把一个包级 `string` 变量的值改掉。

⚠️ 三个限制：
- 必须是**包级的 `string` 变量**，不能是 `const`，也不能是函数的返回值
- **包路径要写全**（`github.com/.../internal/buildinfo`，不是 `buildinfo`）。写错了**不报错**，变量静悄悄地保持原值
- 值里有空格时，引号要嵌套对

### 3.3 两个一起用

| 字段 | 本机 `go build` | Docker 构建 | 怎么补 |
|---|---|---|---|
| 提交号、时间、modified | ✅ 自动有 | ❌ 空的 | Dockerfile 里 `ARG REVISION`，`-X` 注入 |
| 版本号（`v1.2.3`） | ❌ 没有 | ❌ 没有 | `-X` 注入 |
| Go 版本 | ✅ | ✅ | — |

所以生产构建的做法是：**由构建脚本（Makefile、CI）把版本号和提交号作为参数传进去**，`buildinfo` 包优先用注入的值，没有再退回 `ReadBuildInfo`。

### 3.4 在哪里暴露

- **启动日志**：`logger.Info("启动服务", "build", buildinfo.Get())`。日志系统里按版本过滤，马上就知道哪个版本开始出错
- **`GET /version`**：运维、上游服务、你自己都能直接问
- **Prometheus 的 `build_info` 指标**（了解）：`golearn_build_info{version="v1.2.3",revision="1824697"} 1`。值永远是 1，信息全在 label 里，看板上能画出「每个版本有几个 Pod」，滚动更新时一目了然。controller-runtime、Prometheus 自己都暴露这个指标

## 4. 镜像：在 D14 的基础上再进一步

### 4.1 distroless/static 和 scratch

| | `gcr.io/distroless/static` | `scratch` |
|---|---|---|
| 内容 | CA 证书、时区数据、`/etc/passwd`（有 `nonroot` 用户） | **什么都没有** |
| HTTPS 请求 | ✅ | ❌ 证书要自己 COPY 进去 |
| `time.LoadLocation("Asia/Shanghai")` | ✅ | ❌ 要么 COPY 时区数据，要么 `import _ "time/tzdata"` 编进二进制（约 450KB） |
| 非 root 运行 | `USER nonroot` | 要自己处理 |
| 大小 | 约 2MB | 0 |

省下的那 2MB 换来的是自己处理证书、时区和用户。**一般用 distroless/static**，D14 的选择是对的。

### 4.2 BuildKit 缓存挂载：重复构建快很多

```dockerfile
RUN --mount=type=cache,target=/root/.cache/go-build \
    --mount=type=cache,target=/go/pkg/mod \
    CGO_ENABLED=0 go build ...
```

Docker 的层缓存是「这一层的输入没变，就直接用上次的结果」。代码一改，`COPY . .` 那一层就失效了，后面的 `go build` **从零开始编译**。

缓存挂载让 Go 的**编译缓存**在多次构建之间保留下来：只改了一个包，就只重新编译那个包。

### 4.3 多架构镜像

你的 Mac 是 arm64，kind 节点是 arm64，但很多线上集群是 amd64。一个镜像 tag 要能在两种机器上运行：

```bash
docker buildx build --platform linux/amd64,linux/arm64 -t golearn-api:xxx .
```

Dockerfile 里要配合：

```dockerfile
FROM --platform=$BUILDPLATFORM golang:1.26-alpine AS build   # ① 构建阶段在【构建机的】架构上运行
ARG TARGETOS TARGETARCH
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH go build ...   # ② 交叉编译出目标架构

FROM gcr.io/distroless/static-debian12                      # ③ 运行阶段用【目标】架构的基础镜像
```

关键是第 ① 行的 `--platform=$BUILDPLATFORM`。不写的话，Docker 会用 QEMU **模拟**目标架构来运行整个构建阶段，在 arm64 上编 amd64 会慢好几倍。写了，就是在本机架构上用 Go 自己的交叉编译（§2.1），快得多。

`BUILDPLATFORM`、`TARGETOS`、`TARGETARCH` 是 BuildKit **自动提供**的参数，不用自己传。

## 5. ⭐ 带读 kubebuilder 生成的 Dockerfile 和 Makefile

D20 你跑过 `make docker-build`、`kind load`、`make deploy`，当时没展开。现在倒回来看。

### 5.1 operator 的 Dockerfile，和 D14 的对比

```dockerfile
ARG BASE_IMAGE=golang:1.26
FROM ${BASE_IMAGE} AS builder              # ① 基础镜像可以从外面换（公司内网镜像仓库）
ARG TARGETOS
ARG TARGETARCH
WORKDIR /workspace
COPY go.mod go.mod
COPY go.sum go.sum
RUN go mod download                        # ② 和 D14 一样：先下依赖，缓存这一层
COPY . .                                   # ③ 靠 .dockerignore 过滤（见下）
RUN CGO_ENABLED=0 GOOS=${TARGETOS:-linux} GOARCH=${TARGETARCH} go build -a -o manager cmd/main.go
FROM gcr.io/distroless/static:nonroot
WORKDIR /
COPY --from=builder /workspace/manager .
USER 65532:65532                           # ④ 数字 UID：K8s 的 runAsNonRoot 只认数字
ENTRYPOINT ["/manager"]
```

| | operator（kubebuilder 生成） | golearn-api（你 D14 写的） |
|---|---|---|
| `.dockerignore` | **白名单**：`**` 先排除一切，再 `!**/*.go`、`!go.mod`、`!go.sum` 放回来，`*_test.go` 再排除 | 黑名单：列出不要的 |
| 构建参数 | `-a`（强制全部重编，让缓存失效），**没有** `-s -w`、`-trimpath` | `-ldflags "-s -w"` |
| 多架构 | 接收了 `TARGETOS/ARCH`，但第一行**没写** `--platform=$BUILDPLATFORM` | 没有 |
| 用户 | `USER 65532:65532`（数字） | `USER nonroot:nonroot`（名字） |

- **白名单比黑名单安全**：以后仓库里多了一个 `secrets.env`，黑名单要记得加进去，白名单天然就排除了
- **数字 UID**：Pod 设置了 `runAsNonRoot: true` 时，kubelet 只能检查**数字** UID 是不是 0，写名字的话它无法判断，会拒绝启动
- **`-a`**：kubebuilder 加它是为了「保证干净地全部重编」，代价是用不上任何缓存。配合 §4.2 的缓存挂载时应该去掉
- **没写 `--platform=$BUILDPLATFORM`**：所以 Makefile 的 `docker-buildx` 才要先用 `sed` 生成一个 `Dockerfile.cross`，把这一句**插进去**（§5.2 最后一段）

### 5.2 Makefile：一个 target 一个 target 读

**变量**：

```make
IMG ?= controller:latest          # ?= ：命令行或环境变量没设时才用这个默认值
YEAR ?= $(shell date +%Y)         # $(shell ...)：执行 shell 命令，拿它的输出
SHELL = /usr/bin/env bash -o pipefail
.SHELLFLAGS = -ec                 # -e：任意一行失败就停；pipefail：管道里任意一段失败都算失败
```

`make docker-build IMG=golearn-operator:dev`，就是用命令行的值覆盖了 `?=` 的默认值。

**`help`**：`make help` 会列出所有 target，原理是一段 `awk`：扫描 Makefile 里形如 `target: ## 说明` 的行打印出来，`##@` 开头的当作分组标题。所以**每个 target 后面的 `## ...` 注释不是装饰**，是 `make help` 的数据来源。

**`test`**：

```make
test: manifests generate fmt vet setup-envtest ## Run tests.
	KUBEBUILDER_ASSETS="$(shell "$(ENVTEST)" use $(ENVTEST_K8S_VERSION) --bin-dir "$(LOCALBIN)" -p path)" \
	  go test $$(go list ./... | grep -v /e2e) -coverprofile cover.out
```

- 冒号后面是**前置依赖**：跑测试之前，先重新生成 CRD 和 RBAC（`manifests`）、DeepCopy 代码（`generate`），再 `fmt`、`vet`，最后确保 envtest 的二进制已经下载好。**测试永远跑在最新生成的代码上**
- `$$`：Makefile 里 `$` 是变量符号，要传给 shell 一个真正的 `$`，就写 `$$`
- `KUBEBUILDER_ASSETS`：告诉 envtest 去哪里找 `kube-apiserver` 和 `etcd` 的二进制。`setup-envtest use ... -p path` 打印的就是那个目录

**工具依赖**：

```make
LOCALBIN ?= $(shell pwd)/bin
CONTROLLER_GEN ?= $(LOCALBIN)/controller-gen
CONTROLLER_TOOLS_VERSION ?= v0.22.0
$(CONTROLLER_GEN): $(LOCALBIN)
	$(call go-install-tool,$(CONTROLLER_GEN),sigs.k8s.io/controller-tools/cmd/controller-gen,$(CONTROLLER_TOOLS_VERSION))
```

- 所有工具都装在**项目自己的** `bin/` 里，**版本写死**在 Makefile 里。和你全局的 `~/go/bin` 无关
- 好处：每个人、CI 用的都是**同一个版本**的 controller-gen。版本不同，生成的 CRD 可能有差别，`git diff` 里会冒出一堆无关的改动
- 这和 D6 讲的 `go.mod` 锁依赖版本是同一个思路，只是锁的是**工具**
- `$(CONTROLLER_GEN): $(LOCALBIN)`：target 是一个**文件路径**。文件已经存在，make 就跳过，不会每次都重新安装

**`docker-build` 和 `deploy`：D20 你跑过的那几条**：

```make
docker-build:
	$(CONTAINER_TOOL) build $(if $(BASE_IMAGE),--build-arg BASE_IMAGE=$(BASE_IMAGE)) -t ${IMG} .
deploy: manifests kustomize
	cd config/manager && "$(KUSTOMIZE)" edit set image controller=${IMG}
	"$(KUSTOMIZE)" build config/default | "$(KUBECTL)" apply -f -
```

D20 的三步：

| 你跑的命令 | 实际做了什么 |
|---|---|
| `make docker-build IMG=golearn-operator:xxx` | `docker build -t golearn-operator:xxx .` |
| `kind load docker-image golearn-operator:xxx` | 把本机的镜像**复制进** kind 节点。kind 节点拉不到你本机的镜像，又没有镜像仓库 |
| `make deploy IMG=golearn-operator:xxx` | ① **改写 `config/manager/kustomization.yaml`**，把镜像设成 `xxx` ② kustomize 渲染出全部 YAML ③ `kubectl apply` |

⚠️ 第 ① 步**直接修改了你仓库里的文件**。每次用不同的 IMG 跑 `make deploy`，`git status` 都会多一个改动。这是 kubebuilder 的有意设计，但要知道它在发生。

**`docker-buildx`**：先用 `sed` 复制一份 `Dockerfile.cross`，在第一个 `FROM` 后面插入 `--platform=${BUILDPLATFORM}`，用它构建多架构镜像并推送，最后删掉。也就是 §4.3 那件事，只是用**改写文件**的方式补上的。

### 5.3 `go generate`

```go
//go:generate stringer -type=Level
```

- `go generate ./...` 会扫描所有 `//go:generate` 注释，**按原样执行**后面的命令。只是一个约定好的「在哪写生成命令」的地方
- ⚠️ **`go build` 和 `go test` 不会执行它**。生成的代码必须**提交进仓库**
- kubebuilder 没用 `go generate`，而是用 Makefile 的 `generate`、`manifests` 调用 controller-gen，原理一样

⭐ 有生成代码，就一定要有一道 CI 检查：**重新生成一遍，看和仓库里提交的是否一致**。

```bash
make manifests generate && git diff --exit-code
```

有人改了 `webapp_types.go` 却忘了重新生成 CRD，这一步会失败。否则线上的 CRD 和代码对不上，要到部署时才发现。

## 6. CI：让它真的测到该测的东西

### 6.1 现状：绿的，但 operator 从来没被测过

`.github/workflows/ci.yml` 现在只有一个 job，`working-directory: go`，跑的是 `go test ./...`。
`go/operator/` 有自己的 `go.mod`，是**另一个模块**，`go test ./...` 不会进去。

GitHub 上 D15 到 D17 的 CI 都是绿的，但 operator 那 10 个测试**一次都没在 CI 上跑过**。D15 讲义里写过一句：「又是一种『你以为跑着，其实从来没跑过』」，这里就是又一个例子。

### 6.2 要加的东西

| job | 做什么 | 为什么 |
|---|---|---|
| `operator` | `make test`、`make lint`；`make manifests generate` 后 `git diff --exit-code` | 补上缺口；生成代码过期检查（§5.3） |
| `image` | 构建 golearn-api 镜像（VERSION = 提交号），检查大小，`docker run` 跑一下 | 「能编译」不等于「镜像能启动」 |

- 两个 job 默认**并行**运行，互相不依赖
- envtest 的二进制：`make test` 会通过 `setup-envtest` 自动下载。GitHub 的 runner 能访问外网，没问题
- 镜像能不能启动：golearn-api 启动时要连数据库，连不上就退出。CI 里怎么验证「镜像本身没问题」？这是练习 ⑤ 要你想的

### 6.3 选读：benchmark 当卡点

D17 §4.5 说过，CI 机器吵，`ns/op` 不可靠，但 `allocs/op` 稳定。可以在 CI 里跑关键的 benchmark，`allocs/op` 超过某个值就失败：有人在热路径上加了分配，合并前就能发现。这次不做，知道有这个做法就行。

## 7. operator 的日志：关掉开发模式

D16 发现的：`operator/cmd/main.go` 里 `zap.Options{Development: true}` 是写死的，部署进集群以后：
- 默认 Debug 级别：`V(1)` 的日志全部打印
- Warn 以上**带完整堆栈**：D16 练习 ① 那条 409 冲突的 ERROR 后面那一大段
- **文本格式**，不是 JSON：日志系统没法按字段检索

改成默认 `false`，本机调试时用 `--zap-devel=true` 打开。

关掉以后带来一个新问题：冲突分支的 `V(1)` 日志不打印了，**持续冲突就完全看不见了**（D16 ② 3c 的那个取舍）。所以要补上 `golearn_webapp_conflicts_total`：日志可以安静，指标要能告警。

---

### 7.1 课堂补充：冲突为什么还需要指标

冲突分支返回 nil 并安排重试，所以不会计入框架的 reconcile 错误结果；生产模式又默认隐藏 V(1) 日志。专用 counter 用于发现反复冲突，日志保留单次事件细节。**仅在 IsConflict 分支加一，不是每次 Reconcile 都加一。**

本地运行如果报 `no matches for kind "WebApp"`，说明当前集群未提供对应 API 版本。确认 kubeconfig context 后，先 `make install` 安装 CRD，再启动 controller。CRD 是类型定义，WebApp 是实例；`go run` 不会安装 CRD，`make deploy` 则部署 controller。
