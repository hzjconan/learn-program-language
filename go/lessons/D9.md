# D9 · sync、内存模型、竞态

> **D8 讲了「用通信来同步」，今天讲另一半：「用锁来保护共享状态」。**
>
> 题眼是第 8 节 **happens-before**——它解释了为什么「看起来只是慢一点」的竞态
> 实际上可以让程序读到**从来没被写入过的值**。
>
> 先跑 `go run ./cmd/syncdemo`（十分钟）。

---

## 1. 什么时候用锁，什么时候用 channel

D8 §9 的判据，现在补上后半句：

| 情况 | 用什么 |
|---|---|
| 数据有明确的**主人**，别人通过消息请求它 | **channel** |
| 一块**大家都要读写**的共享状态 | **mutex** |
| 只是个**计数器 / 标志位** | **atomic** |
| 要**传递数据 + 传递时序** | **channel** |
| 要**保护一段临界区** | **mutex** |

> Go 团队自己的话：**「用 channel 传递数据的所有权，用 mutex 保护状态。」**
> 给计数器套一层 channel + 协调 goroutine 是过度设计——`atomic.Int64` 一行搞定。

## 2. `sync.Mutex`

```go
type Cache struct {
	mu sync.Mutex          // ⭐ 放在它保护的字段【上面】，这是惯例
	m  map[string]int
}

func (c *Cache) Set(k string, v int) {
	c.mu.Lock()
	defer c.mu.Unlock()    // ⭐ 永远配 defer
	c.m[k] = v
}
```

四条规则：

1. **零值可用**——`var mu sync.Mutex` 直接能用，不需要初始化（D4 §1）
2. **永远用 `defer` 解锁**——中途 `return`、`panic` 都能保证释放
3. **不可重入**——同一条 goroutine 再次 `Lock` 会**死锁**，Go 没有 Java 的 `ReentrantLock`
4. **不可拷贝**——拷贝会把锁状态一起复制，两份锁互不知情

> 第 3 条和 Java 差别很大：Java 的 `synchronized` 是可重入的，同一线程可以反复进入。
> Go 里 `mu.Lock()` 之后调用另一个也 `Lock()` 的方法 = **自锁死**。
> 惯例是**导出方法加锁，内部方法不加锁**，把不加锁的版本抽成小写函数。

### 拷贝锁：`go vet` 会抓

```go
func (c Cache) Bad() { ... }        // ❌ 值接收者 → 每次调用都拷贝整个 struct，包括锁
```

```
passes lock by value: Cache contains sync.Mutex (copylocks)
```

**所以含 `sync.Mutex` 的类型，方法必须全用指针接收者**（D4 §3 那张表里「类型含不可拷贝字段」那一行）。

## 3. `sync.RWMutex`

```go
mu.RLock()   / mu.RUnlock()    // 读锁：多个读者可以【同时】持有
mu.Lock()    / mu.Unlock()     // 写锁：独占
```

**只在「读远多于写、且临界区不是极短」时才值得。** 否则 `Mutex` 更快——`RWMutex` 内部要维护读者计数，开销更大。

⚠️ **读锁里不能写**。D6 那个 `cache.Get` 的竞态就是这个：方法看起来是「读」，里面却更新了命中计数。**只要方法体里有一处赋值，它就是写方法。**

⚠️ **`RLock` 也不可重入**。读锁递归获取在有写者等待时会死锁。

## 4. `sync.WaitGroup`

D8 用过了，补三个坑：

1. **`Add` 必须在 `go` 之前**（D8 §1）
2. **`Wait` 返回后不能再 `Add`**，除非确定没有并发的 `Wait`
3. **不可拷贝**——传参要传 `*sync.WaitGroup`，或者用闭包捕获

Go 1.25 的 `wg.Go(f)` 把 `Add`/`go`/`defer Done` 打包了，新代码优先用它。

## 5. `sync.Once`

```go
var (
	once sync.Once
	conn *DB
)

func GetDB() *DB {
	once.Do(func() { conn = connect() })
	return conn
}
```

**`Do` 保证那个函数在整个程序生命周期里只执行一次**，而且**其他 goroutine 会阻塞等它执行完**——不会拿到半初始化的对象。

### 为什么不要自己写双检锁

```go
// ❌ 经典错误写法
if conn == nil {              // 无保护的读 → 竞态
	mu.Lock()
	if conn == nil {
		conn = connect()      // 这个赋值和上面那个读之间没有 happens-before
	}
	mu.Unlock()
}
```

**这段在 Java 里也是错的**（除非 `volatile`），原因见 §8：**没有同步原语建立顺序时，一条 goroutine 可能看到「指针已赋值但对象字段还没初始化完」的中间状态。**

`sync.Once` 内部用 `atomic` + `Mutex` 正确处理了这件事。**永远别自己写。**

> Go 1.21 起还有 `sync.OnceValue` / `sync.OnceFunc`，更简洁：
> ```go
> var GetDB = sync.OnceValue(func() *DB { return connect() })
> ```

## 6. `sync.Map`

**先说结论：99% 的情况你不需要它。** 普通 `map` + `RWMutex` 更快也更清楚。

`sync.Map` 只在两种场景有优势（文档明说的）：

1. **键只写一次、之后大量读**（缓存型）
2. **多个 goroutine 读写不相交的键集合**（分片型）

代价：**没有类型安全**（`any` 进 `any` 出）、**没有 `len()`**、API 别扭（`LoadOrStore`、`Range`）。

**默认用 `map` + `RWMutex`，被 benchmark 证明是瓶颈了再换。**

## 7. `atomic`

```go
var n atomic.Int64          // ⭐ Go 1.19+ 的类型化原子变量，优先用这个

n.Add(1)
n.Load()
n.Store(5)
n.CompareAndSwap(old, new)  // CAS
```

比 `atomic.AddInt64(&n, 1)` 那套老函数好：**类型安全、零值可用、不可能忘记用 `atomic` 去读**。

可用类型：`Int32/Int64/Uint32/Uint64/Bool/Pointer[T]/Value`。

### 什么时候用 atomic 而不是 mutex

**只在「单个变量的读改写」时用。** 一旦需要保证**多个变量之间的一致性**，就必须用锁：

```go
// ❌ 两个 atomic 之间没有原子性
total.Add(1)
sum.Add(v)        // 另一条 goroutine 可能在这两行之间读到 total 和 sum 不匹配

// ✅ 要一致就用锁
mu.Lock()
total++
sum += v
mu.Unlock()
```

## 8. ⭐ Go 内存模型与 happens-before —— 今天的题眼

### 竞态不只是「数错了」

大部分人以为数据竞态的后果是「计数少了几个」。**实际上后果可以任意离谱**——你可能读到一个**从来没有被写入过的值**。

原因有三层：

1. **编译器会重排指令**（只要单 goroutine 看起来行为不变）
2. **CPU 会乱序执行、会有各级缓存**
3. **一次赋值不一定是原子的**（比如 32 位平台上写 int64）

### happens-before 是什么

Go 内存模型定义：**如果事件 A happens-before 事件 B，那么 B 一定能看到 A 的所有写入。**

**没有 happens-before 关系的两个事件，彼此看到什么是未定义的。**

建立 happens-before 的手段只有这些：

| 手段 | 建立的关系 |
|---|---|
| 同一条 goroutine 内的顺序 | 前面的语句 happens-before 后面的 |
| `go f()` | `go` 语句 happens-before `f` 开始执行 |
| **channel 发送** | 发送 happens-before 对应的接收**完成** |
| **channel 关闭** | `close` happens-before 收到零值 |
| **`mu.Unlock()`** | happens-before 下一次 `mu.Lock()` 返回 |
| **`once.Do`** | 那个函数返回 happens-before 任何 `Do` 返回 |
| `atomic` 操作 | 顺序一致（Go 1.19 起明确了） |

> **锁不只是「防止同时进入」，它还负责「把我的写入让对方看见」。** 这是最容易被忽略的一半——
> 很多人以为「反正我这个变量只有一处写、一处读，不会冲突，不用加锁」，
> **但没有锁就没有 happens-before，读那一侧可能永远看不到那次写入。**

### 一个能真的死循环的例子

```go
var done bool
var msg string

go func() {
	msg = "hello"
	done = true          // 没有任何同步原语
}()

for !done {              // ⚠️ 编译器可以把它优化成 if !done { for {} }
}
fmt.Println(msg)         // 甚至可能打印空字符串
```

**两个问题**：循环可能永远不退出（编译器把 `done` 缓存进寄存器）；就算退出了，`msg` 也可能还是空的（两次写入的可见顺序没有保证）。

加一个 channel 或 mutex 就都解决了——**不是因为「互斥」，是因为建立了 happens-before。**

## 9. `errgroup` —— 生产代码里最常用的并发工具

```go
import "golang.org/x/sync/errgroup"

g, ctx := errgroup.WithContext(ctx)
g.SetLimit(10)                       // 并发上限（D8 那个 worker pool 的替代品）

for _, url := range urls {
	g.Go(func() error {              // 返回 error！
		return fetch(ctx, url)
	})
}

if err := g.Wait(); err != nil {     // 返回【第一个】非 nil 错误
	return err
}
```

比手写 `WaitGroup` 强在三点：

1. **错误能传出来**——`WaitGroup` 没有错误通道，你得自己搞
2. **`WithContext` 会在第一个错误时自动取消 ctx**，其他任务能提前退出（D10 细讲）
3. **`SetLimit` 就是并发上限**，不用自己写 worker pool

**这是本周最实用的一个 API。** 你 D8 手写的 `FetchAll` 用 errgroup 能砍掉一半代码——但先手写一遍是值得的，否则你不知道它替你做了什么。

## 10. `-race` 实战

```bash
go test -race ./...
go run -race ./cmd/xxx
go build -race          # 也能编译进二进制，预发环境可以开
```

D8 §7 讲过原理（happens-before 追踪，不靠「撞上」）。补三条：

- **只报告实际执行到的**——测试没跑到那条路径就沉默
- **开销**：内存 ×5～10，速度 ×2～20
- **CI 里必须开**。我们的 `make check` 已经是 `go test -race ./...`

### 竞态的三个信号

看到这些就该怀疑：

1. **偶发失败**、重跑就好了
2. **加了日志就不复现**（打印改变了时序）
3. **debug 模式正常、release 异常**（优化级别不同）

## 11. 死锁的几种形态

```go
// ① 自锁（Go 的锁不可重入）
mu.Lock()
mu.Lock()          // 死

// ② 忘了解锁 / 提前 return
mu.Lock()
if err != nil {
	return         // ⚠️ 没解锁 → 下一个 Lock 永远等
}
mu.Unlock()

// ③ 锁顺序不一致（经典的 AB-BA）
// goroutine 1: a.Lock(); b.Lock()
// goroutine 2: b.Lock(); a.Lock()
```

**①②用 `defer` 解决。③只能靠约定：全局规定一个加锁顺序**（比如按地址或按 ID 从小到大），所有代码都遵守。

⚠️ **`-race` 检测不出死锁**，它只检测竞态。死锁靠 D8 说的 `SIGQUIT` dump（栈上会显示 `[semacquire]`）。

go/cmd/syncdemo/         ← 先跑：go run ./cmd/syncdemo

### 主练习 · `racefix`

一个内存统计服务，我在里面**埋了 6 个并发问题**。它们的暴露方式差别巨大 —— 这是今天最该体会的：

| 症状 | 例子 |
|---|---|
| **直接崩溃** | 并发写 map → `fatal error: concurrent map writes`，recover 拦不住 |
| **数值不对** | 计数器丢更新 —— 不报错，只是结果小了 |
| **完全静默** | 返回内部 map 被改掉、双检锁的可见性问题 —— 跑一万次都可能正常 |

**只有 `-race` 能把它们统一指出来，并告诉你具体是哪两行在冲突。**

你的任务：

1. **跑 `go test -race ./internal/racefix/`**，看它报什么
2. **逐个修复**，直到 `-race` 干净、且测试的数值断言全部通过
3. **每个修复点写一行注释**，说明你选了 mutex / atomic / channel 中的哪个，**为什么**

⚠️ 有些问题 `-race` **报不出来**（它只报竞态，不报死锁、不报逻辑错）。测试的数值断言会抓住它们。
