# D9 · sync、内存模型、竞态

> **D8 讲了「用通信来同步」，今天讲另一半：「用锁来保护共享状态」。**
>
> 题眼是第 8 节 **happens-before**——它解释了为什么「看起来只是慢一点」的竞态
> 实际上可以让程序读到**从来没被写入过的值**。
>
> 先跑 `go run ./cmd/syncdemo`（十分钟）。

---

## 1. 什么时候用锁，什么时候用 channel

D8 §9 的判据，现在补上后半句：

| 情况 | 用什么 |
|---|---|
| 数据有明确的**主人**，别人通过消息请求它 | **channel** |
| 一块**大家都要读写**的共享状态 | **mutex** |
| 只是个**计数器 / 标志位** | **atomic** |
| 要**传递数据 + 传递时序** | **channel** |
| 要**保护一段临界区** | **mutex** |

> Go 团队自己的话：**「用 channel 传递数据的所有权，用 mutex 保护状态。」**
> 给计数器套一层 channel + 协调 goroutine 是过度设计——`atomic.Int64` 一行搞定。

## 2. `sync.Mutex`

```go
type Cache struct {
	mu sync.Mutex          // ⭐ 放在它保护的字段【上面】，这是惯例
	m  map[string]int
}

func (c *Cache) Set(k string, v int) {
	c.mu.Lock()
	defer c.mu.Unlock()    // ⭐ 永远配 defer
	c.m[k] = v
}
```

四条规则：

1. **零值可用**——`var mu sync.Mutex` 直接能用，不需要初始化（D4 §1）
2. **永远用 `defer` 解锁**——中途 `return`、`panic` 都能保证释放
3. **不可重入**——同一条 goroutine 再次 `Lock` 会**死锁**，Go 没有 Java 的 `ReentrantLock`
4. **不可拷贝**——拷贝会把锁状态一起复制，两份锁互不知情

> 第 3 条和 Java 差别很大：Java 的 `synchronized` 是可重入的，同一线程可以反复进入。
> Go 里 `mu.Lock()` 之后调用另一个也 `Lock()` 的方法 = **自锁死**。
> 惯例是**导出方法加锁，内部方法不加锁**，把不加锁的版本抽成小写函数。

### 拷贝锁：`go vet` 会抓

```go
func (c Cache) Bad() { ... }        // ❌ 值接收者 → 每次调用都拷贝整个 struct，包括锁
```

```
passes lock by value: Cache contains sync.Mutex (copylocks)
```

**所以含 `sync.Mutex` 的类型，方法必须全用指针接收者**（D4 §3 那张表里「类型含不可拷贝字段」那一行）。

## 3. `sync.RWMutex`

```go
mu.RLock()   / mu.RUnlock()    // 读锁：多个读者可以【同时】持有
mu.Lock()    / mu.Unlock()     // 写锁：独占
```

**只在「读远多于写、且临界区不是极短」时才值得。** 否则 `Mutex` 更快——`RWMutex` 内部要维护读者计数，开销更大。

⚠️ **读锁里不能写**。D6 那个 `cache.Get` 的竞态就是这个：方法看起来是「读」，里面却更新了命中计数。**只要方法体里有一处赋值，它就是写方法。**

⚠️ **`RLock` 也不可重入**。读锁递归获取在有写者等待时会死锁。

## 4. `sync.WaitGroup`

D8 用过了，补三个坑：

1. **`Add` 必须在 `go` 之前**（D8 §1）
2. **`Wait` 返回后不能再 `Add`**，除非确定没有并发的 `Wait`
3. **不可拷贝**——传参要传 `*sync.WaitGroup`，或者用闭包捕获

Go 1.25 的 `wg.Go(f)` 把 `Add`/`go`/`defer Done` 打包了，新代码优先用它。

## 5. `sync.Once`

```go
var (
	once sync.Once
	conn *DB
)

func GetDB() *DB {
	once.Do(func() { conn = connect() })
	return conn
}
```

**`Do` 保证那个函数在整个程序生命周期里只执行一次**，而且**其他 goroutine 会阻塞等它执行完**——不会拿到半初始化的对象。

### 为什么不要自己写双检锁

```go
// ❌ 经典错误写法
if conn == nil {              // 无保护的读 → 竞态
	mu.Lock()
	if conn == nil {
		conn = connect()      // 这个赋值和上面那个读之间没有 happens-before
	}
	mu.Unlock()
}
```

**这段在 Java 里也是错的**（除非 `volatile`），原因见 §8：**没有同步原语建立顺序时，一条 goroutine 可能看到「指针已赋值但对象字段还没初始化完」的中间状态。**

`sync.Once` 内部用 `atomic` + `Mutex` 正确处理了这件事。**永远别自己写。**

> Go 1.21 起还有 `sync.OnceValue` / `sync.OnceFunc`，更简洁：
> ```go
> var GetDB = sync.OnceValue(func() *DB { return connect() })
> ```

## 6. `sync.Map`

**先说结论：99% 的情况你不需要它。** 普通 `map` + `RWMutex` 更快也更清楚。

`sync.Map` 只在两种场景有优势（文档明说的）：

1. **键只写一次、之后大量读**（缓存型）
2. **多个 goroutine 读写不相交的键集合**（分片型）

代价：**没有类型安全**（`any` 进 `any` 出）、**没有 `len()`**、API 别扭（`LoadOrStore`、`Range`）。

**默认用 `map` + `RWMutex`，被 benchmark 证明是瓶颈了再换。**

## 7. `atomic`

```go
var n atomic.Int64          // ⭐ Go 1.19+ 的类型化原子变量，优先用这个

n.Add(1)
n.Load()
n.Store(5)
n.CompareAndSwap(old, new)  // CAS
```

比 `atomic.AddInt64(&n, 1)` 那套老函数好：**类型安全、零值可用、不可能忘记用 `atomic` 去读**。

可用类型：`Int32/Int64/Uint32/Uint64/Bool/Pointer[T]/Value`。

### 什么时候用 atomic 而不是 mutex

**只在「单个变量的读改写」时用。** 一旦需要保证**多个变量之间的一致性**，就必须用锁：

```go
// ❌ 两个 atomic 之间没有原子性
total.Add(1)
sum.Add(v)        // 另一条 goroutine 可能在这两行之间读到 total 和 sum 不匹配

// ✅ 要一致就用锁
mu.Lock()
total++
sum += v
mu.Unlock()
```

## 8. ⭐ Go 内存模型与 happens-before —— 今天的题眼

### 竞态不只是「数错了」

大部分人以为数据竞态的后果是「计数少了几个」。**实际上后果可以任意离谱**——你可能读到一个**从来没有被写入过的值**。

原因有三层：

1. **编译器会重排指令**（只要单 goroutine 看起来行为不变）
2. **CPU 会乱序执行、会有各级缓存**
3. **一次赋值不一定是原子的**（比如 32 位平台上写 int64）

### happens-before 是什么

Go 内存模型定义：**如果事件 A happens-before 事件 B，那么 B 一定能看到 A 的所有写入。**

**没有 happens-before 关系的两个事件，彼此看到什么是未定义的。**

建立 happens-before 的手段只有这些：

| 手段 | 建立的关系 |
|---|---|
| 同一条 goroutine 内的顺序 | 前面的语句 happens-before 后面的 |
| `go f()` | `go` 语句 happens-before `f` 开始执行 |
| **channel 发送** | 发送 happens-before 对应的接收**完成** |
| **channel 关闭** | `close` happens-before 收到零值 |
| **`mu.Unlock()`** | happens-before 下一次 `mu.Lock()` 返回 |
| **`once.Do`** | 那个函数返回 happens-before 任何 `Do` 返回 |
| `atomic` 操作 | 顺序一致（Go 1.19 起明确了） |

> **锁不只是「防止同时进入」，它还负责「把我的写入让对方看见」。** 这是最容易被忽略的一半——
> 很多人以为「反正我这个变量只有一处写、一处读，不会冲突，不用加锁」，
> **但没有锁就没有 happens-before，读那一侧可能永远看不到那次写入。**

### 一个能真的死循环的例子

```go
var done bool
var msg string

go func() {
	msg = "hello"
	done = true          // 没有任何同步原语
}()

for !done {              // ⚠️ 编译器可以把它优化成 if !done { for {} }
}
fmt.Println(msg)         // 甚至可能打印空字符串
```

**两个问题**：循环可能永远不退出（编译器把 `done` 缓存进寄存器）；就算退出了，`msg` 也可能还是空的（两次写入的可见顺序没有保证）。

加一个 channel 或 mutex 就都解决了——**不是因为「互斥」，是因为建立了 happens-before。**

## 9. `errgroup` —— 生产代码里最常用的并发工具

`golang.org/x/sync/errgroup`。由 Go 团队维护，但**不在标准库里**（`x/` 是官方扩展仓库，质量和标准库一样，只是不受 Go 1 兼容性承诺约束）。

### 9.1 它替你做的三件事

手写 `WaitGroup` 时你会遇到：

```go
var wg sync.WaitGroup
var mu sync.Mutex                 // ① 收集错误还得自己加锁
var firstErr error
sem := make(chan struct{}, 10)    // ② 并发上限还得自己造信号量

for _, u := range urls {
	sem <- struct{}{}
	wg.Go(func() {
		defer func() { <-sem }()
		if err := fetch(u); err != nil {
			mu.Lock()
			if firstErr == nil { firstErr = err }
			mu.Unlock()
		}
	})
}
wg.Wait()
// ③ 想让其他任务提前退出？还得自己搞个 done channel
```

`errgroup` 把这三件事包好了：

```go
g, ctx := errgroup.WithContext(context.Background())
g.SetLimit(10)

for _, u := range urls {
	g.Go(func() error { return fetch(ctx, u) })
}

if err := g.Wait(); err != nil { return err }
```

### 9.2 API 速查

| 方法 | 作用 |
|---|---|
| `g.Go(f func() error)` | 起一个任务。**超过 `SetLimit` 时会阻塞** |
| `g.TryGo(f) bool` | 同上但**不阻塞**，满了返回 `false`（任务不会执行） |
| `g.SetLimit(n)` | 并发上限。**必须在任何 `Go` 之前调用** |
| `g.Wait() error` | 等所有任务，返回**第一个**非 nil 错误 |
| `errgroup.WithContext(ctx)` | 返回 `(g, ctx)`，第一个错误时自动取消这个 ctx |

### 9.3 四条容易搞错的语义（都是实测）

**① `Wait` 返回第一个错误，但仍然等【所有】任务**

```
Wait 返回: 我是【第一个】出错的（10ms）    ← 不是最后一个
Wait 耗时: 100ms                         ← 等到了最慢的那个
完成的任务数: 3/3                         ← 没有任何任务被中断
```

**「出错」不会中断其他任务**，`errgroup` 只是替你记住了第一个错误。想让别人提前退出，靠的是 ③。

**② `SetLimit` 之后 `Go` 会阻塞**

```
[0s]    提交任务 0
[0s]    提交任务 1
[0s]    提交任务 2      ← 这行打印了，但 Go() 卡住了
[20ms]  提交任务 3      ← 有位置腾出来才继续
```

这是好事——天然形成背压，不会一次性把几万个任务全排队占内存。不想阻塞就用 `TryGo`，但要自己处理 `false`（重试 / 丢弃 / 排队）。

**③ `WithContext` 的取消是协作式的**

```
[听话的任务]   收到取消信号，提前退出 ✅
[不听话的任务] 我还是跑完了 200ms ⚠️
```

`errgroup` 只负责在第一个错误时调 `cancel()`。**任务收不收、退不退，是任务自己的事**——这就是 D8 §1 那条「Go 里没有杀死 goroutine，只有通知它该走了」。

所以 `ctx` 必须一路传到下游，标准库才会替你响应：

```go
db.QueryContext(ctx, ...)                // ✅
http.NewRequestWithContext(ctx, ...)     // ✅
db.Query(...)                            // ❌ 取消了它也不知道
```

**④ `Wait` 之后不能复用。** 用完就丢，别 `Wait` 之后再 `Go`。

### 9.4 为什么只返回第一个错误

四层理由，按重要性排：

| 理由 | 说明 |
|---|---|
| ⭐ **语义定位是 fail-fast** | 「这批任务是一个整体，任何一个失败整体就失败」。既然整体失败了，「还有哪些也失败了」通常不重要 |
| ⭐ **API 简单性** | `Wait() error` 符合 Go 惯例，调用方 `if err != nil` 就行。返回 `[]error` 会让**每个**调用点都要处理切片 |
| **历史** | `errgroup` 约 2016 年出现，而合并多个错误的标准表示 `errors.Join` 是 **Go 1.20（2023）** 才有的 |
| **典型用法下其余错误多是噪音** | 见下，但**这条有前提** |

关于最后一条：**用了 `WithContext` 时**，第一个错误会取消其余任务，它们返回的是 `context.Canceled`：

```
收集到 8 个错误：
  任务 3: 数据库连接失败        ← 真错误
  任务 2: context canceled     ← 噪音（是第一个错误【导致】的）
  ...（另外 6 条同样）
真错误 1 个，衍生噪音 7 个
```

**但不用 `WithContext` 时这条不成立**——三个独立故障就是三个真错误，`errgroup` 确实把另外两个丢了：

```
三个任务各自失败，原因互不相干
g.Wait() 返回: 任务 1: 独立的真实故障（10ms 时发生）
另外两个错误: 被丢弃了，无法找回 ⚠️
```

**所以「丢弃其余错误」在独立任务场景下是 `errgroup` 的真实局限，不是优点。**

### 9.5 两个任务同时失败，返回哪个？

**不确定。** 源码里就一行 `sync.Once`：

```go
if err := f(); err != nil {
	g.errOnce.Do(func() {        // ⭐ 只有第一个进来的能赋值
		g.err = err
		if g.cancel != nil { g.cancel(g.err) }
	})
}
```

**「第一个」= 运行时实际先执行到这一行的那条 goroutine**，不是「逻辑上先失败的」，也不是「先 `g.Go` 提交的」。

实测两个任务同时放行，跑 2000 次：

```
第一轮：B 赢 98.6%，A 赢 1.4%
第二轮：B 赢 98.0%，A 赢 2.0%
```

**有明显偏向，但不是必然。** 这种「大部分时候是 A，偶尔是 B」正是最坑的形态——**测试时看到的永远是同一个，线上偶尔换一个。**

三条实践后果：

**① 绝对不能依赖「返回哪个错误」写分支逻辑。**

```go
// ❌ 危险：假定 ErrAuth 一定先
if err := g.Wait(); errors.Is(err, ErrAuth) {
	return http.StatusUnauthorized
}
```

鉴权和限流同时失败时，你会**偶尔**返回错误的状态码——而且只在线上最混乱的时候出现。

**② 要精确区分的错误，别让它们竞争**——提前到 `errgroup` 之外单独做（见 9.6 的分阶段）。

**③ 日志记全部错误，`Wait` 的那个只用来决定整体成败。**

```go
g.Go(func() error {
	err := doWork(ctx)
	if err != nil {
		log.Error("子任务失败", "task", name, "err", err)   // ⭐ 每个都记
	}
	return err                                             // 交给 group 决定整体成败
})
```

**`errgroup` 的定位是「控制流」，不是「诊断信息」。** 诊断该走日志/trace（D16）。

### 9.6 什么时候该用、什么时候绕开

`errgroup` 假设了三件事，任何一条不成立就该绕开（或只用它的一部分）：

1. **任务彼此独立**（没有依赖顺序）
2. **fail-fast**（一个挂了，其余的结果就不重要了）
3. **只需要知道「成没成」**（不需要每个任务的返回值）

**判断方法：问一句「有一个失败了，剩下的成功结果还有用吗？」**

- 没用 → fail-fast → `errgroup` 默认行为正合适
- 有用 → 错误是**数据**不是**控制流** → `return nil`，自己管（见 9.8）

#### 关于「依赖」

> ⭐ **并发的前提就是「无依赖」。有依赖 = 有顺序 = 不能并发。**

`g.Go` 的调用顺序和实际执行顺序毫无关系。如果 B、C、D 依赖 A 的结果，把它们放进**同一个** `errgroup` 是设计错误。正确做法是**分阶段**：

```go
// 阶段 1：串行，因为后面都依赖它
cfg, err := loadConfig(ctx)
if err != nil {
	return fmt.Errorf("加载配置: %w", err)
}

// 阶段 2：这一批彼此无依赖，才能并发
g, ctx := errgroup.WithContext(ctx)
for _, u := range urls {
	g.Go(func() error { return fetch(ctx, cfg, u) })
}
return g.Wait()
```

更复杂的依赖图（DAG）有三种做法：按拓扑排序**切层，每层一个 `errgroup`**（简单，但层内最慢的拖住整层）；**channel 串成 pipeline**（D8 §8，天然表达依赖）；或者手动用 `WaitGroup` 编织（灵活但易死锁）。

**`errgroup` 只服务「一层」**——`Go(f func() error)` 这个签名里没有任何地方能声明「我依赖谁」。

### 9.7 典型场景：为一个响应并行拉数据

这是 `errgroup` 最经典的用法——一个 API 需要聚合三份数据，缺一不可：

```go
func GetUserPage(ctx context.Context, uid string) (*UserPage, error) {
	g, ctx := errgroup.WithContext(ctx)
	var page UserPage

	g.Go(func() (err error) { page.Profile, err = queryProfile(ctx, uid); return })
	g.Go(func() (err error) { page.Orders, err = queryOrders(ctx, uid); return })
	g.Go(func() (err error) { page.Complaints, err = queryComplaints(ctx, uid); return })

	if err := g.Wait(); err != nil {
		return nil, fmt.Errorf("组装用户页面: %w", err)
	}
	return &page, nil
}
```

实测收益：

```
身份信息正常：总耗时 200ms（= 最慢的那个，不是 370ms 串行）
身份信息失败：总耗时  20ms  ← 另外两个收到取消，立刻退出
             返回 「身份信息: 数据库连接失败」
             errors.Is(err, context.Canceled) = false   ← 是根因，不是衍生的取消
```

失败时省下的**不只是时间，还有下游资源**——那两个数据库连接立刻还回连接池了。

> **三个 goroutine 写同一个 struct 的不同字段是安全的**：不同字段是不重叠的内存，Go 内存模型把它们当独立变量，`-race` 不报警。**但只要有两个 goroutine 写同一个字段，立刻就是竞态**——加任务时要检查这条还成不成立。

#### ⚠️ 「其他的没有意义」是产品决策，不是技术事实

| API 契约 | 该怎么写 |
|---|---|
| **全有或全无**（缺一个就整页报错） | ✅ 上面那样 |
| **可降级**（投诉记录挂了就返回空 + 一个提示） | ❌ **那个错误不该进 `errgroup`** |

```go
g.Go(func() error {
	var err error
	page.Complaints, err = queryComplaints(ctx, uid)
	if err != nil {
		log.Warn("投诉记录不可用", "err", err)
		page.ComplaintsUnavailable = true    // ← 记进结果
		return nil                            // ⭐ 不上报，别取消别人
	}
	return nil
})
```

**很常见的判断失误是把「可降级的依赖」当成「致命依赖」**——一个次要模块抖动，整个页面 500。上线前逐个问一遍：**「这个挂了，页面还能给用户看点什么吗？」**

### 9.8 非 fail-fast 场景：标准库没有工具，十几行自己写

`x/sync` 和标准库都**没有**「收集全部结果」的现成工具。Go 的态度是「这个模式太简单，不值得再包一层」。写法是固定的：

```go
type Result[T any] struct {
	Item  string
	Value T
	Err   error
}

func Map[T any](items []string, limit int, f func(string) (T, error)) []Result[T] {
	results := make([]Result[T], len(items))
	var g errgroup.Group
	g.SetLimit(limit)                    // ← 只借它的并发上限

	for i, it := range items {
		g.Go(func() error {
			v, err := f(it)
			results[i] = Result[T]{Item: it, Value: v, Err: err}  // 下标独占，不用锁
			return nil                   // ⭐ 不上报，绕开 fail-fast 语义
		})
	}
	_ = g.Wait()                         // 永远返回 nil，只用来「等」
	return results
}
```

两个要点：**`return nil`** 把 `errgroup` 降级成「带上限的 WaitGroup」，错误变成**数据**；**写 `results[i]`** 每个下标只有一条 goroutine 碰，**不需要锁**（D8 §9）。

最后用 `errors.Join(errs...)`（Go 1.20+）合并——它支持 `errors.Is`/`As` 穿透到任何一个子错误。

> 这个模式你 D8 的 `FetchAll` 已经手写过了，只是当时用的是原生 channel。

### 9.9 `x/sync` 里的另外两个包

**`singleflight` —— 防缓存击穿**

```go
v, err, shared := g.Do("user:123", func() (any, error) {
	return db.QueryUser(123)      // 100 个并发请求里只有 1 个真的执行
})
```

实测：**100 个并发请求同一个 key → 底层只执行了 1 次**。热点 key 缓存过期的瞬间，1000 个请求同时打到数据库时救命。`shared` 告诉你「是不是搭了顺风车」，可以做监控。

⚠️ **返回的值是共享的**——如果是 `*User` 或 `[]byte`，所有调用方拿到**同一个对象**，谁改了都影响别人（又是别名问题）。要么返回不可变数据，要么各自拷贝。

**`semaphore` —— 带权重的并发控制**

```go
sem := semaphore.NewWeighted(100)
sem.Acquire(ctx, 30)              // 这个任务占 30
defer sem.Release(30)
```

比 `SetLimit` 强在两点：**任务成本不同时按权重限流**（小文件占 1、大文件占 10）；**`Acquire` 接受 `ctx`**，等不到能被取消，而 `SetLimit` 阻塞时没法取消。

### 9.10 要不要用第三方库

有几个流行的：`sourcegraph/conc`（`pool.ResultErrorPool` 直接收集全部）、`alitto/pond`、`panjf2000/ants`。

**建议先别用**，三个理由：

- 9.8 那十几行你已经能写，而且**你完全知道它在做什么**
- 引入依赖的成本不只是 `go.mod` 多一行——是**未来每个读代码的人都要先学那个库的语义**
- Go 社区对「小工具库」一贯保守，标准库风格就是给原语让你组合

**等你在三个不同项目里写了三遍同样的代码，再抽出来——抽到你自己的 `internal` 包，而不是引第三方。**

> 这是 Go 和 Java 生态的明显差异：Java 有 `CompletableFuture.allOf`、Guava 的 `Futures.successfulAsList` 这类现成 API；Go 倾向于「给你 goroutine 和 channel，剩下自己拼」。**代价是每个项目重写一遍，收益是没有隐藏语义。**

## 10. `-race` 实战

```bash
go test -race ./...
go run -race ./cmd/xxx
go build -race          # 也能编译进二进制，预发环境可以开
```

D8 §7 讲过原理（happens-before 追踪，不靠「撞上」）。补三条：

- **只报告实际执行到的**——测试没跑到那条路径就沉默
- **开销**：内存 ×5～10，速度 ×2～20
- **CI 里必须开**。我们的 `make check` 已经是 `go test -race ./...`

### 竞态的三个信号

看到这些就该怀疑：

1. **偶发失败**、重跑就好了
2. **加了日志就不复现**（打印改变了时序）
3. **debug 模式正常、release 异常**（优化级别不同）

## 11. 死锁的几种形态

```go
// ① 自锁（Go 的锁不可重入）
mu.Lock()
mu.Lock()          // 死

// ② 忘了解锁 / 提前 return
mu.Lock()
if err != nil {
	return         // ⚠️ 没解锁 → 下一个 Lock 永远等
}
mu.Unlock()

// ③ 锁顺序不一致（经典的 AB-BA）
// goroutine 1: a.Lock(); b.Lock()
// goroutine 2: b.Lock(); a.Lock()
```

**①②用 `defer` 解决。③只能靠约定：全局规定一个加锁顺序**（比如按地址或按 ID 从小到大），所有代码都遵守。

⚠️ **`-race` 检测不出死锁**，它只检测竞态。死锁靠 D8 说的 `SIGQUIT` dump（栈上会显示 `[semacquire]`）。

### 主练习 · `racefix`

一个内存统计服务，我在里面**埋了 6 个并发问题**。它们的暴露方式差别巨大 —— 这是今天最该体会的：

| 症状 | 例子 |
|---|---|
| **直接崩溃** | 并发写 map → `fatal error: concurrent map writes`，recover 拦不住 |
| **数值不对** | 计数器丢更新 —— 不报错，只是结果小了 |
| **完全静默** | 返回内部 map 被改掉、双检锁的可见性问题 —— 跑一万次都可能正常 |

**只有 `-race` 能把它们统一指出来，并告诉你具体是哪两行在冲突。**

你的任务：

1. **跑 `go test -race ./internal/racefix/`**，看它报什么
2. **逐个修复**，直到 `-race` 干净、且测试的数值断言全部通过
3. **每个修复点写一行注释**，说明你选了 mutex / atomic / channel 中的哪个，**为什么**

⚠️ 有些问题 `-race` **报不出来**（它只报竞态，不报死锁、不报逻辑错）。测试的数值断言会抓住它们。
