## 1. 为什么 K8s 生态全是 Go，以及怎么读它们的代码

### 1.1 三个技术原因

| 原因 | 意味着什么 |
|---|---|
| **静态单二进制** | 容器镜像里只有一个文件，没有 JVM/node_modules（D14 你的镜像 12.2MB） |
| **goroutine + channel** | controller 本质是「几十个并发的循环」，每个 watch 一条 goroutine，天然对口 |
| **接口小、组合优先** | `client-go` 的一切都是小接口拼起来的，替换/伪造（fake）任何一层都容易 |

第三条是今天真正要用到的：你会看到 `kubernetes.Interface`、`cache.Store`、
`workqueue.TypedRateLimitingInterface[T]`——全是接口，全能换成 fake 测。

### 1.2 K8s 代码的四个风格特征

读 K8s 源码之前先认识它的口音，不然会以为自己 Go 没学好：

**① 三个包各管一段**

```
k8s.io/api            资源类型定义：corev1.Pod、appsv1.Deployment（纯数据结构）
k8s.io/apimachinery   通用机制：ObjectMeta、GroupVersionKind、Scheme、labels.Selector
k8s.io/client-go      客户端：clientset、informer、workqueue、kubeconfig 加载
```

⭐ **版本号锁在一起**：三个都是 `v0.37.0`，对应 K8s 1.37。混着用会编译报错。
这就是昨天 `kubectl` v1.22 连不上现代集群的同一件事在代码层面的体现。

**② 到处是 `Options` struct 和 `ctx` 第一参数**

```go
client.CoreV1().Pods("default").List(ctx, metav1.ListOptions{LabelSelector: "app=api"})
```

不是函数重载（Go 没有），也不是 builder；就是一个 struct，零值可用（D1 §零值哲学）。

**③ 大量 `interface{}`/`any` + 类型断言**

```go
AddFunc: func(obj interface{}) {
    pod := obj.(*corev1.Pod)
```

informer 是泛型出现之前设计的，事件回调拿到的是 `any`。
⚠️ 断言前先想「这里可能是什么」——删除事件里可能是 `cache.DeletedFinalStateUnknown` 而不是 Pod（§4.4）。

**④ 生成代码占一大半**

`zz_generated.deepcopy.go`、`typed/core/v1/pod.go`……都是工具生成的。
读源码时**跳过 `zz_generated` 和 `typed/`**，看 `types.go` 和 controller 逻辑。
D20 的 kubebuilder 会替你生成这些，D18 再回头讲 `go generate`。

## 2. ⭐ 声明式 + 最终一致 —— 今天的题眼

### 2.1 命令式 vs 声明式

你 Java/TS 的后端习惯是**命令式**：

```java
// 调用方说「做这个」
deployService.scaleTo("api", 3);
```

K8s 的模型是**声明式**：

```yaml
# 调用方说「应该是这样」
spec:
  replicas: 3
```

然后**没有人**去「执行」这份 YAML。它只是被存进 etcd。
真正干活的是一个叫 **controller** 的进程，它的整个人生是一个循环：

```
for {
    desired := 读 spec              // 应该是什么样
    actual  := 观察真实世界           // 现在是什么样
    if desired != actual {
        做【一小步】让 actual 靠近 desired
    }
    等下一次触发
}
```

⭐ 这个循环叫 **reconcile loop**（调谐循环），是 K8s 的全部：
Deployment controller 调谐 ReplicaSet，ReplicaSet controller 调谐 Pod，
scheduler 调谐 `pod.spec.nodeName`，kubelet 调谐容器……
**每个 controller 只管一件事，只看 spec 和现状，不关心谁改的、为什么改。**

### 2.2 你已经见过这个模型

如果你写过 React：

```
UI = render(state)
```

你不会写「把第三个 li 的文字改成 x」，你改 state，React **diff** 出最小改动应用到 DOM。
K8s 是同一件事，只是「DOM」换成了「集群」，「render」换成了「reconcile」，
而且是**持续的**——DOM 不会自己变，集群会（节点宕机、Pod 被驱逐、有人手动删了东西）。

所以 reconcile 不是「apply 完就结束」，是**永远在跑**。这是和 React 的关键差别。

### 2.3 ⭐ 由此推出的四条纪律（D20 写 reconciler 时逐条会撞上）

**① 幂等**：同一个 spec 跑 reconcile 十次，结果必须和跑一次一样。
因为你控制不了它被触发几次（§4.4 的 workqueue 会合并，但不保证只一次）。

**② 只看现状，不信事件**：事件（Add/Update/Delete）只是「该看一眼了」的提醒，
**不要**从事件里读「发生了什么」然后据此做事。永远重新读 spec、重新观察 actual、重新算 diff。

> ⭐ 这叫 **level-triggered**（看电平）而不是 **edge-triggered**（看边沿）。
> 错过一个事件不会丢状态——下次触发时你看的还是完整现状。
> Java 里的 listener/observer 模式是 edge-triggered，事件丢了就丢了。
> **这是最反直觉、也最重要的一条。**

**③ 每次只做一步，然后 return**：创建了一个 Pod 就 return，等下一次触发再看。
不要在一次 reconcile 里「创建 → 等它 Ready → 再做下一步」。
等待是用「return 然后被重新触发」实现的，不是 `time.Sleep`。

**④ spec 是别人的，status 是你的**：controller **只写 status**，不改 spec。
spec 是用户意图，status 是你观察到的现实。两者混写就分不清谁是真相来源。

### 2.4 最终一致的代价

「最终」两个字意味着：**任何时刻，spec 和现状都可能不一致**。

```
kubectl apply → 返回 200        ← 只是存进了 etcd
                                   此时 Pod 一个都没起
```

所以 `kubectl apply` 返回成功**不代表**部署完成。要等就 `kubectl rollout status`——
它做的事就是轮询 status 直到符合 spec。Helm 的 `--wait` 同理（§6.7）。

⚠️ 对 Java 开发者最容易犯的错：把 K8s API 当成同步 RPC，调完 Create 就去用那个资源。

## 3. API 对象模型：读懂任何一份 YAML

### 3.1 每个对象长一样

```yaml
apiVersion: apps/v1          # ← Group/Version
kind: Deployment             # ← Kind
metadata:                    # ← 所有对象都有：name / namespace / labels / annotations / uid / resourceVersion
  name: api
spec:                        # ← 期望（用户写）
  replicas: 3
status:                      # ← 现状（controller 写）
  availableReplicas: 2
```

对应 Go：

```go
type Deployment struct {
    metav1.TypeMeta   `json:",inline"`        // apiVersion + kind
    metav1.ObjectMeta `json:"metadata"`       // name / namespace / labels / ...
    Spec   DeploymentSpec   `json:"spec"`
    Status DeploymentStatus `json:"status"`
}
```

⭐ **嵌入**（D5）在这里派上大用：`TypeMeta` 和 `ObjectMeta` 嵌进每个类型，
所以 `pod.Name`、`deploy.Name`、任何对象 `.Name` 都能用——
这正是 `metav1.Object` 接口能覆盖所有类型的原因（`GetName()`、`GetLabels()`…由嵌入的 ObjectMeta 提供）。

### 3.2 GVK 和 GVR：同一个东西的两个名字

| | 例子 | 用在哪 |
|---|---|---|
| **GVK** Group/Version/Kind | `apps/v1, Kind=Deployment` | YAML 里、Go 类型 |
| **GVR** Group/Version/Resource | `apps/v1, deployments` | URL 里、RBAC 规则里 |

Kind 是单数大写（类型名），Resource 是小写复数（URL 路径段）：

```
GET /apis/apps/v1/namespaces/default/deployments/api
     ─────┬────  ────────┬────────  ─────┬─────  ─┬─
        group/version    namespace     resource   name
```

核心组（Pod、Service、ConfigMap）的 group 是空的，URL 是 `/api/v1/...` 而不是 `/apis/`。
这是历史包袱，记住就行。

> 实测：`kubectl get pods -A -v=6` 能看到它发的请求。
> 第一件事是打 `GET /api` 和 `GET /apis` 做**发现**（这个集群有哪些 GVR），
> 然后才 `GET /api/v1/pods`。你的 kind 集群上 `kubectl api-resources` 列出 71 种资源。

### 3.3 ⭐ `resourceVersion`：乐观并发

```
kubectl get pod etcd-golearn-control-plane -o jsonpath='{.metadata.resourceVersion}'
→ 470
```

每次对象被修改，`resourceVersion` 变（它其实是 etcd 的修改序号，**只能比较相等，不能比较大小**）。

Update 时带上你读到的 `resourceVersion`，如果服务器上的已经不一样 → **409 Conflict**：

```go
pod.Spec.Containers[0].Image = "v2"
_, err := client.CoreV1().Pods(ns).Update(ctx, pod, metav1.UpdateOptions{})
// err 是 409 → 有人在你读和写之间改了它
```

这和 JPA 的 `@Version` 字段、D13 `UpdateStatus` 里查 `RowsAffected` 是同一个机制：
**不加锁，靠版本号检测冲突，冲突了重读重试**。
client-go 给了 `retry.RetryOnConflict` 封装这个循环——D20 会用。

### 3.4 labels / annotations / selector

| | 用途 | 能不能查询 |
|---|---|---|
| **labels** | 给对象分类，**被 selector 用** | ✅ `-l app=api` |
| **annotations** | 给工具/人看的备注，任意字符串 | ❌ |

Service 靠 selector 找 Pod，Deployment 靠 selector 认领 ReplicaSet——
⭐ **对象之间没有指针，只有 label 匹配。** 这是「松耦合」的极致：Service 不知道 Pod 是谁创建的。

⚠️ Deployment 的 `spec.selector` **创建后不可变**。所以 chart 里 selector 只放稳定的 label
（`_helpers.tpl` 的 `selectorLabels` 只有 name + instance，不放 version——练习里会撞到）。

### 3.5 watch：把「轮询」做成「推送」

```
GET /api/v1/pods?watch=true&resourceVersion=470
```

HTTP 长连接，服务器持续推 `{"type":"ADDED","object":{...}}` 这样的事件。
`resourceVersion=470` 表示「从 470 之后的变化开始给我」——
**所以 List 一次拿到全量 + resourceVersion，再从那个版本 watch 增量，就能维护一份和服务器一致的本地副本。**

这个 **List + Watch** 组合就是 §4 informer 的全部原理。

## 4. client-go 概念模型

### 4.1 从 kubeconfig 到 clientset

```go
// 本机：读 ~/.kube/config（或 $KUBECONFIG），用它的 current-context
cfg, err := clientcmd.NewNonInteractiveDeferredLoadingClientConfig(
    clientcmd.NewDefaultClientConfigLoadingRules(), &clientcmd.ConfigOverrides{}).ClientConfig()

// Pod 里：ServiceAccount 的 token 自动挂在 /var/run/secrets/kubernetes.io/serviceaccount/
cfg, err := rest.InClusterConfig()

client, err := kubernetes.NewForConfig(cfg)
```

⭐ 惯例是**先试 in-cluster，失败再读 kubeconfig**——同一个二进制本机跑和部署进集群都不用改。
`cmd/kubeaudit/main.go` 的 `loadConfig` 就是这么写的。

`kubernetes.NewForConfig` 返回 `*Clientset`，它实现了 `kubernetes.Interface`：

```go
client.CoreV1().Pods(ns).Get(ctx, name, metav1.GetOptions{})
       ───┬──  ──┬─  ─┬─
       group   resource  动词：Get / List / Watch / Create / Update / Patch / Delete
```

**⚠️ 依赖 `kubernetes.Interface`，不要依赖 `*Clientset`**——
`fake.NewClientset()` 也实现它，D15 的 fake 又来了（练习①的测试就靠这个）。

### 4.2 typed vs dynamic

| | 拿到什么 | 什么时候用 |
|---|---|---|
| **typed**（上面那个） | `*corev1.Pod`，编译期检查 | 内置资源、你自己的 CRD（生成过 client） |
| **dynamic** | `*unstructured.Unstructured`（本质是 `map[string]any`） | 运行时才知道类型（通用工具、kubectl 自己） |

今天只用 typed。dynamic 知道有就行。

### 4.3 一次性调用 vs 持续观察

练习①的巡检 CLI 跑一次就退出——**直接 List 就够了**，不需要下面的一切。

但 controller 要**一直**知道现状。每次 reconcile 都去 API server `Get` 一次的话：
一万个 Pod × 每秒几次 = API server 被自己人打挂。所以：

### 4.4 ⭐ informer → workqueue → worker：controller 的骨架

```
                     ┌──────────── informer ────────────┐
  API server ──List──►                                   │
             ──Watch─►  Reflector ──► DeltaFIFO ──► Indexer（本地缓存）
                     │                    │              ▲
                     │                    ▼              │ Lister.Get（读缓存，不打 API）
                     │             EventHandler          │
                     └────────────────┬──────────────────┘
                                      │ 只放 key（"ns/name"）
                                      ▼
                                  workqueue（去重 + 限速）
                                      │
                                      ▼ 取 key
                                   worker ──► reconcile(key)
                                                 ├─ Lister.Get(key)   读缓存
                                                 ├─ 算 diff
                                                 └─ client.Update(...)  只有写才打 API
```

三个组件各解决一个问题：

| 组件 | 解决什么 | 类比 |
|---|---|---|
| **informer** | 用 List+Watch 维护本地缓存，缓存变了就回调 | 只读副本 + change feed |
| **lister** | 从缓存读，零网络开销 | 读副本 |
| **workqueue** | 把「该看一眼了」排队；**同一个 key 排队中只保留一份**；失败后指数退避重入队 | debounce + 重试队列 |

⭐ **队列里放的是 key（`"namespace/name"`），不是对象。**
这是 §2.3 ②「只看现状不信事件」的落地：
worker 拿到 key 后去缓存里**重新取最新的对象**——
它看到的可能比触发那个事件时更新，**这是特性不是 bug**。
五次 Update 事件排队时会合并成一次 reconcile，因为 key 一样。

### 4.5 什么时候不需要 informer

| 场景 | 用什么 |
|---|---|
| CLI 跑一次（练习①） | 直接 `List` |
| 脚本、Job、偶尔查一下 | 直接 `Get`/`List` |
| 长跑进程，需要持续知道现状 | informer |
| 长跑进程，要对变化**做出反应** | informer + workqueue（= controller） |

⚠️ informer 的代价：启动要 List 全量（大集群几秒到几十秒），内存里放一份全量副本。
只看一个 namespace 就 `NewFilteredSharedInformerFactory` 限定范围，别缓存整个集群。

## 5. 带读一段真实代码：`client-go/examples/workqueue`

装好依赖之后它在你本机：

```
~/go/pkg/mod/k8s.io/client-go@v0.37.0/examples/workqueue/main.go
```

230 行，是上面那张图的最小实现。**打开它对着读**，我只挑三段：

### 5.1 事件处理器：只入队 key

```go
indexer, informer := cache.NewIndexerInformer(podListWatcher, &v1.Pod{}, 0, cache.ResourceEventHandlerFuncs{
    AddFunc: func(obj interface{}) {
        key, err := cache.MetaNamespaceKeyFunc(obj)     // "ns/name"
        if err == nil {
            queue.Add(key)
        }
    },
    UpdateFunc: func(old interface{}, new interface{}) {
        key, err := cache.MetaNamespaceKeyFunc(new)
        if err == nil {
            queue.Add(key)                               // ⭐ 不看 old/new 差在哪，只入队
        }
    },
    DeleteFunc: func(obj interface{}) {
        // IndexerInformer uses a delta queue, therefore for deletes we have to use this
        // key function.
        key, err := cache.DeletionHandlingMetaNamespaceKeyFunc(obj)   // ⚠️ 删除用另一个
        if err == nil {
            queue.Add(key)
        }
    },
}, cache.Indexers{})
```

⚠️ 删除事件里 `obj` 可能是 `cache.DeletedFinalStateUnknown`——
watch 断线重连期间对象被删了，informer 只知道「它没了」但拿不到最终状态。
`DeletionHandlingMetaNamespaceKeyFunc` 处理了这种情况。**直接 `obj.(*v1.Pod)` 会 panic。**
这是 §1.2 ③ 说的「断言前先想这里可能是什么」。

### 5.2 worker：取 key → 干活 → 处理错误

```go
func (c *Controller) processNextItem(logger klog.Logger) bool {
    key, quit := c.queue.Get()
    if quit {
        return false
    }
    // ⭐ Done 必须调：它解除这个 key 的「处理中」标记。
    // 同一个 key 在处理中时又被 Add，队列会等 Done 之后再交出来 —— 保证同一对象不会被并行 reconcile。
    defer c.queue.Done(key)

    err := c.syncToStdout(key)      // 业务逻辑
    c.handleErr(logger, err, key)   // 重试策略
    return true
}

func (c *Controller) syncToStdout(key string) error {
    obj, exists, err := c.indexer.GetByKey(key)     // ⭐ 读缓存，不打 API server
    if err != nil {
        return fmt.Errorf("fetching object with key %s from store failed: %w", key, err)
    }
    if !exists {
        fmt.Printf("Pod %s does not exist anymore\n", key)   // 被删了：这也是一种「现状」
    } else {
        fmt.Printf("Sync/Add/Update for Pod %s\n", obj.(*v1.Pod).GetName())
    }
    return nil
}
```

注意 `syncToStdout` 的签名：**拿 key，返回 error，不管重试**。
源码注释原话："The retry logic should not be part of the business logic."
这和 D14 分层是同一个原则——业务函数只说「成没成」，谁重试、重试几次是外面的事。

### 5.3 错误处理：限速重入队，五次之后放弃

```go
func (c *Controller) handleErr(logger klog.Logger, err error, key string) {
    if err == nil {
        c.queue.Forget(key)         // ⭐ 成功了要 Forget：清掉这个 key 的失败计数
        return
    }
    if c.queue.NumRequeues(key) < 5 {
        logger.Info("Syncing failed, will retry", "pod", key, "err", err)
        c.queue.AddRateLimited(key) // 指数退避后重新入队：5ms, 10ms, 20ms ... 上限 1000s
        return
    }
    c.queue.Forget(key)
    runtime.HandleErrorWithLogger(logger, err, "Dropping pod out of the queue", "pod", key)
}
```

三个动作对应三种情况：`Forget`（成功/放弃）、`AddRateLimited`（失败重试）、
到上限后 `HandleError`（记日志，别 panic，别让一个坏对象拖垮整个 controller）。

⭐ D20 用的 controller-runtime 把这三段全部包掉了，你只写 `Reconcile(ctx, req) (Result, error)`：
返回 `error` = 上面的 AddRateLimited；返回 `Result{RequeueAfter: 30s}` = 定时再看。
**但包掉的东西就是上面这些，出问题时你得知道底下是什么。**

### 5.4 延伸阅读（今天不要求）

真正的 ReplicaSet controller 在
`k8s.io/kubernetes/pkg/controller/replicaset/replica_set.go` 的 `syncReplicaSet` / `manageReplicas`。
读的时候只盯一件事：它怎么算 `diff := len(filteredPods) - int(*(rs.Spec.Replicas))`，
然后**只创建/删除 `diff` 个**，不多不少——这就是 §2.3 ③「每次只做一步」。

## 6. Helm 专项

> 定位（LEARNING-PLAN 的约定）：**能看懂任何 chart、能从零写一个、知道出问题去哪查**。
> 不是精通 Helm。今天不讲 library chart、OCI、签名、chart 测试框架。

### 6.1 它解决什么问题

裸 `kubectl apply -f` 的三个痛点：

| 痛点 | 例子 |
|---|---|
| **多环境** | dev 1 副本 + 集群内 Postgres；prod 3 副本 + 外部库。同一份 YAML 改来改去 |
| **变量** | 镜像 tag 每次 CI 都变，`sed` 替换？ |
| **一组资源的生命周期** | Deployment + Service + ConfigMap + Secret 是一个整体，升级/回滚/删除要一起 |

三种解法：

| | 思路 | 代价 |
|---|---|---|
| `kustomize` | 基础 YAML + 补丁叠加，**无模板** | 表达能力弱：条件、循环做不了 |
| **Helm** | Go `text/template` 渲染 YAML + release 管理（版本、回滚、hook） | 模板难读（今天就是来解决这个的） |
| 两者混用 | Helm 渲染，kustomize 打补丁 | 常见于「用别人的 chart 但要改一点」 |

Helm 的核心公式：

```
chart（模板）+ values（参数）──render──► YAML ──apply──► 集群
                                  └── 记录成 release（可回滚、可 diff）
```

### 6.2 Chart 结构

`helm create x` 生成的骨架（实测 12 个文件）：

```
Chart.yaml               名字、version（chart 版本）、appVersion（应用版本）
values.yaml              默认参数
templates/
  _helpers.tpl           命名模板（函数库）—— 下划线开头，不渲染成资源
  deployment.yaml        ← 每个文件渲染成一个或多个资源
  service.yaml
  NOTES.txt              安装完打印给用户看的提示（也是模板）
  tests/                 helm test 用
.helmignore
```

⭐ `version` 和 `appVersion` 是两件事：**模板改了升 version，应用发新版升 appVersion**。
两个都不升就 `helm upgrade`，Helm 会说 no changes。

练习的 chart 在 `deploy/chart/golearn-api/`，我已经把 `_helpers.tpl`、`service.yaml`、`configmap.yaml` 写好，
剩下的是练习。

### 6.3 ⭐ 模板语法 —— 你真正缺的那块

Helm 模板就是 Go 的 `text/template` + sprig 函数库。你 D12 见过 `text/template`？没有也没关系，规则很少。

#### 内置对象

| | 是什么 | 例子 |
|---|---|---|
| `.Values` | values.yaml + 覆盖之后的合并结果 | `.Values.image.tag` |
| `.Release` | 本次安装的信息 | `.Release.Name` / `.Release.Namespace` |
| `.Chart` | Chart.yaml 的内容 | `.Chart.Name` / `.Chart.AppVersion` |
| `.Capabilities` | 目标集群能力 | `.Capabilities.KubeVersion` / `.APIVersions.Has "batch/v1"` |
| `.Files` | chart 目录里的文件 | `.Files.Get "files/x.sql"` |
| `.Template` | 当前模板文件 | `.Template.BasePath`（练习里用来算 checksum） |

**`.` 是「当前上下文」**。顶层时 `.` 就是包含上面所有东西的那个对象。

#### 控制结构

```yaml
{{- if .Values.debug }}
debug: "true"
{{- end }}

{{- range .Values.hosts }}
- host: {{ . }}          # range 里 . 变成当前元素
{{- end }}

{{- range $key, $val := .Values.config }}
{{ $key }}: {{ $val | quote }}
{{- end }}
```

#### ⚠️ `with` 会改变 `.` 的指向 —— 最常见的困惑源

```yaml
{{- with .Values.labels }}
team: {{ .team }}              # ← . 现在是 .Values.labels，所以 .team 而不是 .Values.labels.team
release: {{ $.Release.Name }}  # ⭐ 要访问外层，用 $ —— 它永远指向顶层
{{- end }}
```

实测渲染：

```
team: orders
release: r
```

`with` 还有一个功能：值为空（nil / "" / 空 map / 空 list）时整块跳过。
所以「有就渲染、没有就不渲染」用 `with` 比 `if` 少一层缩进。

#### ⭐⭐ 空白控制 `{{-` 和 `-}}` —— 复制粘贴党最看不懂的东西

规则只有一条：**`{{-` 吃掉左边所有空白（含换行），`-}}` 吃掉右边所有空白。**

它直接决定生成的 YAML 合不合法。实测对比：

**不加 `-`**：

```yaml
metadata:
  labels:
    {{ if .Values.debug }}
    debug: "true"
    {{ end }}
    app: ws
```

渲染出来：

```yaml
metadata:
  labels:
    ␣␣␣␣                 ← if 那行留下一行空白（4 个空格）
    debug: "true"
    ␣␣␣␣                 ← end 那行也是
    app: ws
```

YAML 合法但很丑，而且**有些位置的空行会让 YAML 解析出错**。

**加 `{{-`**：

```yaml
metadata:
  labels:
    {{- if .Values.debug }}
    debug: "true"
    {{- end }}
    app: ws
```

渲染出来：

```yaml
metadata:
  labels:
    debug: "true"
    app: ws
```

⭐ 所以你会看到几乎所有 chart 里控制语句都写成 `{{- if ... }}` / `{{- end }}`——
**左边加 `-` 吃掉它自己那行的缩进和前一个换行**，让控制语句「在 YAML 里不占位」。

⚠️ 但 `-}}` 要小心：它会把**下一行的换行也吃掉**，两行会粘在一起。
经验规则：**左边 `{{-` 几乎总加，右边 `-}}` 几乎不加。**

打开 `deploy/chart/golearn-api/templates/deployment.yaml` 跑一下 `helm template`，
看 `annotations:` 下面那行空白——那就是我留的注释块 `{{/* */}}` 没加 `-` 的结果。练习里你会顺手修掉它。

### 6.4 函数和管道

管道 `|` 和 shell 一样，左边的值作为右边函数的**最后一个参数**：

```yaml
{{ .Values.image.tag | default .Chart.AppVersion }}       # tag 空就用 appVersion
{{ .Values.password | quote }}                             # 加引号 —— 值里有 : # 时必须
{{ .Values.replicas | required "replicas 必须设置" }}       # 没给就报错，不部署一个残缺的东西
```

#### ⭐ `toYaml` + `nindent`：把一个 map 塞进 YAML 某一层

```yaml
resources:
  {{- toYaml .Values.resources | nindent 4 }}
```

`toYaml` 把 map 变成 YAML 文本，`nindent 4` = 换行 + 每行缩进 4 格。
配合左边的 `{{-` 吃掉前面的空白，结果刚好对齐。

⚠️ **`indent` 和 `nindent` 的区别是致命的**。实测用 `indent`：

```yaml
  labels:
    {{ toYaml .Values.labels | indent 4 }}
```

渲染出：

```yaml
  labels:
        team: orders        ← 第一行被缩进了两次（模板里的 4 格 + indent 4）
    tier: api               ← 第二行只有 indent 的 4 格
Error: YAML parse error ... did not find expected key
```

因为 `indent` 只给**每行开头**加空格，而第一行前面已经有模板自己的缩进了。
`nindent` 先换行再缩进，第一行和后面的行就一致了。**记住：`{{-` + `nindent`，永远成对。**

#### `define` + `include` vs `template`

```yaml
{{/* _helpers.tpl */}}
{{- define "golearn-api.labels" -}}
app.kubernetes.io/name: {{ .Chart.Name }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- end -}}

{{/* deployment.yaml */}}
metadata:
  labels:
    {{- include "golearn-api.labels" . | nindent 4 }}
```

`template "x" .` 和 `include "x" .` 都能调用命名模板，区别：

| | 返回什么 | 能接管道吗 |
|---|---|---|
| `template` | 直接输出，是一个**语句** | ❌ |
| `include` | 返回**字符串** | ✅ `| nindent 4` |

⭐ 所以几乎总用 `include`——不能 `nindent` 的话，同一段 labels 在 Deployment 里要缩 4 格、
在 Pod template 里要缩 8 格，就得写两份。**define 里不缩进，缩进由调用方决定。**

`define` 的第二个参数 `.` 是传给它的上下文——你传什么它里面的 `.` 就是什么。
`_helpers.tpl` 里用了 `.Chart` 和 `.Release`，所以要传顶层 `.`；在 `with` 里面调就得传 `$`。

### 6.5 values 的覆盖顺序

```
values.yaml  <  -f a.yaml  <  -f b.yaml  <  --set k=v
（chart 默认）   （后面的 -f 盖前面的）      （最高）
```

所以练习的三个文件是这么用的：

```bash
helm template t deploy/chart/golearn-api                                  # 默认
helm template t deploy/chart/golearn-api -f .../values-dev.yaml           # dev
helm template t deploy/chart/golearn-api -f .../values-prod.yaml \
     --set secrets.DATABASE_URL='postgres://...'                          # prod，密码不入库
```

⭐ 覆盖是**按 key 深度合并**，不是整个文件替换：`values-dev.yaml` 只写 `config.LOG_LEVEL`，
`config.RATE_LIMIT` 还是默认值。**所以环境文件只写差异，越短越好。**

⚠️ 但 list 不合并，整个替换。`--set` 的类型推断也有坑（`--set port=8080` 是整数，
`--set tag=1.27` 是浮点数 `1.27`——想要字符串用 `--set-string`）。

### 6.6 常见场景

**① 多环境** —— 上面已经是了。

**② ConfigMap / Secret 注入**

```yaml
# configmap.yaml：整个 .Values.config 变成 data
data:
  {{- toYaml .Values.config | nindent 2 }}

# deployment.yaml：整个注入成环境变量
envFrom:
  - configMapRef:
      name: {{ include "golearn-api.fullname" . }}
  - secretRef:
      name: {{ include "golearn-api.fullname" . }}
```

⚠️ **ConfigMap 改了 Pod 不会重启**——你的 api 只在启动时读环境变量（D12）。
标准解法是把 ConfigMap 内容的 hash 写进 Pod annotation：

```yaml
annotations:
  checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
```

内容变 → hash 变 → Pod template 变 → Deployment 滚动更新。这是练习 ② 的 TODO ①。

**③ 镜像 tag 从 CI 传进来**

```bash
helm upgrade --install api ./chart --set image.tag=$GIT_SHA
```

模板里 `tag | default .Chart.AppVersion` 兜底。

**④ ⭐ Hook：`pre-upgrade` 跑数据库迁移** —— 接 D13 §9.2

D13 说过：**迁移要作为独立的部署前步骤**，不能放在 api 启动时（多副本会同时跑）。
Helm hook 就是这个「部署前步骤」的位置：

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ include "golearn-api.fullname" . }}-migrate
  annotations:
    "helm.sh/hook": pre-install,pre-upgrade       # 什么时候跑
    "helm.sh/hook-weight": "0"                     # 多个 hook 的顺序（小的先）
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
                                                   # 上次的先删掉再建；成功了就删
```

流程：`helm upgrade` → 渲染 → **先创建 hook 资源并等 Job 跑完** → 成功才 apply 其它资源 → 失败整个 upgrade 失败。

⚠️ 两个坑（练习会撞上，也是小题 A7/A8）：

- **hook 资源是单独创建的**，普通资源那时还不存在。Job 要用的 ConfigMap 也得打 hook annotation。
- **迁移脚本必须幂等**。`pre-upgrade` 每次升级都跑——去看看 `migrations/001_orders.sql` 开头两行。

**⑤ 依赖（subchart）** —— 点到为止

```yaml
# Chart.yaml
dependencies:
  - name: postgresql
    version: "16.x"
    repository: https://charts.bitnami.com/bitnami
    condition: postgresql.enabled
```

`helm dependency update` 拉到 `charts/`，values 里用 `postgresql.xxx` 传给它。
本课的 dev Postgres 是自己写的一个小 Deployment（练习 ②），**故意不用 subchart**——
先把自己的模板写熟，再去用别人的。

### 6.7 ⭐ 调试手段 —— 这一节最实用

| 命令 | 干什么 | 什么时候用 |
|---|---|---|
| `helm template r ./chart` | **只渲染不装**，把 YAML 打到 stdout | **改模板时的主要反馈循环** |
| `helm template r ./chart --show-only templates/x.yaml` | 只看一个文件 | 盯着一个模板改 |
| `helm template r ./chart --debug` | 渲染失败时**连坏 YAML 一起打出来** | 报 YAML parse error 时 |
| `helm lint ./chart` | 静态检查：缺 icon、values 类型… | 交作业前 |
| `helm install r ./chart --dry-run --debug` | 渲染 + **发给 API server 校验**（schema、字段名） | template 过了但想确认 K8s 认不认 |
| `helm diff upgrade r ./chart`（插件） | 和已装的 release 比 diff | 升级前看会改什么 |
| `helm get manifest r` | 已装 release 的实际 YAML | 「线上到底跑的什么」 |
| `helm history r` / `helm rollback r 2` | 版本列表 / 回滚 | 出事了 |

⭐ **教学方式就一条：改一处，`helm template` 看一眼。** 比背语法有效十倍。
`--debug` 那条最重要——报 `YAML parse error` 时，没有 `--debug` 你只看到行号，
加了才看到渲染出来的坏 YAML 长什么样（§6.4 那个 `indent` 的例子就是这么抓的）。
