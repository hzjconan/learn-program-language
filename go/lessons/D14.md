# D14 · 周综合项目：一个完整的 REST API 服务

> **题眼是第 2 节：依赖方向。**
>
> Go 没有 Spring，也不需要。三件事合起来就够了：
> **接口定义在消费方 + 构造函数注入 + `main` 里手工组装**。
>
> 这不是「更优雅」的问题——实测两种写法，一种依赖 42 个包，另一种 205 个。

---

## 1. 今天要搭的东西

前五天的积木第一次串成一个真正能跑的服务：

```
cmd/api/main.go          ← 组装：读配置 → 连库 → 建各层 → 挂中间件 → 起服务 → 优雅关闭
  │
  ├─ internal/config     D12：环境变量 + 脱敏
  ├─ internal/httpx      D11：RequestID / Recover / Logging / RateLimit
  ├─ internal/apperr     D12：Kind → HTTP status
  │
  ├─ internal/api        ⭐ 新：HTTP handler + DTO + 错误响应
  ├─ internal/ordersvc   ⭐ 新：业务逻辑 + 状态机
  └─ internal/orders     D13：repository
```

五个 HTTP 端点：

```
POST   /orders              下单
GET    /orders/{id}         查订单
GET    /orders?customer=&status=&limit=    列表
POST   /orders/{id}/pay     支付
POST   /orders/{id}/cancel  取消
GET    /healthz             健康检查
```

## 2. ⭐ 依赖方向 —— 今天的题眼

### 2.1 Java 的做法，和它在 Go 里的代价

Java/Spring 里你会这么想：

```java
// repository 包定义接口 + 实现
public interface OrderRepository { Order findById(long id); }
@Repository class JpaOrderRepository implements OrderRepository { ... }

// service 依赖那个接口
@Service class OrderService {
    @Autowired OrderRepository repo;    // 容器负责注入
}
```

直译到 Go 是这样：

```go
// internal/orders/orders.go
type Repo struct{ db *sql.DB }

// internal/ordersvc/ordersvc.go
import "…/internal/orders"              // ⚠️ 直接依赖具体包

type Service struct{ repo *orders.Repo }
```

**能跑，但 `ordersvc` 从此背上了 `orders` 的全部依赖。**

做个受控实验：两个除了「接口定义在哪」之外完全一样的包，量它们的依赖闭包：

| | 依赖包总数 | 其中 pgx 相关 | 编译测试二进制 |
|---|---|---|---|
| 直接依赖具体实现包 | **205** | 12 | **5492ms** |
| 接口定义在消费方，**且不 import 实现包** | **42** | **0** | **2788ms** |

⚠️ 注意中间那列：**测试会把整个 Postgres 驱动编译进去**，而这个包一句 SQL 都不写。
编译慢一倍只是表象，真正的问题是**业务逻辑和数据库绑死了**。

### ⚠️ 但本课的结构【没有】拿到这个收益——先把话说清楚

上面那行加粗的「**且不 import 实现包**」是前提。而我们的 `ordersvc` 为了用
`orders.Order` 这个类型，还是 import 了 `internal/orders`。实测本项目：

```
internal/orders    依赖 217 个包，其中 pgx 相关 7 个
internal/ordersvc  依赖 218 个包，其中 pgx 相关 7 个     ← 一模一样
```

⭐ **Go 的依赖是包级的**：import 一个包，就继承它的全部依赖，
哪怕你只用了里面一个 struct。

所以本课兑现的是**两个收益里的一个**：

| 收益 | 拿到了吗 | 靠什么 |
|---|---|---|
| **可测试性**——service 测试不需要数据库 | ✅ **拿到了** | 接口定义在消费方 + 手写假实现 |
| **依赖隔离**——编译期不背上驱动 | ❌ 没拿到 | 需要再把领域类型拆出去（§2.3） |

第一个是今天真正重要的：`ordersvc` 的全部测试用一个 `fakeRepo` 就跑起来了，
**不连库、不起容器、毫秒级**。这个收益和类型放在哪无关。

第二个要额外一步，见下。

### 2.2 Go 的做法：接口定义在**消费方**

⭐ **谁用，谁定义。**

```go
// internal/ordersvc/ordersvc.go  —— 消费方
package ordersvc

// Repository 是【本包需要的能力】，不是「orders 包提供的契约」。
//
// ⚠️ 注意这个包【不 import internal/orders】。
type Repository interface {
	Create(ctx context.Context, o *orders.Order) error
	Get(ctx context.Context, id int64) (*orders.Order, error)
	...
}

type Service struct{ repo Repository }

func New(repo Repository) *Service { return &Service{repo: repo} }
```

```go
// internal/orders/orders.go  —— 提供方
package orders

type Repo struct{ db *sql.DB }
func (r *Repo) Create(...) error { ... }
// ⭐ 它【不知道】自己满足了任何接口 —— 隐式实现（D5 §1）
```

组装发生在 `main`：

```go
repo := orders.NewRepo(db)          // *orders.Repo
svc  := ordersvc.New(repo)          // 编译器检查它是否满足 ordersvc.Repository
```

**只有 `main` 同时知道两边。** 这就是 Go 的「依赖注入容器」——一个函数，几十行，编译期类型安全，没有反射，没有注解，出错是编译错误不是启动时 panic。

> 这正是 D5 §1「接口由使用方定义，不是实现方声明」在架构层面的兑现。
> 当时那句话可能显得抽象，现在它是 163 个包的差别。

### 2.3 ⚠️ 但类型还是要共享

上面的 `Repository` 接口签名里出现了 `orders.Order`——**那还是 import 了**。

三种处理，按推荐度：

**① 领域类型放在最内层，谁都可以依赖**（本课用这个）

```
internal/orders/    Order / Item 类型 + Repo 实现
       ↑
internal/ordersvc/  import orders（只为了类型）
```

依赖闭包会因此包含 `orders`，但**不包含它的实现依赖**吗？⚠️ 不——Go 的依赖是包级的，import 了 `orders` 就带上了 `database/sql` 和 pgx。

**② 把领域类型单独拆一个包**

```
internal/domain/    只有 Order / Item / 状态常量，零依赖
       ↑        ↑
   ordersvc   orders
```

这才真正切断了依赖：`ordersvc` 只 import `domain` 和 `apperr`，
两者都不碰数据库，pgx 相关包数会掉到 **0**。

⭐ **这是今天练习的可选加分项**（§8 ④）。验收标准是可测量的：

```bash
go list -deps ./internal/ordersvc | grep -c pgx    # 目标：0
```

代价是多一个包，以及把 `internal/orders` 里的类型定义搬过去。

**③ 在 service 层定义自己的类型，边界处转换**

最彻底，也最啰嗦。适合 domain 和存储结构差异大的项目。

> ⭐ **本课用 ①，但你要知道它的代价。** 这个项目里 `orders.Order` 就是领域模型，
> 拆包收益不大。**等 repository 多起来（订单、用户、库存各一个包）时，
> ② 才开始划算**——那时候每个 service 都不该背上所有 repo 的依赖。
>
> ⚠️ 别一上来就按 ② 建六个包。**分层是为了控制依赖，不是为了目录好看。**

### 2.4 接口要多大

⚠️ **别定义一个「上帝接口」把 repo 的所有方法都列上。**

```go
// ⚠️ 不好：service 只用了两个方法，却声明依赖全部五个
type Repository interface {
	Create(...) error
	Get(...) (*Order, error)
	List(...) ([]Order, error)
	UpdateStatus(...) error
	Delete(...) error
}
```

⭐ **接口应该按「谁需要什么」切，不是按「谁提供什么」切**（D5 §2 的小接口哲学）。
如果某个 handler 只需要读，就给它一个只有 `Get` 的接口——测试时假实现也只需要写一个方法。

本课的 service 确实要用四个方法，所以一个接口是合理的。但**判断依据是「用了几个」，不是「有几个」**。

## 3. 分层：什么该放在哪一层

这是最容易糊的地方。判据只有一条：

> ⭐ **每一层只做「只有它能做」的事。**

| 层 | 只有它能做的事 | ⚠️ 不该出现在这里 |
|---|---|---|
| **handler**（`internal/api`） | 解析 HTTP、写 HTTP | 业务规则、SQL |
| **service**（`internal/ordersvc`） | 业务规则、编排、事务边界 | `http.Request`、`sql.Rows` |
| **repository**（`internal/orders`） | SQL、把存储错误翻译成领域错误 | 业务规则 |

三个具体的判断：

**① 「订单必须至少有一个商品」放哪？** → **service**。
它是业务规则，和 HTTP 无关（gRPC 调用也要校验），也和 SQL 无关（换数据库不变）。

**② 「limit 超过 500 要截断」放哪？** → **repository**（本课这样）或 **service**。
这是「保护存储不被打爆」的规则，放 repo 更贴近它保护的对象。**放 handler 是错的**——那样 gRPC 入口就没有保护了。

**③ 「pending 才能支付」放哪？** → **service**。
这是状态机，是最典型的业务逻辑。⚠️ 放 repository 的话，`UpdateStatus` 就变成了「知道业务含义的 SQL 函数」，换个业务场景就没法复用。

> ⚠️ **最常见的错误是「贫血的 service」**：handler 直接调 repository，service 只是个转发层。
> 那样 service 就是纯粹的噪音——**如果你的 service 方法只有一行 `return s.repo.Xxx(...)`，
> 要么业务逻辑漏在了别处，要么这一层确实不需要。**

## 4. DTO：请求/响应类型不要复用领域类型

```go
// ⚠️ 不好：直接把领域对象当请求体
func handleCreate(w http.ResponseWriter, r *http.Request) {
	var o orders.Order
	json.NewDecoder(r.Body).Decode(&o)      // 客户端能设 ID！能设 Status！能设 TotalCents！
	svc.Place(ctx, &o)
}
```

三个问题：

1. **客户端能设置它不该设置的字段**——`ID`、`Status`、`CreatedAt`、`TotalCents`
   （D13 那条「金额不信调用方」就是被这么绕过的）
2. **领域模型一改，API 契约就跟着变**——加个内部字段就泄漏给客户端了
3. **两边的「可选」语义不同**——请求体要区分「没传」（D12 §1.2 的指针），领域模型不需要

正确做法是在 `api` 层定义独立的类型：

```go
type createOrderRequest struct {
	Customer string             `json:"customer"`
	Note     string             `json:"note,omitempty"`
	Items    []createItemInput  `json:"items"`
	// ⭐ 没有 ID / Status / TotalCents —— 客户端根本没机会设置
}

type orderResponse struct {
	ID         int64           `json:"id"`
	Customer   string          `json:"customer"`
	Status     string          `json:"status"`
	TotalCents int64           `json:"total_cents"`
	CreatedAt  time.Time       `json:"created_at"`
	Items      []itemResponse  `json:"items"`
}
```

加上 `DisallowUnknownFields`（D12 §1.3），客户端多传一个字段直接 400。

> ⭐ 这两个类型都是**小写**的——它们是 `api` 包的内部实现细节，不该被别的包引用。
> 只有 `NewRouter` 是导出的。**API 契约由 JSON 定义，不由 Go 类型定义。**

## 5. 组装：`main` 该长什么样

```go
func main() {
	if err := run(); err != nil {           // ⭐ main 只负责退出码
		fmt.Fprintln(os.Stderr, "fatal:", err)
		os.Exit(1)
	}
}

func run() error {
	cfg, err := config.Load(nil)            // ① 配置
	if err != nil {
		return fmt.Errorf("加载配置: %w", err)
	}

	logger := slog.New(httpx.WithRequestID(handlerFor(cfg)))   // ② 日志
	slog.SetDefault(logger)
	logger.Info("启动中", "cfg", cfg)         // Config.LogValue 保证 token 不泄漏

	db, err := openDB(cfg)                  // ③ 数据库（含 Ping）
	if err != nil {
		return err
	}
	defer db.Close()

	repo := orders.NewRepo(db)              // ④ 组装三层
	svc := ordersvc.New(repo)
	handler := api.NewRouter(svc, logger)

	handler = httpx.Chain(handler,          // ⑤ 中间件（顺序见 D11 §4）
		httpx.RequestID,
		httpx.Logging(logger),
		httpx.Recover(onPanic(logger)),
		httpx.RateLimit(cfg.RateLimit, time.Second),
	)
	// ⚠️ cfg.RateLimit / cfg.IdleTimeout 现在还不存在 —— 给 config.Config
	// 加这两个字段也是今天练习的一部分（照 D12 的样子加：默认值 + 校验 + LogValue）。

	return serve(ctx, cfg, handler, logger) // ⑥ 起服务 + 优雅关闭
}
```

⭐ **`main` 里不要有 `if err != nil { log.Fatal(err) }`。** 用 `run() error` 这个模式：

- `log.Fatal` 会跳过所有 `defer`——`db.Close()` 不会执行
- 返回 error 让**测试可以调用 `run`**（`main` 没法测）
- 退出码只在一个地方决定

### 优雅关闭

```go
func serve(ctx context.Context, cfg config.Config, h http.Handler, log *slog.Logger) error {
	srv := &http.Server{
		Addr:         cfg.Addr,
		Handler:      h,
		ReadTimeout:  cfg.ReadTimeout,       // D11 §8 四个超时
		WriteTimeout: cfg.WriteTimeout,
		IdleTimeout:  cfg.IdleTimeout,
	}

	// ⭐ 监听信号（D10 §8）
	ctx, stop := signal.NotifyContext(ctx, os.Interrupt, syscall.SIGTERM)
	defer stop()

	errCh := make(chan error, 1)            // ⚠️ 缓冲 1，否则 ListenAndServe 那条 goroutine 泄漏
	go func() {
		errCh <- srv.ListenAndServe()
	}()

	select {
	case err := <-errCh:
		if !errors.Is(err, http.ErrServerClosed) {
			return err
		}
		return nil
	case <-ctx.Done():
		log.Info("收到关闭信号，等待在途请求")
	}

	shutCtx, cancel := context.WithTimeout(context.Background(), cfg.ShutdownTimeout)
	defer cancel()
	return srv.Shutdown(shutCtx)            // ⭐ 等在途请求做完
}
```

⚠️ 三个细节：

1. **`errCh` 必须有缓冲**。`Shutdown` 之后 `ListenAndServe` 会返回 `ErrServerClosed`，
   如果没人收，那条 goroutine 永远阻塞在发送上——**优雅关闭本身造成了泄漏**（D8 §7）
2. **`Shutdown` 用的是全新的 `context.Background()`**，不是那个已经被取消的 `ctx`——
   否则它立刻超时，等于没等
3. **`signal.NotifyContext`** 比手工 `signal.Notify` + channel 干净得多（Go 1.16+）

## 6. 测试策略：三层三种打法

⭐ **每一层用最轻的手段测它自己的职责。**

| 层 | 怎么测 | 需要数据库吗 |
|---|---|---|
| **repository** | 真实 Postgres（D13 已完成） | ✅ 需要 |
| **service** | **手写假 repository** | ❌ 不需要 |
| **handler** | `httptest` + 假 service | ❌ 不需要 |
| 全链路 | 起真服务 + 真库，只测 1–2 条主路径 | ✅ 需要 |

### 假实现就是个 struct，不要 mock 框架

```go
type fakeRepo struct {
	orders map[int64]*orders.Order
	err    error                       // 想让它失败时设这个
}

func (f *fakeRepo) Get(_ context.Context, id int64) (*orders.Order, error) {
	if f.err != nil {
		return nil, f.err
	}
	o, ok := f.orders[id]
	if !ok {
		return nil, apperr.NotFound("订单不存在", nil)
	}
	return o, nil
}
```

⚠️ **Go 社区不爱 mock 框架**，理由不是「洁癖」：

- 接口小（§2.4），手写假实现就几行
- 假实现是**普通代码**——能打断点、能被编译器检查、改接口时编译报错
- mock 框架的「验证调用次数/参数」往往在测实现细节，不是行为

> ⭐ 判据：**如果你的假实现写起来很痛苦，通常说明接口太大了**，
> 那是设计信号，不是「该上 mock 框架」的信号。

### 测试金字塔在这里的样子

```
   ▲  全链路（1–2 条）      慢、脆、但能抓到组装错误
  ███  handler（httptest）  快，测 HTTP 契约
 █████ service（假 repo）   最快，测业务规则 ← 大头在这
███████ repository（真库）  慢，测 SQL
```

**业务规则的测试应该是最多的**，而且它们不需要数据库——这正是 §2 那套依赖方向换来的。

## 7. Docker 化

```dockerfile
# ---------- 构建阶段 ----------
FROM golang:1.26-alpine AS build
WORKDIR /src

# ⭐ 先只复制依赖清单，让 go mod download 这层能被缓存
COPY go.mod go.sum ./
RUN go mod download

COPY . .
# CGO_ENABLED=0 → 静态链接，才能跑在 scratch/distroless 上
# -ldflags "-s -w" → 去掉符号表和调试信息，镜像更小
RUN CGO_ENABLED=0 go build -ldflags "-s -w" -o /out/api ./cmd/api

# ---------- 运行阶段 ----------
FROM gcr.io/distroless/static-debian12
COPY --from=build /out/api /api
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/api"]
```

四个要点：

1. **多阶段构建**——最终镜像里没有 Go 工具链、没有源码
2. **`COPY go.mod go.sum` 单独一层**——代码改了但依赖没改时，`go mod download` 直接命中缓存
3. **`CGO_ENABLED=0`**——纯静态二进制，`distroless/static` 里连 libc 都没有
4. **`USER nonroot`**——别用 root 跑服务

> ⭐ 这是 Go 相对 JVM 的巨大优势：**最终镜像通常 10–20MB**，而一个 Spring Boot 镜像
> 动辄 200MB+。D18 会展开讲交付，今天先把它跑起来。

⚠️ **`.dockerignore` 别忘了**，否则 `COPY . .` 会把 `.git` 和本地产物一起塞进构建上下文。

## 8. 今天的练习

```
go/internal/ordersvc/     ⭐ 新：业务逻辑 + 消费方定义的接口
go/internal/api/          ⭐ 新：handler + DTO
go/cmd/api/               ⭐ 新：组装 + 优雅关闭
go/Dockerfile             ⭐ 新
```

### ① `internal/ordersvc`

1. **定义 `Repository` 接口** —— 只列你真正用到的方法，**不要 import 具体实现**
2. **`Place(ctx, *orders.Order)`** —— 业务校验（至少一个 item、qty 上限、customer 非空），再调 repo
3. **`Get` / `List`** —— 基本转发，但 `List` 要把「用户传的 limit」规范化
4. **`Pay(ctx, id)` / `Cancel(ctx, id)`** —— ⭐ **状态机**：
   ```
   pending  --pay-->    paid
   pending  --cancel--> cancelled
   paid     --cancel--> cancelled
   shipped  --*-->      ❌ 都不允许
   已经是目标状态         ❌ Conflict
   ```
   非法转换 → `apperr.Conflict`，消息要说清「从什么状态到什么状态不允许」

### ② `internal/api`

1. **DTO** —— 请求/响应类型独立于领域模型，都是小写
2. **`NewRouter(svc, logger) http.Handler`** —— Go 1.22 路由（D11 §2）
3. **统一错误响应** —— 一个 `writeError`，走 `apperr.HTTPStatus`；
   5xx 要记日志（带完整错误链），4xx 不用
4. **`GET /healthz`** —— 要真的检查数据库（`db.PingContext`），别只返回 `{"status":"ok"}`

### ③ `cmd/api`

按 §5 的样子组装，`run() error` 模式 + 优雅关闭。

### ④ `Dockerfile` + `.dockerignore`

按 §7。验收：`docker build` 出来的镜像 **< 30MB**，且能连上宿主机的 Postgres。
