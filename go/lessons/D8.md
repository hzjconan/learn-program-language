## 1. goroutine 是什么

```go
go doSomething()          // 就这样，起一条并发执行流
go func() { ... }()       // 匿名函数版，最常见
```

### 为什么便宜

| | Java 平台线程 | Java 虚拟线程（21+） | goroutine |
|---|---|---|---|
| 初始栈 | ~1MB（固定） | 小，可增长 | **2KB，可增长到 1GB** |
| 调度者 | 操作系统 | JVM | **Go 运行时** |
| 切换成本 | 系统调用，微秒级 | 用户态 | **用户态，纳秒级** |
| 起 10 万个 | 直接崩 | 可以 | **可以，很正常** |

**goroutine 是用户态的、由 Go 运行时调度的执行流。** 它不是线程——运行时会把 N 个 goroutine 复用到 M 个操作系统线程上（GMP 模型，D21 面试准备时细讲）。

> 如果你用过 Java 21 的虚拟线程，goroutine 的心智模型几乎一样。**区别是 Go 从第一天就这么设计，所以整个标准库都是「阻塞式写法 + 底层非阻塞」**——你写 `conn.Read()` 看起来是阻塞的，运行时会把这条 goroutine 挂起、让出线程。Java 的老库里还有大量真会钉住线程的代码。

### 三个必须知道的性质

**① `main` 返回时，所有 goroutine 直接被丢弃。** 不等，不清理，没有「非守护线程」的概念。

**② goroutine 没有 ID、没有句柄、没法从外部杀死。** 你拿不到任何东西来引用它。要控制它只能靠**通信**（channel、`context`）。

> 这是刻意的设计。Java 的 `Thread.stop()` 早就废弃了，因为从外部强杀线程必然破坏不变量。Go 直接不给你这个选项。

**③ 未捕获的 panic 会杀死整个进程**，不只是那条 goroutine。而且**你不能在别的 goroutine 里 `recover` 它**——`recover` 只对当前 goroutine 的调用栈有效（D2 §7）。

```go
go func() {
    defer func() {
        if r := recover(); r != nil {   // ⭐ 每条 goroutine 自己兜底
            log.Println("recovered:", r)
        }
    }()
    riskyWork()
}()
```

**长期运行的 worker goroutine 都该自己带 recover。**

## 2. channel：Go 的核心抽象

```go
ch := make(chan int)        // 无缓冲
ch := make(chan int, 10)    // 缓冲区大小 10
var ch chan int             // nil channel（⚠️ 读写都永远阻塞）

ch <- 42                    // 发送
v := <-ch                   // 接收
v, ok := <-ch               // ⭐ 二值接收：ok=false 表示【channel 已关闭且已排空】
close(ch)                   // 关闭
```

### 无缓冲 channel = 同步会合（rendezvous）

**这是最重要的一条。** 无缓冲 channel 的发送和接收**必须同时就绪**，任何一方先到都会阻塞等待对方。

```
goroutine A:  ch <- 1   ──┐
                          ├── 两边碰头的那一刻，值才传过去，两边同时继续
goroutine B:  v := <-ch ──┘
```

**它不只是传值，它还传「时序」**——发送方知道「接收方一定拿到了」。这是 Java 的 `BlockingQueue` 给不了的（`put` 到队列里就返回了，不知道有没有人取）。

### 有缓冲 channel = 队列

```go
ch := make(chan int, 2)
ch <- 1     // 不阻塞
ch <- 2     // 不阻塞
ch <- 3     // 阻塞，直到有人取走一个
```

**缓冲区满了才阻塞发送方，空了才阻塞接收方。** 这个才对应 Java 的 `ArrayBlockingQueue`。

### 怎么选

| 场景 | 选 |
|---|---|
| 需要「对方确实收到了」的保证 | **无缓冲** |
| 生产和消费速度不匹配，要削峰 | **有缓冲** |
| 信号量 / 限流（占坑） | **有缓冲，容量 = 并发上限** |
| 不确定 | **先用无缓冲**——它会让问题立刻暴露，而不是被缓冲区藏起来 |

> ⚠️ **别拿缓冲区当性能优化。** 加缓冲只是把「阻塞」推迟了，如果消费者根本跟不上，缓冲区满了照样阻塞——而且现在你还多了一个「队列里积压了多少」的隐藏状态。

## 3. 关闭 channel

```go
close(ch)
```

三条规则：

1. **只有发送方能关闭**，接收方关闭会导致发送方 panic
2. **关闭一个已关闭的 channel → panic**
3. **向已关闭的 channel 发送 → panic**；从已关闭的 channel **接收不会 panic**，返回零值

```go
ch := make(chan int, 1)
ch <- 1
close(ch)
v, ok := <-ch    // 1, true    ← 缓冲区里还有货
v, ok = <-ch     // 0, false   ← 空了，这才表示"关闭"
```

**「关闭」不是「立刻停止」，是「不会再有新值了」。** 已经在缓冲区里的值仍然能被取完。

### `for range` 读到关闭为止

```go
for v := range ch {      // channel 关闭且排空后自动退出循环
    fmt.Println(v)
}
```

**这是消费 channel 的标准写法。** 如果没人 `close(ch)`，这个循环永远不退出——这是 goroutine 泄漏的头号成因（§7）。

### 你不必总是关闭 channel

**channel 会被 GC 回收，不像文件句柄那样必须释放。** 只在「接收方需要知道『没有更多数据了』」时才关闭。

## 4. 方向类型：让编译器帮你

```go
func produce(out chan<- int)   // 只能发送
func consume(in <-chan int)    // 只能接收
```

**函数签名里一律写方向类型。** 好处：

- 编译器挡住「消费者不小心关闭了 channel」这类错误
- **签名自带文档**——一眼看出数据往哪流

双向 `chan T` 可以隐式转成单向，反过来不行。

## 5. `select`：同时等多个 channel

```go
select {
case v := <-ch1:
    ...
case ch2 <- x:
    ...
case <-time.After(time.Second):     // 超时
    ...
default:                            // ⚠️ 有 default 就【永不阻塞】
    ...
}
```

四个要点：

1. **多个 case 同时就绪时，随机选一个**（不是从上到下）——防止饿死
2. **有 `default` 就变成非阻塞**：没有 case 就绪时立刻走 default
3. **没有 `default` 时会阻塞**，直到至少一个 case 就绪
4. **`select {}`（空 select）永久阻塞**，偶尔用来「让 main 永不退出」

### 超时模式

```go
select {
case result := <-work:
    return result, nil
case <-time.After(3 * time.Second):
    return nil, errors.New("超时")
}
```

⚠️ **`time.After` 在超时前不会被 GC**——高频循环里用它会堆积 timer。真实代码用 `context.WithTimeout`（D10）或者复用 `time.NewTimer` + `defer timer.Stop()`。

### nil channel 在 select 里的妙用

**对 nil channel 的读写永远阻塞**，所以在 `select` 里把某个 channel 置 nil 就等于**动态关掉这个 case**：

```go
for a != nil || b != nil {
    select {
    case v, ok := <-a:
        if !ok { a = nil; continue }   // a 关了，禁用这个 case
        ...
    case v, ok := <-b:
        if !ok { b = nil; continue }
        ...
    }
}
```

不然从已关闭的 channel 读会立刻返回零值，`select` 会疯狂空转。

## 6. 死锁

Go 运行时能检测到**所有 goroutine 都阻塞**的情况：

```
fatal error: all goroutines are asleep - deadlock!
```

三个最常见的成因：

```go
// ① 无缓冲 channel 上自己发给自己
ch := make(chan int)
ch <- 1              // 没有接收方，永久阻塞

// ② 忘了 close，for range 收不到结束信号
for v := range ch { ... }    // 生产者结束了但没 close

// ③ WaitGroup 的 Wait 在同一个 goroutine 里等自己
wg.Add(1)
wg.Wait()            // 没人 Done
```

⚠️ **这个检测只在「全部」goroutine 都睡着时触发。** 只要还有一条在跑（哪怕是个空转的循环），死锁就检测不到——**部分死锁是静默的**。

## 7. ⭐ goroutine 泄漏 —— 今天的题眼

**泄漏 = 一条 goroutine 永远阻塞，永远不退出，它占的栈和它引用的对象永远不被回收。**

不像内存泄漏那样有明显症状，它的表现是**进程内存缓慢上涨 + goroutine 数量单调增长**，跑几天才炸。

### 最常见的三种

**① 发送方没有接收者了**

```go
func leak() <-chan int {
    ch := make(chan int)          // 无缓冲
    go func() {
        ch <- expensiveWork()      // ⚠️ 如果调用方不读，这条 goroutine 永远卡这儿
    }()
    return ch
}

result := <-leak()   // 正常路径没问题
// 但如果调用方超时了、提前 return 了，那条 goroutine 就永远留在那儿
```

**修法：给 channel 加容量 1**，这样发送方总能把值放下就走：

```go
ch := make(chan int, 1)    // ⭐ 发送方不会被卡住
```

**② 接收方等一个永远不来的值**

```go
for v := range ch { ... }   // 生产者 panic 了 / 忘了 close → 永久阻塞
```

**③ `select` 里没有退出分支**

```go
for {
    select {
    case v := <-ch:
        ...
    }                        // ⚠️ ch 永远不来值时，这条 goroutine 就死在这儿
}
```

**修法：永远给长期运行的 goroutine 一个退出通道**（`done chan struct{}` 或 `context`，D10）。

### 怎么发现

```go
runtime.NumGoroutine()      // 当前 goroutine 数量
```

**测试里的标准手法**：跑之前记一次，跑完等一小会儿再记一次，数字应该回到原点。今天的练习会用到。

生产上用 `net/http/pprof` 的 `/debug/pprof/goroutine`（D16）。

## 8. 常用模式

### worker pool（今天的主练习）

```go
jobs := make(chan Job)
results := make(chan Result)

// 起 N 个 worker
var wg sync.WaitGroup
for range n {
    wg.Go(func() {                  // Go 1.25+ 的写法
        for j := range jobs {        // jobs 关闭后自动退出
            results <- process(j)
        }
    })
}

// 单独一条 goroutine 负责「等所有 worker 结束后关闭 results」
go func() {
    wg.Wait()
    close(results)
}()

// 主流程投递 + 收集
go func() {
    for _, j := range allJobs { jobs <- j }
    close(jobs)                     // ⭐ 告诉 worker 没活了
}()

for r := range results { ... }      // results 关闭后退出
```

**这个骨架要背下来。** 三个关键点：

1. **`close(jobs)` 让 worker 的 `for range` 自然退出**
2. **`wg.Wait()` 必须在单独的 goroutine 里**——否则主流程还没开始读 `results` 就先阻塞了，死锁
3. **`close(results)` 让主流程的 `for range` 退出**

### 信号量限流

```go
sem := make(chan struct{}, 3)      // 最多 3 个并发

for _, task := range tasks {
    sem <- struct{}{}               // 占坑（满了就阻塞）
    go func() {
        defer func() { <-sem }()    // 让坑
        work(task)
    }()
}
```

`chan struct{}` 是零尺寸的（QA #11），纯粹当信号用。

## 9. 「不要用共享内存来通信」的真实含义

> **Do not communicate by sharing memory; instead, share memory by communicating.**

这句话经常被误读成「不许用 mutex」。**不是这个意思。**

它说的是：**把数据的所有权在 goroutine 之间「传递」，而不是让多个 goroutine 同时持有并加锁保护。**

```go
// 共享内存 + 加锁：两个 goroutine 都能碰 counter
var mu sync.Mutex
var counter int

// 通信传递所有权：counter 只属于一条 goroutine，别人通过 channel 请求它
func counterLoop(inc <-chan int, get <-chan chan int) {
    counter := 0                    // ⭐ 只有这条 goroutine 能碰它，天然无竞态
    for {
        select {
        case n := <-inc:  counter += n
        case reply := <-get: reply <- counter
        }
    }
}
```

**判据**：数据有没有一个明确的「主人」？

- 有 → 用 channel 传消息给主人（今天的练习就是这样：去重用的 `visited` map 只属于协调者）
- 没有，就是一块大家都要读写的共享状态 → **老实用 `sync.Mutex`**（D9）

**Go 团队自己也说过**：计数器加锁比套 channel 简单得多，就用锁。**channel 适合传递数据和信号，mutex 适合保护状态。**

### 主练习 · `crawl`

一个**逐层推进、并发受限**的爬取器。抓取行为抽象成 `Fetcher` 接口（D5 的依赖倒置），所以测试里不用真联网。

三个要实现的函数，难度递增：

1. **`FetchWithTimeout`** —— `select` + 超时，**且不能泄漏 goroutine**（测试会数 goroutine）
2. **`FetchAll`** —— 固定 N 个 worker 的 worker pool，并发抓一批 URL
3. **`Crawl`** —— 逐层 BFS，去重，最多 depth 层

要求：

- **并发上限必须真的生效**（测试会记录同时在跑的最大数量）
- **不能有 goroutine 泄漏**（测试会比对前后的 `runtime.NumGoroutine()`）
- **`-race` 必须干净**
- **结果顺序确定**——并发返回的顺序是随机的，你得自己排序（否则测试随机失败）
