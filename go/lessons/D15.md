# D15 · 测试进阶

> **题眼是第 2 节：每种测试替身都有它「看不见」的东西。**
>
> 不是抽象的道理——就用**你昨天写的代码**当案例：
> D14 review 出的 6 个 bug 里，有一个**任何 fake 都抓不到**，
> 而原因是我写的 fake **比真实现更正确**。

---

## 1. 测试替身的四种，以及 Go 只用一种

| 叫法 | 是什么 | Go 里 |
|---|---|---|
| **Fake** | 一个**能用的简化实现**（内存 map 代替数据库） | ⭐ **几乎只用这个** |
| **Stub** | 固定返回预设值，不管你怎么调 | fake 的退化形式 |
| **Mock** | 记录调用并**断言调用方式** | 少用 |
| **Spy** | 记录调用但不断言 | fake 顺手就能做 |

你 D14 写的 `fakeRepo` 其实兼了三个角色：它是 fake（有内存 map）、是 stub（`err` 字段让它返回预设错误）、也是 spy（`created` / `updateCalled` 记录调用）。**一个 struct 三十行，不需要框架。**

### 为什么 Go 社区不爱 mock 框架

不是洁癖，三个具体理由：

1. **接口小**（D5 §2、D14 §2.4）——手写假实现就几行
2. **假实现是普通代码**——能打断点、编译器检查签名、改接口时它会**编译报错**
3. **mock 的「断言调用次数/参数」常常在测实现细节**

> ⭐ 第 3 条要展开：「校验失败时不该调 `repo.Create`」值得测——那是**行为契约**。
> 「`Get` 恰好被调了 2 次」通常不值得——重构一下就红了，而行为没变。
>
> **需要频繁断言调用次数，往往是设计信号，不是「该上 mock 框架」的信号。**

⚠️ mock 框架确实更方便的场景：接口大、要验证复杂的交互序列、或者团队已经在用。这时候 `go.uber.org/mock`（原 gomock）是主流选择。**但先问一句：接口为什么这么大。**

## 2. ⭐ 每种替身看不见什么 —— 今天的题眼

### 2.1 拿你自己的 6 个 bug 当案例

D14 review 出的问题，按「哪一层能抓到」分类：

| # | Bug | 单元测试<br>（fake） | 集成测试<br>（真库） | 端到端 |
|---|---|:--:|:--:|:--:|
| 1 | `o, _ := svc.Get(...)` → 空指针 panic | ✅ | — | ✅ |
| 2 | SKU 去重只比较相邻元素 | ✅ | ✅ | ✅ |
| 3 | Qty 错误消息说反了 | ✅ | — | — |
| 4 | `List` 没走 DTO，返回 Go 字段名 | ✅ | ❌ | ✅ |
| 5 | **`RETURNING` 漏了 `status`** | ❌ | ✅ | ✅ |
| 6 | 405 不是 JSON | ✅ | — | ✅ |

**第 5 行是今天全部内容的起点。**

### 2.2 为什么 fake 抓不到 bug 5

真实的 `orders.Repo.Create` 当时写的是：

```go
RETURNING id, created_at        -- ⚠️ 漏了 status
```

数据库的 `DEFAULT 'pending'` 生效了，但内存里的 `o.Status` 还是空字符串。
所以 `POST /orders` 返回 `"status":""`，而 `GET /orders/{id}` 返回 `"status":"pending"`。

而我写的 fake：

```go
func (f *fakeRepo) Create(_ context.Context, o *orders.Order) error {
	o.ID = f.nextID
	o.Status = orders.StatusPending      // ⭐ 我「帮」它填了
	...
}
```

⚠️ **fake 比真实现更正确**，所以它把 bug 盖住了。而且**两个 fake 都这么写**
（`ordersvc_test.go:50` 和 `api_test.go:43`）——因为我写它们的时候，
脑子里想的是「Create 之后订单应该是 pending」，而不是「真实现现在到底做了什么」。

> ⭐ **这是今天最重要的一句话：**
>
> **你的 fake 体现的是你【以为】真实现在做什么。**
> **当真实现和你的「以为」不一致时，fake 会站在「以为」那一边。**

所以 fake 天然**测不出**：SQL 写错、`RETURNING` 漏列、约束没生效、事务没回滚、
类型映射错误、NULL 处理——**所有「真实现和你的心智模型不一致」的地方**。

### 2.3 反过来：集成测试看不见什么

第 4 行：`List` 没走 DTO，返回 `{"ID":1,"Customer":...}`。
**真库的集成测试完全抓不到**——数据从数据库出来是对的，问题出在**序列化成 JSON 那一步**。
repository 层的测试根本不到那儿。

### 2.4 结论：不是「哪种更好」，是「各自的盲区不重叠」

```
        能抓到                      看不见
fake    业务规则、分支、错误路径      真实现和心智模型的差异
真库    SQL、约束、事务、类型映射     HTTP 层、序列化、组装
端到端  组装错误、配置、真实契约      跑得慢、失败了不知道是哪一层
```

⭐ **测试金字塔的真正理由不是「快的多写点」，是「让盲区互相覆盖」。**

## 3. 让集成测试不再 `t.Skip`

### 3.1 ⚠️ `Skip` 是谎报军情

你 D13 的 `openDB` 长这样：

```go
if err := db.PingContext(ctx); err != nil {
	t.Skipf("连不上数据库（%v）——先跑 `make db-migrate`", err)
}
```

跑 `go test ./...` 时输出是 **`ok`**。⚠️ **绿色的 `ok`，但那一整包一行都没执行。**

CI 上尤其致命：忘了起数据库 → 全部 skip → **流水线绿灯 → 合并 → 线上炸**。

### 3.2 `testcontainers-go`：测试自己起容器

```go
func TestMain(m *testing.M) {
	ctx := context.Background()

	pg, err := postgres.Run(ctx, "postgres:17-alpine",
		postgres.WithDatabase("testdb"),
		postgres.WithUsername("u"),
		postgres.WithPassword("p"),
		testcontainers.WithWaitStrategy(
			wait.ForLog("database system is ready to accept connections").
				WithOccurrence(2).WithStartupTimeout(60*time.Second)),
	)
	if err != nil {
		log.Fatalf("起 Postgres 容器失败: %v", err)   // ⭐ 失败就是失败，不 Skip
	}

	dsn, _ := pg.ConnectionString(ctx, "sslmode=disable")
	testDSN = dsn
	applyMigrations(dsn)

	code := m.Run()
	_ = pg.Terminate(ctx)
	os.Exit(code)
}
```

三个好处：

1. **不再需要「先跑 `make db-migrate`」**——测试自包含
2. **CI 上直接能跑**（只要有 Docker）
3. **每次都是干净的库**——不用担心上次跑剩的数据

### 3.2b ⚠️ 它悄悄起了第二个容器：ryuk

跑完一次测试之后 `docker images` 里会多出一个你没主动拉过的镜像：

```
postgres:17-alpine              291MB
testcontainers/ryuk:0.14.0      2.11MB     ← ⚠️ 这个哪来的
```

**ryuk 是 testcontainers 的清理守护进程。** 它启动时起一个 ryuk 容器，
把你创建的所有容器/网络/卷登记给它；如果你的测试进程崩了、被 `Ctrl-C` 了、
或者忘了 `Terminate`，**ryuk 会在超时后替你清掉**。

⚠️ 它的镜像名**硬编码在库的 `internal/` 里**，你搜不到也引用不到：

```go
// testcontainers-go@v0.44.0/internal/config/config.go:16
const ReaperDefaultImage = "testcontainers/ryuk:0.14.0"
```

⭐ 所以「测试的镜像依赖」是**两个**，不是一个。这个事实在离网环境里会咬人（见 §3.2d）。

> ⭐ 由此提炼一条通用习惯：
> **引入一个「帮你管资源」的库时，先问它自己会起什么。**
> 最快的验证不是读文档，是跑一次然后 `docker ps -a` / `docker images` ——
> **看实际起了几个容器**，比任何文档都准。

### 3.2b-2 为什么 DSN 要写 `sslmode=disable`

```go
dsn, err := pg.ConnectionString(ctx, "sslmode=disable")
```

⚠️ **它不是必需的** —— 不写也能连上。实测：

| DSN | TLS 配置 | pgx 的备选连接数 | 连接耗时 |
|---|---|:--:|---|
| 不写 `sslmode` | `true` | **2** | 10ms |
| `sslmode=disable` | `false` | **1** | 8.3ms |
| `sslmode=require` | `true` | 1 | — |

（`ConnectionString` 的实现就是把参数拼进查询串，不加就是个空的 `?`。）

推荐写它是**三个小收益的叠加**：

**① 省一次握手。** pgx 默认 `sslmode=prefer` ——
「备选连接数 = 2」就是它会先发一个 SSLRequest，
容器里的 Postgres **没配证书**所以拒绝，再用明文重连一次。
⭐ 一次多余的往返，实测 1.7ms。单次无所谓，但连接开得多就累起来了。

**② 意图明确。** 不写的话，读代码的人得同时知道
「pgx 默认 prefer」「官方 postgres 镜像默认不开 SSL」「所以会静默回退」
三件事才能确认这行是对的。写上就一目了然：**本机测试容器，没有 TLS，也不需要**。

**③ 把行为钉死。** 哪天镜像换成一个自带证书的变体，
`prefer` 会**静默地开始用 TLS** —— 测试还是绿的，但行为变了你不知道。

#### ⚠️ 但这行字符串绝对不能进生产

| 场景 | 该用什么 |
|---|---|
| 本机测试容器 | `sslmode=disable` ✅ 明确、快、本来也没 TLS |
| 生产 / 云数据库 | **`sslmode=verify-full`** ✅ 验证证书**和主机名** |
| 生产上写 `disable` | ❌ 凭据和数据全裸奔 |

⚠️ 特别注意 **`sslmode=require` 只加密、不验证证书**，防不住中间人 ——
它不是「生产够用」的那一档。

> ⭐ 这是「测试代码泄漏到生产」的经典路径之一：有人从测试里抄 DSN 模板，
> `disable` 就跟着上线了。
>
> 你的 `config.DatabaseURL` 是 `Secret` 类型、从环境变量读，生产 DSN 由运维配 ——
> **架构上已经隔开了**，这点做得对。

### 3.2c 镜像什么时候会走网络

Docker 的默认拉取策略是 **if-not-present**：本地有就不拉。

| 场景 | 走网络吗 |
|---|---|
| 本地第一次 | ✅ 拉 postgres(291MB) + ryuk(2MB) |
| 本地后续 | ❌ **一个字节都不走** |
| CI（全新 runner） | ✅ **每次都拉** |

实测对照：首次跑 **24.4s**，镜像齐了之后 **5.65s**。

⚠️ 两个容易误解的地方：

**① `docker pull` 即使本地已有也要 8 秒**（去 registry 校验 digest）。
testcontainers **不做**这一步，所以那 8 秒不在你的测试时间里。

**② `17-alpine` 是【可变 tag】。** if-not-present 意味着你本地这个是四周前拉的那一版，
而 CI 上拉的是今天重建的那一版 —— ⭐ **两边跑的其实不是同一个 Postgres。**
这是「本地过了 CI 挂」的一种隐藏来源。要消除就钉 digest：

```go
postgres.Run(ctx, "postgres:17-alpine@sha256:abc123...")
```

代价是要定期手动更新。本课不要求（那是 D18 交付那天的话题），
但**知道 `17-alpine` 不是一个确定的东西**很重要。

### 3.2d ⚠️ 如果 CI 环境不允许外网

四种解法，按推荐度：

#### ① Docker daemon 的 registry mirror（最省事，覆盖最全）

```json
// /etc/docker/daemon.json
{ "registry-mirrors": ["https://registry.mycorp.com"] }
```

⭐ **完全透明** —— testcontainers、`docker compose`、`docker build`、`kind` 全部自动走内网，
不改代码也不设环境变量。

⚠️ 前提是你能改 runner 的 daemon 配置（自建 runner 可以，GitHub 托管的不行）。

#### ② `TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX`

```bash
export TESTCONTAINERS_HUB_IMAGE_NAME_PREFIX=registry.mycorp.com/dockerhub/
```

读过源码确认过一件事：它**管所有 Hub 镜像，包括你自己指定的那个**。
`prependHubRegistry.Substitute` 的排除条件只有四条 ——
前缀为空、镜像已带 registry、显式写了 `docker.io`、显式写了 `registry.hub.docker.com`。
`postgres:17-alpine` 哪条都不满足，所以**它和 ryuk 一起改道**。

⚠️ 但它**只管 testcontainers 起的容器** —— 你的 `docker build` 和 `kind` 还是走公网。

#### ③ 镜像预装进 CI runner（真正的离线可跑）

```bash
# 一次性导出
docker save postgres:17-alpine testcontainers/ryuk:0.14.0 -o test-images.tar
```

```yaml
# CI 里
- run: docker load -i /opt/images/test-images.tar
```

⭐ 因为是 if-not-present，**镜像在本地就永远不会尝试联网**。

⚠️ **必须包含 ryuk** —— 这是最常漏的一个，因为它不在你的代码里，搜不到。

#### ④ 关掉 ryuk，少一个依赖

```bash
TESTCONTAINERS_RYUK_DISABLED=true
```

⚠️ 代价：清理全靠你自己的代码。`TestMain` 里的 `pg.Terminate(ctx)` 管得住正常路径，
但 **`log.Fatalf` 那条路径和被 `Ctrl-C` 时会泄漏容器**。

⭐ CI 上每个 job 用完就销毁整个 runner，泄漏无所谓 —— **这是 CI 上关掉它最常见的理由**。
本地开发别关。

#### ⚠️ 第五项：「离网」不只是镜像问题

`go test` 本身也要拉模块。真正 air-gapped 的环境要同时堵三条线：

| 来源 | 解法 |
|---|---|
| **容器镜像** | 上面 ①–③ |
| **Go 模块** | 内网 `GOPROXY`，或 `go mod vendor` 把依赖入库 |
| **工具下载的二进制** | 比如 kubebuilder 的 `envtest`（D20 会用到）—— 要预装 |

> ⭐ 一个比读文档可靠的验证方法：
> ```bash
> docker system prune -a     # ⚠️ 会删掉所有本地镜像
> # 然后断网跑测试
> ```
> **看它卡在哪个镜像上** —— 这能一次性找出所有隐藏依赖，包括 ryuk 这种搜不到的。

#### 我的建议

**能改 daemon → ①。不能 → ② + ④。真正 air-gapped → ③ + Go 模块 vendor 或内网 proxy。**

### 3.3 ⚠️ 代价：慢

实测（你这台机器）：

```
容器启动耗时: 24.436s
```

**24 秒**。所以：

⭐ **必须用 `TestMain` 让整个包共用一个容器**，而不是每个测试起一个。
20 个测试各起一次 = 8 分钟。

还有两个减速的办法：

- **`postgres.WithSnapshot` / 重置数据**——容器复用，每个测试之间只 `TRUNCATE`
- **`testcontainers.WithReuse`**——跨 `go test` 复用同一个容器（本地开发时很爽，
  ⚠️ CI 上别用，会引入测试间的隐藏依赖）

### 3.4 那还要不要 docker compose

要。分工是：

| | 用途 |
|---|---|
| `deploy/docker-compose.yml` | **本地开发**：起一次，`go run ./cmd/api` 连着它 |
| `testcontainers` | **测试**：自动起、自动清、CI 里能跑 |

⚠️ 别让测试连开发库——测试会 `TRUNCATE`，把你手动造的数据清光。

### 3.5 用构建标签把慢测试分开

```go
//go:build integration

package orders_test
```

```bash
go test ./...                      # 只跑快的（毫秒级）
go test -tags=integration ./...    # 跑全部（含容器）
```

⭐ 好处是**日常开发的反馈循环保持在秒级**，CI 上跑全量。
⚠️ 但要保证 CI **真的**跑了带标签的那批——否则又变成了另一种 skip。

## 4. `httptest.Server`：测**客户端**

你之前只测过服务端（`httptest.NewRecorder`）。测客户端要用 `httptest.NewServer`：

```go
func TestClient_RetriesOn503(t *testing.T) {
	var calls int
	srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		calls++
		if calls < 3 {
			w.WriteHeader(http.StatusServiceUnavailable)
			return
		}
		w.Write([]byte(`{"ok":true}`))
	}))
	defer srv.Close()

	c := NewClient(srv.URL)          // ⭐ 把 base URL 做成参数，就是为了能这样测
	...
}
```

⚠️ **可测试性是设计出来的**：如果你的客户端把 URL 写死在代码里，就没法测。
**把「外部依赖的地址」做成构造函数参数**——和 D14 的依赖注入是同一件事。

三种常见的客户端测试：

| 测什么 | 怎么造 |
|---|---|
| 重试逻辑 | 前 N 次返回 5xx |
| 超时处理 | handler 里 `time.Sleep` |
| 错误响应解析 | 返回各种 4xx + 错误 body |

## 5. Fuzz：让 Go 自己找输入

D6 提过，今天真写一个。

```go
func FuzzParseListFilter(f *testing.F) {
	// 种子语料：正常的、边界的
	f.Add("/orders")
	f.Add("/orders?limit=20")
	f.Add("/orders?customer=&status=paid")

	f.Fuzz(func(t *testing.T, rawQuery string) {
		req := httptest.NewRequest("GET", "/orders?"+rawQuery, nil)

		// ⭐ 不变量：无论输入什么，都【不能 panic】，
		// 而且要么返回合法的 filter，要么返回 apperr.Invalid
		filter, err := parseListFilter(req)
		if err != nil {
			if kind, ok := apperr.KindOf(err); !ok || kind != apperr.KindInvalid {
				t.Fatalf("解析失败时应该返回 Invalid，得到 %v", err)
			}
			return
		}
		if filter.Limit < 0 {
			t.Fatalf("解析成功却返回了负数 limit: %d", filter.Limit)
		}
	})
}
```

```bash
go test -fuzz=FuzzParseListFilter -fuzztime=30s ./internal/api/
```

⭐ **fuzz 测的是「不变量」，不是「具体输出」**。你没法预期每个随机输入的正确结果，
但你能说「不管输入什么，都不该 panic」「返回的 limit 不该是负数」。

⚠️ 找到反例时它会**存进 `testdata/fuzz/`**，之后每次 `go test` 都会重跑那个输入——
**自动变成回归测试**。这是 fuzz 最实用的一点。

适合 fuzz 的地方：**解析器**（查询参数、JSON、配置、协议）。不适合：有外部依赖的逻辑。

## 6. Golden file：快照测试

响应体字段一多，手写断言就很痛苦。golden file 把「期望输出」存成文件。

### 6.1 完整生命周期

**① 快照文件里存的就是一份序列化后的输出**，一个普通 JSON 文本：

```json
{
  "id": 1,
  "customer": "alice",
  "status": "pending",
  "total_cents": 2250,
  "created_at": "2026-01-01T10:00:00Z",
  "items": [
    { "id": 1, "sku": "A-1", "qty": 2, "price_cents": 500 }
  ]
}
```

没有魔法——它就是「`toResponse(sample())` 序列化出来应该长这样」。
⭐ **这个文件要提交进仓库**（下面 6.3 会讲为什么）。

**② 你自己用 `-update` 存一次：**

```go
var update = flag.Bool("update", false, "更新 golden 文件")

func TestOrderResponseGolden(t *testing.T) {
	got, err := json.MarshalIndent(toResponse(sample()), "", "  ")
	if err != nil {
		t.Fatal(err)
	}
	got = append(got, '\n')

	goldenPath := filepath.Join("testdata", "order_response.json")

	if *update {                                    // ⭐ 只有带 -update 时才写
		if err := os.WriteFile(goldenPath, got, 0o644); err != nil {
			t.Fatal(err)
		}
		return                                      // 写完就结束，不比较
	}

	want, err := os.ReadFile(goldenPath)            // 平时：读出来比
	if err != nil {
		t.Fatalf("读 golden 文件失败（第一次跑要加 -update）: %v", err)
	}
	if !bytes.Equal(got, want) {
		t.Errorf("响应体和快照不一致\n--- 快照里是 ---\n%s\n--- 现在是 ---\n%s", want, got)
	}
}
```

```bash
go test ./internal/api/ -update     # 生成/更新快照
go test ./internal/api/            # 平时：读文件比较
```

⭐ **第一次跑必然失败**（文件不存在），报错会提示你加 `-update`。
这是刻意的——不让它自动创建，是为了让你意识到**「我正在定下一份契约」**。

**③ 之后每次 `go test` 就是读文件、逐字节比。** 毫秒级，没有魔法。

### 6.2 它抓得到手写断言抓不到的东西

把 `total_cents` 改名成 `amount`、再加一个内部字段 `risk_score`，实测报告：

```
--- 快照里是 ---          --- 现在是 ---
"total_cents": 2250       "amount": 2250
                          "risk_score": 0
```

⚠️ **这两个改动手写断言都可能漏掉**：

- **改名** —— 只有恰好断言了 `m["total_cents"]` 才会红；只断言 id/customer 就过了
- **加字段** —— **所有现有断言照样通过**，而客户端已经多收到一个内部字段了

⭐ golden file 把**整个响应体当成一个整体**比较，任何变化都显形。

### 6.3 ⭐ 真正的价值：让契约变更出现在 `git diff` 里

因为快照文件提交进了仓库，改完 `-update` 之后 `git diff` 会显示：

```diff
-  "total_cents": 2250,
+  "amount": 2250,
+  "risk_score": 0,
```

⭐ **reviewer 看到 `testdata/` 里有 diff，立刻会问「这是要让客户端改代码吗？」**

手写断言做不到这一点——它们的 diff 在测试文件里，看起来像「测试也跟着改了」，
而不是「**契约变了**」。

### 6.4 ⚠️ 它不是契约测试

很容易把 golden file 当成契约测试。**它不是。**

> ⭐ **golden file 保证的是「和上次一样」，不是「和约定一样」。**

严格说它是**回归测试（regression test）**：

| | golden file | 契约测试 |
|---|---|---|
| 真相来源 | **现在的实际输出** | **事先约定的规格** |
| 谁定的 | 提供方（你跑 `-update`） | 消费方声明需求 / 双方协商的 schema |
| 失败的含义 | 「变了」 | 「**违约了**」 |
| 能发现「一开始就错了」吗 | ❌ | ✅ |
| 加一个可选字段 | ❌ **报错**（噪音） | ✅ 通过（向后兼容） |

#### 第四行的实验

假设 D14 那个 bug 5（`Create` 的 `RETURNING` 漏了 `status`）**还没修**的时候就建了快照：

```
快照里现在是:  "status": "",
之后每次跑:    ok    0.490s
```

⚠️ **绿的。bug 被固化成了期望值**，而且从此再也不会被发现 ——
**哪天有人把 bug 修好了，这个测试反而会变红。**

`-update` 那一刻你写下的不是「应该是什么」，只是「现在是什么」。

### 6.5 三种东西，别混

| 工具 | 回答什么问题 |
|---|---|
| **golden file** | 「输出和上次一样吗」—— 回归 |
| **JSON Schema / OpenAPI 校验** | 「输出符合规格吗」——`id` 必须存在且是整数、`status` 只能是那四个值 |
| **契约测试**（Pact 那类） | 「**消费方实际需要的**字段我都提供了吗」—— 消费方驱动 |

第三类在 Go 项目里不常见（要双方都接入）。**第二类才是 golden file 的天然搭档**：

- golden file 看不见「一开始就错了」
- schema 看不见「改名了但仍然合规」（`total_cents` → `amount`，两个都是整数，schema 可能都过）

⭐ 又是 §2.4 那条：**让盲区互相覆盖。**

### 6.6 所以怎么用它

把定位想清楚：

> ⭐ **它是一个「变更检测器」，不是「正确性判据」。**

实践顺序：

1. **先用别的测试确认输出是对的**（手写断言、集成测试）
2. **然后**建快照，锁住「已经确认过的正确输出」
3. 之后它只干一件事：**任何变化都让你看见**

⚠️ **别在「还没验证过正确性」的时候建快照。** D14 那 6 个 bug 里，
bug 4 和 5 如果在修之前建了快照，就会被固化进去。

### 6.7 ⚠️ 两条纪律

**① 不稳定的值必须固定住。**

```go
CreatedAt: time.Date(2026, 1, 1, 10, 0, 0, 0, time.UTC),   // ⭐ 不是 time.Now()
```

用 `time.Now()` 的话每次跑都不一样，快照永远对不上。随机 ID、map 遍历顺序同理。

**② `-update` 之后必须看 diff。**

这是 golden file 最大的风险：测试红了，顺手 `-update` 一跑就绿了 ——
**你把 bug 固化成了「期望」**。

⭐ **把 `-update` 当成「修改 API 文档」来对待**，不是「让测试闭嘴的开关」。
每次跑完 `git diff testdata/` 看一眼，问自己「这个变化我接受吗」。

## 7. CI：一键跑全部

```yaml
# .github/workflows/ci.yml
name: CI
on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: '1.26'

      - name: 静态检查
        uses: golangci/golangci-lint-action@v6

      - name: 单元测试
        run: go test -race ./...

      # ⭐ testcontainers 在 GitHub Actions 上开箱即用（runner 自带 Docker）
      - name: 集成测试
        run: go test -race -tags=integration ./...

      - name: 覆盖率
        run: go test -coverprofile=coverage.out ./...
```

⚠️ **`-race` 一定要开**。CI 是最适合跑 race detector 的地方——它慢 5–10 倍，
本地嫌烦可以不开，CI 没理由不开。
