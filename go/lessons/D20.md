## 1. 今天要搭的东西

一个 CRD `WebApp`，用户写：

```yaml
apiVersion: apps.golearn.dev/v1alpha1
kind: WebApp
metadata:
  name: golearn-api
spec:
  image: golearn-api:e8c4b99
  replicas: 2
  port: 8080
  healthPath: /healthz
  env:
    DATABASE_URL: postgres://...
```

你的 controller 负责让集群里**一直**有一个对应的 Deployment 和 Service：

```
WebApp（用户写 spec）
  │
  ▼  reconcile
  ├── Deployment   image / replicas / port / probe / env    ──owns──┐
  └── Service      ClusterIP, port → targetPort              ──owns──┤ ownerReference 指回 WebApp
                                                                     │
  ◄── status（controller 写）：readyReplicas / Available / observedGeneration
```

它就是 D19 那个 Helm chart 的 Deployment + Service 那部分，**但从「渲染一次」变成了「持续保证」**：
有人 `kubectl scale` 了 Deployment，Helm 不知道，你的 controller 几百毫秒内改回来。
这是 operator 和 chart 的本质区别（D19 §2.2 说的「持续的」）。

### 1.1 项目在哪、怎么来的

`go/operator/` 是一个**独立的 Go 模块**——kubebuilder 要求自己管一个模块。
我已经跑了两条命令生成骨架：

```bash
kubebuilder init --domain golearn.dev --repo github.com/hzjconan/learn-program-language/go/operator --project-name golearn-operator
kubebuilder create api --group apps --version v1alpha1 --kind WebApp --resource --controller
```

⚠️ 因为是嵌套模块，`go/` 下的 `go test ./...`、golangci-lint、CI **都不会进这个目录**。
operator 有自己的 `Makefile`（`make test` / `make lint`），CI 接进去是 D18 的事。

## 2. API 定义：`webapp_types.go`

### 2.1 CRD 是什么

`kubectl api-resources` 列出的 71 种资源里，`Deployment`、`Pod` 是 API server 编译进去的。
**CRD 让你在运行时往 API server 里注册一种新资源**——之后 `kubectl get webapp`、
`client.Get(ctx, key, &WebApp{})`、watch、RBAC 全部自动可用，API server 替你存到 etcd、做校验、发事件。

你要提供的只有两样：**schema**（字段、类型、校验）和**行为**（controller）。前者就是 types.go。

### 2.2 marker：注释即配置

打开 `api/v1alpha1/webapp_types.go`，每个字段上面那些 `// +kubebuilder:...` 注释是 **controller-gen 读的**，
决定生成的 CRD yaml 长什么样：

| marker | 生成到 CRD 里 | 效果 |
|---|---|---|
| `+kubebuilder:validation:Minimum=0` | `minimum: 0` | API server 拒绝 `replicas: -1`，**你的 controller 不用校验** |
| `+kubebuilder:default=8080` | `default: 8080` | 用户没写 port → 存进 etcd 的对象里就有 8080 |
| `+required` / `+optional` | `required: [image]` | 没写 image → 创建直接 400 |
| `+kubebuilder:subresource:status` | `subresources: {status: {}}` | `/status` 单独一个端点（§4.3） |
| `+kubebuilder:printcolumn:...` | `additionalPrinterColumns` | `kubectl get wa` 显示哪几列 |
| `+kubebuilder:resource:shortName=wa` | `shortNames: [wa]` | `kubectl get wa` |

⭐ **校验和默认值放在 schema 里，不放在 controller 里。** 理由和 D12「配置在边界校验」一样：
坏数据在 `kubectl apply` 那一刻就被拒，controller 拿到的永远是合法对象。
实测：`make manifests` 之后 `config/crd/bases/apps.golearn.dev_webapps.yaml` 第 61–79 行就是这些 default/minimum。

### 2.3 `generation` 和 `observedGeneration`

两个数字，两个写的人：

| 字段 | 谁改 | 什么时候改 |
|---|---|---|
| `metadata.generation` | **API server** | 每次 spec 被修改时 +1（改 status、labels 不算） |
| `status.observedGeneration` | **你的 controller** | 每次 reconcile 完，抄进去「我这次处理的是第几代 spec」 |

它解决的问题：**status 是异步写的，读 status 的人怎么知道它是「新鲜」的？**

```
用户 apply v1 spec        generation=1   observedGeneration=0   ← status 还是空的，别信
controller reconcile 完   generation=1   observedGeneration=1   ← 一致：status 说的就是这份 spec ✅

用户改 replicas 2→5       generation=2   observedGeneration=1   ← ⚠️ 不一致：Available=True 说的是
                                                                   【上一代】spec，已经过时
controller reconcile 完   generation=2   observedGeneration=2   ← 又一致了
```

没有这个字段，看到 `Available: True` 你分不清「当前 spec 已满足」和「上一版满足了、新的还没处理」。
有了它判断只有一行：

```
observedGeneration == generation  →  status 可信
observedGeneration <  generation  →  controller 还没追上，等
```

`kubectl rollout status` 等 Deployment 就是先等 `observedGeneration` 追上 `generation`，再看 `readyReplicas`；
D19 的 `helm --wait` 底下也是它。controller-manager 追得快，健康集群里肉眼看不到那个不一致的瞬间——
但 controller 挂了或忙不过来时，**这个差值就是「apply 了怎么没生效」的第一线索**。

对应练习：`Reconcile` 第 ④ 步 `app.Status.ObservedGeneration = app.Generation`；
`TestReconcile_SetsStatus` 要断言它等于 `app.Generation`。

⚠️ 一个前提：CRD 开了 `+kubebuilder:subresource:status`，API server 才会「只在 spec 变时」加 generation——
这是那个 marker 除了分开读写端点之外的第二个作用。

## 3. ⭐ controller-runtime：informer 重讲

D19 §4.4 那张图是 client-go 的裸件。controller-runtime 把它们包成三个概念，**名字换了，东西没换**：

```
D19 §4.4（client-go）                 controller-runtime（今天）
─────────────────────────────────    ─────────────────────────────────
Reflector + Indexer（本地缓存）       Manager.GetCache()  ── 每种你 For/Owns/Watches 的类型一个 informer
Lister.Get（读缓存）                  r.Get / r.List      ── ⭐ 默认读缓存，不打 API server
workqueue                             controller 内部，看不见，但 Result / error 就是在操作它
worker → syncHandler(key)             Reconcile(ctx, req) ── req 就是那个 key
handleErr: AddRateLimited / Forget    return err → 限速重入队；return nil → Forget
EventHandler 里 queue.Add(key)        For() / Owns() / Watches() 的接线
```

### 3.1 Manager：一个进程里所有 controller 共享的东西

```go
mgr, _ := ctrl.NewManager(cfg, ctrl.Options{Scheme: scheme, ...})
(&WebAppReconciler{Client: mgr.GetClient(), Scheme: mgr.GetScheme()}).SetupWithManager(mgr)
mgr.Start(ctx)
```

它持有：**共享缓存**（所有 informer）、一个**读缓存写直连的 client**、leader election、
`/healthz` `/metrics` 端点。`cmd/main.go` 就是这些，读一遍，和你 D14 的 `main.go` 对照——同一种文件。

### 3.2 `For` / `Owns`：informer 是在这里被创建的

```go
ctrl.NewControllerManagedBy(mgr).
    For(&appsv1alpha1.WebApp{}).      // ① 主资源：WebApp 变 → 入队【它自己的】key
    Owns(&appsv1.Deployment{}).        // ② 子资源：Deployment 变 → 顺着 ownerReference 找父 → 入队【父的】key
    Owns(&corev1.Service{}).
    Complete(r)
```

每一行都让 Manager 为那个类型起一个 informer（List + Watch，本地缓存），并挂一个事件处理器。
区别只在**入队哪个 key**：

- `For`：对象自己的 `namespace/name`
- `Owns`：读对象的 `ownerReferences`，找 `controller: true` 那条，入队**父对象**的 `namespace/name`

⭐ 所以 `Owns(&appsv1.Deployment{})` 的完整含义是：「**任何** Deployment 变化时，如果它的 controller owner 是 WebApp，就 reconcile 那个 WebApp」。
没有这行，有人 `kubectl delete deploy golearn-api`，你的 controller **永远不会知道**——
它不 watch Deployment，也没有定时器。这是练习里 `Owns` 留成 TODO 的原因：**先感受一下没有它会怎样**（§7 ③ 有实验）。

### 3.3 `r.Get` 读的是缓存 —— 两个后果

**① 快、不打 API server。** 一万个 WebApp 每秒 reconcile 也不会压垮集群。这是 D19 §4.3 informer 存在的理由。

**② ⚠️ 可能是旧的。** 你 `r.Update(ctx, deploy)` 之后立刻 `r.Get`，拿到的可能还是更新前的——
watch 事件还没到、缓存还没更新。所以：

- **不要在一次 reconcile 里「写完再读回来验证」**。写完就 return，下一次 reconcile（由写触发的事件）自然会看到新状态。
- 测试里用的 `k8sClient` 是 `client.New(cfg)` 直连的，没有缓存，所以测试里读写是一致的。**这是测试和生产的一个真实差别**，D15 §2 又一次。

### 3.4 `Result` 和 `error`：你在操作 workqueue

| return | 含义 | 对应 D19 §5.3 |
|---|---|---|
| `Result{}, nil` | 这次完了，等下次事件 | `Forget(key)` |
| `Result{}, err` | 失败，**指数退避**重试（5ms → 10ms → … → 16 分钟上限） | `AddRateLimited(key)` |
| `Result{RequeueAfter: 30s}, nil` | 成功，但 30 秒后再看一眼（等外部系统之类） | 定时 `AddAfter` |

⭐ 本课的 reconcile **不需要 `RequeueAfter`**：Deployment Ready 了会产生事件，`Owns` 把它路由回来。
用 `RequeueAfter` 轮询是 edge-triggered 思维的残留——除非你等的东西**不在集群里**（外部 API），否则不用。

⚠️ 返回 `err` 的代价：日志里一条 ERROR + 退避。对「对象不存在」这种**正常情况**返回 err 是错的——
它会一直重试一个永远不会出现的对象。NotFound 要 `return Result{}, nil`。

### 3.5 一次完整的事件流（对着日志看）

`make run` 起 controller，另一个终端 `kubectl apply` 一个 WebApp，日志会是：

```
WebApp 创建 → For 的 informer 收到 ADDED → 入队 default/golearn-api
  → Reconcile #1：Get WebApp → Create Deployment → Create Service → Status().Update → return
Deployment 创建 → Owns 的 informer 收到 ADDED → 找 owner → 入队 default/golearn-api
  → Reconcile #2：Get WebApp → Deployment 已存在且一致（无写）→ Service 一致 → status 不变 → return
WebApp status 更新 → For 收到 MODIFIED → 入队
  → Reconcile #3：全部一致，无写 → return
Deployment 的 Pod Ready → Deployment.Status 变 → Owns 收到 MODIFIED → 入队
  → Reconcile #4：readyReplicas 变了 → Status().Update → return
  → Reconcile #5（由 #4 的 status 写触发）：一致，无写 → 收敛 ✅
```

⭐ 注意 **#2、#3、#5 都是「什么都没改」的空转**——这是正常的，也是幂等为什么重要：
如果 #2 有写，就会触发 #3 有写，触发 #4 有写……**永不收敛**。
练习的 `TestReconcile_IsIdempotent` 用 `resourceVersion` 抓的就是这个。

## 4. ⭐ 一个收敛的 reconcile —— 今天的题眼

`webapp_controller.go` 的 `Reconcile` 注释里有五步。这里讲每一步**为什么这样写**。

### 4.1 取主资源，NotFound 是正常路径

```go
var app appsv1alpha1.WebApp
if err := r.Get(ctx, req.NamespacedName, &app); err != nil {
    return ctrl.Result{}, client.IgnoreNotFound(err)   // NotFound → nil；其它 → err 重试
}
```

被删了什么都不用做：子资源有 ownerReference，**K8s 的 GC controller 替你级联删除**。
这是「不写删除逻辑」的前提——只要 ownerReference 挂对了。

### 4.2 ⭐ `CreateOrUpdate` + 只改你管的字段

```go
deploy := &appsv1.Deployment{ObjectMeta: metav1.ObjectMeta{Name: app.Name, Namespace: app.Namespace}}
_, err := controllerutil.CreateOrUpdate(ctx, r.Client, deploy, func() error {
    desired := desiredDeployment(&app)
    deploy.Labels = desired.Labels
    deploy.Spec.Replicas = desired.Spec.Replicas
    deploy.Spec.Selector = desired.Spec.Selector          // ⚠️ 创建后不可变，改了 Update 会 422
    deploy.Spec.Template = desired.Spec.Template
    return controllerutil.SetControllerReference(&app, deploy, r.Scheme)
})
```

`CreateOrUpdate` 的流程：`Get` → 不存在就跑 mutateFn 然后 `Create`；存在就跑 mutateFn，
**比较前后有没有变**，变了才 `Update`。所以**收不收敛完全取决于 mutateFn**。

⚠️ **整个覆盖 `deploy.Spec = desired.Spec` 会怎样？** 实测（envtest，连跑 3 次）：

```
第 1 次: created   resourceVersion=218
第 2 次: updated   resourceVersion=218    ← CreateOrUpdate 报了 updated，但服务端没写
第 3 次: updated   resourceVersion=218
```

客户端比较时 desired 里没有 API server 填的默认值（`strategy`、`progressDeadlineSeconds`、
`terminationGracePeriodSeconds`、`imagePullPolicy`……），所以每次都「不一样」→ 发 PUT。
但 **API server 对内容没变的 PUT 做 no-op**：填完默认值和存的一样 → 不写 etcd、不改 resourceVersion、不发事件。
所以它**不会**死循环——代价是每次 reconcile 白发一个 PUT，日志和指标里全是 `updated`，
你分不清「真改了」和「空转」。

**真正会死循环的是 desired 本身不确定**：`Env` 直接 `range` map，每次顺序不同 → 内容真的变了 →
`generation` +1 → Pod 滚动重启 → `Owns` 事件 → 再 reconcile → 再滚动。
**每次 reconcile 都要算出字节级相同的 desired**——map 排序、不用 `time.Now()`、不用随机数。

两档写法：

**A. 整块赋 Template**（先这么做）——正确、收敛（靠服务端 no-op），代价是 `updated` 噪音：

```go
deploy.Labels = desired.Labels
deploy.Spec.Replicas = desired.Spec.Replicas
deploy.Spec.Template = desired.Spec.Template
if deploy.CreationTimestamp.IsZero() {          // ⚠️ Selector 只在创建时设，之后不可变（改了 Update 会 422）
    deploy.Spec.Selector = desired.Spec.Selector
}
```

**B. 只抄叶子字段**——`CreateOrUpdate` 能真的报 `unchanged`，日志里的 `updated` 一定是真更新：

```go
tmpl := &deploy.Spec.Template
tmpl.Labels = desired.Spec.Template.Labels
if len(tmpl.Spec.Containers) != 1 || tmpl.Spec.Containers[0].Name != "app" {
    tmpl.Spec.Containers = []corev1.Container{{Name: "app"}}
}
c, want := &tmpl.Spec.Containers[0], &desired.Spec.Template.Spec.Containers[0]
c.Image, c.Ports, c.Env, c.ReadinessProbe = want.Image, want.Ports, want.Env, want.ReadinessProbe
```

`ImagePullPolicy`、`RestartPolicy`、`DNSPolicy` 这些**不设**，保留服务端填的值。
两档都要：探针的 `TimeoutSeconds/PeriodSeconds/SuccessThreshold/FailureThreshold` 要么不设、要么设成服务端默认（1/10/1/3）。

> 另一条路：**Server-Side Apply**（`client.Apply` + `FieldOwner`），把「哪些字段归我管」交给 API server 记账。
> controller-runtime v0.25 支持，是更现代的做法，但概念多一层。本课先用 CreateOrUpdate 把问题看清楚，D21 之后有兴趣再换。

### 4.3 status 走子资源

```go
app.Status.ObservedGeneration = app.Generation
app.Status.ReadyReplicas = deploy.Status.ReadyReplicas
meta.SetStatusCondition(&app.Status.Conditions, metav1.Condition{
    Type:    appsv1alpha1.ConditionAvailable,
    Status:  metav1.ConditionTrue,          // 或 False
    Reason:  "ReplicasReady",              // ⚠️ CamelCase，机器读的
    Message: fmt.Sprintf("%d/%d ready", ready, want),   // 人读的
})
if err := r.Status().Update(ctx, &app); err != nil {
    return ctrl.Result{}, err
}
```

三个点：

- **`r.Status().Update` 不是 `r.Update`**。前者打 `/status` 子端点，**只写 status，忽略 spec 的变化**；
  后者打主端点，**只写 spec/metadata，忽略 status**。用错了不报错，就是没生效——排查起来很诡异。
  这就是 `+kubebuilder:subresource:status` 那个 marker 的作用，也是 D19 §2.3 ④ 在 API 层的强制实施。
- **`meta.SetStatusCondition`** 处理去重（同 Type 只留一条）和 `LastTransitionTime`（Status 没变就不更新时间）。
  手写 append 会越写越多。
- **Update 可能 409**（有人同时改了 status）——直接 `return err`，下次 reconcile 重来。
  不用 `RetryOnConflict`，因为 reconcile 本身就是重试循环。

### 4.4 每次只做一步

Deployment 建好了不等它 Ready，`return`。等它 Ready 是**事件**的事（§3.5 的 #4）。
在 reconcile 里 `time.Sleep` 或 `wait.Poll` 是把 worker 卡住——controller-runtime 默认一个 controller **只有 1 个 worker**
（`MaxConcurrentReconciles`），你卡 30 秒，其它所有 WebApp 都等 30 秒。

### 4.4b ⭐ 「写成功」≠「最终成功」：K8s 是一个数据库加一群 worker

把 K8s 拆开看：

```
API server + etcd        ← 一个带校验的【对象数据库】
controller-manager       ← 一群 watch 数据库、往里写别的记录的 worker（Deployment → ReplicaSet → Pod）
scheduler                ← 也是 worker：给 Pod 记录填 nodeName
kubelet                  ← 节点上的 worker：看到 Pod 记录就起容器
你的 controller          ← 也是 worker：读 WebApp 记录，写 Deployment / Service 记录
```

**worker 之间从不直接通信，只通过数据库里的对象。** 所以 `CreateOrUpdate` 返回 nil 的含义只有一个：
**意图已记录**——Deployment 这条记录写进 etcd 了。后面 ReplicaSet 建不建得出、Pod 调不调度得上、
镜像拉不拉得下来、探针过不过，全是别的 worker 的事，可能在几秒到几分钟后失败，你的 reconcile 早就 return 了。

「成功」是分层的：

| 层 | 含义 | 谁告诉你 |
|---|---|---|
| `CreateOrUpdate` 返回 nil | 意图存进去了 | 返回值 |
| Deployment 真的有 2 个 Ready Pod | 意图实现了 | `deploy.Status.ReadyReplicas`——**下一次** reconcile 才看得到 |
| Pod 起不来 | 意图实现失败 | Pod 的 `ImagePullBackOff` / `Unschedulable` → Deployment 的 `Progressing=False` |

⭐ **K8s 里没有任何一个写调用能告诉你「最终成功」，`kubectl apply` 也不能。** 想知道结果，看 status。
这就是 status 和 condition 存在的理由（§4.3），也是 D19 §2.4 那句「apply 返回 200 只是存进了 etcd」在你自己代码里的体现。

三个推论：

- 第一次 reconcile 写出 `Available=False, 0/2 replicas ready` 不是 bug，是诚实。等 Pod 起来 → Deployment.status 变 → `Owns` 事件 → 再 reconcile → True。
- 用户侧「等最终成功」用 `kubectl wait --for=condition=Available wa/x`，它轮询的就是你写的 condition。`helm --wait` 底下同一种循环。
- 进阶：Deployment 自己的 `Progressing` / `ReplicaFailure` condition 带失败原因（`ProgressDeadlineExceeded` 等），
  reconcile 可以读它们**往上传**到 WebApp 的 Message——用户 `kubectl get wa` 就能看到「为什么没好」，不用去翻 Pod。

### 4.5 Finalizer：今天不做，但要知道

如果你的 controller 管的东西**不在集群里**（云上的负载均衡、外部 DNS 记录、数据库 schema），
K8s 的 GC 管不到它。这时用 finalizer：在对象上挂一个标记，删除时 API server **只设 `deletionTimestamp` 不真删**，
你的 reconcile 看到 `deletionTimestamp != nil` → 清理外部资源 → 摘掉 finalizer → 对象才真的消失。

本课两个子资源都在集群里，ownerReference + GC 就够。**判据：有没有 K8s 之外的东西要清。**

## 5. RBAC 和部署

### 5.1 rbac marker

`webapp_controller.go` 上面那几行：

```go
// +kubebuilder:rbac:groups=apps,resources=deployments,verbs=get;list;watch;create;update;patch;delete
// +kubebuilder:rbac:groups=core,resources=services,verbs=get;list;watch;create;update;patch;delete
```

`make manifests` 把它们变成 `config/rbac/role.yaml` 的 ClusterRole。
**你的 controller 碰什么资源、用什么动词，都要在这里声明。**

### 5.2 ⚠️ 本机能跑、集群里 403

`make run` 用**你的 kubeconfig**（kind 的 admin，什么都能做）；
`make deploy` 进集群后用 **ServiceAccount + 上面那个 ClusterRole**。
少一行 marker（比如忘了 `services`），本机全绿，集群里日志一片：

```
ERROR  Reconciler error  ... services is forbidden: User "system:serviceaccount:golearn-operator-system:golearn-operator-controller-manager" cannot create resource "services"
```

`Owns()` 也需要 `list;watch` 权限——informer 要 List+Watch。**每加一种子资源，rbac marker 和 Owns 成对加。**

### 5.3 部署：照着跑，D18 讲

```bash
make install                                  # CRD 装进集群（kubectl apply config/crd）
make run                                      # ① 本机跑 controller，连 kind —— 开发时用这个
# 另一个终端
kubectl apply -k config/samples/
kubectl get wa -w

# ② 真部署进集群（D18 会拆开讲这三步）
make docker-build IMG=golearn-operator:dev
kind load docker-image golearn-operator:dev --name golearn
make deploy IMG=golearn-operator:dev
kubectl -n golearn-operator-system logs deploy/golearn-operator-controller-manager -f
```

用户的决定（LEARNING-PLAN §0'）：**这三条命令今天只用，不展开**。
但你已经能认出它们各是什么：`docker-build` = D14 的多阶段构建，`kind load` = D19 的那个，
`deploy` = `kustomize build config/default | kubectl apply`。

## 6. 测试：envtest

`suite_test.go` 的 `TestMain` 起一个 **envtest**：真的 `kube-apiserver` + `etcd` 二进制（`make setup-envtest` 下载到 `bin/k8s/`），
**没有** kubelet / scheduler / controller-manager。所以：

| 能测 | 不能测 |
|---|---|
| CRD 校验、默认值真的生效了 | Pod 真的起来 |
| Reconcile 建/改了什么对象 | Deployment 的 `ReadyReplicas` 会自己变 |
| ownerReference、status 子资源 | GC 级联删除（没有 GC controller） |

按 §4.4b 的拆法，envtest = **只有数据库，没有 worker**。所以 `CreateOrUpdate` 一个 Deployment 照样成功——
那只是往 etcd 写一条记录；不会有 ReplicaSet、Pod，`Status.ReadyReplicas` 永远是 0，级联删除也不发生。
测试里**唯一在跑的 worker 是你的 reconciler，而且是测试代码手动调的**（`r.Reconcile(ctx, req)`），
没有 Manager、没有 informer、没有队列——和 D14 §6「直接调 handler，不起 http.Server」同一个取舍。

`r.Get` 在测试里也不是假的：`WebAppReconciler.Client` 是嵌入的接口，`main.go` 塞的是 `mgr.GetClient()`（读缓存），
测试塞的是 `client.New(cfg)`（直连 envtest）——D14 §2 的构造函数注入，两个都是真 client，只差有没有缓存。
CRD 是 `TestMain` 里 `CRDDirectoryPaths` 从 `config/crd/bases/` 装进去的，所以 `make test` 依赖 `manifests`。

结构和 D15 的 testcontainers 一样：起环境 → `m.Run()` → 清理 → `os.Exit`。
kubebuilder 默认生成 Ginkgo 套件，我换成了标准 `testing`——少学一个框架，D15 的习惯直接用。

**测试策略：直接调 `Reconcile`，不起 Manager**（`webapp_controller_test.go` 顶部注释）。
同步、确定、一次一步；Manager 的接线留给真集群验。

⭐ **幂等测试用 `resourceVersion`**：`Reconcile` 两次，Deployment 的 `resourceVersion` 不变 = 第二次没写。
这是 D19 §3.3 的知识在测试里的用法。
