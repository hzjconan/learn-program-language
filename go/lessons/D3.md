## 1. slice 到底是什么

D2 §2.6 说过了，这里展开：**slice 变量是一个三字段的 struct**，24 字节。

```
[ 指向底层数组的指针 | len | cap ]
```

- `len`：当前有多少个元素，`s[i]` 只能访问 `i < len`
- `cap`：**从 slice 的起点数到底层数组末尾**有多少个位置

```go
arr := [6]int{0, 1, 2, 3, 4, 5}
s := arr[1:4]
// s = [1 2 3]   len=3   cap=5
```

**`cap` 是 5 不是 3** —— 从下标 1 数到数组末尾还有 5 个位置。这个「多出来的 2 个位置」就是所有 slice 事故的源头：**`s` 有能力通过 `append` 覆盖 `arr[4]`。**

### 那「起点」存在哪？

header 只有三个字段，没有 offset —— **因为指针指向的不是数组开头，是【切片自己的第 0 个元素】。起点已经编码在指针值里了。**

实测（`int` 占 8 字节，相邻元素地址差 8）：

```
&arr[0] = 0x...8030
&arr[1] = 0x...8038
&arr[3] = 0x...8048

arr[0:3]   ptr=0x...8030  len=3 cap=6      ← ptr == &arr[0]
arr[1:4]   ptr=0x...8038  len=3 cap=5      ← ptr == &arr[1]
arr[3:6]   ptr=0x...8048  len=3 cap=3      ← ptr == &arr[3]

header 一共 24 字节（3 个字长）
```

`s[0]` 就是 `*ptr`，`s[i]` 就是 `*(ptr + i*元素大小)`。由此推出三件事：

**① 切片不知道自己前面还有东西。** `arr[1:4]` 到手后只知道「我从这里开始，往后还有 5 个位置」，**完全不知道自己是从哪个数组的第几位切出来的** —— 那个信息在切的那一刻就丢了。所以切片是**单向**的，`s[-1]` 连语法都不合法。

**② `cap` 的定义因此变得自然**：从**我的起点**数到底层数组末尾。切片只认得自己的起点。

**③ 内存泄漏的原理也在这里**（§4 会展开）：**GC 的回收单位是「整个分配块」，不是「你指着的那一小段」。** 只要有一个指针落在那块内存里——哪怕指着中间——整块就活着。

> Java 的 `List` 也有 capacity，但它是私有的实现细节，你拿不到、也影响不了别人。**Go 的 cap 是公开语义，而且多个 slice 可以共享同一个底层数组** —— 这是 Java/TS 里完全没有的概念。

## 2. 核心陷阱：`append` 有时扩容，有时不扩容

这是今天最重要的一节。`append` 的行为是**条件性的**：

- **`cap` 还有富余** → 直接写进底层数组的空位，**返回的 slice 和原来共享同一块内存**
- **`cap` 满了** → 分配一块更大的新数组，**把数据拷过去，和原来的联系彻底断开**

跑 demo 看两种情况：

### ② cap 有富余 —— 改的是同一块内存

```
append 前: arr=[0 1 2 3 4 5]  s=[1 2 3] (len=3 cap=5)
append 后: arr=[0 1 2 3 999 5]  s=[1 2 3 999]
                        ^^^
```

`arr[4]` 被 999 覆盖了。你以为只是往 `s` 里加了个元素。

### ③ cap 满了 —— 偷偷搬家

```
append 前: arr=[0 1 2 3]  s=[1 2 3] (len=3 cap=3)  地址 0x...a008
append 后: arr=[0 1 2 3]  s=[1 2 3 999] (len=4 cap=6)  地址 0x...40f0
```

`arr` 毫发无伤，因为 `s` 已经搬到别的地址去了。

### ⚠️ 真正可怕的地方

**②和③的代码写法一模一样，行为却相反。**

到底走哪条路，取决于**运行时 cap 够不够** —— 而 cap 取决于这个 slice 是怎么来的、之前 append 过几次、扩容策略当时给了多少。

这就是为什么 slice 事故：

- 本地测试跑不出来（数据量小，cap 恰好够/恰好不够）
- 线上偶发（数据量一变，走了另一条分支）
- 加个日志就好了（改变了分配行为）

**记住这条：`append` 的返回值是唯一可信的东西，其他任何指向那块内存的 slice 都可能已经被污染或已经失效。**

### 扩容策略（了解即可，别依赖）

Go 1.18 之后大致是：容量小于 256 时翻倍，之后按 1.25 倍左右平滑增长，最后还要按元素大小做内存对齐。**具体数字是实现细节，各版本都在调**。demo 里 `cap=3` 扩容后变成 6，你在别的版本上可能看到别的数。

**结论：永远不要写依赖具体 cap 值的代码。**

## 3. 三个自保手段

### ① 三索引切片 `s[a:b:c]`

```
s[a : b : c]      len = b - a      cap = c - a
```

**`a`、`b`、`c` 全是【相对底层数组起点的下标】，而 len/cap 是【相对切片起点的长度】** —— 所以都要减掉 `a`。

```
arr[1:4]       → len=3 cap=5      不写 c，cap 一直到数组末尾
arr[1:4:4]     → len=3 cap=3      4-1
arr[1:4:6]     → len=3 cap=5      6-1
arr[0:2:6]     → len=2 cap=6      6-0  ← 起点是 0 时 cap 才等于第三个数
arr[3:3:3]     → len=0 cap=0      全空也合法
```

还有个约束：**`0 ≤ a ≤ b ≤ c ≤ cap(原)`**。所以三索引只能**缩小** cap，不能凭空扩大——它的用途就是「主动放弃我本来能访问到的那部分」。越界会 panic：

```
arr[1:4:10] → runtime error: slice bounds out of range [::10] with length 6
arr[1:2:1]  → runtime error: slice bounds out of range [:2:1]     （c < b，cap 不能小于 len）
```

> **记法：三个数是「切到哪」，len/cap 是「有多长」。从下标换算成长度，一律减起点。**

```go
s := arr[1:4:4]    // len=3, cap=3 —— cap 焊死
s = append(s, 999) // cap 已满 → 必然分配新数组
```

```
append 后: arr=[0 1 2 3 4 5]  s=[1 2 3 999]     ← arr 毫发无伤
```

**什么时候必须用**：当你把一个内部数组的子切片返回给外部时。

```go
func (b *Buffer) Bytes() []byte {
	return b.buf[:b.n:b.n]    // ⭐ 不加第三个索引，调用方 append 就能踩烂你的缓冲区
}
```

### ② `slices.Clone` —— 要独立就明确拷贝

```go
out := slices.Clone(s)     // 1.21+，等价于 append([]T(nil), s...)
```

**默认选它。** 除非你在写热点路径且用 benchmark 证明了拷贝是瓶颈，否则「省一次拷贝」换来的是一个随时会炸的别名 bug，不划算。

### ③ `copy(dst, src)`

按元素拷贝，返回实际拷贝的个数（`min(len(dst), len(src))`）。

```go
dst := make([]int, 3)
n := copy(dst, src)        // n = 3
```

注意 **`copy` 只拷贝 `len` 个，不看 cap**。`copy(make([]int, 0, 100), src)` 拷贝 0 个 —— 这是新手常见错误。

## 4. 四个必须认识的经典事故

### ⑤ `s[:0]` 复用陷阱

网上到处能搜到的「零分配过滤」写法：

```go
out := s[:0]                 // 复用底层数组
for _, v := range s {
	if keep(v) { out = append(out, v) }
}
return out
```

```
原始 src = [1 2 3 4 5 6]
过滤结果 = [2 4 6]        ← 看着对
但 src  = [2 4 6 4 5 6]   ← 调用方的数据被就地改写了！
```

**这个写法本身不是错的** —— 在你**拥有**那个 slice 的场合（比如复用一个内部 buffer）它是合法优化。**错的是把它用在别人传进来的参数上。**

> 判断标准：**这块内存是我的吗？** 不是我的，就别原地改。

今天的主练习 `Filter` 就是要你写出**不犯这个错**的版本，测试会验。

### `Delete` 的经典写法会改坏入参

```go
func Delete(s []int, i int) []int {
	return append(s[:i], s[i+1:]...)   // ⚠️ 就地移动，s 被改写
}
```

**关键在于 `s[:i]` 的 cap 不是 `i`。** 它省略了第三个数，所以 cap 保持原样（§3.1 的公式）：

```
s = [1 2 3 4 5]  len=5 cap=5，删下标 2

① head := s[:2]  = [1 2]  len=2 cap=5   ← cap 还是 5！它有权限写到下标 2、3、4
② tail := s[3:]  = [4 5]

③ append(head, tail...) —— head 的 cap 够（5 ≥ 2+2），不扩容，直接往原数组写：
     下标 2 ← tail[0] = 4     （原来的 3 被覆盖）
     下标 3 ← tail[1] = 5     （原来的 4 被覆盖）
     下标 4  没人动它，还是旧的 5

   底层数组: [1 2 3 4 5]  →  [1 2 4 5 5]
```

**为什么「看着是对的」：**

```
返回值 got = [1 2 4 5]      len=4   ← 完全正确
调用方的 s = [1 2 4 5 5]    len=5   ← 但它还是 len=5，看得见那条尾巴
```

返回的 `got` 是同一个数组的 `[0:4]`，len 少了 1，**正好把尾巴挡在视野之外**。所以你测返回值怎么测都对。

**危害不只是「多个尾巴」——中间的元素全被移动了。** 如果调用方还持有别的视图：

```go
s := []int{1, 2, 3, 4, 5}
view := s[2:4]        // [3 4]，某处保存的一个视图
Delete(s, 2)          // 就地移动
// view 现在是 [4 5] —— 它什么都没做，内容却变了
```

这类 bug 极难定位：肇事代码和出问题的代码可能隔着好几个函数。

> **标准库的 `slices.Delete` 也是就地修改**，但从 Go 1.22 起会把尾巴清成零值：
> `slices.Delete([1 2 3 4 5], 2, 3)` 之后调用方的 s 是 `[1 2 4 5 0]` 而不是 `[1 2 4 5 5]`。
> `go doc slices.Delete` 原文：*"Delete zeroes the elements s[len(s)-(j-i):len(s)]"*。
>
> **清零是为了防内存泄漏** —— 元素是指针时，留着旧值意味着被「删掉」的对象仍被数组引用，GC 回收不了。和「子切片拖住底层数组」是同一类问题。
> 但**「会改坏调用方的 s」这条一点没变**，标准库只是把泄漏堵上了。

**用之前先想清楚：你是想改，还是想要个新的。** 本练习要的是后者：

```go
out := make([]T, 0, len(s)-1)     // 自己的内存
out = append(out, s[:i]...)
out = append(out, s[i+1:]...)
return out
```

### ⑥ 子切片拖住整个底层数组（内存泄漏）

```go
big := make([]byte, 10<<20)   // 10MB
small := big[:3]              // 只要 3 个字节
```

```
small = [0 0 0]  len=3 cap=10485760
  ⚠️ 只要 small 活着，那 10MB 就回收不了
```

**GC 回收的是整个底层数组，不是「你用到的那一小段」。** 典型场景：读了一个大文件/大响应体，只留了里面的几十字节，结果整块内存永远不释放。

修法：

```go
safe := make([]byte, 3)
copy(safe, big)               // 或 slices.Clone(big[:3])
```

> 这是**唯一一个「拷贝反而省内存」**的场合，值得单独记住。

### 函数参数里的 append 看不见

D2 §2.6 讲过，这里再强调一次：

```go
func addItem(s []int) { s = append(s, 1) }   // 调用方完全看不到
```

**惯用做法是返回新 slice**：`func addItem(s []int) []int`。

## 5. `map`

### 遍历顺序是【故意】随机的

```
第 1 次遍历: k3 k4 k5 k6 k7 k8 k2 k9 k0 k1
第 2 次遍历: k1 k3 k4 k5 k6 k7 k8 k2 k9 k0
第 4 次遍历: k9 k0 k1 k3 k4 k5 k6 k7 k8 k2
```

**不是「碰巧无序」，是运行时每次都随机一个起点。** Go 团队故意这么做，就是为了让「依赖 map 顺序」的代码尽早暴露 —— 早年 Go 的 map 遍历顺序是稳定的，导致大量代码悄悄依赖了它，后来改哈希实现就全炸了。

要确定顺序，自己排：

```go
keys := slices.Sorted(maps.Keys(m))   // 1.23+，一行搞定
for _, k := range keys { ... }
```

### 三个硬性限制

**① nil map 可读不可写**（D1 §3 讲过）

```go
var m map[string]int
m["k"]        // OK，返回 0
len(m)        // OK，0
m["k"] = 1    // panic: assignment to entry in nil map
```

**② map 元素不可寻址**

```go
m := map[string]User{}
&m["k"]           // ❌ 编译错误
m["k"].Name = "x" // ❌ 编译错误
```

因为 map 会在扩容时搬迁元素，地址随时会变，Go 干脆禁止取地址。**解法：存指针 `map[string]*User`，或者取出来改完再放回去。**

**③ 并发写直接 panic，不是数据竞争而已**

```
fatal error: concurrent map writes
```

注意是 `fatal error` 不是 `panic` —— **`recover` 接不住，进程必死**。Go 运行时故意这么设计：map 的并发写会破坏内部结构，与其让你带着损坏的数据跑下去，不如立刻停。

并发场景的选择（第 2 周细讲）：`sync.RWMutex` 保护普通 map（默认选它）、或 `sync.Map`（只在「写一次读多次」或「不同 goroutine 操作不相交的 key」时才更快）。

### 逗号 ok

```go
v, ok := m[k]     // ok 区分「值是零值」和「键不存在」
delete(m, k)      // 删除，键不存在也不报错
clear(m)          // 1.21+，清空
```

**遍历时删除当前键是安全的**（规范明确允许），但遍历时新增的键**可能被遍历到也可能不会** —— 别这么干。

## 6. `string`

### string 是不可变的 byte 序列

```go
s := "hello"
s[0] = 'H'    // ❌ 编译错误：cannot assign
```

不可变带来一个好处：**子串共享底层数组，`s[1:3]` 是零拷贝的**（和 slice 一样，但因为不可变所以没有别名风险）。

### `len` 是字节数，不是字符数

```
s = "Go语言"
len(s) = 8          ← 字节数！
[]rune(s) 长度 = 4   ← 这才是字符数
```

UTF-8 里 ASCII 占 1 字节，中文占 3 字节，部分 emoji 占 4 字节。**`len(s)` 对中文永远是错的字符数。**

### 索引给 byte，range 给 rune

```
s[i] 逐字节:  71 111 232 175 173 232 168 128     ← 中文被拆成 3 个字节
range 逐字符: [0]G [1]o [2]语 [5]言              ← 下标是【字节偏移】，会跳跃
```

**两条铁律：**

1. **`s[i]` 返回 `byte`（`uint8`），不是字符。** 对纯 ASCII 才有意义。
2. **`for i, r := range s` 里的 `i` 是字节偏移，`r` 是 `rune`（`int32`）。** 注意 `i` 从 0 跳到 2 再跳到 5 —— 它不是「第几个字符」。

### 切片会切碎字符

```
s[0:2] = "Go"            ← 切在字符边界上，正常
s[0:3] = "Go\xe8"        ← 切进「语」的中间，切出半个字符
s[0:5] = "Go语"          ← 「语」占 3 字节，切到 5 才完整
```

**按字符截断必须先转 `[]rune`**，或者用 `utf8.RuneCountInString` / `utf8.DecodeRuneInString` 算边界。今天的 `TruncateRunes` 练的就是这个。

### `byte` vs `rune`

```go
type byte = uint8    // 别名！不是新类型
type rune = int32    // 别名
```

**注意是 `=`，它俩是类型别名**（D1 §4 讲过 alias 和 defined type 的区别）。`byte` 用于二进制数据，`rune` 用于「一个 Unicode 码点」。

### 转换的拷贝成本

```go
b := []byte(s)      // 拷贝一份（因为 []byte 可变，string 不可变）
r := []rune(s)      // 拷贝 + 解码，成本更高
s2 := string(b)     // 又拷贝一份
```

**这三个都是 O(n) 的分配**，在循环里反复转换是常见的性能问题。编译器对 `for range []byte(s)`、`m[string(b)]` 等少数模式做了优化，其余都是真拷贝。

### 拼接用 `strings.Builder`

```go
// ❌ 循环里 += ：每次都分配一个新字符串，O(n²)
s := ""
for _, x := range items { s += x }

// ✅
var b strings.Builder
for _, x := range items { b.WriteString(x) }
s := b.String()
```

和 Java 的 `String` vs `StringBuilder` 完全一样的道理。

### 主练习 · `slicex`

三个函数，**统一的硬要求：不得修改入参，返回的切片不得与入参共享底层数组。**

- `Filter[T any]` —— 直接针对 `s[:0]` 陷阱
- `Delete[T any]` —— 直接针对 `append(s[:i], s[i+1:]...)` 陷阱
- `Dedup[T comparable]` —— 顺便练 map 做集合

测试会用两种方式验证「没共享」：**改结果看入参变不变**、**往结果里 append 看入参变不变**。第二种能抓住「结果虽然是新的但 cap 伸进了入参数组」这种更隐蔽的情况。

> 关于 `[T any]` 这个语法：那是泛型，D5 才正式讲。今天你只需要知道 **`T` 是个类型占位符，`any` 表示「什么类型都行」，`comparable` 表示「必须支持 == 比较」**（map 的 key 就要求这个）。函数体里把 `T` 当成一个普通类型用就行。
