# D5 · interface 与泛型

> **昨天拆了继承，今天装上它的替代品。**
> Go 的接口和 Java 的 `interface` 长得像，但有一处根本差别，它会改变你摆放代码的方式。
>
> 先跑 `go run ./cmd/ifacedemo`（五分钟），第 ④ 段是今天的题眼，**也是 Go 面试出现率最高的一道题**。

---

## 1. 隐式实现 —— 和 Java 的根本区别

```go
type Stringer interface{ String() string }

type Celsius float64
func (c Celsius) String() string { return fmt.Sprintf("%.1f°C", float64(c)) }
```

`Celsius` 就已经是 `Stringer` 了。**没有 `implements`，没有任何一处声明它俩有关系。**

对比：

| | Java / TS | Go |
|---|---|---|
| 建立关系 | 实现方 `implements Foo` | **不需要声明，编译器结构匹配** |
| 谁先存在 | 接口必须先存在 | **接口可以后加** |
| 加一个接口 | 要改所有实现类的源码 | **一行都不用改** |

D4 小题 B 你已经碰到过这个：`Payer` 是我后定义的，`Contractor` 一行没改就满足了。在 Java 里做不到——除非你能改 `Contractor` 的源码。

> TS 的 `interface` 也是结构化的（duck typing），这点和 Go 一样。**但 TS 是编译期擦除，Go 的接口在运行时是有实体的**（见 §3），这决定了 §4 那个坑的存在。

### 推论：你可以给别人的类型「定义」接口

```go
// 第三方库给你的类型，你改不了源码
type ThirdPartyClient struct{ ... }
func (c *ThirdPartyClient) Do(req *Request) (*Response, error)

// 但你可以在【你自己的包】里定义
type Doer interface{ Do(*Request) (*Response, error) }
```

`*ThirdPartyClient` 自动满足 `Doer`，于是你的代码可以只依赖 `Doer`，测试时换成假的。**这是 Go 里做依赖倒置和打桩的标准手法**，今天的练习就是它。

## 2. 接口由使用方定义 —— 今天最该改变的习惯

Java 的习惯是：**先定义 `UserService` 接口，再写 `UserServiceImpl`**。一个接口一个实现，接口放在实现旁边。

**Go 反过来。**

```go
// ❌ Java 味：实现方定义大接口，然后自己实现
package store
type Store interface {          // 15 个方法
    Get(...); Put(...); Delete(...); List(...); ...
}
type MySQLStore struct{}        // 唯一的实现

// ✅ Go 味：实现方只提供【具体类型】，接口由使用方按需定义
package store
type MySQLStore struct{}        // 就是个 struct，不声明实现什么

package report
type recordGetter interface{    // 使用方定义，小写不导出
    Get(id string) (Record, error)
}
func Build(g recordGetter) ...  // 只依赖它真正用到的那一个方法
```

> **"The bigger the interface, the weaker the abstraction."** —— Rob Pike

两条实践规则：

1. **接口放在使用它的包里**，不放在实现它的包里
2. **接口要小**。标准库的典范：

```go
type error interface{ Error() string }              // 1 个方法
type Stringer interface{ String() string }          // 1 个
type Reader interface{ Read(p []byte) (int, error) }// 1 个
type Writer interface{ Write(p []byte) (int, error)}// 1 个
```

`io.Reader` 一个方法，撑起了整个标准库的 IO 生态——文件、网络、内存缓冲、gzip、加密全都是它。**接口越小，能塞进去的类型越多。**

### 接口组合（D4 §4 的嵌入，用在接口上）

```go
type ReadWriter interface {
    Reader          // 嵌入接口
    Writer
}
```

大接口由小接口拼出来，而不是一开始就写个大的。`io` 包里 `ReadWriter` / `ReadCloser` / `ReadWriteCloser` 全是这么拼的。

### 什么时候才该先定义接口

一条实用判据：**有两个及以上真实实现时才抽接口**（测试替身算半个）。只有一个实现就先别抽——Go 里接口是零成本后加的，不用提前设计。

## 3. 接口值的内部结构：`(类型, 值)` 二元组

这一节是理解 §4 的前提，务必看懂。

**一个接口变量在运行时占两个字长：**

```
接口值 = ( 动态类型 type , 动态值 value )
```

```go
var s Stringer                  // (nil, nil)          ← 零值
s = Celsius(20)                 // (Celsius, 20)
s = (*MyType)(nil)              // (*MyType, nil)      ← ⚠️ 记住这一行
```

对照 D4 的方法集：赋值给接口时，Go 把**具体类型的信息**和**值（或指向值的指针）**一起存进去。方法调用时靠那个动态类型找到真正的函数——**这才是 Go 的动态派发**，而 D4 的嵌入没有这个。

打印出来看：

```go
fmt.Printf("%T %v\n", s, s)     // *main.MyType <nil>
```

`%T` 打的是**动态类型**，`%v` 打的是**动态值**。今天调试接口问题就靠这两个动词（QA #5）。

## 4. ⚠️ `nil` 接口 ≠ 装着 nil 指针的接口 —— 今天的题眼

### 现象

```go
type MyErr struct{}
func (e *MyErr) Error() string { return "boom" }

func mayFail(ok bool) error {
    var e *MyErr            // nil 指针
    if !ok {
        e = &MyErr{}
    }
    return e                // ⚠️ 返回的 error 永远不是 nil
}

err := mayFail(true)        // 没出错
fmt.Println(err)            // boom         ← 打印出来的东西完全不可信，见下
fmt.Println(err == nil)     // false        ← 它不是 nil ！！
```

**调用方的 `if err != nil` 会成立，然后走进错误分支处理一个不存在的错误。**

### ⭐ 先说清楚：`e` 本身不是接口，装箱发生在 `return` 那一行

这一步不说透，后面全是死记硬背。

```go
func mayFail(ok bool) error {   // ← 返回类型是 error，这是个【接口】
    var e *MyErr                // ① e 就是个 *MyErr 指针，值 = nil。此处【没有接口】
    if !ok { e = &MyErr{} }
    return e                    // ② 隐式转换：把 e 装进 error 接口 ← 坑在这一行
}
```

**第 ② 步是隐式的，没有任何语法提示。** 因为签名写的是 `error`，而你 `return` 的是 `*MyErr`，编译器必须在这里做一次转换：

```
        e （*MyErr 类型的变量）
        └── 值：nil
                │
                │  return e  ── 装进 error 接口
                ↓
        接口值 = ( 类型: *MyErr , 值: nil )
                    ↑              ↑
                 从【静态类型】填    从【变量的值】填
                 编译期定死，永远非空   这里是 nil
```

**类型那一格填的是「表达式的静态类型」，编译期就定死了，跟这个值是不是 nil 毫无关系。**

同一个变量，比较结果能反过来——这是最能说明问题的一段：

```go
var e *MyErr
fmt.Println(e == nil)        // true    ← 指针比较

var err error = e            // 装箱
fmt.Println(err == nil)      // false   ← 接口比较。e 一点没变，变的是拿什么去比
```

会发生隐式装箱的位置（都是同一件事）：

| 写法 | 装箱时机 |
|---|---|
| `return e`（返回类型是接口） | return 那一行 |
| `var err error = e` | 赋值那一行 |
| `f(e)`（形参是接口） | 传参那一刻 |
| `[]error{e}` / `map[string]error{...}` | 构造字面量时 |

### 原因

用 §3 的二元组解释，一眼就清楚：

| 表达式 | 类型格 | 值格 | `== nil` |
|---|---|---|---|
| `var e *MyErr` | —（它不是接口，就一个指针） | nil | ✅ true |
| `var err error` | nil | nil | ✅ true |
| `var err error = e` | **`*MyErr`** | nil | ❌ **false** |
| `var err error = &MyErr{}` | `*MyErr` | `0x...` | ❌ false |

**接口只有「类型和值都为 nil」时才等于 nil。** 第 3 行的动态类型是 `*MyErr`，非 nil，所以整个接口非 nil——**尽管它装的值是 nil**。注意第 1 行和第 3 行装的是同一个 nil，结论却相反。

> **和 Java 对比**（你觉得别扭的根源）：
>
> ```java
> MyErr e = null;
> Exception err = e;          // err 就是 null
> System.out.println(err == null);   // true —— Java 里没有这个坑
> ```
>
> Java 的引用变量只存一个地址，null 就是 null，赋给谁都还是 null——**类型信息长在对象自己身上，对象不存在就没有类型信息**。
>
> Go 的接口值是两个字长，**类型格由编译器按静态类型填死，哪怕值格是 nil 也照填**。所以「空指针」和「空接口」在 Go 里是两个不同的状态。

### ⚠️ 打印出来的东西完全不可信（实测，我第一版讲义在这里写错了）

`fmt` 遇到 `error` 会**调用它的 `Error()` 方法**。于是打印结果取决于这个方法碰没碰接收者：

```go
type A struct{ Code int }
func (e *A) Error() string { return "boom" }                          // 不碰接收者

type B struct{ Code int }
func (e *B) Error() string { return fmt.Sprintf("code=%d", e.Code) }  // 解引用了
```

```
var errA error = (*A)(nil)   →  fmt.Println(errA) 打出  boom     ← 方法正常返回了
var errB error = (*B)(nil)   →  fmt.Println(errB) 打出  <nil>    ← 方法 panic 了
```

`errB` 那个 `<nil>` 是 **`fmt` 内部兜的底**：`Error()` 在 nil 接收者上解引用会 panic，`fmt` 捕获这个 panic，发现实参是个 nil 指针，就打了 `<nil>`。**它不是「值是 nil」的意思。**

所以同一个坑，你在日志里可能看到 `boom`、可能看到 `<nil>`、也可能看到 `%!v(PANIC=...)`——**三种都不告诉你这个 error 其实非 nil**。

**唯一可信的两个东西是 `%T` 和 `== nil`：**

```go
fmt.Printf("%v %T %v\n", err, err, err == nil)   // boom *main.A false
//                            ^^^^^^^ 只有这一格能说明问题
```

### 怎么避免

**规则一：函数返回值类型写 `error`，不要写具体的错误类型。**

```go
func Validate(r Record) *ValidationError   // ❌ 埋雷：调用方一转成 error 就中招
func Validate(r Record) error              // ✅
```

**规则二：中间变量是具体类型时，返回前必须显式判断。**

```go
func Save(r Record) error {
    if verr := validate(r); verr != nil {   // verr 是 *ValidationError
        return verr                          // ✅ 只在真的非 nil 时才返回它
    }
    return nil                               // ✅ 显式返回 nil 接口
}
```

**千万别写成 `return validate(r)`** ——这一行就是今天练习里埋的雷。

### 🛠 好消息：这个坑有工具兜底

写 `cmd/ifacedemo` 时 `golangci-lint` 当场就报了：

```
SA4023: badMayFail never returns a nil interface value (staticcheck)
SA4023: this comparison is never true
```

和 D4 那个 `SA4005` 一样——**只要你跑 `make check`，这类经典 bug 抓得住**。演示里那两个函数是加了 `//nolint:staticcheck` 才编过 lint 的。

但别把工具当保险：`staticcheck` 只能识别它能静态推导出「永远非 nil」的情形。中间隔几层函数调用、或者那个具体类型来自另一个包时，它就看不出来了。**规则还是要记在脑子里。**

### 顺带：nil 接收者本身是合法的

```go
var p *MyErr = nil
var err error = p
err.Error()     // 会真的调用 (*MyErr).Error，接收者 p 是 nil
                // 只要方法体不解引用 p 就不 panic（D4 §3 我们验证过）
```

所以这个坑**不会立刻 panic**，它会安安静静地让你的错误处理逻辑走错分支——**症状出现的地方离病根很远**，和我 D4 review 里说的可观测性问题是同一类。

## 5. 类型断言与 type switch

### 类型断言

```go
var v any = "hello"

s := v.(string)         // ⚠️ 断言失败会 panic
s, ok := v.(string)     // ✅ comma-ok：失败时 ok=false，s 是零值
```

**永远用 comma-ok 形式**，除非你能证明它不会失败。我们的 `.golangci.yml` 开了 `errcheck.check-type-assertions: true`，单值形式会被 lint 直接拦下。

断言的目标也可以是**另一个接口**：

```go
if c, ok := v.(io.Closer); ok {   // v 除了当前接口，还实现了 Closer 吗？
    c.Close()
}
```

### ⭐ 可选接口（optional interface）—— 很 Go 的一个模式

标准库大量使用：`http.ResponseWriter` 只有 3 个方法，但如果底层实现还支持 `Flush`，你可以断言出来：

```go
if f, ok := w.(http.Flusher); ok {
    f.Flush()
}
```

**基础能力放接口里，增强能力用断言探测。** 这样接口能保持小，又不丢功能。今天练习里的 `Len` 就是这个模式。

### type switch

```go
func describe(v any) string {
    switch x := v.(type) {
    case nil:                   // ← 注意 nil 是一个独立的 case
        return "nil"
    case int:
        return fmt.Sprintf("int %d", x)         // x 在这里是 int
    case string:
        return fmt.Sprintf("string %q", x)      // x 在这里是 string
    case error:                                 // 接口也能做 case
        return "error: " + x.Error()
    case []int, []string:                       // 多类型 case：x 仍是 any！
        return fmt.Sprintf("slice %v", x)
    default:
        return fmt.Sprintf("其他 %T", x)
    }
}
```

三个细节：

1. `x` 在每个 case 里是**该 case 的类型**——这是 Go 里少见的「同名变量不同类型」
2. **多类型 case 里 `x` 退化成 `any`**，因为编译器无法确定是哪个
3. **case 从上往下匹配**，接口类型的 case 要放在具体类型后面，否则会提前命中

> **警告**：type switch 用多了通常是设计信号。如果你在对自己定义的类型做 type switch，八成应该改成给它们加一个方法。合理场景是处理 `any`（JSON 解码结果、日志字段）或探测可选接口。

## 6. `any` 就是 `interface{}`

Go 1.18 起 `any` 是 `interface{}` 的别名（完全等价，随便用哪个，新代码写 `any`）。

**空接口不代表「任意类型」，它代表「我放弃了类型信息」。** 拿到 `any` 之后你只能断言或反射，两者都是运行时才报错。

```go
func Process(v any)              // ❌ 能编译，运行时炸
func Process[T Number](v T)      // ✅ 泛型：编译期就检查
```

Go 1.18 之前 `any` 是没办法的办法；有了泛型之后，**大部分 `any` 都该换成类型参数**。

## 7. 泛型

### 语法

```go
func Map[T, U any](s []T, f func(T) U) []U {
    out := make([]U, 0, len(s))
    for _, v := range s {
        out = append(out, f(v))
    }
    return out
}

Map([]int{1, 2, 3}, strconv.Itoa)      // 类型推断：T=int, U=string
Map[int, string](nums, strconv.Itoa)   // 也可以显式写，通常不用
```

`[T, U any]` 是**类型参数列表**，`any` 是**约束**。

### 约束是「接口的另一面」

约束就是接口，只是接口里可以写**类型集合**：

```go
type Number interface {
    ~int | ~int64 | ~float64        // 类型集
}

func Sum[T Number](s []T) T {
    var total T                      // 零值
    for _, v := range s {
        total += v                   // 只有约束允许，才能用 +
    }
    return total
}
```

**`~int` 里的波浪号是「底层类型是 int 的所有类型」**——包括 D1 那个 `type Celsius float64`。不写 `~` 的话，`Celsius` 就用不了。**几乎总是要写 `~`。**

三个内置/标准约束：

| 约束 | 含义 | 来源 |
|---|---|---|
| `any` | 任意类型 | 内置 |
| `comparable` | 支持 `==` `!=`（能当 map key） | 内置 |
| `cmp.Ordered` | 支持 `< > <= >=` | 标准库 `cmp`（1.21+） |

> **`comparable` 的坑（实测过，容易记反）**：Go 1.20 起放宽了规则，**`any` 是满足 `comparable` 的**。
>
> ```go
> func Uniq[T comparable](s []T) int { m := map[T]struct{}{}; ... }
>
> Uniq([]any{1, "a", 1})      // ✅ 编译，返回 2
> Uniq([]any{[]int{1}})       // ✅ 也编译！但运行时 panic:
>                             //    hash of unhashable type []int
> ```
>
> 也就是说 **`comparable` 挡不住「装了 slice 的 any」**——编译期放行，运行时才炸。D4 §1 那条「slice/map/func 不可比较会传染」在这里变成了一个运行时问题。
>
> 实践建议：约束尽量写具体的类型集（`~string | ~int`），少用 `comparable` 兜底，除非你确实要接受任意可比较类型。

### 泛型类型

```go
type Stack[T any] struct{ items []T }

func (s *Stack[T]) Push(v T) { s.items = append(s.items, v) }
func (s *Stack[T]) Pop() (T, bool) {
    if len(s.items) == 0 {
        var zero T              // ⭐ 泛型里拿零值的标准写法
        return zero, false
    }
    v := s.items[len(s.items)-1]
    s.items = s.items[:len(s.items)-1]
    return v, true
}

var s Stack[int]                // 使用时必须指定类型实参
```

`var zero T` 是泛型代码里最常用的一个小技巧——你不知道 T 是什么，没法写字面量。

### 三条限制（Java/TS 过来的人会撞）

1. **方法不能有自己的类型参数**。`func (s *Stack[T]) MapTo[U any](...)` ❌ 编译不过。要转类型只能写成包级函数——这就是 `Map` 为什么是函数不是方法。
2. **不能对类型参数做 type switch**。`switch T {...}` ❌。
3. **不能在约束里要求字段**，只能要求方法和类型集。想访问 `.Name`？只能加个 `GetName()` 方法。

### 对比 Java / TS

| | Java | TS | Go |
|---|---|---|---|
| 实现方式 | 类型擦除 | 类型擦除 | **编译期实例化**（按 GC shape 分组） |
| 值类型 | 不支持（`List<int>` ❌，要装箱） | —— | **支持，无装箱** |
| 运行时能拿到类型吗 | 不能 | 不能 | 不能（但有 `%T`） |
| 通配符 `? extends` | 有 | —— | **没有，也不需要** |

Go 泛型**没有协变逆变**，`[]Dog` 不能当 `[]Animal` 用。想要多态还是用接口：`[]Animal` 里装接口值。

## 8. ⭐ 什么时候用泛型，什么时候用接口

这是今天最需要判断力的一节。Go 团队给的判据：

**用泛型：**
- 操作 slice / map / chan 的**通用函数**：`Map`、`Filter`、`Keys`
- **通用数据结构**：`Stack[T]`、`Set[T]`、`Cache[K,V]`
- 特征：**对所有类型，函数体的代码是完全一样的**

**用接口：**
- 不同类型**行为不同**：`Store`、`Reader`、`Payer`
- 特征：**你需要的是「调用它们各自的实现」**

一句话判据：

> **函数体里要不要根据类型做不同的事？**
> 要 → 接口。不要 → 泛型。

反例（新手最常犯）：

```go
// ❌ 泛型用错了：函数体里立刻就要 type switch
func Print[T any](v T) {
    switch any(v).(type) { ... }     // 这说明你要的是接口
}

// ❌ 接口用错了：为了「接受多种数字」定义接口
type Number interface{ Value() float64 }   // 逼着调用方包装 int
```

还有一条：**别为了「以后可能要泛型」提前泛型化。** 泛型的代价是可读性和编译期，先写具体类型，出现第二个类型时再抽。

### 主练习 · `store`

一个「记录存储」的可插拔抽象。要求：

- **小接口**：`Getter` / `Putter` 各一个方法，`Store` 由它俩组合
- **依赖倒置**：`CopyAll` 只依赖接口，不依赖任何具体实现
- **零值可用**（D4 §1）：`var m MemStore` 直接能 `Put`
- **可选接口**：`Count` 用类型断言探测 `Counter`，探测不到返回 `-1`
- ⚠️ **`Save` 里埋了 §4 那个 nil 接口的雷**，测试会专门抓它

### 副练习 · `genx`

六个泛型工具函数。重点不是写出来（都很短），是**体会约束怎么选**：什么时候 `any` 够用、什么时候要 `comparable`、什么时候要自定义类型集。

> 注意：`slices.Index`、`slices.Sort`、`maps.Keys` 标准库已经有了（`maps.Keys` 在 1.23+ 返回的是迭代器 `iter.Seq[K]`，不是切片）。**真实项目里别自己写这些**。这里手写一遍是为了理解约束。而 `Map` / `Filter` 标准库**故意没有**——Go 团队认为 `for` 循环更清楚。
