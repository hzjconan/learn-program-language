# D10 · context 与并发模式

> **D8 说「goroutine 杀不掉」，D9 说「取消是协作式的」——今天讲那个「协作」到底怎么做。**
>
> 题眼是第 5 节：**`context` 不会停掉任何东西，它只是关了一个 channel。**
>
> 先跑 `go run ./cmd/ctxdemo`（十分钟）。

---

## 1. `context` 解决什么问题

一个 HTTP 请求进来，你的代码扇出成十几个 goroutine：查数据库、调下游、读缓存。这时候：

- **用户按了取消 / 连接断了** → 那十几个 goroutine 还在烧资源
- **整个请求要求 3 秒内返回** → 每个子任务怎么知道自己还剩多少时间
- **需要把 request-id 传到最深处打日志** → 每层函数都加一个参数？

`context.Context` 就是**把「取消信号 + 截止时间 + 少量请求域数据」打包成一个值，沿调用链传下去**。

> 对比 Java：`Thread.interrupt()` 是**线程级**的标志位，而 `context` 是**调用链级**的值。
> 一个 goroutine 可以同时参与多个 context 的取消范围，这在 `interrupt` 模型里做不到。

## 2. 接口只有四个方法

```go
type Context interface {
	Done() <-chan struct{}                   // ⭐ 取消信号：关闭即取消
	Err() error                              // 为什么取消：Canceled / DeadlineExceeded
	Deadline() (deadline time.Time, ok bool) // 什么时候超时
	Value(key any) any                       // 请求域的值
}
```

**`Done()` 返回的是个 channel，取消 = 关闭它。** 这就是全部机制——D8 §8 讲过 `close` 是 Go 里唯一的一对多广播手段。

### 五个构造函数

```go
context.Background()                          // 根，通常在 main / 请求入口
context.TODO()                                // 「还不知道该传什么」的占位符
context.WithCancel(parent)      → ctx, cancel
context.WithTimeout(parent, d)  → ctx, cancel
context.WithDeadline(parent, t) → ctx, cancel
context.WithValue(parent, k, v) → ctx
```

**每个 `With*` 都返回一个新的 context，形成一棵树。** 父 context 取消时，**所有后代自动取消**；取消子 context 不影响父。

⚠️ **`cancel` 必须被调用**，哪怕已经正常结束了：

```go
ctx, cancel := context.WithTimeout(parent, 3*time.Second)
defer cancel()          // ⭐ 不调用会泄漏 —— 父 context 会一直持有这个子节点
```

`go vet` 的 `lostcancel` 检查会抓漏掉的 `cancel`。

## 3. 取消是怎么传播的

```
            Background
                │
         WithCancel (请求级)
            ╱       ╲
   WithTimeout      WithValue
    (查库 500ms)      (带 traceID)
        │               │
    子 goroutine     子 goroutine
```

- **父取消 → 所有后代的 `Done()` 全部关闭**（一次 `close` 广播给整棵子树）
- **子取消 → 父不受影响**
- **超时到期 = 自动取消**，`Err()` 返回 `context.DeadlineExceeded`

```go
ctx1, cancel1 := context.WithCancel(context.Background())
ctx2, cancel2 := context.WithTimeout(ctx1, time.Hour)  // 子节点
defer cancel1()
defer cancel2()

cancel1()               // 父取消
<-ctx2.Done()           // ⭐ 子也立刻就绪了，尽管它自己的超时是 1 小时
```

## 4. 超时与截止时间

```go
ctx, cancel := context.WithTimeout(parent, 3*time.Second)   // 相对：从现在起 3 秒
ctx, cancel := context.WithDeadline(parent, t)              // 绝对：到 t 这个时刻
```

**`WithTimeout(parent, d)` 就是 `WithDeadline(parent, time.Now().Add(d))`。**

⭐ **取更早的那个**：子 context 的超时**不能超过**父的。

```go
parent, _ := context.WithTimeout(bg, 1*time.Second)
child, _  := context.WithTimeout(parent, 10*time.Second)   // ⚠️ 实际只有 1 秒
```

这个性质非常有用：**在请求入口设一个总超时，下游怎么设都不会突破它。**

### 剩余时间

```go
if dl, ok := ctx.Deadline(); ok {
	remaining := time.Until(dl)
	// 剩得太少就别发请求了，直接返回
}
```

## 5. ⭐ 取消不会停掉任何东西 —— 今天的题眼

```go
cancel()
```

这一行做的事**只有一件**：**关闭 `ctx.Done()` 那个 channel**（以及递归关闭所有后代的）。

它**不会**：

- ❌ 停掉任何 goroutine
- ❌ 中断正在执行的函数
- ❌ 关闭任何连接
- ❌ 回滚任何事务

**所有的「响应取消」都是接收方自己写的代码。** 一个不检查 `ctx.Done()` 的循环，`cancel()` 一万次也拦不住它。

```go
// ❌ 完全无视取消
for _, item := range items {
	process(item)          // 跑到天荒地老
}

// ✅ 协作
for _, item := range items {
	select {
	case <-ctx.Done():
		return ctx.Err()   // ⭐ 自己退出
	default:
	}
	process(item)
}
```

### 标准库替你检查了

好消息是：**只要你把 `ctx` 传下去，标准库会替你响应**。

```go
http.NewRequestWithContext(ctx, ...)   // ✅ 连接会被中断
db.QueryContext(ctx, ...)              // ✅ 查询会被取消
db.ExecContext(ctx, ...)               // ✅
conn.Read(...)                         // ❌ 不吃 ctx，要自己 SetReadDeadline
```

**看到函数名带 `Context` 后缀，就是「我会响应取消」的承诺。**

> ⚠️ 「响应取消」不等于「立刻停止」。数据库查询被取消时，服务端可能还在跑那条 SQL——
> **你只是不等它了**。真正的资源回收取决于对端。

## 6. `WithValue`：能用，但别滥用

```go
ctx = context.WithValue(ctx, traceIDKey{}, "abc-123")
id, ok := ctx.Value(traceIDKey{}).(string)
```

### 三条硬规则

**① key 必须是自定义类型，不能是 string**

```go
type traceIDKey struct{}                        // ✅ 不可能和别的包冲突
ctx = context.WithValue(ctx, traceIDKey{}, id)

ctx = context.WithValue(ctx, "traceID", id)     // ❌ 别的包用同样的字符串就覆盖了
```

`go vet` 会警告用内置类型当 key。

**② 只放「请求域的数据」，不放「依赖」**

| ✅ 该放 | ❌ 不该放 |
|---|---|
| trace ID / request ID | 数据库连接 |
| 认证后的用户身份 | logger（除非带了请求域字段） |
| 语言 / 时区偏好 | 配置对象 |
| 幂等键 | 任何 service / repository |

**为什么不能当 DI 容器：**

- **完全没有类型安全**——`Value` 返回 `any`，拿错了是运行时 panic 或者静默的零值
- **依赖关系变成隐式的**——函数签名 `f(ctx)` 看不出它需要什么，只能读实现
- **测试变难**——每个测试都要手工塞一堆值进 ctx
- **编译器帮不了你**——删掉一个依赖，编译照过，运行时才炸

**依赖用构造函数注入。** D14 的分层架构会正面讲这个。

**③ 提供类型安全的包装函数**

```go
type userKey struct{}

func WithUser(ctx context.Context, u *User) context.Context {
	return context.WithValue(ctx, userKey{}, u)
}

func UserFrom(ctx context.Context) (*User, bool) {
	u, ok := ctx.Value(userKey{}).(*User)
	return u, ok
}
```

**把 `Value` 的调用锁在一个包里**，外面只用这两个函数——类型安全回来了。

## 7. 三条惯例

**① `ctx` 永远是第一个参数，且命名为 `ctx`**

```go
func Fetch(ctx context.Context, url string) ([]byte, error)   // ✅
func Fetch(url string, ctx context.Context) ([]byte, error)   // ❌
```

**② 不要把 `ctx` 存进 struct**

```go
type Server struct {
	ctx context.Context      // ❌ 几乎总是错的
}
```

`context` 是**请求域**的，struct 通常是**进程域**的。存进去意味着「所有请求共用一个 ctx」——要么永不取消，要么一取消全挂。

> 例外确实存在（比如某些 `struct` 本身就代表一次操作），但标准库文档明说了「除非万不得已」。

**③ 不要传 `nil` context**，用 `context.TODO()`

## 8. 经典并发模式

### pipeline（今天的主练习）

**每个阶段：读上游 channel → 处理 → 写下游 channel。**

```go
func Square(ctx context.Context, in <-chan int) <-chan int {
	out := make(chan int)
	go func() {
		defer close(out)              // ⭐ 谁创建谁关闭
		for v := range in {           // 上游关了就自然退出
			select {
			case out <- v * v:
			case <-ctx.Done():        // ⭐ 下游不要了也要能退出
				return
			}
		}
	}()
	return out
}
```

**两个退出路径缺一不可：**

1. **上游关闭** → `for range in` 自然结束
2. **ctx 取消** → `select` 里那个分支

**只有第 1 条的话**，下游提前不读了，这条 goroutine 会永远卡在 `out <- v*v` 上——**泄漏**（D8 §7）。

### fan-out / fan-in

```
              ┌→ worker1 ─┐
Source ──────→┼→ worker2 ─┼──→ Merge ──→ 结果
              └→ worker3 ─┘
```

**fan-out**：多个 goroutine 从**同一个** channel 读（D8 讲过，一个值只有一个人拿到，天然是工作队列）。

**fan-in**：把多个 channel 汇成一个：

```go
func Merge(ctx context.Context, ins ...<-chan int) <-chan int {
	out := make(chan int)
	var wg sync.WaitGroup
	for _, in := range ins {
		wg.Go(func() {
			for v := range in {
				select {
				case out <- v:
				case <-ctx.Done():
					return
				}
			}
		})
	}
	go func() { wg.Wait(); close(out) }()   // ⭐ 全部结束才关（D8 §8）
	return out
}
```

### 优雅退出

```go
func main() {
	ctx, stop := signal.NotifyContext(context.Background(),
		os.Interrupt, syscall.SIGTERM)
	defer stop()

	srv := &http.Server{...}
	go func() { srv.ListenAndServe() }()

	<-ctx.Done()                              // 等 Ctrl-C / SIGTERM
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	srv.Shutdown(shutdownCtx)                 // 等在途请求处理完
}
```

⚠️ **`Shutdown` 要用一个新的 ctx**——不能用那个已经被信号取消的，否则它立刻超时。

## 9. `ctx.Err()` 与错误判断

```go
switch {
case errors.Is(err, context.Canceled):         // 主动取消
case errors.Is(err, context.DeadlineExceeded): // 超时
}
```

**`context.DeadlineExceeded` 实现了 `net.Error` 接口且 `Timeout() == true`**，所以很多网络库的超时判断能直接认出它。

⚠️ **别用 `==` 比较**——`ctx.Err()` 返回的可能是包装过的。用 `errors.Is`（D2）。

## 10. 五个常见坑

| 坑 | 后果 |
|---|---|
| 忘了 `defer cancel()` | 父 context 一直持有子节点 → 内存泄漏（`go vet` 能抓） |
| 循环里不检查 `ctx.Done()` | 取消完全无效 |
| pipeline 阶段只处理「上游关闭」，不处理「ctx 取消」 | **goroutine 泄漏** |
| `Shutdown` 复用已取消的 ctx | 立刻超时，在途请求被砍 |
| 用 `ctx` 传依赖 | 隐式依赖 + 运行时 panic |

## 11. 今天的练习

```
go/cmd/ctxdemo/           ← 先跑：go run ./cmd/ctxdemo
go/internal/pipeline/     ← 主练习：可取消的多阶段 pipeline
```

### 主练习 · `pipeline`

一个三阶段的数据处理流水线：**产生 → 并发加工 → 汇总**。

四个要实现的函数：

1. **`Source`** —— 把切片变成 channel，支持取消
2. **`Stage`** —— 一个加工阶段，读上游写下游，两个退出路径都要有
3. **`Merge`** —— fan-in，把 N 个 channel 汇成一个
4. **`Run`** —— 组装完整 pipeline：`Source` → fan-out 到 N 个 `Stage` → `Merge` → 收集

硬要求（测试会验）：

- **取消之后所有 goroutine 必须干净退出**（比对 `runtime.NumGoroutine()`）
- **超时和主动取消要能区分**（`errors.Is(err, context.DeadlineExceeded)`）
- **`-race` 干净**
- **并发上限真的生效**
- **正常路径结果正确且顺序确定**（并发返回顺序随机，你得自己排）
