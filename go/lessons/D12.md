## 1. `encoding/json` 的五个坑

### 1.1 ⚠️ 数字精度：`int64` 过一遍 `any` 就废了

```
原始 int64:      9007199254740993
序列化:          {"id":9007199254740993}
反序列化成 any:  9007199254740992    ← ⚠️ 变了！
类型是:          float64
```

**JSON 的数字在 Go 里默认解析成 `float64`**，而 `float64` 只能精确表示到 2^53。超过之后**静默丢精度**。

真实事故：雪花 ID、订单号、时间戳（纳秒）——**全都超过 2^53**。

#### 起决定作用的是「目标类型具不具体」，不是 struct 还是 map

容易误读成「要用 struct」。实测同一份 `{"id":9007199254740993}` 换六种目标：

| 反序列化的目标类型 | 结果 | |
|---|---|:--:|
| `map[string]any` | `9007199254740992` | ❌ |
| `map[string]float64` | `9007199254740992` | ❌ |
| `map[string]int64` | `9007199254740993` | ✅ |
| `map[string]json.Number` | `9007199254740993` | ✅ |
| `struct{ ID int64 }` | `9007199254740993` | ✅ |
| `map[string]int`（64 位机） | `9007199254740993` | ✅ |

**`map[string]int64` 和 `struct{ID int64}` 走的是同一条路径**，都精确。`encoding/json` 解析数字时看目标的**静态类型**：

- 目标是 `int64` → 直接 `strconv.ParseInt` 解析原始字节，**全程没有 float64 出场**
- 目标是 `any` → 没有类型信息可依，只能按 JSON 规范选默认类型，也就是 `float64`

所以真正的规则是**「别让 `any` 接住数字」**，跟容器是 map 还是 struct 无关。

#### ⭐ 具体类型还能**拒绝**坏数据

```
目标 map[string]int64：
  {"id":1.5}                    → json: cannot unmarshal number 1.5 into Go value of type int64
  {"id":99999999999999999999}   → json: cannot unmarshal number 999... into Go value of type int64

目标 map[string]any：
  {"id":99999999999999999999}   → err=<nil>，值 = 1e+20        ⚠️ 不报错
```

最后一行是重点：同一个**溢出**的数字，解析成 `any` 完全不报错，你拿着一个 `1e+20` 继续往下跑。

**`any` 不只是丢精度，它让 json 失去了拒绝坏数据的能力**——和 §1.3「未知字段被静默忽略」是同一类问题：**类型信息越少，能替你把关的就越少。**

三个解法：

```go
// ① 让接住数字的是【具体类型】—— struct 字段或 map 的 value 类型都行
type Resp struct{ ID int64 `json:"id"` }     // ✅ 精确
var m map[string]int64                        // ✅ 同样精确

// ② 形状不固定、只能用 any 时，用 json.Number
dec := json.NewDecoder(r)
dec.UseNumber()                               // ⭐ 数字保持字符串形式
var m map[string]any
dec.Decode(&m)
id, _ := m["id"].(json.Number).Int64()        // ✅ 精确

// ③ API 设计上：大整数用 string 传
type Resp struct{ ID string `json:"id"` }     // ✅ JavaScript 那边也不会炸
```

> **什么时候才真的需要 ②**：只有当 JSON 的形状不固定（每个字段类型都不一样），
> 你不得不用 `map[string]any` 时。如果你事先知道 value 全是整数，
> 直接 `map[string]int64` 更好——既精确，又能拒绝坏数据。
>
> `json.Number` 底层就是 `string`，原始字面量原封不动留着，
> 等你自己决定按 `Int64()` 还是 `Float64()` 读。

> **第 ③ 条是很多大厂 API 的做法**（Twitter 的 `id_str`、Stripe 的 ID 都是字符串）——因为 JavaScript 的 `number` 也是 float64，前端同样会丢精度。

### 1.2 ⚠️ 零值和「字段缺失」分不清

```
{"port":8080,"debug":true}   → Port=8080 Debug=true
{"port":0,"debug":false}     → Port=0 Debug=false
{}                           → Port=0 Debug=false     ← 和上一行【完全一样】
```

**「用户显式传了 0」和「用户没传」得到的结果一模一样。** 配置更新、PATCH 接口里这是致命的——你分不清「把超时改成 0」和「这次不改超时」。

**解法：用指针。**

```go
type Config struct {
	Retries *int `json:"retries"`
}
```

```
{"retries":0}    → Retries = 0（【显式传了】这个值）
{}               → Retries 是 nil（字段【缺失】）
```

代价是每次用都要判空。**所以只在真的需要区分时才用指针**——大部分字段用零值就够了。

> ⚠️ **序列化那一侧是同一个问题**：`omitempty` / `omitzero` 是**按值省略**，不是「按有没有设置过」省略。显式写 `N: 0` 和从没赋值，输出都是 `{}`——Go 不记录赋值历史，标签能看的只有值本身（见 §1.4）。

---

#### ⭐ 落地：一个完整的 PATCH 接口

场景：配置有 `retries` 和 `timeout` 两项，当前是 `{5, 300}`。客户端要**把 retries 改成 0，timeout 不动**，于是传 `{"retries":0}`。

**第一步也是最关键的一步：请求体的类型和存储的类型必须分开。**

```go
// 存储 / 领域里的样子 —— 值类型，因为每一项都必然有值
type Config struct {
	Retries int `json:"retries"`
	Timeout int `json:"timeout"`
}

// 请求体的样子 —— 每项都是指针，因为每项都可能「没传」
type ConfigPatch struct {
	Retries *int `json:"retries"`
	Timeout *int `json:"timeout"`
}
```

> **用同一个 struct 收 PATCH 请求，就是所有「timeout 莫名其妙变成 0」事故的根源。**

打补丁——`nil` 判断就是「这个字段有没有出现在 JSON 里」：

```go
func (p ConfigPatch) Apply(c *Config) {
	if p.Retries != nil {
		c.Retries = *p.Retries
	}
	if p.Timeout != nil {
		c.Timeout = *p.Timeout
	}
}
```

校验——**只校验传了的字段**：

```go
func (p ConfigPatch) Validate() error {
	var errs []error
	if p.Retries != nil && *p.Retries < 0 {
		errs = append(errs, fmt.Errorf("retries 不能为负，得到 %d", *p.Retries))
	}
	if p.Timeout != nil && *p.Timeout <= 0 {
		errs = append(errs, fmt.Errorf("timeout 必须为正，得到 %d", *p.Timeout))
	}
	return errors.Join(errs...)
}
```

⭐ `p.Timeout != nil &&` 那半句是关键。漏掉它的话，`{"retries":0}` 会因为「timeout 是 0，必须为正」被拒绝——**一个客户端压根没提到的字段**。

解析——顺手把 §1.3 那条也用上：

```go
func decodePatch(body []byte) (ConfigPatch, error) {
	var p ConfigPatch
	dec := json.NewDecoder(bytes.NewReader(body))
	dec.DisallowUnknownFields()          // 拼错字段名要报错，别静默忽略
	if err := dec.Decode(&p); err != nil {
		return p, err
	}
	return p, p.Validate()
}
```

实测（起点都是 `{Retries:5 Timeout:300}`）：

| 请求体 | 结果 | |
|---|---|---|
| `{"retries":0}` | `{Retries:0 Timeout:300}` | ← timeout 保持 300 ✅ |
| `{}` | `{Retries:5 Timeout:300}` | 什么都不改 |
| `{"retries":0,"timeout":600}` | `{Retries:0 Timeout:600}` | |
| `{"timeout":0}` | `400` | `timeout 必须为正，得到 0` |
| `{"retrys":0}` | `400` | `json: unknown field "retrys"` |

对照——**同一个请求体**，用值类型直接收会怎样：

```
改之前: {Retries:5 Timeout:300}
收到的: {Retries:0 Timeout:0}   ← timeout 被解析成 0 了
写回去: {Retries:0 Timeout:0}   ⚠️ timeout 从 300 变成了 0
```

**一个正确、一个数据损坏，差别只在请求类型的字段是不是指针。**

#### 三个补充

**① `{"retries":null}` 和 `{}` 仍然分不清。** 两者都让指针保持 `nil`。如果 API 需要「传 `null` 表示删除/重置」，`*int` 就不够了，得用 `json.RawMessage` 或自定义三态类型。绝大多数 API 不需要。

**② 字段一多，`Apply` 会很啰嗦。** 三五个字段手写最清楚；再多可以用 `map[string]json.RawMessage` 先拿到「哪些 key 存在」，或者上 JSON Merge Patch（RFC 7386）。**别一上来就上反射。**

**③ PUT 不用指针。** PUT 的语义是**整体替换**，客户端本来就该传全量，没传就是要设成零值。指针那套只属于 PATCH——「只改一项、其余不动」正是 PATCH 而不是 PUT。

### 1.3 ⚠️ 未知字段默认被**静默忽略**

```
{"prot":9999}（拼错了）→ err=<nil> Port=0    ← 静默吃掉
```

用户配置文件里把 `port` 拼成 `prot`，程序**不报错**，用默认值跑起来了——然后你花两小时查「为什么端口没生效」。

```go
dec := json.NewDecoder(r)
dec.DisallowUnknownFields()        // ⭐
err := dec.Decode(&cfg)
// → json: unknown field "prot"
```

**配置文件解析一定要开这个。** API 请求体则视情况——开了之后客户端多传一个字段就 400，可能过于严格。

### 1.4 `omitempty` 对 struct 无效

```go
type S struct {
	A string          `json:"a,omitempty"`
	E struct{ X int }  `json:"e,omitempty"`
}
json.Marshal(S{})   // → {"e":{"X":0}}     ← e 还在
```

`omitempty` 只认这些「空值」：`false` / `0` / `""` / `nil` / 空切片 / 空 map。**struct 不在列表里**，哪怕它所有字段都是零值。

#### 解法一：改成指针

```
值类型 Inner：
  Inner{}      → {"d":{"X":0}}    ← 零值也被输出了 ⚠️
  Inner{X:7}   → {"d":{"X":7}}

指针 *Inner：
  nil          → {}               ← 省掉了 ✅
  &Inner{}     → {"d":{"X":0}}    ← 零值但【存在】，保留
  &Inner{X:7}  → {"d":{"X":7}}
```

⭐ **注意第二组的中间那行**：`&Inner{}` 是零值，但它**被保留了**。

指针区分的是「**有没有**」，不是「是不是零值」——和 §1.2 是同一个道理。所以改指针不只是「让 `omitempty` 生效」的小把戏，它**换了一种语义**：

| | 含义 |
|---|---|
| `nil` | 这个字段**不存在** |
| `&Inner{}` | 存在，值恰好是零 |

代价是每次读都要判空。**只在真的需要区分时才用。**

#### 解法二：`omitzero`（Go 1.24+）

```go
D Inner `json:"d,omitzero"`     // 值类型，不是指针
```

```
Inner{}      → {}               ← 零值，省掉了 ✅
Inner{X:7}   → {"d":{"X":7}}
```

不用改指针，也不用判空。**只想「零值就别输出」的话，这个更省事。**

#### ⚠️ 但 `omitzero` 不是 `omitempty` 的超集

两者在**两个方向**上都不一样：

```
零值 time.Time + omitempty → {"t":"0001-01-01T00:00:00Z"}    ⚠️
零值 time.Time + omitzero  → {}                              ✅

空切片 []int{} + omitempty → {}                              
空切片 []int{} + omitzero  → {"s":[]}                        ← 反过来了
```

**第一组是个真实事故**：`time.Time` 是个 struct，`omitempty` 对它无效，于是「从没设置过的时间」被当成**公元 1 年**发给了客户端。

**第二组方向相反**：`omitzero` 只认**零值**，而 `[]int{}` 不是 `nil`，所以保留。

> **记法**：`omitempty` 问「**空不空**」，`omitzero` 问「**是不是零值**」。
>
> - struct、`time.Time` → 用 `omitzero`
> - 想让空切片输出成 `[]` 而不是消失 → 也用 `omitzero`

#### ⚠️ 两者都是「按值省略」，不是「按有没有设置过」

```
V{}（没赋值）+ omitzero        → {}
V{N: 0}（显式赋 0）+ omitzero  → {}        ← 一模一样
V{N: 7} + omitzero            → {"n":7}
```

`omitempty` 同样如此。**Go 不记录赋值历史**——「从没赋值」和「显式赋了 0」在内存里是同一个字节，标签能看的只有值本身。

要表达「我就是要传 0」，还是只能靠指针：

```
P{}（nil）+ omitzero            → {}
P{N: &zero}（指向 0）+ omitzero  → {"n":0}    ← 保留了 ✅
```

因为对**指针**来说，「零值」就是 `nil`——只要非空，不管指向什么都会被序列化。

> 这和 §1.2 是同一个问题的两侧：**反序列化时值类型收不到「缺失」，序列化时值类型也造不出「缺失」。** 想要这个状态，类型里就得有个东西能表示它——指针的 `nil` 就是干这个的。

### 1.5 `time.Duration` 在 JSON 里是纳秒整数

```
Text handler: took=15ms
JSON handler: "took":15000000        ← 纳秒
```

`time.Duration` 底层是 `int64`，`encoding/json` 就按整数序列化。给人看的话要自己转：

```go
type Resp struct {
	TookMs int64 `json:"took_ms"`     // ⭐ 明确单位（D7 那条：边界做转换）
}
```

### 其他常用 tag

```go
type T struct {
	A int    `json:"-"`                  // 完全忽略这个字段
	B int    `json:"b,string"`           // 序列化成字符串 "123"
	c int                                 // 小写字段【永远不参与】序列化
	D int    `json:"d,omitzero"`         // Go 1.24+：省略【零值】（≠ omitempty，见 §1.4）
}
```

## 2. 配置：十二要素

**原则：配置从环境变量读，代码里只有默认值。**

```go
type Config struct {
	Addr         string
	ReadTimeout  time.Duration
	LogLevel     slog.Level
}

func Load() (Config, error) {
	c := Config{                                   // ⭐ 默认值写在代码里
		Addr:        ":8080",
		ReadTimeout: 10 * time.Second,
		LogLevel:    slog.LevelInfo,
	}
	if v := os.Getenv("ADDR"); v != "" {
		c.Addr = v
	}
	...
	return c, c.Validate()                          // ⭐ 加载完立刻校验
}
```

四条实践：

1. **默认值必须能跑**——`Load()` 在没有任何环境变量时应该返回一份可用的配置
2. **启动时校验，别等到用的时候**——端口是 0、超时是负数，应该在启动时就 `log.Fatal`
3. **不要在业务代码里读 `os.Getenv`**——全部集中在 `config` 包，否则配置项散落各处
4. **敏感信息（密码、token）不要打进日志**——见下

> `os.Getenv` 分不清「没设」和「设成空字符串」——需要区分时用 `os.LookupEnv`（返回 `(string, bool)`）。和 §1.2 是同一个问题。

### ⚠️ 脱敏：一个 `String()` 挡不住

给密码类型加一个 `String()` 返回 `[REDACTED]`，看起来就安全了：

```go
type Secret string
func (s Secret) String() string { return "[REDACTED]" }
```

实测——同一个值走六条输出路径，看哪条会泄漏（`✅` = 已脱敏）：

| 只实现了 | `%v` | `json.Marshal` | slog(JSON) | slog(Text) | 包在 struct 里<br>slog(JSON) | 包在 struct 里<br>slog(Text) |
|---|:--:|:--:|:--:|:--:|:--:|:--:|
| *什么都没有* | ⚠️ | ⚠️ | ⚠️ | ⚠️ | ⚠️ | ⚠️ |
| `String()` | ✅ | ⚠️ | ⚠️ | ✅ | ⚠️ | ✅ |
| `MarshalJSON()` | ⚠️ | ✅ | ✅ | ⚠️ | ✅ | ⚠️ |
| `LogValue()` | ⚠️ | ⚠️ | ✅ | ✅ | **⚠️** | **⚠️** |
| 三个都有 | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

读出四条规则：

1. **`fmt` 只认 `String()`**，**`encoding/json` 只认 `MarshalJSON()`**——各管各的，互不代班。
2. **slog 先找 `LogValue()`；找不到就看 Handler**：JSON handler 退回 `json.Marshal`（认 `MarshalJSON`），Text handler 退回 `fmt`（认 `String`）。**同一份代码换个 Handler 就可能开始泄漏。**
3. ⭐ **`LogValue()` 不会向下递归。** 看第 4 行最后两列：`Secret` 实现了 `LogValue`，但把整个 `Config` 当一个 attr 记进去时照样泄漏——slog 只在**最外层的值**上找 `LogValuer`，`Config` 没实现，就整个丢给序列化了，内层的 `LogValue` **根本没机会被调用**。
   而 `String()` / `MarshalJSON()` **会**递归（`fmt` 和 `json` 遍历字段时会各自调用它们），所以第 2、3 行的「包在 struct 里」是安全的。
4. **`%#v` 六条之外，谁也堵不住**——它按设计就要打 Go 语法表示，绕过所有接口：

   ```
   %#v: main.Config{Addr:":8080", Token:"super-secret-token"}     ⚠️
   ```

   **别用 `%#v` 打日志。**

**结论：`String()` + `MarshalJSON()` 两个就能盖住全部六条路**（第 5 行）。那还要 `LogValue()` 干嘛？三个理由：它是 slog 的正规入口、不走反射所以更快、而且能返回 `slog.GroupValue` 把一个值展开成多个字段：

```go
func (c Config) LogValue() slog.Value {
	return slog.GroupValue(
		slog.String("addr", c.Addr),          // ⭐ 顺便把字段名统一成 snake_case
		slog.Any("api_token", c.APIToken),
	)
}
```

> 这条本质上还是 D5 的接口满足：**方法只在「有人按那个接口调用它」时才生效**。`json` 不按 `Stringer` 调用你，你的 `String()` 就是不存在。

## 3. `log/slog`：Go 1.21 起的标准答案

**别再用第三方日志库了**（logrus、zap 的 API 仍然更丰富，但 slog 是标准库、有生态、够用）。

```go
slog.Info("请求完成", "method", "GET", "status", 200)
```

### 两种 Handler

```
Text: time=... level=INFO msg=请求完成 method=GET status=200 took=15ms
JSON: {"time":"...","level":"INFO","msg":"请求完成","method":"GET","status":200,"took":15000000}
```

**开发用 Text（人读），生产用 JSON（机器读）**——这应该是个配置项。

### 强类型 attr vs 键值对

```go
slog.Info("x", slog.String("method", "GET"), slog.Int("status", 200))   // ⭐ 快
slog.Info("x", "method", "GET", "status", 200)                          // 方便，但走反射
```

**热路径用强类型**（`slog.String`/`Int`/`Duration`/`Any`），其余随意。

⚠️ 键值对形式**参数个数必须是偶数**，落单的会变成 `!BADKEY`——编译器不管，只能靠 lint（`sloglint`）。

### `With`：把公共字段固定下来

```go
reqLog := logger.With("request_id", id, "user", user)
reqLog.Info("开始处理")      // 自动带上那两个字段
reqLog.Warn("命中限流")
```

**这是给每个请求做「日志上下文」的标准手法**——比每条日志手动重复那些字段好得多。

### `Group`：分组

```go
slog.Info("x", slog.Group("http", slog.String("method", "POST"), slog.Int("status", 201)))
// → {"http":{"method":"POST","status":201}}
```

### ⭐ 从 `ctx` 自动提取字段——最实用的扩展点

`slog` 的 `Handler` 是个接口，包一层就能让**每条日志自动带上 trace ID**：

```go
type ctxHandler struct{ slog.Handler }

func (h ctxHandler) Handle(ctx context.Context, r slog.Record) error {
	if id, ok := httpx.RequestIDFrom(ctx); ok {
		r.AddAttrs(slog.String("request_id", id))    // ⭐ 自动加
	}
	return h.Handler.Handle(ctx, r)
}
```

```
l.InfoContext(ctx, "带 ctx 的日志")   → {"msg":"带 ctx 的日志","request_id":"trace-xyz"}
l.Info("不带 ctx 的日志")             → {"msg":"不带 ctx 的日志"}
```

⚠️ **必须用 `XxxContext` 系列方法**（`InfoContext`/`ErrorContext`），普通的 `Info` 传的是 `context.Background()`，提取不到东西。

> 这是 D11 §5 那个「嵌入接口 + 只重写关心的方法」的又一次应用。

### 别忘了配置默认 logger

```go
slog.SetDefault(logger)        // 让 slog.Info(...) 也走你的配置
```

## 4. 错误分层：为什么需要

D2 讲了 `%w` 和 `errors.Is/As`。今天讲**怎么在分层架构里用它**。

问题场景：

```go
// repository 层
func (r *Repo) Get(id string) (*Item, error) {
	if !exists { return nil, sql.ErrNoRows }     // ← 数据库的错误
}

// handler 层
func handler(w http.ResponseWriter, r *http.Request) {
	item, err := repo.Get(id)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {        // ⚠️ handler 知道了 SQL 的存在
			http.Error(w, "not found", 404)
			return
		}
		http.Error(w, "internal", 500)
	}
}
```

**三个问题：**

1. **handler 依赖了存储层的实现细节**——换成 MongoDB 就要改所有 handler
2. **每个 handler 都要重复这段映射**——20 个 handler 就是 20 份
3. **内部错误细节可能泄漏给用户**——`sql: connection refused` 直接返回给客户端是安全问题

## 5. ⭐ 错误分层的解法 —— 今天的题眼

**定义一组「领域错误类别」，在边界处一次性映射成 HTTP 状态码。**

```go
type Kind int

const (
	KindInternal Kind = iota      // 默认：500
	KindNotFound                   // 404
	KindInvalid                    // 400
	KindConflict                   // 409
	KindUnauthorized               // 401
)

type Error struct {
	Kind    Kind
	Message string     // ⭐ 给用户看的，不含内部细节
	Err     error      // ⭐ 给日志看的，含全部细节
}

func (e *Error) Error() string { return e.Message + ": " + e.Err.Error() }
func (e *Error) Unwrap() error { return e.Err }     // D2：让 errors.Is 能穿透
```

**关键在于「两个消息」**：

| 字段 | 给谁看 | 例子 |
|---|---|---|
| `Message` | **用户** | `"找不到这个商品"` |
| `Err` | **日志** | `"query items: dial tcp 10.0.0.5:5432: connection refused"` |

### 各层的职责

```go
// ① repository：把底层错误【翻译】成领域错误
func (r *Repo) Get(ctx context.Context, id string) (*Item, error) {
	err := r.db.QueryRowContext(ctx, "...").Scan(...)
	if errors.Is(err, sql.ErrNoRows) {
		return nil, apperr.NotFound("找不到这个商品", err)     // ⭐ 翻译
	}
	if err != nil {
		return nil, apperr.Internal("查询失败", err)
	}
	return item, nil
}

// ② service：加上下文，但不改 Kind
func (s *Service) Buy(ctx context.Context, id string) error {
	item, err := s.repo.Get(ctx, id)
	if err != nil {
		return fmt.Errorf("购买 %s: %w", id, err)     // ⭐ %w 保持 Kind 可被 errors.As 找到
	}
	...
}

// ③ handler：只做一件事 —— 映射成 HTTP
func handler(w http.ResponseWriter, r *http.Request) {
	if err := svc.Buy(ctx, id); err != nil {
		writeError(w, r, err)        // ⭐ 一行，不需要知道任何领域细节
		return
	}
}

// ④ writeError：统一的出口
func writeError(w http.ResponseWriter, r *http.Request, err error) {
	status, msg := apperr.HTTPStatus(err)         // 用 errors.As 找到 *apperr.Error

	if status >= 500 {
		slog.ErrorContext(r.Context(), "请求失败", "err", err)   // ⭐ 完整细节进日志
	}
	writeJSON(w, status, map[string]string{"error": msg})       // ⭐ 只有 Message 给用户
}
```

**收益：**

- handler 里没有任何 `errors.Is(err, sql.ErrNoRows)`
- 换数据库只改 repository 层
- 内部细节**只**进日志，用户只看到你想让他看的
- 新增一种错误类别 = 改一处映射表

> ⚠️ **别把 HTTP 状态码写进领域层**。`apperr.Kind` 是领域概念（「找不到」），HTTP 状态码是传输细节——同一个 `KindNotFound` 在 gRPC 里映射成 `codes.NotFound`，在 CLI 里映射成退出码 1。**映射发生在边界。**
