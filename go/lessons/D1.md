## 1. module / package / import path

### 三个概念的关系

```
module  = 依赖管理和版本发布的单位   （≈ Maven 的一个 artifact / npm 的一个 package）
package = 编译和可见性的单位         （≈ Java 的 package / TS 的一个模块文件夹）
import path = module path + 目录相对路径
```

我们的 `go.mod` 第一行：

```
module github.com/hzjconan/learn-program-language/go
```

于是 `go/internal/units/` 这个目录里的包，它的 import path 就是
`github.com/hzjconan/learn-program-language/go/internal/units`。

**关键差异（对比 Java/TS）：**

| | Java | TypeScript | Go |
|---|---|---|---|
| 坐标从哪来 | Maven `groupId:artifactId` 人为约定 | npm registry 上的名字 | **就是代码托管的 URL 路径** |
| 一个目录能有几个包 | 一个目录 = 一个 package | 一个文件 = 一个模块 | **一个目录 = 恰好一个包**（除了 `xxx_test` 包） |
| package 名和目录名 | 必须一致（编译器强制） | 无此概念 | 惯例一致，但**不强制**；真正决定名字的是文件里的 `package xxx` |
| 导入是否可省 | 需要 import | 需要 import | 需要 import，且**未使用的 import 是编译错误** |

Go 没有中央仓库注册表这一层。`import "github.com/foo/bar"` 时，`go` 命令直接按这个路径去拉代码（默认经过 `proxy.golang.org` 缓存）。这就是为什么 module path 必须写成域名开头的形式 —— **路径即地址**。

### 包名的惯例

Go 的包名风格和 Java 完全相反：

```go
// Java 味（别这么写）
package stringutils
func StringUtilsReverse(s string) string

// Go 味
package strings          // 短、全小写、单个词、无下划线无驼峰
func Reverse(s string) string
```

调用方写的是 `strings.Reverse(s)` —— **包名是调用表达式的一部分**，所以 `units.CToF` 就够了，不要写成 `units.UnitsConvertCToF`。这条叫「避免 stutter（结巴）」，是 Go code review 里最常被指出的问题之一。

### 未使用 = 编译错误

```go
import "os"   // 没用到 → 编译失败：imported and not used
x := 42       // 没用到 → 编译失败：declared and not used
```

Java/TS 里这些只是 IDE 的黄色警告，Go 里直接不给编译。刚开始会很烦，习惯后你会发现死代码根本没机会长出来。
（例外：包级变量不受此限制；`import _ "xxx"` 是显式的「只要副作用」导入。）

## 2. 变量、`:=`，和那个作用域陷阱

### 四种声明方式

```go
var a int           // 显式类型，取零值 0
var b = 42          // 类型推断为 int
var c int = 42      // 都写（冗余，golangci-lint 会说你）
d := 42             // 短变量声明，只能在函数内部用
```

包级（函数外）只能用 `var` / `const` / `type` / `func` 开头，**`:=` 在函数外不合法**。

### `:=` 的两条规则（陷阱全在这）

**规则一：`:=` 左边只要有一个是新变量就合法，其余的是赋值。**

```go
a, err := f()     // a、err 都是新变量
b, err := g()     // b 是新的，err 是【赋值】不是新声明 —— 这是允许的，也是惯用写法
```

这条规则让「每次调用都写 `err`」变得可行，是 Go 错误处理能忍受的前提（D2 细讲）。

**规则二：换一层作用域，`:=` 就一定创建新变量 —— 哪怕同名。**

这就是「变量遮蔽（shadowing）」，Go 里最容易 debug 到怀疑人生的坑：

```go
func run() error {
	err := step1()
	if err != nil {
		return err
	}

	if cond {
		err := step2()      // ← 这里的 err 是【新变量】，只活在 if 块里
		if err != nil {
			log.Println(err)  // 打了日志
		}
	}                       // ← 新 err 在这里死掉了

	return err              // ← 返回的是外层那个 err（nil），错误被吞了
}
```

Java 里这段代码根本编译不过（局部变量不允许遮蔽外层局部变量），TS 里 `let` 遮蔽也会被 ESLint 拦。**Go 编译器对此完全沉默** —— 它是合法语义，只是通常不是你想要的。

> 工具兜底：我给你配的 `golangci-lint` 里 `govet` 带了 shadow 检查的一部分，但它并不能抓全。真正的护城河是你的肌肉记忆：**在 if / for 内部写 `:=` 之前，先问一句「外面有同名的吗」**。

## 3. 零值可用（zero value）—— 这是 Go 的设计哲学，不是省事

Go 里**没有未初始化的内存**。每个类型都有确定的零值：

| 类型 | 零值 |
|---|---|
| 数值类型 | `0` |
| `bool` | `false` |
| `string` | `""`（不是 null！） |
| 指针 / slice / map / chan / func / interface | `nil` |
| struct | 每个字段各自的零值（递归） |

对比一下你的旧世界：

```java
String s;            // Java: null，用了就 NPE
List<String> list;   // null
```

```go
var s string         // ""，可以直接 len(s)、拼接、比较
var list []string    // nil slice，但 len(list) == 0、可以 range、可以 append！
```

`append(nil切片, x)` 会正常工作并返回新切片。`range` 一个 nil slice 循环 0 次。这不是「容错」，是**语言承诺**。

**由此产生的设计惯例：好的 Go 类型，零值就应该是可用状态。**

```go
var buf bytes.Buffer   // 直接就能 buf.WriteString(...)，不需要 new
var mu sync.Mutex      // 直接就能 mu.Lock()
var wg sync.WaitGroup  // 直接能用
```

这就是为什么 Go 不需要构造函数：`&Config{}` 拿到的东西应该已经能用了。你写自己的 struct 时也要往这个方向设计（D4 会专门练）。

**唯一的坑：nil map 可读不可写。**

```go
var m map[string]int
fmt.Println(m["k"])   // OK，返回 0
fmt.Println(len(m))   // OK，0
m["k"] = 1            // panic: assignment to entry in nil map
```

因为 slice 的 append 会返回新 header 给你，map 的写入却是原地的，没法「返回一个新 map」。map 必须 `make` 或字面量初始化。D3 详解。

## 4. 基本类型与「没有隐式转换」

### 类型清单

```
整数    int8/16/32/64  uint8/16/32/64  int  uint  uintptr
浮点    float32  float64
复数    complex64  complex128
其他    bool  string  byte(=uint8)  rune(=int32)
```

`int` 的宽度跟平台走（你的 arm64 上是 64 位）。**默认用 `int`**，除非你在做二进制协议、位运算或明确的内存优化 —— 别学 Java 那样纠结 `long` 还是 `int`。

### 零隐式转换

```go
var i int = 3
var f float64 = i        // ❌ 编译错误：cannot use i (int) as float64
var f float64 = float64(i)  // ✅ 必须显式

var a int32 = 1
var b int64 = 2
c := a + b               // ❌ 编译错误：mismatched types int32 and int64
```

Java 会悄悄把 `int` 提升成 `long`、`float`，JS 更是万物皆 number。**Go 一律不给。** 两个不同的类型之间做算术就是编译错误，哪怕它们底层都是整数。

这个规则连「自己定义的类型」也管：

```go
type Celsius float64
type Fahrenheit float64

var c Celsius = 100
var f Fahrenheit = c      // ❌ 编译错误！虽然底层都是 float64
var f Fahrenheit = Fahrenheit(c)  // ✅
```

**这正是今天主练习的核心**：用 `type Celsius float64` 这种「具名类型（defined type）」把单位编码进类型系统，让编译器帮你拦住「把华氏度当摄氏度用」这类 bug。Java 里要达到同样效果，你得包一个 `final class Celsius { private final double value; }`，付出装箱和样板代码的代价；Go 里零成本 —— 运行时它就是个 float64。

> 注意区分：
> - `type Celsius float64` —— **defined type**，新类型，不能互相赋值。用这个。
> - `type Celsius = float64` —— **type alias**（有等号），只是别名，完全等价，编译器不会拦你。极少用，主要用于渐进式重构。

### 浮点数比较

顺便一条今天写测试就会碰到的：**浮点数永远不要用 `==` 比较**。

```go
if got != want { ... }              // ❌ 0.1+0.2 != 0.3
if math.Abs(got-want) > 1e-9 { ... } // ✅ 容差比较
```

我给你的测试骨架里已经用了容差，注意看写法。

## 5. 常量与 iota

### 常量是编译期的、无类型的

```go
const Pi = 3.14159        // 无类型常量（untyped constant）
const MaxRetry int = 3    // 有类型常量
```

「无类型常量」是 Go 的一个精妙设计：它在被使用时才确定类型，且精度是任意的。

```go
const big = 1 << 62       // 合法，编译期算
var f float64 = Pi        // Pi 在这里成为 float64
var c Celsius = 100       // 100 这个无类型常量在这里成为 Celsius —— 不需要转换！
```

注意最后一行：**无类型常量可以直接赋给具名类型**，这不违反「零隐式转换」，因为常量还没有类型。所以你的 `const FreezingC Celsius = 0` 写起来是自然的。

常量只能是基本类型（数值/字符串/布尔），**不能是 slice、map、struct** —— 这些用 `var` 或函数返回。

### iota

`iota` 是「当前 const 块里的行索引」，每个 `const (` 块从 0 开始，每行 +1：

```go
const (
	A = iota   // 0
	B          // 1  —— 省略右边＝重复上一行的表达式
	C          // 2
)
```

真正好用的是配合表达式：

```go
const (
	_  = iota             // 跳过 0
	KB = 1 << (10 * iota) // 1 << 10 = 1024
	MB                    // 1 << 20
	GB                    // 1 << 30
	TB                    // 1 << 40
)
```

这就是标准库和整个生态的写法，今天的小题 A 就是它。

Java 的 enum 是对象、带方法、类型安全；Go 没有 enum，**惯例是「具名类型 + iota 常量组」**：

```go
type Weekday int

const (
	Sunday Weekday = iota
	Monday
	Tuesday
)
```

代价：它本质是个 int，`Weekday(99)` 也能构造出来，编译器不拦。Go 靠的是「你别这么干」+ 校验函数，不是靠类型系统封死。这点比 Java enum 弱，要有心理准备。（配套的 `String()` 方法一般用 `stringer` 工具生成，D4 讲方法时再练。）

## 6. 可见性：首字母大小写

```go
func CToF(c Celsius) Fahrenheit   // 大写开头 → 导出，包外可见
func toKelvin(c Celsius) Kelvin   // 小写开头 → 仅本包内可见
```

只有这两档，**没有 protected、没有 package-private 之外的第三种**。

要点：

1. **粒度是包，不是文件。** 同一个包内的所有文件互相之间完全没有隔离，小写标识符照样随便用。这和 Java 的 default 可见性一致，但和 TS 的「每文件一模块」完全不同 —— 别按文件去想封装。
2. **struct 字段也遵守这条规则。** 小写字段包外读不到，也 **JSON 序列化不了**（D12 会栽在这上面的人很多）。
3. **`internal/` 是编译器强制的第三层。** 路径中含 `internal/` 的包，只有 `internal/` 的父目录子树内才能导入。我们的练习放在 `go/internal/units/`，意味着外部项目即使知道 import path 也导入不了。D6 细讲。

命名惯例（`revive` 会管你）：

- 缩写全大写：`URL`、`ID`、`HTTP`、`API` —— 写 `Url`、`Id` 会被 lint 拦
- 导出的标识符**必须有文档注释**，且注释以标识符名开头：`// CToF 把摄氏度转换为华氏度。`
- getter 不加 `Get` 前缀：`func (u User) Name()` 而不是 `GetName()`

## 附录：你今天问的两个问题

### Q1. Makefile 是什么？

**一句话：Makefile 是「项目命令的快捷方式清单」，等价于 npm 的 `scripts` 字段或 Maven 的 goal。**

`make` 本身是 1976 年的构建工具，本职是「根据文件依赖和时间戳决定重新编译哪些文件」。但在 Go 项目里，**编译依赖分析是 `go build` 自己干的，`make` 那套本职能力用不上**。现在 Go 社区用 Makefile 只剩一个理由：**给一堆记不住的长命令起名字**。

对照着看你就懂了：

```jsonc
// package.json
{ "scripts": {
    "test": "vitest run",
    "lint": "eslint . && prettier --check ."
}}
```
```bash
npm run lint
```

```makefile
# Makefile
lint:
	golangci-lint run ./...
```
```bash
make lint
```

一模一样的东西。

**语法只有四件事要知道：**

```makefile
target: dep1 dep2      # ← 目标名，冒号后面是「先跑哪些别的目标」
<TAB>command1          # ← 必须是真 Tab！不能是空格，这是 make 最恶名昭彰的坑
<TAB>command2
```

1. **缩进必须是 Tab。** 用空格会报 `missing separator`。编辑器自动转空格是新手第一号事故。
2. **依赖会先执行。** 我们的 `check: fmt lint race` 意思是「跑 check 时，依次跑 fmt、lint、race」。
3. **每一行命令是独立的 shell 进程。** 所以 `cd foo` 和下一行的命令不在同一个目录里 —— 要连起来得用 `cd foo && ./run.sh` 写在同一行。
4. **`.PHONY`** 声明「这些 target 不是真实文件名」。因为 make 的本职是造文件，如果目录里恰好有个叫 `test` 的文件，`make test` 会认为「文件已存在且是最新的，无需执行」而直接跳过。`.PHONY: test` 就是告诉它别做这个判断。**Go 项目里几乎所有 target 都该进 `.PHONY`。**

再看我们的 Makefile 就全明白了：

```makefile
.PHONY: check test race lint fmt cover clean

check: fmt lint race     # 交作业前跑这一个
```

`make check` = 格式化 → lint → 带竞态检测跑测试。你只要记 `make check` 一个命令。

**为什么不用别的？** Go 官方没有内置的 task runner（`go run` 只跑程序，不是脚本编排）。社区选项：Makefile（最普遍，零依赖，macOS/Linux 自带）、[Taskfile](https://taskfile.dev)（YAML 写的，跨平台，语法友好得多，新项目值得考虑）、或者干脆 `scripts/*.sh`。D18「构建与交付」会再聊。我们先用 Makefile，因为你去读任何 K8s 生态项目，见到的都是它。

### Q2. `cmd/` 是 Go 的命名规范吗？

**是惯例，不是语言规范。** 分三层说清楚：

**第一层：语言真正强制的，只有两条**

1. `package main` + `func main()` 的包会被编译成可执行文件；其他包编译成库。
2. 路径里含 `internal/` 的包有导入限制（编译器强制）。

除此之外，`cmd/`、`pkg/`、`api/`、`configs/` 这些目录名，**Go 工具链一个都不认识**，纯粹是人类之间的约定。

**第二层：`cmd/` 解决的真实问题**

一个 module 里可能有多个可执行文件。但「一个目录 = 一个包」，而每个可执行文件都得是 `package main` —— 所以**每个可执行文件必须占一个自己的目录**，且目录名就是默认的二进制文件名：

```
go/
├── cmd/
│   ├── hello/main.go      → go build ./cmd/hello  → 产出名为 hello 的二进制
│   └── logstat/main.go    → 产出 logstat
└── internal/
    └── units/             → 库代码，不产出二进制
```

把它们统一收进 `cmd/` 下，好处是「一眼看出这个项目提供哪些命令」，且根目录不会被一堆 main 包目录淹没。标准库自己就这么干（`go/src/cmd/go`、`cmd/compile`、`cmd/vet`）。

**第三层：什么时候不该用**

这是要紧的一点 —— 别当成必须品：

- **单一可执行文件的小项目**：直接在根目录放 `main.go` 就行，别为一个二进制建 `cmd/xxx/`。很多优秀的小工具就是这样。
- **纯库项目**：根本不需要 `cmd/`（比如 `github.com/google/uuid` 就没有）。
- **`pkg/` 争议更大**：那个流传很广的 [golang-standards/project-layout](https://github.com/golang-standards/project-layout) 仓库**不是官方的**（名字有误导性），Go 团队成员公开批评过它把 Java/企业级的目录仪式带进了 Go。`pkg/` 尤其常被认为是纯粹的噪音 —— 把包直接放根目录下就好。

**我们为什么用了 `cmd/hello/`？** 因为这个仓库后面会长出多个可执行文件（D7 的日志分析 CLI、D14 的 API 服务、D19 的巡检 CLI），提前分好比后面搬家省事。

**该记住的原则：Go 的目录结构应该反映「这个项目有哪些包」，而不是套模板。** 从平铺开始，等真的有了多个二进制、真的需要隔离内部实现时，再引入 `cmd/` 和 `internal/`。这和 Java 那种「一上来就 controller/service/dao/dto 四件套」的思路是相反的。
