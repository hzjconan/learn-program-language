## 1. 内存从哪来：Go 和 Java 的不同

| | Java | Go |
|---|---|---|
| 对象放哪 | `new` 一律在堆上。JIT 运行时可能做逃逸分析、标量替换，**你看不到** | **编译期**由编译器决定，`-gcflags=-m` **看得到** |
| 堆分配有多贵 | 很便宜：TLAB 里移动一个指针 | 也不算贵，但每个对象都要 GC 去**扫描** |
| GC | 分代（年轻代 / 老年代）、会整理内存（G1、ZGC） | **不分代、不整理**，并发标记清除 |
| 调参 | `-Xmx`（硬上限）、几十个 GC 参数 | 基本只有两个：`GOGC`、`GOMEMLIMIT`（软上限） |

Java 的经验在这里有两处会误导你：
- **「短命对象很便宜」**：在分代 GC 里，短命对象死在年轻代，几乎不花成本。Go 没有分代，**每次 GC 都要从头标记所有存活对象**。分配得越频繁，GC 就跑得越勤
- **「用对象池是反模式」**：现代 JVM 上确实如此。Go 里 `sync.Pool` 是标准库提供的、正经的手段，`fmt`、`encoding/json` 内部都在用（§7）

## 2. 逃逸分析实操

### 2.1 怎么读 `-m` 的输出

```bash
go build -gcflags='-m' ./internal/escapex
```

| 输出 | 意思 |
|---|---|
| `moved to heap: p` | 局部变量 `p` 被搬到了堆上 |
| `&Point{...} does not escape` | 这个取地址的对象留在栈上 |
| `p escapes to heap` | `p` 的值被复制到堆上（常见于装进 `interface`） |
| `leaking param: p` | 参数 `p` 指向的东西被存到了函数外面（调用方传进来的那块内存会被留住） |
| `p does not escape` | 参数只在函数里用，没被存下来 |
| `func literal escapes to heap` | 闭包本身被分配到了堆上 |
| `can inline F` / `inlining call to F` | 内联，见 §2.3 |

想知道**为什么**逃逸，用 `-m=2`，它会把推理链打出来。

### 2.2 常见原因（更新版）

QA #10 有一张表，今天用 Go 1.26 实测后**更正了一行**：

| 原因 | 例子 | 实测（Go 1.26） |
|---|---|---|
| 返回局部变量的地址 | `return &p` | `moved to heap` |
| 存进包级变量或更外层的结构 | `global = p` | `leaking param` |
| 装进 `interface{}` | `fmt.Sprint(p)` | `p escapes to heap`，**最容易忽略** |
| 闭包捕获、闭包本身被返回 | `return func() { c++ }` | `moved to heap: c` |
| 局部变量太大 | `var a [1 << 20]byte` | `moved to heap`。显式声明的变量超过 **128KB**，`make` 超过 **64KB** 就上堆 |
| ⚠️ `make` 的长度在编译期不确定 | `make([]int, n)` | **`does not escape`**。Go 1.25 起，编译器在栈上预留 32 字节，运行时放得下用栈、放不下才上堆。实测 `n≤4` 个 int 是 0 次分配，`n=5` 是 1 次 |

最后一行说明了一件事：**`-m` 说 `does not escape`，意思是「不一定上堆」，不是「一定不上堆」。** 最终要以 benchmark 的 `allocs/op` 为准。

### 2.3 内联会改变逃逸的结果

```
escapex.go:20:6: can inline NewPoint
escapex.go:21:2: moved to heap: p
```

`NewPoint` 返回 `&p`，所以**单独看这个函数**，`p` 必须上堆。但它能被内联：调用方 `q := NewPoint(1, 2); return q.X` 内联展开后，如果 `q` 在调用方里没有逃逸，`p` 就**可以留在栈上**。

所以分析某个热点函数时，要看的是**调用方那一行**的 `-m` 输出，而不只是函数定义处的。

内联有一个预算：函数「复杂度」超过 80 就不内联。`-m=2` 会打出 `cannot inline F: function too complex: cost 92 exceeds budget 80`。
把热路径上的小函数写得足够小，让它能被内联，是 Go 里常见的优化手段。PGO（§8）会对热点函数放宽这个预算。

### 2.4 逃逸不是罪过

`-m` 里满屏的 `escapes to heap` 很正常。**只在热路径上**（profile 里排在前面的那些函数）才值得关心。
在一个每秒调用三次的函数里消灭一次分配，没有任何意义。

## 3. GC 是怎么工作的

### 3.1 一句话模型

Go 的 GC 是**并发的标记-清除**：
1. **标记**：从根（栈、全局变量）出发，顺着指针找到所有还活着的对象。大部分时间和你的代码**并发**进行，只有开头和结尾各有一次很短的 STW（stop-the-world，通常远小于 1ms）
2. **清除**：没被标记到的内存回收，留给后面的分配使用。「回收」其实还分两步，见下面

#### 标记完以后，垃圾什么时候真的被回收

```
① 标记    判定谁是垃圾                  ← gctrace 的 220->222->138 到这一步为止
② 清扫    把垃圾占的位置标成「可复用」     ← 标记一结束就开始，并发、按需进行
③ 归还    把长期空着的内存还给操作系统     ← 更晚，后台慢慢做，RSS 到这一步才下降
```

**② 清扫（sweep）**：Go 把堆切成固定大小的格子，同样大小的格子放在一起叫一个 **span**。清扫就是逐个 span 检查，没打上标记的格子记为空闲。
**不移动对象，也不清零**，只是改记账；下次分配到这个格子时才清零。两种方式同时推进：

- **后台清扫**：`bgsweep` goroutine 用空闲 CPU 一个个扫
- **分配时顺带清扫**：分配前先替 GC 扫一些 span（`deductSweepCredit`）。分配越多、顺带扫得越多，进度跟得上。和 mark assist 同一个思路：**谁分配，谁出力**

一个 span 全空了，整块交还给堆，可以切成别的大小再用。**截止时间**：下一次 GC 开始前必须扫完（`finishsweep_m`）。

**③ 归还（scavenge）**：清扫完的内存仍然**属于进程**，RSS 不变。后台的 `bgscavenge` 找长时间没用的空闲页，通过 `madvise` 告诉操作系统「不要了」，RSS 才下降。
故意做得慢：刚释放的很可能马上又要用，还了再要回来更贵。想观察用 `GODEBUG=scavtrace=1`。这就是下面 §3.5「RSS 对不上」的原因。

| | Java（G1、ZGC） | Go |
|---|---|---|
| 怎么回收 | **复制**：存活对象搬到新区域，旧区域整块变空 | **不移动**：存活对象原地不动，垃圾的格子标成可复用 |
| 碎片 | 搬完就没有 | 可能有。按大小分类的格子能缓解很多 |
| 回收后多快能用 | 整块区域立刻可用 | 要等清扫到那个 span |

Go 不移动对象的好处是**指针永远不变**（cgo、`unsafe` 都依赖这一点），也省了搬运成本；代价是碎片和多出来的清扫这一步。

⭐ 准确的说法：**标记后判定为垃圾，清扫后可以复用，归还后才从 RSS 里消失。**

标记期间，你的代码还在改指针，所以编译器会插入**写屏障**，让 GC 不漏掉任何对象。这部分开销是自动的，你不用管。

Go 1.26 默认启用了新的标记实现 **Green Tea**：按内存页成批扫描小对象，缓存命中率更高。D16 的 CPU profile 里出现过的 `runtime.tryDeferToSpanScan` 就是它。对你写代码没有影响。

### 3.2 ⭐ GC 的成本由什么决定

```
GC 总开销 ≈ 每次 GC 的成本 × GC 的次数
            └ 和存活对象的数量、里面指针的多少成正比
                                └ 和分配速度成正比，和预留的空间成反比
```

所以降低 GC 开销**只有两个方向**：
- **少分配**：GC 次数自然就少了。这是 §5、§6 要做的事
- **给更多空间**：调大 `GOGC`，每次 GC 之间允许堆长得更大。用内存换 CPU

还有一个不太常用的方向：**减少存活对象里的指针**。一个 `[]int64` 不含指针，GC 不用扫描它的内容；一个 `[]*Entry` 里的每个元素都要扫描。

### 3.3 `GOGC`：下一次 GC 在什么时候发生

```
目标堆大小 = 存活堆 + (存活堆 + GC 根) × GOGC / 100
```

默认 `GOGC=100`：上次 GC 后剩下 100MB，那么堆长到大约 200MB 时触发下一次。
`GOGC=200` 等到 300MB，`GOGC=50` 等到 150MB，`GOGC=off` 完全关闭 GC。

### 3.4 `GOMEMLIMIT`：内存软上限（Go 1.19）

告诉 runtime「整个进程的 Go 内存尽量别超过这个数」。快要到上限时，不管 `GOGC` 怎么设，GC 都会更频繁地运行。

⚠️ 它是**软上限**，和 Java `-Xmx` 的硬上限不一样：
- 如果**存活的数据本身就超过了上限**，GC 再怎么跑也压不下去。runtime 会限制 GC 最多占用约 50% 的 CPU（防止「死亡螺旋」，即 CPU 全被 GC 吃掉），然后**允许内存超过上限**
- 它只管 Go runtime 管理的内存，不包括 cgo 分配的内存

### 3.5 实测：100 万行日志，`cmd/loganalyze`

每种配置跑 3 次（Apple M1 Pro，10 核）：

| 配置 | GC 次数 | 最大 RSS | 耗时 |
|---|---|---|---|
| `GOGC=100`（默认） | 20–22 | 307–368MB | 0.60s |
| `GOGC=50` | 25 | 333–397MB | 0.70s |
| `GOGC=400` | 5–6 | 374–407MB | 0.59s |
| `GOGC=off` | 0 | 679MB | 0.60s |
| `GOGC=off GOMEMLIMIT=600MiB` | 1 | 645MB | 0.60s |
| `GOGC=100 GOMEMLIMIT=150MiB` | **48–53** | **234–287MB** | **0.78s** |

读这张表：
- GC 次数确实跟着 `GOGC` 走：50 → 25 次，400 → 6 次
- **耗时几乎没变**：这个程序只跑 0.6 秒，GC 是并发的，10 个核里有空闲的核替它干活。在 CPU 已经吃满的线上服务上，差距会大得多
- **RSS 和 GOGC 对不上**，甚至 `GOGC=50` 比 `100` 还高。原因见下面「RSS 是什么」。**看 Go 内存要看 gctrace 和 `go_memstats_*` 指标，不要只看 RSS**
- **最后一行**：这个程序要把所有记录存到最后，存活数据超过 150MB。上限设得比存活数据还小：GC 次数翻倍、耗时多了 30%，**RSS 还是超过了 150MB**。这就是「软上限」的意思

#### RSS 是什么，为什么它和 GOGC 对不上

**RSS（Resident Set Size，常驻内存集）**：进程此刻**实际占用了多少物理内存**。`top`、`ps`、活动监视器里的「内存」基本都是它。

Go 进程的 RSS 由好几部分组成，堆只是其中之一：

```
RSS（操作系统看到的）
├── Go 堆里正在用的对象              ← gctrace 的「存活堆」主要说的是这块
├── Go 堆里已经释放、还没还给操作系统的内存   ← 上面那张表 RSS 对不上的主因
├── goroutine 的栈
├── runtime 自己的数据结构（GC 元数据等）
└── 程序代码、动态链接库
```

GC 回收的内存**不会马上还给操作系统**，因为很可能马上又要用。后台的 scavenger 会**慢慢地**把长时间没用的内存还回去。
所以同一个配置跑三次，RSS 能差出几十 MB；`GOGC=50` 的 RSS 也可能比 `GOGC=100` 高：GC 跑得更勤，但回收下来的内存还有多少留在进程里，取决于 scavenger 恰好进行到哪一步。

和 Java 一样：`-Xmx2g` 的进程，`top` 里显示 2.6GB 很正常（元空间、线程栈、直接内存、JIT 代码……）。**堆大小和进程的 RSS 从来不是一回事。**

| 想知道 | 看什么 |
|---|---|
| Go 程序有没有泄漏、堆有多大 | gctrace 的存活堆，或指标 `go_memstats_heap_inuse_bytes` |
| 会不会被 OOMKill | 容器内存用量 `container_memory_working_set_bytes`（cgroup 按它判断，包括 RSS 和一部分文件缓存） |
| 进程整体占了多少物理内存 | RSS，指标 `process_resident_memory_bytes`（D16 ① operator 的 `/metrics` 上就有） |

⚠️ 两个实操的坑：
- `/usr/bin/time -l` 的 `maximum resident set size`：macOS 上单位是**字节**，Linux（`/usr/bin/time -v`）上是 **KB**。练习 ③ 算的时候别差出 1024 倍
- 它是整个运行过程中的**峰值**，不是结束时的值

### 3.6 读 `GODEBUG=gctrace=1`

```
gc 19 @0.548s 3%: 0.017+3.1+0.020 ms clock, ..., 220->222->138 MB, 225 MB goal, 0 MB stacks, 0 MB globals, 10 P
```

| 片段 | 意思 |
|---|---|
| `gc 19` | 第 19 次 GC |
| `@0.548s` | 进程启动后多久 |
| `3%` | 到目前为止 GC 占了总 CPU 的 3% |
| `0.017+3.1+0.020 ms clock` | STW 开始 + **并发标记** + STW 结束。两头的 STW 都远小于 1ms |
| `220->222->138 MB` | GC 开始时堆多大 → 标记结束时多大 → **标记后还活着多少** |
| `225 MB goal` | 这次的目标堆大小，按 §3.3 的公式算出来的 |
| `10 P` | 用了几个 P，也就是 GOMAXPROCS |

#### `220->222->138`：为什么标记期间堆还会变大

三个数是同一次 GC 里三个时间点的值（runtime 文档：heap size at GC start, at GC end, and live heap）：

```
220 MB   标记开始时堆有多大
  │      并发标记进行中（3.1ms，就是 0.017+3.1+0.020 中间那个数）
  │      程序没停，还在分配 → 堆又长了 2MB
222 MB   标记结束时堆有多大
  │      所有能从根找到的对象都标记完了
138 MB   其中还活着的 = 存活堆。222 − 138 = 84MB 是垃圾，接下来清除
```

**标记期间新分配的对象，这一轮一律当作存活**：GC 来不及判断，等下一轮。所以那 2MB 也算在 138MB 里。

**为什么在 220 就开始，而不是等到 goal 225**：runtime 的 **pacer** 会根据上一轮估算「标记期间还会分配多少」，**提前**启动，让标记刚好在堆长到 goal 之前完成。这一次 222 < 225，估得很准。

⚠️ 如果第二个数**超过了 goal**，说明分配快到 GC 追不上。runtime 会让正在分配的 goroutine **先帮忙标记一部分再继续**，叫 **mark assist**。它直接拖慢业务代码，是「分配一多延迟就突然升高」的常见原因，CPU profile 里显示为 `runtime.gcAssistAlloc`。

和 Java 对比：CMS、G1 的并发标记原理一样，标记期间新分配、来不及判断的对象叫「浮动垃圾」。区别是 G1 跟不上时退化成一次长时间的 Full GC；Go 让分配的 goroutine 帮忙，把代价**摊到每次分配上**，不会出现一次很长的停顿。

`->138 MB` 是最重要的数：它就是**存活堆**。如果它在一次次 GC 之间**一直往上涨**，说明有东西被留着没释放，就是 D16 ⑤ 的那种泄漏。

### 3.7 ⭐ 在 K8s 里怎么设

- **`GOMEMLIMIT` 设成容器内存上限的 90% 左右**：比如容器限制 512Mi，就设 `GOMEMLIMIT=460MiB`。不设的话，GC 不知道容器有上限，堆一路长到 OOMKill
- 剩下的 10% 留给 goroutine 栈之外、runtime 管不到的内存（cgo、page cache 等）
- 内存紧张、CPU 有余的服务：`GOGC=off` 加 `GOMEMLIMIT`，只在快到上限时才 GC
- **GOMAXPROCS**：Go 1.25 起，runtime 会读取容器的 CPU 限制来设置它（`runtime/cgroup_linux.go`）。以前容器限制 2 核、节点有 64 核时，GOMAXPROCS 会是 64，导致严重的 CPU 节流，那时大家都要引入 `automaxprocs` 这个库。现在不需要了

## 4. 先测量，再优化

### 4.1 流程

```
① 基线      go test -bench=Big_EndToEnd -benchmem -count=10 ./internal/logx > base.txt
② 找热点    -cpuprofile / -memprofile，go tool pprof 看 top 和 list
③ 改一处    一次只改一个地方
④ 守住行为  golden 测试 + 原有测试全绿
⑤ 证明      同样的命令跑 new.txt，benchstat base.txt new.txt
⑥ 记录      把这一步的 benchstat 结果写进笔记，然后回到 ②
```

**一次只改一处**是这里面最容易被跳过的一条。一次改三处、快了 40%，你不知道是哪一处起的作用，也不知道是不是有一处其实让它变慢了。

### 4.2 从 benchmark 直接拿 profile

```bash
go test -run '^$' -bench Big_EndToEnd -benchmem \
  -cpuprofile profile/d17/cpu.out -memprofile profile/d17/mem.out ./internal/logx

go tool pprof -top profile/d17/cpu.out
go tool pprof -sample_index=alloc_objects -top profile/d17/mem.out   # D16 小题 B5：看分配次数
go tool pprof -http=localhost:0 profile/d17/cpu.out                  # 火焰图
```

`-run '^$'` 是为了不跑普通测试（QA #14）。`-memprofile` 记录的就是 D16 讲的 heap profile，查**GC 压力**时看 `alloc_objects` 或 `alloc_space`，查**泄漏**时看 `inuse_*`。

### 4.3 benchstat：差别是不是真的

装一次就行（代理不在跑的话，前面加 `env -u HTTP_PROXY -u HTTPS_PROXY`）：

```bash
go install golang.org/x/perf/cmd/benchstat@latest
```

```bash
go test -run '^$' -bench Big_EndToEnd -benchmem -count=10 ./internal/logx > profile/d17/base.txt
# ……改代码……
go test -run '^$' -bench Big_EndToEnd -benchmem -count=10 ./internal/logx > profile/d17/step1.txt
benchstat profile/d17/base.txt profile/d17/step1.txt
```

输出大概是这样（数字是示意）：

```
                 │  base.txt   │              step1.txt              │
                 │   sec/op    │   sec/op     vs base                │
Big_EndToEnd-10    111.8m ± 2%   84.8m ± 1%  -24.15% (p=0.000 n=10)
```

- **`± 2%`**：10 次运行的波动范围。两边的区间重叠很多的话，差别可能只是噪音
- **`p=0.000`**：差别是噪音的概率。小于 0.05 才算数。benchstat 判断不显著时会显示 `~`，**那就等于没有提升**
- **`-count=10`**：少于 10 次，p 值算不出来，或者不可信

一次跑出来快了 15%，不说明任何问题。笔记本的温度、后台开的浏览器都能造成这个差别。

#### 读 benchstat 的完整输出

benchstat 的输出通常有**三块**，行和列都一样，区别在每块表头的**第二行**：

| 块 | 表头第二行 | 意思 |
|---|---|---|
| 第一块 | `sec/op` | 每次操作的耗时（原始输出的 `ns/op`，换算成了 `m`、`µ` 这类单位） |
| 第二块 | `B/op` | 每次操作分配的字节数（`Mi` = MiB） |
| 第三块 | `allocs/op` | 每次操作分配的次数 |

每块里：行是 benchmark，列是输入文件，单元格是 10 次的**中位数** `± 波动范围`，`vs base` 是相对第一个文件的变化。

**`geomean`（几何平均）**：n 个数相乘再开 n 次方，用一个数概括「这一批 benchmark 总体快了还是慢了」。
用几何平均而不是算术平均，是因为性能变化是**比例**：A 从 1ms 变 2ms（慢 2 倍）、B 从 100ms 变 50ms（快 2 倍），
算术平均说「快了 48%」，几何平均说「没变」，后者才对。只关心一个 benchmark 时可以忽略它。

**`¹ benchmark set differs from baseline; geomeans may not be comparable`**：两个文件里的 benchmark 不是同一批
（比如基线跑了 3 个，新的只跑了 1 个），两边的 geomean 一个是三个数的平均、一个是单独一个数，没法比较。
`vs base` 的百分比只用两边都有的 benchmark 算，所以那一列仍然可信。解决办法：

```bash
benchstat -filter '.name:Big_EndToEnd' profile/d17/base.txt profile/d17/step4.txt   # 只比这一个
```

或者两边始终跑同一批 benchmark。

### 4.4 ⚠️ benchmark 测的场景，必须和真实使用一致

`internal/logx/big_test.go` 里有三个 benchmark：

| | 测什么 | 用来 |
|---|---|---|
| `BenchmarkBig_EndToEnd` | 解析一遍 + 出一份报告，就是 `cmd/loganalyze` 做的事 | ⭐ **判断优化效果，以它为准** |
| `BenchmarkBig_Analyze` | 只解析 | 判断时间花在哪一半 |
| `BenchmarkBig_Format` | 只出报告，**每一轮用同一个 Report** | 同上 |

最后一行有个坑，我备课时踩到了：如果你在 Report 里加了缓存，`BenchmarkBig_Format` 只有第一轮真正在计算，后面全部命中缓存，结果显示快了很多。但 `cmd/loganalyze` 每次只调用一次 Format，**根本用不上这个缓存**。

**benchmark 的数字只对它所测量的那个场景有效。** 场景和真实使用不一致，数字就会骗人。D6 讲的「返回值不赋给 sink，编译器把整个调用优化掉」也是同一类问题。

### 4.5 本地 benchmark 和线上环境

**本地 benchmark 的绝对数字不能直接代表线上。** 它真正可信的是「同样条件下，A 比 B 快多少」这个**相对比较**。

| | 本地 benchmark | 线上 |
|---|---|---|
| 输入数据 | `bigLog` 合成数据：耗时均匀、服务名 5 个 | 真实日志：分布可能很偏 |
| CPU 和系统 | Apple M1、macOS（`madvise` 的特殊行为） | x86 / ARM 服务器、Linux |
| CPU 资源 | 10 核独占，GC 后台工作有空闲核 | 容器可能只有 1～2 核，GC 和业务**抢同一份 CPU** |
| 并发 | 一个 goroutine | 几百个请求同时进来，锁竞争、缓存干扰 |
| 存活堆 | 只有 benchmark 自己的数据 | 整个服务的数据（连接池、缓存），每次 GC 都要扫 |

例：§3.5 里 `GOGC=50` 和 `400` 耗时几乎一样，因为 10 个核有空闲的给 GC 用。放进限制 1 核的容器，GC 的每一毫秒都从业务那里抢，差距会大得多。

**能带到线上的结论**：
- ✅ `allocs/op`：和机器、系统无关
- ✅ 算法改进：O(n log n) → O(n) 在哪都成立
- ⚠️ `ns/op` 的百分比：方向一般对，幅度会不同
- ❌ `ns/op` 的绝对值

**线上怎么验证**：

1. **部署前后对比线上指标**（D16）：
   - 分配速度 `rate(go_memstats_alloc_bytes_total[5m])`：本地 `B/op` 在线上的对应物，应该直接下降
   - GC 开销 `go_gc_duration_seconds`、GC CPU 占比
   - 请求延迟 P99（QA #21）：用户真正感受到的
   - 每个请求的 CPU：容器 CPU 使用量 ÷ QPS
2. **持续 profiling**（Pyroscope、Parca，QA #24）：部署前后直接看那个函数在线上的占比降了多少，最直接的证据
3. **金丝雀发布**：新版本先接 5% 流量，和旧版本同时跑、比较。两边承受同一时刻的真实流量，排除「今天流量本来就少」这类干扰
4. **预发环境压测**：回放录下来的真实流量或真实数据（HTTP 常用 k6、vegeta）
5. **让 benchmark 更接近线上**：输入用真实数据的样本；CI 里用和线上相同的架构和系统跑。CI 机器吵，`ns/op` 波动大，**拿 `allocs/op` 当卡点**更稳
6. **PGO**（§7）：把线上 profile 喂回编译器，同一个思路：以线上为准

⭐ **本地 benchmark 用来比较「改了比没改好多少」、开发时快速迭代；线上指标、持续 profiling、金丝雀用来证明「线上确实变好了」。** 只有本地数据，不知道线上有没有效果；只有线上数据，每试一次都要部署一次。

对 `loganalyze` 来说，「线上」就是在真实日志文件上运行它。练习 ③ 用 100 万行比较新旧两个版本，相当于一次小规模的线上验证。

## 5. 减少分配的常用手法

先看 profile，**profile 指向哪里才改哪里**。下面这些是常见的手法，不是清单，不需要全部用上：

| 手法 | 说明 |
|---|---|
| 预分配 | `make([]T, 0, n)`、`make(map[K]V, n)`、`strings.Builder.Grow(n)`（D6、QA #12） |
| 别重复转换 | `[]byte` ↔ `string` 每次转换都要分配并复制。同一份数据不要转两次 |
| 别为了切分而分配 | `strings.Split` 返回一个新的 `[]string`；只需要前几段时，`strings.Cut` 不分配 |
| 热路径上避免装箱 | 值装进 `interface{}`（包括传给 `fmt`）往往会逃逸（§2.2） |
| 少存指针 | 存活的数据里指针越少，GC 扫描越快（§3.2） |
| 复用缓冲区 | `sync.Pool`（§6） |
| ⭐ **先想算法** | 最大的提升往往不在分配上：同一份数据排序了几次？只要前 10 个时，有没有必要把 20 万个全部排好？ |

最后一行要单独强调：**常数级的优化（少一次分配）最多让你快几成，算法上的改进可以快好几倍。** 先看 CPU profile 里最大的那几块是什么，再决定往哪个方向使劲。

## 6. `sync.Pool`

```go
var bufPool = sync.Pool{
	New: func() any { b := make([]byte, 64<<10); return &b },
}

func handle(...) {
	bp := bufPool.Get().(*[]byte)
	defer bufPool.Put(bp)
	buf := *bp
	...
}
```

### 6.1 它是什么

- 一个**临时对象**的缓存。`Get` 拿一个出来，没有就调用 `New` 新建；用完 `Put` 回去，下次复用
- 每个 P 有自己的本地缓存，所以高并发时几乎没有锁竞争
- ⚠️ **每次 GC 都可能清空它**（准确地说，放进去的对象最多能活过一次 GC）。它**不是**连接池，不能用来存数据库连接这类必须保留的东西

### 6.2 四个坑

1. **放指针，不要放切片本身**：`Put(buf)` 会把切片头（3 个字段）装进 `any`，装箱这一步本身又要分配一次。所以要放 `*[]byte`。staticcheck 的 SA6002 会检查这一点
2. **放回去之前要清理**：`bytes.Buffer` 要 `Reset()`，结构体要清空字段。否则下一个使用者会读到上一个请求的数据
3. **放回去以后，任何人都不能再引用它**：`Put` 之后这块内存随时可能被另一个请求拿走、覆盖。如果有地方还留着它的引用（比如一个切片指向它），那里的数据会**悄悄变掉**
4. **别把特别大的对象放回去**：某次请求把 buffer 扩容到了 10MB，放回池子以后，它就一直占着这 10MB。常见做法是 `Put` 之前判断 `cap(buf) > 某个上限` 时直接丢弃

第 3 条和你 D16 ⑤ 修的那个 bug 直接相关，练习 ④ 会遇到。

### 6.3 什么时候值得用

- **高频**：每秒成千上万次
- **对象偏大**：几 KB 以上的缓冲区
- **生命周期很短**：在一次请求里用完就还

三条都满足，profile 里也确实看到它是分配的大头，才值得引入。它让代码变复杂了，而且第 3 条那种 bug 很难查。
