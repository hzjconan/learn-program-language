## 1. 多返回值

Go 的函数可以返回多个值，这不是语法糖，它重塑了整个标准库的 API 形态：

```go
func Divide(a, b float64) (float64, error)
v, ok := m["key"]        // map 查找的「逗号 ok」惯用法
n, err := f.Read(buf)
```

Java 想返回两个值，要么造个 `Pair<A,B>`、要么造个 DTO、要么抛异常。TS 可以返回元组或对象，但 `{ value, error }` 这种形状从来没成为主流。**Go 把它变成了默认姿势**，于是「返回一个值 + 一个错误」成了整个生态的统一形状。

三个必须记住的惯例：

1. **`error` 永远是最后一个返回值。**（`revive` 的 `error-return` 规则强制）
2. **返回 error 时，其他返回值应该是零值**，调用方不该去读它们。
3. **「逗号 ok」形式**：`v, ok := m[k]`、`v, ok := x.(T)`、`v, ok := <-ch`。这三个地方的第二个值是 `bool` 不是 `error`——因为「键不存在」不是错误，是正常结果。

### 忽略返回值

```go
v, _ := strconv.Atoi(s)   // 显式丢弃错误
```

`_` 是空白标识符（blank identifier）。**注意：Go 编译器并不强制你处理 error**——`v, _ := f()` 完全合法，甚至 `f()` 单独一行丢弃所有返回值也合法。

真正拦你的是 lint。我给你配的 `errcheck` 打开了 `check-blank: true`，意思是**连 `_` 显式丢弃都要报**。这比多数生产项目严，学习期故意的：让你每次丢弃错误时都必须停下来想一秒。

## 2. 值、指针与参数传递

### 2.1 三个符号

```go
x := 42
p := &x          // & 取地址 → p 的类型是 *int
fmt.Println(*p)  // * 解引用 → 42
*p = 100         // 通过指针改原值
fmt.Println(x)   // 100
```

| 写法 | 出现位置 | 含义 |
|---|---|---|
| `*int` | **类型位置** | 「指向 int 的指针」这个类型 |
| `*p` | **表达式位置** | 解引用，取出 p 指向的值 |
| `&x` | 表达式位置 | 取 x 的地址 |

`*` 在两个位置意思完全不同，这是初学最容易糊的地方。**看它是在类型声明里，还是在算式里。**

### 2.1.1 两个变量的地址一定不同

```go
a := 1
b := 1
```

```
&a = 0x547d08ba0010
&b = 0x547d08ba0018        ← 差 8 字节，栈上相邻的两个槽

a == b   → true    (比【值】)
&a == &b → false   (比【地址】)
```

**两个不同的变量 = 两块不同的内存**，值恰好相同不影响这一点。Go 不会把相同的整数「合并」成一个。

### 2.1.2 `==` 到底比什么 —— Java 的旧直觉在这里是反的

Java 里这段是有名的面试题：

```java
Integer a = 1,    b = 1;     a == b  →  true      ← 因为有 Integer 缓存（-128..127）
Integer c = 1000, d = 1000;  c == d  →  false     ← 超出缓存范围，两个对象
```

**Java 的 `==` 对包装类型比的是引用**，而 `Integer.valueOf` 对小整数做了缓存，于是同一段代码的行为随数值大小而变。你得记住写 `.equals()`。

**Go 没有这个坑**，理由是双重的：

1. **`int` 就是 `int`，没有包装类型**，不存在「装箱后是不是同一个对象」的问题。
2. **`==` 的语义按类型固定**，不会因为数值大小而改变行为：

| 类型 | `==` 比什么 |
|---|---|
| 数值 / bool | 值 |
| **string** | **内容** ⭐ 不需要 `.equals()`，不需要 `intern()` |
| 指针 | 地址 |
| interface | 动态类型 + 动态值 |
| struct | 逐字段比较（字段全部可比较时） |
| **slice / map / func** | **不可比较**，`==` 是编译错误（只能和 `nil` 比） |

```go
s1, s2 := "hello", "hello"
s1 == s2      // true   ⭐ 字符串比内容
&s1 == &s2    // false  两个不同的变量

var i1 any = 1
var i2 any = 1
i1 == i2      // true   接口比「类型+值」，也是比值
```

**「字符串用 `==` 比」是 Java 程序员最容易带错旧习惯的地方**，在 Go 里放心用。

（Go 运行时内部确实对 0~255 的小整数做了缓存以避免装箱分配，但**这个优化不可观测**——语义上永远是比值，不像 Java 那样把实现细节泄漏成了语义。）

### 2.1.3 不是所有东西都能取地址

```go
&42                    // ❌ 编译错误：不能对字面量取地址
const c = 1; &c        // ❌ 常量没有地址
m := map[string]int{}
&m["k"]                // ❌ map 元素不可寻址（D3 讲为什么）
```

能取地址的叫**可寻址（addressable）**：变量、指针解引用 `*p`、slice 元素、数组元素、可寻址 struct 的字段。

两条延伸：

- **零尺寸类型是个未定义地带。** 规范原文：*"Two distinct zero-size variables **may** have the same address in memory."* 实测 `var x, y struct{}; &x == &y` 这次是 `false`，但**两种结果都合法**。实际影响：用 `map[string]struct{}` 当集合时，别去比 value 的地址。
- **没取地址的变量可能压根不在内存里。** 编译器的逃逸分析会把它放进寄存器，此时它没有地址可言。你一写 `&a` 就强制它可寻址——但**不一定逃逸到堆**，只有指针跑出函数作用域时才会。D17 用 `-gcflags=-m` 实测。

### 2.2 你在 Java 里一直在用指针，只是不让你选

Java 的 `User u = new User()` —— **`u` 就是一个指针**（Java 管它叫「引用」）。JVM 只是不让你写 `&` 和 `*`，也不让你选择要不要间接层。

**Go 的区别是把这个选择权交还给你了：**

```go
var a User      // 一个 User 值，就在栈上/结构体里，没有间接层
var b *User     // 一个指向 User 的指针，可以是 nil
```

于是有了 Java 里不存在的一个后果——**Go 的 struct 赋值是拷贝**：

```go
a := User{Name: "Alice"}
c := a              // ⭐ 整个 struct 被复制了一份
c.Name = "Bob"
fmt.Println(a.Name) // "Alice" —— 没变

p := &a
q := p              // 复制的是指针（8 字节），指向同一个 User
q.Name = "Bob"
fmt.Println(a.Name) // "Bob" —— 变了
```

Java 里 `User c = a; c.name = "Bob";` **一定**会改到 `a`，因为你拿到的永远是引用。**Go 里默认是拷贝，要共享必须显式说。** 这是从 Java 过来最需要重装的直觉之一。

（TS 同理：对象和数组都是引用，`const c = a` 之后改 `c.name` 会影响 `a`。）

### 2.3 关键语法糖：自动解引用

```go
p := &User{Name: "Alice"}
fmt.Println(p.Name)      // ✅ 不用写 (*p).Name
p.Name = "Bob"           // ✅ 直接改
```

**访问字段和调用方法时，Go 自动帮你解引用。** 所以实际写 Go 时你极少手写 `*p`——只有处理 `*int`、`*string` 这种指向基本类型的指针时才需要。

这也是为什么 Go 代码看起来「不像 C」：C 里到处是 `p->field`，Go 里 `.` 通吃。

**但自动解引用只有三个地方生效：**

| 场景 | 等价于 |
|---|---|
| 字段访问 `p.Name` | `(*p).Name` |
| 方法调用 `p.Method()` | `(*p).Method()` |
| 指向数组的指针取下标 `pa[i]` | `(*pa)[i]` |

**传参、比较、赋值都不解引用。** `p == q` 比的是两个地址相不相等，不是内容。

### 那 `fmt.Println(p)` 呢？

```go
p := &User{Name: "Alice"}
fmt.Println(p)     // → &{Alice}
```

**打印出了内容，但这不是语言的自动解引用。** 传给 `fmt.Println` 的确确实实是那根指针本身（§2.5：Go 永远传值）。是 `fmt` 在运行时用反射发现「这是个指向 struct 的指针」，主动替你打了内容，并加个 `&` 提示你原物是指针。

区分清楚这一点很重要，因为 `fmt` 的照顾**只有一层**，而且有几个会咬人的边界：

```
%v   → &{Alice <nil>}
%+v  → &{Name:Alice Boss:<nil>}
%#v  → &main.User{Name:"Alice", Boss:(*main.User)(nil)}   ← 最精确，一眼看出是指针
%p   → 0x3d8280cba000
```

**① 嵌套的指针字段不递归，直接打地址：**

```
&{Name:Alice Boss:0x3d8280cba078}      ← Boss 是 *User 字段
```

**② ⚠️ 最容易撞的坑：`[]*T` 打出来是一排地址**

```
[]*User  →  [0x3d8280cba0a8 0x3d8280cba0c0]     ← 啥也看不见
[]User   →  [{A <nil>} {B <nil>}]                ← 正常
```

切片元素不是最外层，`fmt` 的照顾不生效。而 `[]*T` 在真实代码里到处都是（数据库查询结果、对象列表…），你迟早会打出满屏十六进制。

**③ 指向基本类型的指针一律打地址：**

```go
n := 42
fmt.Println(&n)    // 0x3d8280c94020  —— 不是 42
fmt.Println(*n)    // 42  —— 必须手动解引用
```

`fmt` 只对**指向 struct 的指针**做特殊处理。

**④ nil 指针打 `<nil>`，不会炸。** `fmt` 内部有 recover。但如果你的 `String()` 方法里解引用了 nil，输出会变成 `%!v(PANIC=...)`——不崩程序，但很难看。

**⑤ 正统解法：给类型实现 `String() string`**

```
Temp(36.6)   →  36.6°C
&Temp(36.6)  →  36.6°C      ← 值和指针都走 String()
```

只要类型有 `String() string` 方法，`fmt` 的所有 `%v` / `Println` 都改走它。**这就是解决 `[]*User` 打地址问题的正确办法**——给 `*User` 实现 `String()`，切片自然就可读了。

接收者用值还是指针会影响「谁能用上这个 `String()`」，这正是 D4 的核心话题。

> **一句话记法：`fmt` 帮你解一层，语言只在 `.` 和 `[]` 上帮你解。其余地方指针就是指针。**

### 2.4 `&T{...}`：Go 最常见的一行

```go
p := &User{Name: "Alice"}    // ⭐ 复合字面量取地址
p := new(User)               // 等价于 &User{}，但更少用
```

Go 没有构造函数，惯例是返回指针的 `NewXxx` 函数：

```go
func NewUser(name string) *User {
	return &User{Name: name}
}
```

你今天写 `return &ParseError{Line: n, Text: line, Err: ErrEmptyKey}` 用的就是它。

### 2.5 Go 永远传值 —— 没有例外

这是本节最重要的一条：**Go 只有值传递。传指针时，传进去的是「指针变量的拷贝」**——一个新的 8 字节变量，里面装着同一个地址。

```go
func modifyPointee(u *User)   { u.Name = "改了" }         // 改【指向的对象】
func reassignPointer(u *User) { u = &User{Name: "换了"} } // 改【指针本身】
```

跑 `go run ./cmd/ptrdemo` 看真实输出：

```
传入前:            原始            (地址 0x...020)
函数里改 u.Name:   改了指向的对象    (地址 0x...020)   ← 可见
  （函数内 · 赋值前: 改了指向的对象   地址 0x...020）
  （函数内 · 赋值后: 换了个对象      地址 0x...060 ← 确实变了，但只在这里）
函数里改 u 本身:   改了指向的对象    (地址 0x...020)   ← 没变
```

**盯住地址那一列**：函数内部赋值后地址从 `...020` 变成了 `...060`，说明赋值**确实生效了**——生效在那份拷贝上。函数一返回，拷贝消失，调用方手里的 `u` 还是 `...020`。

这就是「传值」最硬的证据：不是「赋值没起作用」，而是**你改的根本不是同一个变量**。

> **一句话记法：拷贝的是指针，不是指针指向的东西。**
> 你能透过它改远端的数据，但改不了调用方手里那根「指针」本身。

**和 Java 完全一致。** Java 也是永远传值——传对象时传的是「引用的拷贝」。`void f(User u) { u.name = "x"; }` 调用方看得见；`void f(User u) { u = new User(); }` 调用方看不见。你已经懂这个模型，Go 只是把 `*` 明写出来了。

**这条直接解释了今天作业里的一个写法：**

```go
var pe *ParseError          // pe 本身已经是指针类型
errors.As(err, &pe)         // 但要传 &pe，也就是 **ParseError
```

因为 `errors.As` **要给 `pe` 赋值**——它找到匹配的错误后要写进去。既然只有值传递，想改调用方的变量就必须传变量的地址。同理：

```go
json.Unmarshal(data, &cfg)   // 要填充 cfg
fmt.Sscanf(s, "%d", &n)      // 要填充 n
```

**看到标准库要求 `&`，一律是「它要写回给你」。**

### 2.5.1 返回值同样是拷贝

「永远传值」不只管参数，**返回值也一样**：

```go
func t() Config {
	a := Config{...}
	return a          // 把整个 Config 拷贝一份给调用方
}

func t2() *Config {
	a := Config{...}
	return &a         // 拷贝【指针】，指向同一个 Config（它会逃逸到堆上）
}
```

（编译器可能优化掉实际的内存拷贝——直接在调用方的栈帧上构造那个 struct。但这是不可观测的实现细节，语义上就是拷贝。）

**这条直接解释了 §6 的 defer 谜题 ③④：**

```go
func c() (n int) { defer func() { n *= 2 }(); return 5 }   // → 10
func d() int     { n := 5; defer func() { n *= 2 }(); return n }  // → 5
```

`d()` 里 `return n` 的第一步就把 `5` **拷进了匿名返回槽**。之后 defer 把局部变量 `n` 改成了 10——但返回槽早就装好了，改不到。`c()` 的返回槽有名字，所以 defer 够得着。

#### ⚠️ 但那是【浅】拷贝

```go
type Config struct {
	Name  string
	Tags  []string
	Extra map[string]string
}

c1 := makeConfig()
c2 := c1              // 拷贝
```

```
改 Name:  c1.Name="orig"          c2.Name="changed"          ← 独立（值字段）
改 Tags:  c1.Tags=[CHANGED]       c2.Tags=[CHANGED]          ← 串了！
改 Extra: c1.Extra=map[k:CHANGED] c2.Extra=map[k:CHANGED]    ← 串了！
```

拷贝复制的是 **struct 的每个字段**。值字段（`string`、`int`）真正独立了；但 **slice 字段拷的是那个 24 字节 header，map 字段拷的是那个指针**——底层数据仍然是同一份（§2.6）。

> **「struct 是值类型」不等于「拷贝出来的两份互不影响」。**
> 只要 struct 里有 slice / map / 指针字段，拷贝之后就仍然共享数据。

Java 的 `clone()` 默认也是浅拷贝，同样的坑。Go 没有 `clone()`，要深拷贝得自己逐字段处理（`slices.Clone` / `maps.Clone` 各管一层）。

**这条以后会咬你**：把一个带 slice 字段的 config「拷贝」给另一个 goroutine，两边同时写那个 slice → 数据竞争。第 2 周专讲。

### 2.6 slice / map / chan：值里面含着指针

你会常听到「slice、map、chan 是引用类型」——**这个说法是偷懒的**。精确的说法是：

> Go 永远传值。它们只是「值本身里面就含了一个指针」。

**map 和 chan：变量本身就是一个指针。** `map[string]int` 底层实实在在就是个 `*hmap`。拷贝它 = 拷贝一个地址，两边指向同一张哈希表，所以函数里写 `m["new"] = 1` 调用方看得见。`chan` 同理（`*hchan`）。

**slice：只有一半是「引用」——这才是重点。** slice 变量是个三字段的 struct：

```
[ 指向底层数组的指针 | len | cap ]     ← 24 字节，传参时整个被拷贝
```

三个字段都复制了。**指针字段指向同一个底层数组**，所以改元素调用方看得见；但 **`len` / `cap` 是独立的副本**。于是：

```
函数里 s[0]=999:   [999 2 3]      ← 可见（同一个底层数组）
函数里 append:     [999 2 3]      ← 不可见！
```

`append` 干了两件事：可能重新分配底层数组、**一定会改 len**。而 `len` 只存在于函数里那份拷贝中，调用方那份纹丝不动。

> **这就是为什么 `s = append(s, x)` 的赋值不能省**——`append` 返回的是一个新的 slice header，你必须自己接住。

**那什么时候需要 `*[]T`？** 只有一种：函数要改变调用方的 slice header 本身（append / 重新切片 / 置 nil）。但 **Go 的惯用做法是返回新 slice，不传 `*[]T`**：

```go
func appendAll(s []int, vals ...int) []int { return append(s, vals...) }
s = appendAll(s, 4, 5)      // 调用方自己接住
```

标准库全是这个形状（`append`、`strconv.AppendInt`、`slices.Delete`…）。看到 `*[]T` 出现在 API 里，八成是设计味道不对。至于 `*map[k]v`，那是在指针上再套一层指针，纯噪音。

**一张表收尾：**

| 类型 | 传参时拷贝了什么 | 改元素调用方可见？ | 改长度可见？ |
|---|---|---|---|
| `int` / `struct` / `[3]int` | 整个值 | — / ❌ | — |
| `*T` | 8 字节地址 | ✅（改 `*p`） | — |
| `map` / `chan` | 8 字节地址 | ✅ | ✅ |
| `[]T` | 24 字节 header | ✅ | ❌ |

**唯一需要单独记的就是最后一行那个 ❌。** 其余都能从「永远传值」推出来。

（`[3]int` 那行的 ❌ 回到 D1 那条：数组是值类型，传参全量拷贝，所以它在 API 里基本没法用。）

### 2.7 什么时候用指针

| 用指针 | 用值 |
|---|---|
| 需要**修改**调用方的数据 | 只读 |
| struct 很大，拷贝成本高 | 小 struct（几个字段）——拷贝往往比解引用还快 |
| 需要表达「**可能不存在**」（nil） | 零值就够用 |
| 类型内部有 `sync.Mutex` 等**不能拷贝**的东西 | —— |

两条重要提醒：

1. **slice、map、channel 不要再取指针**（见 2.6）。
2. **不要为了「性能」无脑用指针。** 小 struct 传值往往更快，而且指针会让变量逃逸到堆上，增加 GC 压力。D17 会用 `-gcflags=-m` 实测给你看。

方法接收者该用值还是指针，是 D4 的主题，规则比这里更细。

### 2.8 三件让你安心的事

1. **Go 没有指针算术。** `p++`、`p + 1` 全是编译错误。你不可能像 C 那样越界乱写内存。
2. **不会有野指针。** 有 GC，只要还有指针指着，对象就不会被回收。**返回局部变量的地址完全合法**——Java 程序员觉得理所当然，C 程序员会吓一跳：
   ```go
   func New() *User { u := User{}; return &u }   // ✅ 完全没问题
   ```
   编译器的逃逸分析会决定 `u` 放栈上还是堆上，你不需要管（D17 细讲）。
3. **nil 指针解引用会 panic，不会静默出错。** 等价于 Java 的 NPE，报错清楚。

> 📌 `cmd/ptrdemo` 是本节所有结论的可运行验证版：`go run ./cmd/ptrdemo`。
> 改着玩——把 `appendToSlice` 里的 `s` 初始 cap 调大再试，你会看到 append 行为的另一面（D3 主题）。

## 3. 命名返回值，以及为什么少用

```go
func split(sum int) (x, y int) {   // x、y 已声明并置零值
	x = sum * 4 / 9
	y = sum - x
	return                          // 「裸返回」naked return
}
```

**默认不要用。** 理由：

- **裸返回让人读不出返回什么**。函数一长，你得翻回签名才知道 `return` 到底返回了谁。
- 它诱使你写出「在函数中段给 `x` 赋值，结尾裸返回」的代码，赋值点和返回点隔了三十行。

**唯一正当的场景：`defer` 需要修改返回值。**

```go
func SafeDivide(a, b int) (result int, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("除法 panic: %v", r)   // ← 只有命名返回值才改得到
		}
	}()
	return a / b, nil
}
```

`defer` 里的闭包在 `return` 之后、函数真正退出之前运行，此时它能读写命名返回值。**匿名返回值没有名字，defer 碰不到。** 这是命名返回值存在的核心理由，今天的小题 B 就是它。

次要场景：签名里返回三四个同类型值时，名字起到文档作用——但这种情况下你更该考虑返回一个 struct。

## 4. 错误即值

### `error` 就是一个普通接口

标准库里它长这样，一共两行：

```go
type error interface {
	Error() string
}
```

**没有栈追踪、没有 cause 链（1.13 前）、没有错误码、不继承任何基类。** 任何有 `Error() string` 方法的类型都自动是 `error`——不需要 `implements`（这是 D5 的隐式接口，今天先接受这个事实）。

于是 error 是**值**：能赋值、能比较、能放进 slice、能当字段、能从 channel 里传出来。这句话是今天所有内容的地基。

### 三种造错误的方式

```go
// 1. 一次性的错误
return fmt.Errorf("解析第 %d 行失败", n)

// 2. 哨兵错误（sentinel error）—— 包级变量，调用方可以比对
var ErrNotFound = errors.New("未找到")
return ErrNotFound

// 3. 自定义错误类型 —— 需要携带结构化数据时
type ParseError struct {
	Line int
	Err  error
}
func (e *ParseError) Error() string { return fmt.Sprintf("第 %d 行: %v", e.Line, e.Err) }
```

选择标准很清楚：

- **调用方只需要知道「是哪一类错误」** → 哨兵错误（`ErrNotFound`、`io.EOF`、`sql.ErrNoRows`）
- **调用方需要从错误里取数据出来**（行号、字段名、HTTP 状态码） → 自定义类型
- **调用方什么都不需要，只是往上传** → `fmt.Errorf`

命名规范（`revive` 的 `error-naming` 规则强制）：哨兵变量必须 `ErrXxx`，错误类型必须 `XxxError`。

### 「哨兵错误」到底是什么

**它是纯粹的编程约定，Go 语言本身零支持。** 编译器不认识这四个字，`errors.New("未找到")` 返回的就是一个普通的 `error` 值。

「哨兵（sentinel）」是计算机科学的通用术语：**用一个预先约定好的特殊值表示某种特殊状态**。你早就见过——C 字符串的 `\0`、`indexOf` 返回 `-1`、链表末尾的 `NULL`。Go 只是把这个老套路用在了错误上。

**它靠「身份」工作，不靠消息。** 关键在于 `errors.New` 每次调用都造一个全新的值：

```go
e1 := errors.New("boom")
e2 := errors.New("boom")
e1 == e2                    // false —— 消息一样，但是两个不同的值
e1.Error() == e2.Error()    // true
```

因为它返回的是 `*errors.errorString`（**指针**），比较的是地址。所以哨兵模式成立的前提是：**全世界只有那一个 `ErrNotFound` 变量**，调用方比对的是「是不是就是那个」。

**推论：绝不能用字符串比较错误。**

```go
if err.Error() == "未找到" { }     // ❌ 消息一改就崩，也没法国际化
if errors.Is(err, ErrNotFound) { } // ✅
```

**推论二：也不能用 `==`。**

```go
wrapped := fmt.Errorf("查询用户 42: %w", ErrNotFound)
wrapped == ErrNotFound              // false ← 包一层就失效
errors.Is(wrapped, ErrNotFound)     // true
```

**永远用 `errors.Is`，哪怕你「确定」没有包装**——你控制不了下游哪天加一层。`errorlint` 就是专门抓这个的。

### 哨兵错误的两个真实代价

**① 它只能是 `var`，改得掉。**

`error` 是接口，而 Go 的常量只能是基本类型（D1 §5），所以哨兵**没法写成 `const`**。后果：

```go
io.EOF = nil      // 语法完全合法，没人拦得住
```

任何 import 了 `io` 的包都能改掉它。**这是 Go 一个公认的设计缺陷**，没有语言层面的解法，只能靠「没人会那么干」。

> **有个绕过办法，但社区没普及**：如果错误类型的底层是基本类型，它就能是真常量。
>
> ```go
> type MyErr string
> func (e MyErr) Error() string { return string(e) }
>
> const ErrOops = MyErr("出错了")   // ⭐ 真·常量，改不掉
> ```
>
> 标准库里有这种写法（`syscall.Errno` 底层是 `uintptr`，`runtime.plainError` 底层就是 `string`）。代价是它变成了**值类型**，两个内容相同的 `MyErr` 会被 `errors.Is` 认为相等，失去身份语义。
>
> 顺带回答一个常见疑问：**`errors.New` 收字符串，是不是说明 `error` 本质上就是 string？** 不是。`error` 是接口，`errors.New` 只是把字符串塞进一个实现了 `Error() string` 的内部类型 `*errorString`——**字符串是它的一个字段，不是它本身**。差别在于 error 有身份（两个同消息的 error 不相等）、能携带任意数据（你的 `ParseError` 有三个字段）、能形成链（`Unwrap`）。string 三样都做不到。上面的 `MyErr` 是「你选择用 string 实现 error」，不是「error 本质是 string」。

（顺带：`io.EOF` 的动态类型就是 `*errors.errorString`，和你自己 `errors.New` 出来的东西一模一样，它没有任何特殊地位。而且注意 `io.EOF` 甚至不表示「错误」——它是正常的终止信号。）

**② 一旦导出，它就是 API 契约。**

调用方会围绕它写 `if errors.Is(...)`，你以后**不能删、不能改语义、不能换成别的错误**。Russ Cox 和 Dave Cheney 都写过文章劝人少用哨兵错误。

**只在包内部用的就别导出**，写成小写 `errXxx`，这样不构成 API 承诺，随时能改。

### 和 Java 的对应关系

有意思的是，Go 的两条路对应 Java 的**同一个**东西：

| Java | Go |
|---|---|
| `catch (NotFoundException e)` | `errors.Is(err, ErrNotFound)` —— 比对**值** |
| `catch (ParseException e) { e.getLine(); }` | `errors.As(err, &pe); pe.Line` —— 比对**类型** |

Java 里两种都得「定义一个异常类」，靠 `catch` 的类型匹配区分。Go 把它拆成了两条：**只需要区分种类就用值（哨兵），需要携带数据才定义类型。**

前者轻得多——不用定义类型、不用写 `Error()` 方法，一行 `var` 搞定。这是「用值表达错误种类」的直接好处。

> 你今天写的 `kvconf` 正好是这两条路的组合：三个哨兵（`ErrMissingSeparator` / `ErrEmptyKey` / `ErrDuplicateKey`）让调用方区分是哪类语法错误，一个自定义类型（`*ParseError`）让调用方取到行号。**这个组合是 Go 错误设计的标准形态。**

> 注意 §4 里那个方法的接收者是 `*ParseError` 而不是 `ParseError`——**错误类型几乎总是用指针接收者**，这样 `errors.As` 拿到的是同一个对象，而且比较身份时不会被拷贝搞混。为什么，D4 讲透。

### `%w`：包装错误

```go
if err := doWork(); err != nil {
	return fmt.Errorf("处理订单 %s: %w", id, err)
}
```

`%w` 和 `%v` 的区别是**关键**：

| | 效果 |
|---|---|
| `%v` | 把底层错误**渲染成字符串**塞进新错误。原错误的类型和身份**永久丢失**。 |
| `%w` | 把底层错误**包起来**。新错误多一个 `Unwrap() error` 方法，`errors.Is` / `errors.As` 能穿透进去。 |

**默认用 `%w`。** 只有在你刻意要切断错误链（不想让调用方依赖内部实现的错误类型）时才用 `%v`。

包装时的措辞惯例：**只加本层的上下文，不重复下层已有的信息，不加「失败」「错误」这类废话**，因为错误消息会层层拼接：

```
❌ "读取配置失败: 打开文件出错: 解析失败: open /etc/app.conf: no such file or directory"
✅ "读取配置: 打开 /etc/app.conf: no such file or directory"
```

规则：**小写开头、不加标点结尾、像日志前缀那样只写「我在干什么」。**

### `errors.Is` vs `errors.As`

```go
// Is：这条错误链上，有没有某个特定的错误【值】？
if errors.Is(err, os.ErrNotExist) { ... }
if errors.Is(err, ErrNotFound) { ... }

// As：这条错误链上，有没有某个特定【类型】的错误？有的话给我。
var pe *ParseError
if errors.As(err, &pe) {
	fmt.Println("出错行号:", pe.Line)   // ← 拿到了结构化数据
}
```

两个都会**顺着 `Unwrap()` 一路往下找**，所以包了五层的错误照样能匹配到最里面那个。

**永远不要用 `==` 比较错误**，因为包装过就不相等了。`errorlint` 这个 linter 就是专门抓这个的，`make check` 会拦你。

`errors.As` 的第二个参数必须是**指向目标类型的指针**（`&pe`，而 `pe` 本身已是 `*ParseError`，所以传的是 `**ParseError`）。原因见 §2.5：**Go 只有值传递，`As` 要写回给你，就必须拿到你那个变量的地址。** 第一次写一定会写错，写错了 `As` 会直接 panic 告诉你。

### 让自定义错误支持 Unwrap

```go
func (e *ParseError) Unwrap() error { return e.Err }
```

加上这个方法，`errors.Is(err, ErrEmptyKey)` 就能穿透 `*ParseError` 找到里面包的哨兵错误。**没有这个方法，错误链在你这里断掉。** 今天的主练习就要求你实现它。

## 5. 对比 Java 和 TypeScript（这节请认真读）

### Java 的 checked exception 和 Go 的 error 想解决同一个问题

两者的出发点完全一致：**强迫调用方正视失败的可能性**，不让错误被静默忽略。

Java 的方案：把错误放进类型系统的旁路（`throws` 子句），编译器强制你要么 `catch` 要么继续 `throws`。

结果大家都知道：

```java
try {
    doWork();
} catch (Exception e) {
    // 吞掉，或者 e.printStackTrace()
}
```

以及 `throws Exception` 一路污染到 main。**Java 的强制可以用一行代码绕过，而且绕过的代价比正确处理低得多**，所以人们大规模绕过它。这是 checked exception 被公认为失败设计的原因，也是为什么 C#、Kotlin、Scala 都没有跟进。

Go 的方案：**根本不进类型系统的旁路，就是个普通返回值。**

代价是编译器也不强制了（`v, _ := f()` 合法）。Go 赌的是「让正确处理变得容易，而不是让忽略变得困难」。实践中靠 lint（我们的 `errcheck`）补上强制。

### 异常真正的问题是控制流不可见

这才是 Go 拒绝异常的核心理由，比「啰嗦」重要得多：

```java
void process() {
    a();      // 这行可能抛异常吗？
    b();      // 这行呢？
    c();      // 不看每个方法的实现和它调用的所有东西，你不知道
}
```

**在有异常的语言里，任意一行都是潜在的非局部跳转点。** 你读一段代码，看不出它有几条退出路径。资源清理、状态一致性、部分完成的副作用——全都要靠想象力去覆盖。

Go 里：

```go
if err := a(); err != nil { return err }   // ← 退出点，写在脸上
b()                                         // ← 这行不会失败，签名说的
if err := c(); err != nil { return err }   // ← 退出点
```

**每一条错误路径都是可见的、局部的、可以用眼睛追踪的。** 你为此付出的代价是三行样板代码，换来的是「读代码时不需要想象」。

Rob Pike 的原话：*"Errors are values."* 值可以被编程——你可以把 error 存起来、聚合、传进函数、做成表。异常不行，异常只能被 catch。

### 但 Go 的方案也确实有真问题

我不打算给你灌鸡汤，这几条是真的：

1. **啰嗦。** `if err != nil { return err }` 在一个正经函数里出现五六次是常态，视觉上淹没主逻辑。
2. **默认丢失上下文。** 裸 `return err` 传上去，调用方只知道「文件没找到」，不知道是哪个流程要找哪个文件。`%w` 是补救，但要靠自觉。
3. **没有栈追踪。** 标准库的 error 不带调用栈。生产环境定位问题时这是实打实的痛点，所以有 `pkg/errors`（已归档）、`cockroachdb/errors` 这类第三方库。**但学习期一律用标准库**，先把 `%w` + `Is`/`As` 这套写熟。
4. **社区多次尝试改进都失败了。** Go 2 的 `try` 提案、`check/handle` 提案全部被否决或撤回，因为改进方案都比现状更难懂。**现状就是长期答案**，接受它。

### TypeScript 的对照

TS 里 `throw` 可以抛任何东西（`throw 42` 合法），`catch (e)` 里的 `e` 类型是 `unknown`——**类型系统对错误完全无能为力**，比 Java 还弱。所以 TS 社区反而在往 Go 的方向靠：`Result<T, E>` 类型、neverthrow 这类库、以及 `{ data, error }` 的返回形状（Supabase、Astro 都这么设计 API）。

你在 TS 里如果用过 `const { data, error } = await client.from(...)`，那你已经写过 Go 风格的错误处理了。

## 6. `defer`

### 基本语义

```go
func work() error {
	f, err := os.Open(path)
	if err != nil {
		return err
	}
	defer f.Close()     // ← 注册，函数退出时执行
	// ... 中间随便 return 多少次，f 都会被关掉
}
```

三条规则，每条都反直觉：

**规则一：defer 在【函数】返回时执行，不是在块结束时。**

```go
for i := range 3 {
	f, _ := os.Open(files[i])
	defer f.Close()          // ❌ 三个 Close 全堆到函数结束才执行
}
```

这是 Go 最常见的资源泄漏写法。循环里打开一万个文件，就有一万个 fd 撑到函数结束。**修法：把循环体抽成一个函数**，让 defer 的作用域跟着缩小。

和 Java 的 `try-with-resources` 对比：Java 的资源在 `try` 块结束就关，作用域是块；**Go 的 defer 作用域是函数**。这个差异是循环坑的根源。

**规则二：参数在 `defer` 语句执行时就求值，不是在调用时。**

```go
i := 0
defer fmt.Println("deferred:", i)   // 此刻 i 的值 0 已经被捕获
i = 42
fmt.Println("normal:", i)
// 输出：normal: 42
//      deferred: 0     ← 不是 42
```

想延迟到最后才求值，就套一层闭包：`defer func() { fmt.Println(i) }()`。**闭包捕获的是变量本身，不是值。**

**规则三：多个 defer 按 LIFO（后进先出）执行。**

```go
defer fmt.Println("1")
defer fmt.Println("2")
defer fmt.Println("3")
// 输出：3 2 1
```

符合直觉：后获取的资源先释放。

### defer 能修改命名返回值

```go
func f() (result int) {
	defer func() { result *= 2 }()
	return 5        // 先把 result 设为 5，再跑 defer，最终返回 10
}
```

`return 5` 不是一步操作，它是「**给返回值赋值**」+「**执行 defer**」+「**真正返回**」三步。理解这个，`recover` 转 error 的写法就顺理成章了。

### `defer f.Close()` 和 errcheck

`Close()` 返回 error，被你丢掉了——`errcheck` 会报。三种处理：

```go
defer f.Close()                                    // ❌ lint 报错
defer func() {                                     // 只读文件：丢弃 + 写明理由
	_ = f.Close() //nolint:errcheck // 只读文件，关闭错误无需处理
}()
defer func() {                                     // ⭐ 写文件必须这样
	if cerr := f.Close(); cerr != nil && err == nil {
		err = cerr    // 需要命名返回值 err
	}
}()
```

**为什么写文件必须检查 `Close` 的错误**：数据可能还在缓冲区里，`Close` 才真正刷盘，此时磁盘满/网络断的错误只会从 `Close` 返回。只读文件则无所谓。

**注意本仓库的 `errcheck` 开了 `check-blank: true`**——连 `_ =` 显式丢弃都会被拦，所以只读文件那种写法还得配一行 `//nolint:errcheck` 并**写明理由**。这比多数生产项目严，是学习期故意的：逼你把「为什么可以不管这个错误」讲出来，而不是顺手一个 `_` 划过去。

## 7. `panic` / `recover` —— 90% 的情况都不该用

### panic 不是异常

`panic` 的语义是：**「程序进入了不该存在的状态，继续跑下去是危险的」**。它不是「这个操作失败了」。

什么时候 Go 自己会 panic：越界访问、nil 指针解引用、除零、向 nil map 写入、类型断言失败。**注意共同点：这些全是程序 bug，不是可预期的运行时状况。**

什么时候你该主动 panic：

```go
// 1. 包初始化时的不可恢复错误
var tmpl = template.Must(template.ParseFiles("index.html"))

// 2. 「这里绝对不可能发生」的分支
switch v := x.(type) {
case A: ...
case B: ...
default:
	panic(fmt.Sprintf("未知类型 %T", v))   // 加了新类型却忘了改这里
}
```

**什么时候绝对不该 panic：任何可预期的失败。** 文件不存在、网络超时、用户输入非法、JSON 格式错——这些全都返回 error。

**铁律：panic 不许穿过包的 API 边界。** 你的库对外必须只用 error 说话。内部用 panic 做深层递归的快速退出是可以的（标准库 `encoding/json` 就这么干），但必须在导出函数里 `recover` 掉，转成 error。

### recover 的三个限制

```go
func safe() (err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("recovered: %v", r)
		}
	}()
	// ...
}
```

1. **`recover` 只在 `defer` 调用的函数里有效。** 直接写在函数体里返回 nil，没有任何效果。
2. **必须配合命名返回值**才能把错误传出去（§3）。
3. **不能跨 goroutine。** 一个 goroutine 里的 panic，别的 goroutine recover 不到——**整个进程会挂**。这条在第 2 周会反复出现：`go func()` 里如果可能 panic，必须在那个 goroutine 内部自己 recover。

合法的 recover 用例其实很少，最典型的是 **HTTP 服务器的恢复中间件**：一个请求 handler 里的 bug 不该搞垮整个服务进程。D11 你会亲手写一个。

### 运行时 panic vs 应用 panic

真要写 recover，第一件事是搞清楚**你接住的是谁扔的**。

| | 谁触发 | 代码里有 `panic(` 这个词吗 |
|---|---|---|
| **运行时 panic** | **Go 运行时**替你触发 | ❌ 没有 |
| **应用 panic** | 你（或某个库）显式写的 | ✅ 有 |

```go
a, b := 1, 0
_ = a / b              // ← 你没写 panic，运行时替你 panic 了

panic("配置文件损坏")     // ← 这行是你自己写的
```

运行时 panic 是「程序做了语言规范禁止的事」时运行时被迫叫停，实测的六种：

```
除以零              → runtime.errorString      runtime error: integer divide by zero
切片越界             → runtime.boundsError      runtime error: index out of range [5] with length 0
nil 指针解引用        → runtime.errorString      runtime error: invalid memory address or nil...
向 nil map 写入      → runtime.plainError       assignment to entry in nil map
类型断言失败          → *runtime.TypeAssertionError
关闭 nil channel    → runtime.plainError       close of nil channel
```

应用 panic 的值可以是任何东西（`panic()` 接受 `any`）：`string`、`int`、`error`、自定义 struct 都见得到。

**技术上靠 `runtime.Error` 接口区分：**

```go
type Error interface {
	error
	RuntimeError()   // 空实现，什么都不干 —— 它是个纯【标记】
}
```

上面四种运行时类型彼此毫无关系，唯一共同点就是都有这个方法。所以 `r.(runtime.Error)` 断言成功 = 「这是运行时替你 panic 的」。文档明确写了：标准库以外的包不该实现它。

> **为什么要放一个啥也不干的方法？**
> 因为 **Go 的接口是隐式实现的**。如果 `runtime.Error` 只写 `interface{ error }`，那任何 error 都自动满足它，标记完全失效。必须塞一个「别人不会碰巧拥有」的方法名进去。
>
> 对比 Java：`Serializable` 是**完全空**的接口就行，因为 Java 靠 `implements` 显式声明。**Go 没有 `implements`，编译器只看方法集，所以「空的标记接口」在 Go 里不可能存在。** 这是隐式接口的一个真实代价，D5 展开。

**⚠️ 陷阱**：`panic(errors.New("..."))` 的值**是个 `error`，但不是 `runtime.Error`**。所以：

```go
if err, ok := r.(error); ok { }           // ← 对两者都成立，区分不了
if re, ok := r.(runtime.Error); ok { }    // ← 这个才是「运行时」的判据
```

**为什么要分**：运行时 panic ≈ 100% 是你的 bug（越界、nil 解引用不是「环境不好」，是代码写错了），必须打完整栈追踪 + 告警；而应用 panic 可能是**有意的控制流**（`template.Must` 的初始化断言、某些框架的 abort 信号、库在内部做深层递归退出）。

### 怎样才算正确地 recover —— 三条纪律

```go
func SafeDivide(a, b int) (result int, err error) {
	defer func() {
		r := recover()
		if r == nil {
			return
		}
		re, ok := r.(runtime.Error)
		if !ok {
			panic(r)   // ① 不是我认识的 panic → 原样抛回去
		}
		err = fmt.Errorf("%d / %d: %w", a, b, re)   // ② 带上原始信息，别自己编
	}()
	return a / b, nil
}
```

**① 只 recover 你认识的，其余 `panic(r)` 重新抛出。** 你的 recover 不该吞掉别人的 panic——上层可能故意 panic 了一个自定义类型想让更外层接住，你在中间无差别吞掉，那个机制就废了。

**② 用 `%w` 包住原始的 panic 值，别自己编消息。** `runtime.Error` 实现了 `error`，可以直接 `%w`。反面教材：

```go
err = fmt.Errorf("除以零: %d / %d", a, b)   // ❌ 原始信息 100% 丢失
```

如果实际 panic 是 nil 解引用，这行代码会**理直气壮地撒谎**。

**③ 别指望能精确分类运行时 panic。** 看上面的表：**除以零和 nil 指针解引用是同一个类型 `runtime.errorString`**，类型断言区分不了；`runtime` 包也没导出任何哨兵可供 `errors.Is` 比对。唯一剩下的手段是字符串匹配 `strings.Contains(re.Error(), "divide by zero")`——**那是实现细节，Go 团队随时能改措辞，改了你的代码静默失效**。

这不是疏忽，是设计意图：

> **panic 的语义是「程序进入了不该存在的状态」。** 一个「不该存在的状态」压根不该被分类处理——它该被修复。

如果你发现自己在写「如果是除零就怎样，如果是越界就怎样」，说明这些情况本来就该在 panic 发生**之前**被检查掉：

```go
var ErrDivideByZero = errors.New("除以零")

func Divide(a, b int) (int, error) {
	if b == 0 {
		return 0, fmt.Errorf("%d / %d: %w", a, b, ErrDivideByZero)   // ⭐ 正确答案
	}
	return a / b, nil
}
```

`b == 0` 不是需要 panic 的「异常状况」，它就是个普通的输入校验。回到 §7 开头那条铁律：**任何可预期的失败都返回 error。**

> 小题 B 的 `mathx.SafeDivide` 故意用了反模式（无条件断定「除以零」）——那道题练的是机制配合，不是生产实践。但你现在多知道了一层：不推荐它不只因为啰嗦，而是因为**它在原理上就做不到你想要的精确性**。
