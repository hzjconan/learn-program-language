## 1. 三个核心类型

```go
type Handler interface {
	ServeHTTP(w http.ResponseWriter, r *http.Request)
}
```

**服务端的一切都是 `Handler`**——路由器是 Handler、中间件返回 Handler、你写的处理函数也要变成 Handler。

### 1.1 `HandlerFunc`：把「函数」适配成「接口」

标准库的定义只有两行：

```go
type HandlerFunc func(ResponseWriter, *Request)              // ① 一个【函数类型】

func (f HandlerFunc) ServeHTTP(w ResponseWriter, r *Request) { // ② 给它加个方法
	f(w, r)                                                    //    方法体就是「调用我自己」
}
```

⚠️ **它不是接口，是函数类型。** 因为它有了 `ServeHTTP` 方法，所以它**满足** `Handler` 接口。

```
普通函数 f 的类型:  func(http.ResponseWriter, *http.Request)   ← 没有 ServeHTTP 方法
转换后 hf 的类型:   http.HandlerFunc                           ← 有 ServeHTTP
var _ http.Handler = hf                                       ← ✅
var _ http.Handler = f                                        ← ❌ 编译不过
```

**这是 D4 §2「接收者可以是任何类型，不只是 struct」的经典用例**——给一个函数类型加方法。

### 1.2 没有它会怎样

每个 handler 都得定义一个 struct + 一个方法：

```go
type helloHandler struct{}
func (helloHandler) ServeHTTP(w, r) { fmt.Fprint(w, "hello") }

type byeHandler struct{}
func (byeHandler) ServeHTTP(w, r) { fmt.Fprint(w, "bye") }
```

**20 个路由 = 20 个空 struct + 20 个方法**，而这些 struct 里什么状态都没有，纯粹为了「挂一个方法上去」。`HandlerFunc` 把这个仪式消掉了。

### 1.3 ⚠️ `http.HandlerFunc(f)` 是【类型转换】，不是函数调用

这里最容易卡住。`T(x)` 在 Go 里有两种含义，靠 `T` 是**类型**还是**函数**区分：

| 写法 | `T` 是什么 | 含义 |
|---|---|---|
| `int64(42)` | **类型** | **类型转换** |
| `string(rune(65))` | **类型** | **类型转换**，得到 `"A"` |
| `len("abc")` | 函数 | 函数调用 |
| **`http.HandlerFunc(f)`** | **类型** | **类型转换** |

```go
http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) { ... })
│                └────────────── 被转换的【值】，不是参数 ──────────────┘
└─ 类型名
```

**就像 `int64(42)` 里的 42 不是「传给 int64 的参数」一样。**

常见的困惑是：「`HandlerFunc` 定义的时候接受 2 个参数，为什么这里只传了 1 个？」——因为那说的是**转换之后得到的东西**怎么调用，不是转换本身怎么写：

```go
h := http.HandlerFunc(f)        // ← 转换：把 f 变成 HandlerFunc 类型
h(w, r)                          // ← 调用：这时候才传 2 个参数

// 完全对照：
n := int64(42)                   // 转换
n + 1                            // 使用
```

**转换不改变底层的函数，只是换了个「类型标签」**，而那个标签上挂着 `ServeHTTP` 方法：

```
普通函数 plain 的类型: func(string) string
Greeter(plain) 之后:   main.Greeter
底层还是同一个函数:     g("世界") = "你好, 世界"
但现在多了方法:         g.Greet("世界") = "你好, 世界"
```

> 这就是 D1 讲的**具名类型**：`type Greeter func(string) string` 和 `func(string) string` 是两个不同的类型，底层结构一样，但前者可以有方法。
>
> **和你 D1 写的 `type Celsius float64` 是同一个机制**——只是这次底层类型是函数而不是数字。

### 1.4 ⚠️ `HandlerFunc` vs `HandleFunc`：差一个 `r`

`net/http` 里最容易看花眼的一对名字：

| 名字 | 是什么 | 用法 |
|---|---|---|
| `http.Handler` | **接口** | `var h http.Handler = ...` |
| `http.HandlerFunc` | **函数类型**（有 `ServeHTTP`） | `http.HandlerFunc(f)` ← **转换** |
| `mux.Handle` | 方法，收 `Handler` | `mux.Handle("/p", h)` |
| `mux.HandleFunc` | 方法，收裸函数 | `mux.HandleFunc("/p", f)` ← **调用** |

`HandleFunc` 就是语法糖，内部帮你做了转换：

```go
func (mux *ServeMux) HandleFunc(pattern string, h func(ResponseWriter, *Request)) {
	mux.Handle(pattern, HandlerFunc(h))     // ⭐ 内部就是转换一下
}
```

**所以你天天在用 `HandlerFunc`，只是被糖包着。**

### 1.5 你会在三个地方显式用到它

**① 写中间件时——必须显式转换**

```go
func Logging(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		//     ^^^^^^^^^^^^^^^^ 签名要求返回 http.Handler，而你手上是个匿名函数
		next.ServeHTTP(w, r)
	})
}
```

**今天练习的四个中间件都得这么写。**

**② 把已有的普通函数适配成 Handler**

```go
mux.Handle("/health", http.HandlerFunc(healthCheck))
```

**③ 需要给 handler 传依赖时——用闭包，而不是 struct**

```go
func newItemHandler(s *Store) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		v, ok := s.Get(r.PathValue("key"))     // ← 闭包捕获 s
		...
	}
}
mux.Handle("GET /items/{key}", newItemHandler(store))
```

**今天的 `NewRouter(s *Store)` 就该用这种**——把 store 通过闭包传给各个 handler，而不是定义一堆 struct。

（handler 依赖很多、或者需要共享方法时，struct + 指针接收者也合理，两种都常见。）

### 1.6 ⚠️ 别和「中间件」混了

两者都跟 `Handler` 打交道，但方向完全不同：

| | 输入 | 输出 | 干什么 |
|---|---|---|---|
| **`HandlerFunc`** | 一个**普通函数** `func(w, r)` | 一个 `Handler` | **适配**：让函数满足接口 |
| **中间件** `func(Handler) Handler` | 一个 **`Handler`** | 一个 `Handler` | **包装**：在前后加逻辑 |

```go
http.HandlerFunc(f)              // 适配器：函数 → Handler
Logging(mux)                     // 中间件：Handler → Handler
```

中间件的实现里**同时用到两者**——收一个 `Handler`，用 `HandlerFunc` 把新的匿名函数适配回 `Handler`：

```go
func Logging(next http.Handler) http.Handler {     // ← 中间件：Handler → Handler
	return http.HandlerFunc(func(w, r) {           // ← 适配器：函数 → Handler
		next.ServeHTTP(w, r)
	})
}
```

### 1.7 为什么用「函数类型」而不是 struct

用 struct 包一个函数字段**完全可以**，标准库里两种都有。但适配器这个场景选函数类型，有三条理由——**性能不是其中之一**：

```
FuncAdapter   8 字节           ← type FuncAdapter func(w, r)
StructAdapter 8 字节           ← type StructAdapter struct{ fn func(w, r) }
```

**内存一样。** 真实理由：

**① 语义：「它就是」 vs 「把它装进」**

```go
HandlerFunc(f)          // 转换：f 本来就是个 handler，只是之前没这么标注
StructAdapter{fn: f}    // 构造：造一个盒子，把 f 装进去
```

一个 handler 函数的**全部内容就是那个函数本身**，没有别的状态。用 struct 包一层等于说「这里还有别的东西」——但其实没有。**类型转换更准确地表达了「换个视角看同一个东西」。**

**② 保留「可调用」**

```
fa(nil, nil)  ✅ 能直接调 —— 它本来就是个函数
sa(nil, nil)  ❌ 编译不过 —— struct 不能被调用
```

`HandlerFunc` 既能当接口用，**也还是个函数**：

```go
h := http.HandlerFunc(myHandler)
h.ServeHTTP(w, r)      // 当 Handler
h(w, r)                // 当函数 —— 少一层间接，测试时方便
```

**③ 惯例**：看到 `HandlerFunc`、`FilterFunc`、`WalkFunc`，Go 程序员立刻知道这是适配器。用 struct 得读实现才能确认。

#### 什么时候该用 struct

**需要多个字段时**——函数类型只装得下一个函数：

```go
type itemHandler struct {
	store  *Store
	logger *slog.Logger
}
func (h *itemHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) { ... }
```

**但 Go 里更常见的是闭包捕获**（§1.5 那个）：依赖少（1~3 个）用闭包，依赖多或者多个 handler 要共享方法时用 struct。两种都地道。

⭐ **判据：这个 Handler 除了「怎么处理请求」之外，还需要记住别的东西吗？**
不需要 → 函数类型 / 闭包；需要 → struct。

`HandlerFunc` 属于前者——它存在的唯一目的就是「让一个函数满足接口」，**没有任何额外状态**。

### 1.8 这个模式不只属于 net/http

> **`XxxFunc` 是个通用适配器：把「函数」适配成「单方法接口」。**

标准库里到处都是，你自己也能造：

```go
type HandlerFunc func(ResponseWriter, *Request)      // net/http
type HandlerFunc func(context.Context, ...) error    // 很多库都有类似的

// 你自己的：
type FilterFunc func(string) bool
func (f FilterFunc) Filter(s string) bool { return f(s) }
```

**这也是「小接口」的又一个好处**（D5 §2）——**只有单方法接口才适合做这种适配**，五个方法的接口没法用一个函数满足。

> 对比 Express：`(req, res) => {}` ≈ `HandlerFunc`。区别是 **Go 没有 `next`**——中间件靠**包装**而不是**调用 next**（见 §4）。

## 2. `ServeMux`：Go 1.22 起够用了

```go
mux := http.NewServeMux()
mux.HandleFunc("GET /items/{id}", handler)          // ⭐ 方法 + 路径参数
mux.HandleFunc("POST /items/{id}/tags/{tag}", handler)
mux.HandleFunc("/static/{path...}", handler)        // 通配剩余部分
mux.Handle("/api/", http.StripPrefix("/api", sub))  // 挂子 mux
```

```go
id := r.PathValue("id")     // 取路径参数
```

实测：

```
GET    /items/42          → 200 GET item 42
POST   /items/7/tags/hot  → 200 tag hot on 7
DELETE /items/42          → 405 Method Not Allowed   ← 自动的
```

**方法不匹配自动返回 405**，不用自己写。

### 匹配规则

- **最长匹配优先**：`/items/{id}` 比 `/items/` 更具体，前者赢
- **`/path` 精确匹配，`/path/` 匹配子树**
- **冲突的模式会 panic**（在注册时，不是运行时）

> Go 1.22 之前 `ServeMux` 只能按前缀匹配、不能按方法路由，所以大家都用 `chi`/`gin`/`echo`。
> **现在标准库够用了**——除非你需要中间件链的语法糖、参数绑定、或者路由分组。**先用标准库。**

## 3. `ResponseWriter` 的三个坑

```go
w.Header().Set("Content-Type", "application/json")   // ① 必须在 WriteHeader 之前
w.WriteHeader(http.StatusCreated)                     // ② 只能调一次
w.Write([]byte(`{"ok":true}`))                        // ③ 第一次 Write 会隐式 WriteHeader(200)
```

**① 顺序**：`WriteHeader` 之后再改 header 完全无效（响应头已经发出去了）。

**② 只能调一次**：调第二次会打日志 `http.ResponseWriter.WriteHeader on hijacked/already written`，但**不会 panic**，也不会改变状态码——**静默失效**。

**③ 隐式 200**：只要你 `Write` 了，状态码就定死成 200。所以**错误处理必须在任何 `Write` 之前**：

```go
// ❌ 太晚了
w.Write([]byte("部分数据"))
if err != nil {
	w.WriteHeader(500)      // 无效，客户端已经收到 200
}

// ✅ 先算完，再写
data, err := compute()
if err != nil {
	http.Error(w, "内部错误", http.StatusInternalServerError)
	return
}
w.Write(data)
```

### `http.Error` 的两个细节

```go
http.Error(w, "not found", http.StatusNotFound)
```

它做三件事：设 `Content-Type: text/plain`、`WriteHeader(code)`、写消息 + 换行。

⚠️ **它会覆盖你之前设的 `Content-Type`**——想返回 JSON 错误就不能用它，得自己写。

## 4. 中间件：洋葱模型

```go
type Middleware func(http.Handler) http.Handler

func Logging(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		start := time.Now()
		next.ServeHTTP(w, r)                      // ← 洋葱的核心：调用下一层
		log.Printf("%s %s %v", r.Method, r.URL.Path, time.Since(start))
	})
}
```

**签名固定是 `func(http.Handler) http.Handler`**——收一个 handler，返回一个包装过的 handler。

### 组合

```go
handler = Logging(Recover(RequestID(mux)))     // 手工嵌套，从里往外读，别扭
```

写个 `Chain` 更清楚：

```go
func Chain(h http.Handler, ms ...Middleware) http.Handler {
	for i := len(ms) - 1; i >= 0; i-- {         // ⭐ 倒着包，让第一个参数在最外层
		h = ms[i](h)
	}
	return h
}

handler := Chain(mux, Logging, Recover, RequestID)   // 从左到右 = 从外到内
```

### 执行顺序

```
请求 → Logging 前半 → Recover 前半 → RequestID 前半 → handler
                                                        ↓
响应 ← Logging 后半 ← Recover 后半 ← RequestID 后半 ←────┘
```

**和 Express 的 `app.use` 顺序一致**，区别是 Go 没有 `next()` 这个参数——**「调用下一层」就是 `next.ServeHTTP(w, r)`，「不调用」就是短路**。

```go
func Auth(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if !valid(r) {
			http.Error(w, "未授权", http.StatusUnauthorized)
			return                              // ⭐ 不调 next = 短路
		}
		next.ServeHTTP(w, r)
	})
}
```

### 顺序很重要

**推荐顺序**（从外到内）：

```go
Chain(mux, RequestID, Logging, Recover, RateLimit, Auth)
```

| 位置 | 中间件 | 为什么 |
|---|---|---|
| **1（最外）** | **RequestID** | ⭐ **必须在最外** —— 它用 `r.WithContext(ctx)` 造了个**新的 `*http.Request`** 只传给内层。放内层的话，外面的 Logging / Recover 手上还是老的 `r`，**ctx 里根本没有 ID** |
| 2 | **Logging** | 要记录真实总耗时 + 最终状态码，包括被限流拒绝的请求 |
| 3 | **Recover** | 在 Logging **内层**，这样它写的 500 才能被记进日志 |
| 4 | **RateLimit** | 在业务之前拒绝，省下后面的开销 |
| 5（靠内） | **Auth** | 前面的日志/追踪对未授权请求也该生效 |

⚠️ **Recover 和 Logging 谁在外**是个取舍：

- **Logging 在外**（推荐）：能记到 Recover 写的 500 ✅；但 Logging 自己 panic 就没人兜了
- **Recover 在外**：能兜住 Logging 的 panic；但 Logging 记到的是 panic 前的状态码（通常是 0/200）

实践中 Logging 中间件很简单、不太会 panic，所以**优先保证日志准确**。

> ⭐ **一条会反复用到的性质**：`r` 是**逐层传递的**（不可变，每层可以 `WithContext` 造新的，只对内层可见）；`w` 是**全链路共享的一个对象**（任何一层写响应头，所有层都看得到）。
>
> 这解释了为什么 RequestID 必须在最外层——它往 ctx 塞的东西只能向内传播。

## 5. 记录状态码：包装 `ResponseWriter`

日志中间件想记状态码，但 `ResponseWriter` 没有「读状态码」的方法。得自己包一层：

```go
type statusRecorder struct {
	http.ResponseWriter          // ⭐ 嵌入（D4 §4），自动获得所有方法
	status int
	bytes  int
}

func (r *statusRecorder) WriteHeader(code int) {
	r.status = code
	r.ResponseWriter.WriteHeader(code)          // 转发给真正的 w
}

func (r *statusRecorder) Write(b []byte) (int, error) {
	if r.status == 0 {
		r.status = http.StatusOK                // 隐式 200（§3 那条）
	}
	n, err := r.ResponseWriter.Write(b)
	r.bytes += n
	return n, err
}
```

**这就是 D4「嵌入 = 语法糖」的正面用法**：只重写你关心的两个方法，其余自动转发。

### 5.1 ⚠️ 但包装会丢掉可选接口

实测：一个这样的包装**一次性丢掉 4 个能力**。

```
真实的 ResponseWriter:  ✅ Flusher  ✅ Hijacker  ✅ ReaderFrom  ✅ StringWriter
包装之后:               ❌          ❌           ❌            ❌
```

后果：**SSE / 流式响应失败**（没有 `Flusher`）、**WebSocket 升级失败**（没有 `Hijacker`）、
**`http.ServeFile` 用不了 sendfile 零拷贝**（没有 `ReaderFrom`，大文件性能掉档但功能正常，
你根本发现不了）。

#### 为什么嵌入接口不会自动带上这些方法

**方法提升看的是嵌入字段的【静态类型】，而且发生在编译期。**

```go
type statusRecorder struct {
	http.ResponseWriter        // ← 静态类型是【接口】，只声明了 3 个方法
}
```

编译器去查 `http.ResponseWriter` 接口声明了什么 —— 只有 `Header`/`Write`/`WriteHeader`。
所以 `statusRecorder` 的方法集里**没有 `Flush`**。

对比实测：

```
① 嵌入接口 Writer         → 是 Flusher 吗: false   ⚠️ 丢了
② 嵌入具体类型 realWriter  → b.Flush() = "刷新"      ✅ 提升上来了
```

嵌入具体类型时编译器知道那个类型的**全部**方法，所以都能提升。

**但能力一直都在，只是「够不着」**：

```
a.Writer 装的动态类型: main.realWriter
手动断言之后能调: a.Writer.(Flusher).Flush() = "刷新"
```

运行时那个接口值里装的确实是有 `Flush` 的对象（D5 §3 的二元组）。
**丢的不是能力，是编译期的可见性** —— 编译期的提升 vs 运行期的动态类型，两者对不上。

> 这不是「嵌入」的问题，是**「可选接口」这个设计模式的固有代价**。Go 选择了
> 「主接口保持最小 + 增强能力靠断言探测」（D5 §2、§5），收益是任何类型都容易满足小接口，
> 代价就是包装时会丢。

#### 风险范围其实很窄

| 场景 | 有风险吗 |
|---|---|
| 嵌入**具体类型**（`type Manager struct{ Employee }`，D4 那道题） | ❌ 编译器知道全部方法 |
| 嵌入接口但**不往外传**（自己内部用） | ❌ |
| **嵌入接口 + 把包装后的东西交给别人** | ⚠️ **有** |

**判据：你的包装类型会被别人当成原接口用吗？** 会 → 有风险。

### 5.2 ⭐ `Unwrap` 约定 —— Go 官方的回答

Go 1.20 起，标准库确立了一个约定：**包装类型提供 `Unwrap()`，调用方用 `ResponseController`。**

```go
// 写包装（中间件）的人：
func (r *statusRecorder) Unwrap() http.ResponseWriter { return r.ResponseWriter }

// 写 handler 的人：
rc := http.NewResponseController(w)
rc.Flush()                                     // ⭐ 自动顺着 Unwrap 链往下找
```

#### ⚠️ 它是【约定】，不是语言特性

**Go 什么都不会自动做。** `ResponseController` 的源码就是一个手写循环：

```go
func (c *ResponseController) Flush() error {
	rw := c.rw
	for {                                    // ⭐ 普通的 for 循环
		switch t := rw.(type) {
		case interface{ FlushError() error }:
			return t.FlushError()
		case Flusher:                         // ① 这一层支持吗？
			t.Flush()
			return nil
		case rwUnwrapper:                     // ② 不支持 → 剥掉一层
			rw = t.Unwrap()
		default:
			return errNotSupported()          // ③ 剥到底了还没找到
		}
	}
}
```

**没有任何魔法**，就是 type switch + 循环。所以准确的说法是：

> **`Unwrap` 不能让你的包装类型「获得」`Flusher`，它只是让愿意配合的调用方能「找到」底层的 `Flusher`。**

实测证实：加了 `Unwrap` 之后 `w.(http.Flusher)` **仍然是 false**，但 `ResponseController.Flush()` 能成功。

| | 方法提升（嵌入） | `Unwrap` 约定 |
|---|---|---|
| 什么时候 | **编译期** | **运行期** |
| 谁做的 | **语言特性**，编译器改写 | **库代码**，手动遍历 |
| 让直接类型断言变 true 吗 | 嵌入具体类型时会 | **不会** |

#### 这是 Go 里的一类模式

你已经见过一个 —— **`errors.Unwrap`**（D2）。`errors.Is` 内部同样是手写循环剥洋葱。
这类「靠命名约定 + 库代码遍历」的接口还有：

| 方法 | 谁在用它 |
|---|---|
| `Unwrap() error` | `errors.Is` / `errors.As` |
| `Unwrap() []error` | `errors.Join` |
| `Unwrap() http.ResponseWriter` | `http.ResponseController` |
| `Is(error) bool` | `errors.Is`（自定义相等，QA #8 里 `fs.ErrNotExist`） |
| `String() string` | `fmt` 的 `%v` |

**共同点：不在任何接口声明里被强制，靠文档约定 + 运行时类型断言。**

⚠️ **两个后果：**

1. **只有知道这个约定的代码才受益** —— 老代码和第三方库（比如 `gorilla/websocket` 直接断言
   `Hijacker`）享受不到。所以实践中常常 **`Unwrap` + 转发 `Flush` 两个都做**。
2. **拼错名字或签名 = 静默失效**（小写的 `unwrap`、返回 `any`），编译器不报错 ——
   因为你没「声明实现某接口」，只是碰巧有/没有一个方法（D5 隐式实现）。
   防御办法是编译期断言：
   ```go
   var _ interface{ Unwrap() http.ResponseWriter } = (*statusRecorder)(nil)
   ```

### 5.3 哪些可选接口该转发，哪些不该

**判据：转发之后，我这一层还在链路上吗？**

| 接口 | 转发之后 | 你的包装 | 结论 |
|---|---|---|---|
| **`Flusher`** | 只刷缓冲，后续 `Write` **仍然经过你** | ✅ 继续有效 | **转发** |
| **`Hijacker`** | 连接被接管，handler 直接写 `net.Conn`，**你的方法再不被调用** | ❌ **彻底失效** | **别裸转发** |
| **`io.ReaderFrom`** | 绕过你的 `Write` 直接写底层（这正是它快的原因） | ⚠️ **字节统计会漏** | 转发就得自己补计数 |

实测（同一个 recorder，两个端点）：

```
/flush   [日志] status=202 bytes=18    客户端收到 202  ✅ 一致
/hijack  [日志] status=0   bytes=0     客户端收到 418  ⚠️ 日志全错
```

`Hijack` 之后 handler 直接往裸连接写了 418，**recorder 什么都没记到**。

⭐ **所以「不该裸转发 Hijack」的真正理由不是「HTTP/2 不支持」，而是「转发了你的包装就在说谎」。**

`Hijacker` 的文档里那句话是决定性的：

> After a call to Hijack **the HTTP server library will not do anything else with the connection**.

**「不再管这条连接」= 你的包装也出局了。** 任何有这种语义的方法都要警惕。
（`Flusher` 的文档只说「把缓冲的数据发出去」，没有任何「之后就不管了」的措辞。）

#### 怎么自己判断一个陌生的可选接口

1. **读文档，找「会不会终止正常流程」的措辞**
2. **问：这个方法改变控制权吗？** 纯旁路操作（`Flush`、`SetWriteDeadline`）安全；
   移交控制权（`Hijack`、`Upgrade`）危险；绕过你的方法（`ReadFrom`）要补救
3. **实测** —— 写个 probe 探测包装前后的能力差异，再验证转发后统计还准不准

#### 三种立场

```go
// ① 不转发 —— 承认「我不支持」，最诚实。handler 的断言得到 false，走降级分支

// ② 转发但标记数据已失效
func (r *statusRecorder) Hijack() (net.Conn, *bufio.ReadWriter, error) {
	if h, ok := r.ResponseWriter.(http.Hijacker); ok {
		r.status = -1      // ⭐ 标记「被劫持了，统计不可信」
		return h.Hijack()
	}
	return nil, nil, http.ErrNotSupported
}

// ③ 提供 Unwrap，让 ResponseController 去处理
func (r *statusRecorder) Unwrap() http.ResponseWriter { return r.ResponseWriter }
```

**推荐 ③ + ②**：`Unwrap` 让新代码能用 `ResponseController`；还要兼容直接断言的老代码时，
转发的同时用 `status = -1` 之类的标记让日志诚实。

> 这个判断方法不只用于 HTTP。**任何「装饰器 + 可选接口」的场景都适用** ——
> 比如包装 `io.Reader` 时要不要转发 `io.Seeker`，同样的问题。
>
> 中间件写多了可以用现成的 `github.com/felixge/httpsnoop`：
> 它用代码生成穷举了所有可选接口的组合，包装后一个都不丢。

## 6. 请求：`r.Context()` 是关键

```go
ctx := r.Context()      // ⭐ 客户端断开连接时，这个 ctx 会自动取消
```

**D10 学的全部在这里派上用场**：

```go
func handler(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()

	rows, err := db.QueryContext(ctx, "SELECT ...")    // 客户端断了就不白查了
	if err != nil {
		if errors.Is(err, context.Canceled) {
			return                                      // 客户端走了，不用回响应
		}
		http.Error(w, "查询失败", http.StatusInternalServerError)
		return
	}
	...
}
```

### 给单个 handler 加超时

```go
ctx, cancel := context.WithTimeout(r.Context(), 3*time.Second)
defer cancel()
```

**注意是基于 `r.Context()` 派生**，这样「客户端断开」和「3 秒超时」哪个先发生都能响应（D10 §4：取更早的那个）。

### 读请求体

```go
defer r.Body.Close()                              // 其实 Server 会自动关，但显式写没坏处
body, err := io.ReadAll(r.Body)                   // ⚠️ 没有大小限制 = DoS 风险

r.Body = http.MaxBytesReader(w, r.Body, 1<<20)    // ⭐ 限制 1MB
```

**`MaxBytesReader` 是必须的**——否则一个 10GB 的请求体能直接打爆你的内存。

## 7. ⭐ `http.Server` 的四个超时 —— 今天的题眼

```go
srv := &http.Server{
	Addr:              ":8080",
	Handler:           handler,
	ReadHeaderTimeout: 5 * time.Second,    // 读完请求头
	ReadTimeout:       10 * time.Second,   // 读完整个请求（含 body）
	WriteTimeout:      15 * time.Second,   // 写完响应
	IdleTimeout:       60 * time.Second,   // keep-alive 空闲
	MaxHeaderBytes:    1 << 20,
}
```

**`http.ListenAndServe(":8080", handler)` 这个便捷函数用的是零值 `Server`——四个超时全是 0，也就是「永不超时」。**

后果：

| 攻击/故障 | 没有超时时 |
|---|---|
| **Slowloris**（每秒发一个字节的请求头） | 连接永远挂着，几千个就打满连接数 |
| 客户端连上不发数据 | 一条 goroutine 永远阻塞在读 |
| 下游卡住，响应写不出去 | goroutine + 连接一起泄漏 |

**生产环境必须显式构造 `http.Server` 并设这四个值。** 至少设 `ReadHeaderTimeout`——这是防 Slowloris 的关键。

> `golangci-lint` 有个 `gosec` 规则（G112）专门检查 `ReadHeaderTimeout` 没设。

### `WriteTimeout` 的一个陷阱

它是**从读完请求头开始算**，不是从 handler 开始写响应算。所以慢 handler + 大响应体容易撞上它。需要长时间处理时，用 `http.ResponseController.SetWriteDeadline` 单独调整。

## 8. 优雅关闭

```go
func main() {
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()

	srv := &http.Server{Addr: ":8080", Handler: handler, ReadHeaderTimeout: 5 * time.Second}

	go func() {
		if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Fatal(err)                      // ⭐ ErrServerClosed 是正常关闭，不算错
		}
	}()

	<-ctx.Done()                                 // 等 Ctrl-C / SIGTERM
	log.Println("正在关闭…")

	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()                               // ⚠️ 必须用【新的】ctx，不能用上面那个
	if err := srv.Shutdown(shutdownCtx); err != nil {
		log.Printf("强制关闭: %v", err)
	}
}
```

三个要点：

1. **`ErrServerClosed` 不是错误**——`Shutdown` 会让 `ListenAndServe` 返回它
2. **`Shutdown` 的 ctx 必须是新的**——用那个已被信号取消的，会立刻超时，在途请求直接被砍
3. **`Shutdown` 只等在途请求**，不会取消它们。要「限时后强杀」就靠那个 10 秒超时

`Shutdown` vs `Close`：前者优雅（等在途请求），后者立刻断所有连接。

## 9. 客户端

```go
// ❌ 每次新建 Client
resp, _ := http.Get(url)                        // 用的是 DefaultClient，没有超时！

// ✅ 复用一个配置好的 Client
var client = &http.Client{
	Timeout: 10 * time.Second,                  // ⭐ 整个请求的总超时
	Transport: &http.Transport{
		MaxIdleConns:        100,
		MaxIdleConnsPerHost: 10,                // ⭐ 默认只有 2，HTTP/1.1 高并发时是瓶颈
		IdleConnTimeout:     90 * time.Second,
	},
}

req, _ := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
resp, err := client.Do(req)
if err != nil { return err }
defer resp.Body.Close()                         // ⭐⭐ 不关就泄漏
io.Copy(io.Discard, resp.Body)                  // ⭐⭐ 读完才能复用连接
```

四个必须知道的：

1. **`http.DefaultClient` 没有超时**——永远别在生产用 `http.Get`/`http.Post`
2. **`resp.Body` 必须 `Close`**（`bodyclose` linter 会抓，我们已经开了）
3. **body 要读完才能复用连接** ← 见 §9.1，这条最容易漏
4. **`MaxIdleConnsPerHost` 默认是 2**——HTTP/1.1 下只调一个下游时的经典瓶颈

### 9.1 ⭐ 为什么「body 要读完」

先看 HTTP/1.1 的 keep-alive 机制。

**HTTP/1.0**：每个请求新建 TCP 连接，用完就关。100 个请求 = 100 次三次握手。
**HTTP/1.1（默认 keep-alive）**：连接不关，下一个请求接着用——**多个请求-响应在一条连接上排队**。

关键问题：**响应之间没有分隔符。** 用原始 TCP 连接抓一下就很清楚：

```
HTTP/1.1 200 OK⏎
Content-Length: 13⏎
⏎
body-of-first          ← 第一个响应到此结束
HTTP/1.1 200 OK⏎       ← 第二个响应【紧接着】开始（同一个字节流）
...
```

**TCP 只是个字节流，它不知道什么是「一个 HTTP 响应」。** 解析器必须自己算出边界，靠两种方式之一：

**① `Content-Length`（长度已知）**

```
Content-Length: 13
⏎
body-of-first
└─── 正好 13 字节，读完就是下一个响应 ───┘
```

**② `Transfer-Encoding: chunked`（流式，长度未知）**

```
9⏎          ← 这一块 9 字节
第一块⏎
9⏎
第二块⏎
0⏎          ← ⭐ 0 长度块 = 结束标记
⏎
```

每块前面写长度，`0` 表示完了。**SSE / 流式响应用的就是这个**——所以 §5 那条「包装 `ResponseWriter` 丢掉 `Flusher`」会让 SSE 失败：不 flush 就不产生 chunk。

#### 没读完会怎样

```
[响应1 header][响应1 body 共 13 字节]
                      ↑
                你读到这儿（第 6 字节）就 Close 了
```

**连接的读位置停在 body 中间，还剩 7 个字节。** 复用它发下一个请求：

```
你以为读到的：  HTTP/1.1 200 OK...
实际读到的：    -first HTTP/1.1 200 OK...
                └┬───┘
              上个响应的残留 → 解析失败
```

所以 Go 的 `Transport` 的判断很简单：

| 状态 | 处理 |
|---|---|
| body 读到 **EOF** | ✅ 读位置正好在边界上 → **放回空闲池** |
| body **没读完**就 `Close()` | ❌ 位置不明 → **直接关掉这条连接** |

它不会帮你把剩余的读完——那可能是 1GB。

#### 实测

同一个 client 连发 5 个请求，用 `r.RemoteAddr` 数 TCP 连接数：

```
body    100 字节  读完 body  → 用了 1 条 TCP 连接   ✅ 复用了
body    100 字节  不读 body  → 用了 5 条 TCP 连接   ⚠️ 每次新建
body 100000 字节  读完 body  → 用了 1 条 TCP 连接   ✅
body 100000 字节  不读 body  → 用了 5 条 TCP 连接   ⚠️
```

**即使 body 只有 100 字节也一样。**

#### 后果：不是「慢一点」，是三个真实问题

| 问题 | 说明 |
|---|---|
| **TCP 握手开销** | 每次新建 = 三次握手（TLS 的话还有几个 RTT） |
| **端口耗尽** | 关闭的连接进入 `TIME_WAIT`（默认 60 秒），高 QPS 下本地端口被耗光 |
| **下游连接数暴涨** | 你以为复用了 10 条，实际每秒新建几千条 |

**症状很典型**：压测 QPS 上不去、`netstat` 一堆 `TIME_WAIT`、下游报 "too many connections"。

### 9.2 正确写法（含最容易漏的错误分支）

```go
resp, err := client.Do(req)
if err != nil {
	return err
}
defer resp.Body.Close()             // ⭐ 必须，释放你这侧的资源

// ① 需要 body：读完就行
var result Data
if err := json.NewDecoder(resp.Body).Decode(&result); err != nil {
	return err
}

// ② 不需要 body（只看状态码）：显式丢弃
io.Copy(io.Discard, resp.Body)
```

⚠️ **最容易漏的是错误分支**：

```go
if resp.StatusCode != http.StatusOK {
	return fmt.Errorf("状态码 %d", resp.StatusCode)   // ❌ body 没读，连接废了
}
```

**4xx/5xx 的响应也有 body**，也要读完。而且这个分支恰恰在「下游出问题」时高频触发——**故障时连接池崩得最快**。

```go
if resp.StatusCode != http.StatusOK {
	io.Copy(io.Discard, resp.Body)                    // ⭐ 或者读出来放进错误消息
	return fmt.Errorf("状态码 %d", resp.StatusCode)
}
```

> **`Close()` 释放的是「你这一侧的资源」，`读完` 才能让「连接回到池子」。两件事，都要做。**

**什么时候故意不读完**：body 特别大而你只需要开头几个字节时——读完一个 1GB 的响应只为了复用连接，代价更大，主动放弃是对的。

### 9.3 `io.Discard` 到底把数据读到哪了

```go
func (discard) Write(p []byte) (int, error) {
	return len(p), nil        // ⭐ 就这一行：假装写了，直接返回
}
```

而且它**还实现了 `ReaderFrom`**，`io.Copy` 会优先走这条路：

```go
var blackHolePool = sync.Pool{
	New: func() any { b := make([]byte, 8192); return &b },   // ⭐ 8KB，复用
}

func (discard) ReadFrom(r Reader) (n int64, err error) {
	bufp := blackHolePool.Get().(*[]byte)
	for {
		readSize, err = r.Read(*bufp)     // ⭐ 反复读进【同一个】缓冲区
		...
	}
}
```

**数据流**：

```
网络 ──读 8KB──→ [复用的 8KB 缓冲区] ──覆盖──→ 网络 ──读下一个 8KB──→ ...
                        ↑
                 从 sync.Pool 拿的，用完还回去
```

**内存占用是 O(1) = 8KB，不管 body 是 1KB 还是 1GB。** 实测（10MB 数据，纯 Reader）：

```
io.Copy(io.Discard, r)      7259 ns/op         0 B/op    0 allocs/op   ⭐ 零分配
io.ReadAll(r)             786379 ns/op  23469874 B/op   30 allocs/op   ← 切片扩容
io.Copy(&bytes.Buffer{}) 1232829 ns/op  33553990 B/op   17 allocs/op
```

⚠️ **所以「我不需要 body」时千万别写 `io.ReadAll(resp.Body)` 然后扔掉**——那会把整个 body 装进内存，10MB 的 body 峰值要 23MB（扩容时新旧数组共存）。

#### 顺带：`io.Copy` 有三条路径

```go
func Copy(dst Writer, src Reader) (int64, error) {
	if wt, ok := src.(WriterTo); ok { return wt.WriteTo(dst) }      // ① 源会写
	if rf, ok := dst.(ReaderFrom); ok { return rf.ReadFrom(src) }   // ② 目标会读
	// ③ 都不会 → 自己分配 32KB 缓冲区来回搬
}
```

这是 **D5 §5「可选接口」在标准库里的大规模应用**：用类型断言探测「你会不会更高效的方式」，会就用，不会就退回通用实现。

（`strings.Reader` 有 `WriteTo` → 走 ①；真实的 `*http.body` 没有 → 走 ②，也就是那个 8KB 循环。）

### 9.4 HTTP/2 下有什么不同

Go **从 1.6 起标准库内置 HTTP/2**，而且默认就开：

```go
srv.ListenAndServeTLS(cert, key)   // ⭐ 自动启用 HTTP/2（内部调 setupHTTP2_ServeTLS）
srv.ListenAndServe()               // 明文 → 只有 HTTP/1.1
```

**必须是 TLS**——HTTP/2 靠 **ALPN**（TLS 握手时协商应用层协议）确定用 h2 还是 http/1.1，明文没有这个机会。

客户端也是自动的（`http.DefaultTransport` 里 `ForceAttemptHTTP2: true`）。
⚠️ **但自定义 `TLSClientConfig` 或 `DialContext` 会把它关掉**，要显式加回来。

明文 HTTP/2（h2c，内网/网关卸载 TLS 时常用）**不在标准库**，要引 `golang.org/x/net/http2/h2c`。

**行为差异**：

| | HTTP/1.1 | HTTP/2 |
|---|---|---|
| 连接复用 | 一条连接**串行排队** | **多路复用**——一条连接多个并发 stream |
| **body 没读完的后果** | **整条连接作废** | 只影响那个 stream |
| `MaxIdleConnsPerHost` | 关键参数（默认 2） | **基本无关**——一条连接够用 |
| `http.Hijacker` | ✅ 支持 | ❌ **不支持**（WebSocket 升级得走 h1） |

**最实际的两条**：`MaxIdleConnsPerHost` 只对 h1 重要；**包装 `ResponseWriter` 转发 `Hijacker` 时必须用 comma-ok**，不能假设它存在（§5 那条）。

> 即便如此，**「读完 + Close」的习惯不变**——h2 的 stream 也要释放，而且你的代码可能跑在 h1 上（内网服务、老代理）。

go/cmd/httpdemo/          ← 先跑：go run ./cmd/httpdemo

### 主练习 · `httpx`

不用任何框架，手写四个中间件和一个 REST handler。

**中间件**（签名统一为 `func(http.Handler) http.Handler`）：

1. **`RequestID`** —— 生成 ID 放进 ctx 和响应头，已有 `X-Request-ID` 就复用
2. **`Recover`** —— 兜住 panic，返回 500，**不能让进程挂掉**
3. **`Logging`** —— 记录方法/路径/状态码/耗时（要包装 `ResponseWriter`）
4. **`RateLimit`** —— 简单的令牌桶，超限返回 429

**外加 `Chain`** 把它们串起来（顺序：从左到右 = 从外到内）。

**API**：一个内存 KV 存储的 CRUD，用 Go 1.22 的新路由。

硬要求：

- **`Recover` 之后进程必须还活着**，且日志里能看到 panic 的堆栈
- **`Logging` 记录的状态码必须准确**（包括 404、500、429）
- **中间件顺序可验证**（测试会检查执行顺序）
- **`RateLimit` 的计数必须并发安全**（`-race` 干净）
- **handler 里必须用 `r.Context()`**
