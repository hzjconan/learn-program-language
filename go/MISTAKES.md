# 错题本

> 练习和小题里**答错过**的知识点。第 21 天面试模拟会逐条重测，**换场景问**。
>
> 每条记三样：**当时的错误直觉** / **要测的正确规则** / **重测的角度**。
> 记「错误直觉」而不只是「正确答案」，是因为要验的是那个直觉有没有真的被拆掉——
> 直接复用原题只会测出「记不记得答案」。
>
> 记录规则：每次 code review 发现答错就追加一条，别删——**改对了也留着**，
> 那正是复测的对象。

## 1 · D4 值接收者与调用者无关（小题 A①）

**错误直觉**：「手里是指针 → 调什么方法都能改到原对象」，把 `p.N` 答成 2（实际 1）。

**正确规则**：`p.Inc()` 展开成 `(*p).Inc()`，**先解引用再整个拷贝**。有没有拷贝**只由接收者类型决定**，和调用者手里拿的是值还是指针无关。

| 手里是 | 调值接收者方法 | 调指针接收者方法 |
|---|---|---|
| 值 `c` | 直接传 → **拷贝** | `(&c)` → 取地址，无拷贝 |
| 指针 `p` | `(*p)` → **解引用 + 拷贝** | 直接传 → 无拷贝 |

**重测角度**：可顺带测推论——nil 指针上调值接收者方法会 panic，调指针接收者方法不会。

## 2 · D4 可寻址 vs 方法集是两条规则（小题 A②）

**错误直觉**：「值上不能调指针接收者方法」，把 `c := Cat{}; c.Speak()` 判成编译错误（实际能编译），同时漏判了真正编译不过的 `var s Speaker = Cat{}`。

**正确规则**：

| 写法 | 结果 | 原因 |
|---|---|---|
| `c.Speak()`，`c` 是变量 | ✅ | 可寻址 → 编译器改写成 `(&c).Speak()` |
| `m["a"].Speak()` | ❌ | map 元素不可寻址 |
| `var s Speaker = Cat{}` | ❌ | **接口赋值只认方法集，不帮忙取地址** |

**重测角度**：map 元素那条当时答对了，可以不再测；重点考「接口赋值不走自动取地址这条路」。

## 3 · D4 继承的代价说不出口（小题 B，半答）

**当时的状态**：能说出「Go 靠碰巧有方法就满足接口」，但答不出「Java 用继承别扭在哪」。

**要能说出的四点**：多余字段（`Contractor` 背上用不到的 `baseSalary`）、无意义的抽象方法（`bonus()` 只能返回 0 或抛异常）、模板方法被子类掀翻（`calculatePay()` 对它是错的）、最后还是得抽接口（Java 也会走到 `Payable`，只是要先动整个类层次）。

**重测角度**：给一个继承层次，让我说出**这个设计会在哪里付出代价**，而不只是「Go 怎么写」。

## 4 · D5 type switch 的匹配顺序（小题 A②）

**错误直觉**：「传什么具体类型就走哪个 case」。把 `kind(&MyErr{})` 答成 `*MyErr`，实际是 `error`。

**正确规则**：type switch **从上往下匹配，第一个命中就返回**。`case error` 排在 `case *MyErr` 前面时，后者是永远走不到的死代码。

⭐ **case 越具体越靠前，接口 case 垫底。** nil 接口不匹配任何类型 case，只被独立的 `case nil` 接住。

## 5 · D5 `comparable` 挡不住装了 slice 的 `any`（小题 A④）

**错误直觉**：以为 `Uniq([]any{[]int{1}})` 返回 1。

**实际**：**编译得过，运行时 panic**（`hash of unhashable type []int`）。Go 1.20 起 `any` 满足 `comparable`。

**正确规则**：约束是编译期的，而「可比较」这件事对 `any` 只能推迟到运行时。想挡住就写具体的类型集（`~string | ~int`），少用 `comparable` 兜底。

## 6 · D5 「打印出来」≠「内部状态」（小题 A①第二行）

**错误直觉**：问 `fmt.Println(f())` 输出什么，答了接口二元组 `<*MyErr, nil>`。

**正确规则**：`fmt` 遇到 error 会**调用它的 `Error()` 方法**，输出取决于这个方法碰没碰接收者：

```
Error() 不碰接收者   → 打出方法的返回值（比如 boom）
Error() 解引用了     → panic，被 fmt 兜成 <nil>
```

三种可能（`boom` / `<nil>` / `%!v(PANIC=...)`）**都不告诉你这个 error 其实非 nil**。可信的只有 `%T` 和 `== nil`。

> ⚠️ Claude 第一版讲义在这里也写错了，重测时别再拿错的标准答案考。

## 7 · D5 泛型 vs 接口的判据用反（小题 B 第 2 问 d）

**错误直觉**：自己总结的判据是「需不需要区分实际类型」，对 a/b/c 都判对了，但「对能算出金额的东西求和」判成泛型（应为接口）——因为从调用方看「不需要区分」，可行为本身按类型不同。

**正确规则**：

> **泛型 = 同一段代码作用于不同类型**（代码相同，类型不同）
> **接口 = 不同的代码通过同一个名字被调用**（名字相同，代码不同）

**杀手锏例子**：`func Total[T Payer](ps []T)` 能编译，但 `[]T` 是**同质**的——装不下混合类型的集合。要「一堆不同类型放一起」只能用 `[]Payer`。

## 8 · D6 `b.Loop()` 的好处记错了（小题 A④）

**错误直觉**：「应该用 `b.Loop` 让 Go 自己决定跑多少轮」。

**实际**：老写法 `for i := 0; i < b.N; i++` 的轮数**也是 Go 决定的**（`b.N` 由框架填）。这不是两者的区别。

**正确规则**：`b.Loop()` 的两个好处是**自动排除 setup 计时**和**保证调用不被编译器删掉**。而且它**挡不住逃逸分析**——丢弃返回值仍可能测出假的 `0 allocs/op`，所以 sink 该加还是要加。

## 9 · D6 MVS「最小」的含义表述不准（小题 A②）

**当时的说法**：「选这个包里面最小版本」——答案对（v1.5.0），表述不准。

**准确说法**：在「**满足所有约束的版本集合**」里取最小。那几个版本号（v1.2.0/v1.3.0/v1.5.0）是**下界**，不是候选。满足全部下界的集合是 `{v1.5.0, v1.6.0, ..., v1.9.0, ...}`，Go 取最小的 v1.5.0，npm/Maven 取最大的 v1.9.0。

**最关键的一点当时没答出来**：**Go 根本不去查最新版是多少**。这才是它和 npm/Maven 的分歧根源，也是构建可复现、不需要 lockfile 的原因。

## 10 · D7 「零值可用」的适用条件（设计问答 1）

**错误直觉**：问 `Report` 能不能零值可用，答「不能，因为有 map 字段」。

**实际**：**能**——在 `Add` 里惰性初始化就行，D6 刚给 `genx.Set` 做过一模一样的事，没联想起来。

**正确规则**：nil map 不可写不是障碍。「零值可用」是**默认倾向不是铁律**，判据是「**有多少调用点会写 `var x T` 而不是 `NewT()`**」——接近零就老实给构造函数（`Report` 只有 `Analyze` 一个生产入口，所以 `NewReport` 是对的）。

## 11 · D7 具名类型的价值说偏（设计问答 5）

**错误直觉**：问 `time.Duration` 比 `int` 好在哪，答「int64 范围大」。**范围不是理由**——64 位平台上 `int` 也是 64 位。

**正确规则**：**类型自带单位 + 编译器挡住裸数字运算**，这是 D1 具名类型的核心价值。

```go
Latency: 15 * time.Millisecond   // 一眼看出单位
Latency: 15                      // 毫秒？秒？纳秒？
latency + 5                      // 编译不过 ✅
```

**同题第二问当时没答**：「进来转、出去再转值不值？」——**值**。**边界做转换，内部用富类型**：领域模型该有语义，传输格式该简单。这和 `JSONFormatter` 用独立序列化 struct 是同一个原则。

## 12 · D8 CPU 密集 vs IO 密集的并发收益（小题后的追问）

**错误直觉**：「CPU 密集型开多线程更快；IO 密集型因为 CPU 闲着，开多线程提升不大。」

**前半句对，后半句反了。** 10 核机器实测（60 个任务）：

```
                1 worker    2       5       10      20      50
CPU 密集        8.65ms   4.46   1.87    1.13    1.14    1.15    ← 到核数就平了
IO  密集      136.43ms  68.27  27.30   14.16    7.36    4.74    ← 一直在加速
加速比(IO)         1×    2.0×   5.0×    9.6×   18.6×   28.8×
```

**正确规则**：**「CPU 闲着」正是并发有用的原因，不是没用的原因。** 等待不占 CPU，
所以几百个等待可以互相重叠。真正的区别是**天花板**：

| 类型 | 每个任务在干什么 | 加 worker 的天花板 |
|---|---|---|
| **零工作量** | 什么都不干 | **纯亏**，只剩协调开销 |
| **CPU 密集** | 占着 CPU 算 | **= 核数**，超过只是徒增切换 |
| **IO 密集** | 等外部，不占 CPU | **远高于核数**（受下游/连接数限制） |

统一公式（Java 里也是这个）：**最优并发数 ≈ 核数 × (1 + 等待时间 / 计算时间)**。

**重测角度**：给一个具体场景（比如「压缩 1 万个文件」vs「调 1 万次外部 API」），
问最优并发数怎么定、为什么。别直接问定义。

## 13 · D8 「杀死线程 / goroutine」（小题 B 第 1 问，答「不知道」）

**知识盲点**：以为 Java 的 `Future.cancel(true)` 能真的取消任务，所以困惑 Go 为什么不提供。

**正确规则**：**`Future.cancel(true)` 也杀不掉线程。** 它调 `Thread.interrupt()`，
**只设一个标志位**；目标线程必须自己检查 `isInterrupted()`，或正好阻塞在可中断调用里
（sleep/wait/join）才会响应。跑死循环又不检查标志的线程，它拿不下来。

**所以 Java 的取消也是协作式的**，和 Go 的 context 同类。

真正的「杀死」是 `Thread.stop()` —— **Java 1.2 就废弃了**：它释放该线程持有的所有
monitor，让被保护的对象处于不一致状态，且毫无征兆。锁永远不释放、`defer` 全部跳过。

**Java 试过、失败了、废弃了；Go 直接不提供这个坑。**

**重测角度**：问「Go 为什么没有 `killGoroutine()`」，看能不能说出
「从外部强杀执行流必然破坏不变量」以及「Java 的前车之鉴」。

## 14 · D9 「重入」的含义（小题 A②③）

**错误直觉**：以为「一条 goroutine 里对同一个 mutex 做两次 `Lock`」就是重入。

```go
// ❌ 我以为这是重入 —— 其实完全合法
mu.Lock(); n++; mu.Unlock();   mu.Lock(); n++; mu.Unlock()
//                    ↑ 锁在这两次之间是【空闲】的

// ✅ 这才是重入 —— 还没解锁就再次加锁
mu.Lock()
mu.Lock()      // 死
```

**判断方法**：画一条时间线，看 `Unlock` 有没有在第二次 `Lock` 之前。

**同题漏掉的实战形态**（②(3)，实测卡死）：

```go
func (s *S) Get() int  { s.mu.Lock(); defer s.mu.Unlock(); return s.n }
func (s *S) Both()     { s.mu.Lock(); defer s.mu.Unlock(); s.Get() }  // ← 自锁死
//                                     ↑ defer 要到函数结束才解锁
```

**正确规则**：Go 的 mutex **不可重入**（Java 的 `synchronized` 是可重入的）。
惯例是**导出方法加锁，内部方法不加锁**，不加锁的版本命名带 `Locked` 后缀。

**重测角度**：给一段「A 方法调 B 方法，两个都加锁」的代码，问会发生什么。
别直接问「什么是重入」。

## 15 · D9 双检锁错在哪（小题 A④）

**错误直觉**：以为手写双检锁的问题是「两个 goroutine 都看到 nil，都去初始化」。

**不会。** 里面那层 `if !loaded` 在锁的保护下，**双重检查的「第二重」正是防这个的，它有效**。

**真正的问题是可见性**：

```go
if !loaded {              // ① 无保护的读
    mu.Lock()
    if !loaded {
        cfg = &Config{...}    // ② 写对象
        loaded = true         // ③ 写标志
    }
    mu.Unlock()
}
return cfg                // ④ 无保护的读
```

goroutine B 在 ① 读到 `loaded == true`、在 ④ 读 `cfg`，**这两次读都没有 happens-before 保护**，
所以可能看到：`loaded` 已是 true 但 `cfg` 还是 nil；或 `cfg` 非 nil 但**字段还没写完**。

⭐ **「初始化执行了两次」不是症状，「拿到半成品」才是。**
Java 里同样的代码要给标志位加 `volatile` —— `volatile` 建立的正是 happens-before。

**正确做法**：`sync.Once` / `sync.OnceValue`，**永远别自己写双检锁**。

**重测角度**：给一段手写双检锁，问「它可能出什么问题」，看能不能说到「半初始化的对象」
而不是「重复初始化」。

## 16 · D9 并发代码「跑对了」不等于「是对的」（小题 A①⑤）

**错误直觉两处：**

**①** 忙等循环 `for !done {}`，答「会一直跑」。**实测退出了，1ms。**
但理由（没有同步就没有 happens-before）是对的 —— 所以正确答案是
**「这是未定义行为，今天退出不保证明天退出」**，而不是二选一。

**⑤** 10 条 goroutine 并发写 map，答「会 panic」。两处偏差：
- 是 **`fatal error`** 不是 panic —— `recover()` 拦不住
- 是**概率性**的 —— 实测 20 次里崩 7 次，13 次静默通过

**正确规则**：**普通代码测试通过基本就没问题，并发代码测试通过什么也证明不了。**
`-race` 判的是「有没有 happens-before」，不是「这次跑对没跑对」——
所以它能在程序表面正常时照样报警。

**重测角度**：给一段有竞态但「跑起来结果正确」的代码，问「这段代码有问题吗」。
看会不会因为「我跑了一万次都对」就下结论。
