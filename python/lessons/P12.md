## 2. 从 main 中的断言到独立测试

P11 的断言放在 main 中，一处失败会使该次 main 后续语句不再执行。pytest 能发现并分别运行测试函数，默认会继续运行其他已收集测试，最后汇总失败信息。

默认使用 `test_*.py` 文件、`test_` 开头的函数；本课在 `tests/` 下组织文件。测试函数不需要由用户在 main 中调用，也不要求继承测试基类。简单示例：

```python
# 示例，不是项目练习答案
def test_strip_keeps_internal_spaces():
    actual = "  A  B  ".strip()
    assert actual == "A  B"
```

测试按「准备输入 → 调用被测行为 → 断言契约」组织。仍使用 assert，pytest 会展示失败表达式及相关实际值。断言应从需求推导预期，不能再调用同一被测函数计算所谓期望值，也不能只写比较表达式而丢弃结果。

从课程根目录运行单文件：

```bash
uv run python -m pytest -q tests/test_processor.py
```

`-q` 减少常规输出。使用 python -m pytest 也让当前课程根目录进入模块搜索路径，便于导入 p11_docs。单独选择一个测试可用 `tests/test_processor.py::test_name`。本阶段先显式指定测试路径，不需要改包布局或额外配置。

## 4. 首组评审与参数化

用户的三个独立测试已通过。完整输出列表断言能同时验证文本、ID、首次保留与顺序；`is not` 明确检查输出新字典。测试也应各自聚焦，输入不变不必重复整个混合批次。含坏输入的清洗测试可以补错误行号断言，不能把测试数量等同覆盖充分。

参数化用于「相同验证规则，多组输入」，pytest 会把每组参数作为独立测试项运行。例如：

```python
import pytest


@pytest.mark.parametrize(
    "raw, expected",
    [(" A ", "A"), ("B", "B"), ("  A  B  ", "A  B")],
)
def test_strip_examples(raw, expected):
    assert raw.strip() == expected
```

装饰器中名字与函数参数对应，每个元组提供一组输入与预期。本例收集为3项，不需要手写循环；一项失败仍可看到其他项结果。当前先把装饰器作为 pytest 用法使用，装饰器机制留到 A03。仅使用参数化不要求自己编写 fixture。

### 4.1 为什么需要参数化

如果有多组 strip 输入，直接写三个函数会重复「调用 strip，再与期望比较」的测试逻辑；把三个 assert 塞进同一个测试函数，则第一条断言失败会使该函数退出，余下断言不再执行。参数化将同一段验证逻辑与数据表结合，pytest 为每行数据生成独立测试项，能够分别报告通过或失败。默认没有 -x 等提前停止选项时，会继续执行后面的测试项。

### 4.2 拆开看语法

`import pytest` 引入 pytest 模块。`pytest.mark.parametrize` 是 pytest 提供的参数化装饰器；以 @ 开头的一行及后面的括号内容修饰紧随其后的函数，告诉 pytest 如何为它生成多组测试。不需要手动调用该函数，也不需要在函数内自己写循环。装饰器的一般实现留到 A03，此处先掌握其框架契约。

第一个参数 `"raw, expected"` 是一个字符串，声明两个参数名；逗号分隔的名字必须能对应测试函数签名中的参数。也可以写成 `("raw", "expected")` 等名称序列，但不要把两种写法混成 `parametrize("raw", "expected", ...)`。

第二个参数是数据表，外层列表的一项代表一组测试数据；两个参数时，每项为包含两个值的元组，位置与名称顺序对应：第一个值给 raw，第二个值给 expected。raw 是原始输入，expected 是根据契约写出的期望输出，二者不是 pytest 的保留字，可以改名，但装饰器和函数签名应一起改。

| 数据组 | raw | expected | 本次断言 |
|---|---|---|---|
| 1 | `" A "` | `"A"` | `" A ".strip() == "A"` |
| 2 | `"B"` | `"B"` | `"B".strip() == "B"` |
| 3 | `"  A  B  "` | `"A  B"` | `"  A  B  ".strip() == "A  B"` |

第三组专门验证内部的两个空格不会消失。用多组值不是为了增加测试数量，而是覆盖不同契约：去掉首尾空白、不需要清洗时保持原值、保留内部空白。

### 4.3 收集与运行是两个阶段

pytest 先导入测试模块，读取装饰器中的参数声明，收集成3个测试项；随后为每个测试项准备对应参数并调用同一个函数。可把执行效果近似理解成三次调用：

```python
test_strip_examples(raw=" A ", expected="A")
test_strip_examples(raw="B", expected="B")
test_strip_examples(raw="  A  B  ", expected="A  B")
```

这只是帮助理解传参的等效示意，不要把这三次调用追加到测试文件；pytest 自己负责调用、记录和汇总。一项失败时报告该组参数的具体值。原文件已有3个普通测试，再添加这个3组示例，就会有6项；测试函数数量不等于测试项数量。

运行 `uv run python -m pytest -v tests/test_processor.py` 可以查看逐项结果。只看该函数可用 `tests/test_processor.py::test_strip_examples`；`--collect-only -q` 只展示收集项，不执行断言。

### 4.4 一个参数时的数据形状

只需要一个参数时，不必给每个值再包一层元组：

```python
@pytest.mark.parametrize("raw", [" A ", "B", "  A  B  "])
def test_strip_is_idempotent(raw):
    once = raw.strip()
    assert once.strip() == once
```

这个不同的例子验证重复 strip 不再改变结果。每个外层列表元素作为一个完整的 raw 传入。单参数即使本身是列表或字典，也会作为一个整体传入，不会自动拆成多个函数参数；例如数据表 `[[], [1, 2]]` 对应两个测试项，分别传入空列表和列表 `[1, 2]`。这里不展开「单参数本身是元组」与「显式包裹参数行」的其他变体。

### 4.5 可读名称与常见问题

可用 ids 给数据行添加易读名称：

```python
@pytest.mark.parametrize(
    "raw, expected",
    [(" A ", "A"), ("B", "B"), ("  A  B  ", "A  B")],
    ids=["trim_edges", "unchanged", "keep_inner_spaces"],
)
def test_strip_examples(raw, expected):
    assert raw.strip() == expected
```

此版本替换前面的同名示例，不要同时定义两个同名函数，后定义会覆盖前定义。ids 数量对应数据行数，不改变测试逻辑。-v 输出会包含 `test_strip_examples[trim_edges]` 等名称。

常见错误：名字与函数签名不对应；声明两个名字但某行只有一个值；误以为 parametrize 会自动断言函数返回值；根据被测代码计算 expected 使测试失去独立依据。参数化只负责提供数据，测试函数仍需写 assert。

另外，pytest 不会自动深拷贝参数中的列表或字典；数据按对象引用传入。若复用一个可变对象，某次测试修改它，其他引用可能受到影响，回访 P04。当前任务的函数契约要求不修改输入，测试也应避免修改参数表中的共享对象。

## 5. fixture：由 pytest 准备测试依赖

fixture 用来准备测试所需的数据或资源，并由 pytest 管理调用。测试在参数中声明 fixture 名称，pytest 按名称找到定义、运行准备逻辑，把返回值作为实参传入；不是 Python 自动根据参数名创建对象。

```python
import pytest


@pytest.fixture
def document():
    return {"text": "  示例  "}


def test_document_has_text(document):
    assert document["text"] == "  示例  "
```

此处 document 在定义处是 fixture 函数的名字，在测试体内是形参，指向 fixture 返回的字典。不要在测试里写 document()；使用 fixture 由 pytest 负责解析依赖。默认 function 作用域，即不同测试分别执行该准备函数；本例每次执行字典字面量创建新字典，所以不同测试数据独立。同一个测试内部反复请求同一默认 fixture 通常复用该次准备结果；若 fixture 返回全局可变对象，作用域不会自动帮忙复制它。

参数化给同一测试提供多组值；fixture 准备可复用的测试依赖，两者目的不同，也能一起使用。当前先在测试文件里定义 fixture，不需要立即学习 conftest.py 或修改作用域。

## 6. tmp_path：内置的临时目录 fixture

tmp_path 由 pytest 提供，每个测试拿到独立临时目录，类型为 pathlib.Path，不需要手动导入 tmp_path 或使用 TemporaryDirectory。

```python
@pytest.fixture
def greeting_file(tmp_path):
    path = tmp_path / "greeting.txt"
    path.write_text("你好", encoding="utf-8")
    return path


def test_greeting(greeting_file):
    assert greeting_file.read_text(encoding="utf-8") == "你好"
```

依赖链为测试请求 greeting_file → greeting_file 请求 tmp_path → pytest 创建目录 → 写示例文件并返回路径 → 路径传入测试。fixture 也能请求其他 fixture，和测试请求 fixture 的规则一致。

tmp_path 不同于 TemporaryDirectory 退出 with 立即删除的生命周期；pytest 按临时目录保留策略管理，默认可能留下最近几次运行的数据便于排错，不能依赖测试结束时目录立刻消失。测试始终使用本次拿到的目录，不依赖上次运行残留文件。

## 7. pytest.raises：验证预期异常

P11 用标记变量和 try/except 检查是否出现异常，pytest 提供更直接的 with 写法：

```python
def test_invalid_integer():
    with pytest.raises(ValueError):
        int("abc")
```

无异常、或发生其他不兼容异常，都不会让这项测试通过；与断言异常数量相比，它验证的是指定代码块的失败行为。with 内只放预期抛异常的操作，后续普通断言应放在 with 外面，异常发生后块内后续语句不会运行。

## 9. CLI 集成测试：运行独立子进程

单测 read_records 和 write_records 不能证明入口解析参数正确、退出码正确、stdout/stderr 分开，也不能证明程序能以 -m 启动。CLI 测试用 subprocess.run 运行另一个 Python 进程，从外部检查行为。示意：

```python
import subprocess
import sys

result = subprocess.run(
    [sys.executable, "-c", "print('hello')"],
    capture_output=True,
    text=True,
    timeout=10,
)
assert result.returncode == 0
assert result.stdout == "hello\n"
assert result.stderr == ""
```

sys.executable 是当前运行测试的解释器路径，避免误用系统 Python 3.9。参数用列表传递，各元素是一个参数，含空格的路径也不需要自己拼引号。capture_output=True 捕获两个输出通道，text=True 让结果为字符串而非 bytes，timeout 限制等待秒数。默认 check=False，非零退出码作为结果返回；不要加 check=True，否则预期失败的 CLI 用例会先抛 CalledProcessError。

启动助手可放在 tests/test_cli.py（是普通辅助函数，不是测试，也不是 fixture）：

```python
import subprocess
import sys
from pathlib import Path


def run_cli(*args):
    return subprocess.run(
        [sys.executable, "-m", "p11_docs.app", *map(str, args)],
        cwd=Path(__file__).resolve().parents[1],
        capture_output=True,
        text=True,
        timeout=10,
    )
```

__file__ 是当前测试文件路径；其 parents[0] 是 tests 目录，parents[1] 是课程根目录。cwd 只设置子进程工作目录，使其找到 p11_docs。map(str, args) 将 Path 等参数转为字符串，星号把结果展开为多个列表元素；run_cli("--input", source, "--output", target) 就生成完整启动参数。不要改成 shell 字符串或在子进程中再调用 uv，当前解释器已有所需依赖。

### return 与 assert 的详细纠正

`return False` 是函数正常返回一个布尔值，不会抛出异常；pytest 不把这个布尔值当作通过/失败协议。`assert False` 则抛 AssertionError，pytest 会报告测试失败。当前 pytest 9.2.0 默认配置下，教师用两个临时测试验证：

```python
def test_return_false():
    return 2 + 2 == 5


def test_assert_false():
    assert 2 + 2 == 5
```

结果为1 passed、1 failed、1 warning。第一个测试正常返回 False，被报告通过并产生 PytestReturnNotNoneWarning，提醒测试函数应返回 None；第二个因 AssertionError 失败。警告可被配置为错误，因此不要把「返回 False 永远通过」当成契约，正确测试应使用 assert。裸比较表达式同样不会自动导致失败。

对于缺失文件，直接调用 read_records 时异常在测试进程内发生，pytest.raises 可以捕获；subprocess.run 启动 CLI 时，异常发生在另一个解释器进程，app 捕获后写 stderr 并以1退出，父进程拿到 CompletedProcess 的 returncode/stdout/stderr。不是「父进程无法知道错误」，而是错误信息通过进程结果传递，而非 Python 异常对象跨进程抛出。若 check=True，父进程抛出的将是 CalledProcessError，也不是子进程内部的 FileNotFoundError。

裸比较不等于返回比较结果。函数中单独写 `actual == expected`，计算出 False 后丢弃结果；没有 return 的函数正常结束时返回 None。只有明确写 `return actual == expected` 才返回 False；写 `assert actual == expected` 则在条件为假时抛 AssertionError。Python 不会把最后一条表达式自动当成返回值，这与 JS/TS 箭头函数的表达式函数体需要区分。

用户最终正确回答：`def check(): 1 == 2` 正常调用后得到 None，返回值区别复测通过。子进程异常不会直接跨进程抛到父进程，错误信息仍可从 returncode 与 stderr 判断；用户现有 CLI 测试已正确验证这两个通道。
