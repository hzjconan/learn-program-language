## 1. 从单个生成器到处理链

A04 的 batched_docs 已经可以逐批提供结果。进一步，可以让每个步骤只负责一件事，把上一步的迭代器交给下一步：来源产出原始文本，清洗步骤逐项处理，消费者逐项接收清洗结果。

```python
stream = clean(source())
```

假设 source 与 clean 都是生成器函数，这行只是创建两个生成器对象，并把 source 的对象作为参数交给 clean；不会预先运行两个函数体。消费者调用 next(stream) 后，clean 开始执行；clean 的 for 需要输入时，才向 source 索取值。clean 可以跳过某些输入，因此下游取一个输出不一定只读取一项输入。

这种同步处理链由消费者取值推动：每一步用上一步逐项提供的值继续处理，避免必须先等待全部结果。惰性与内存使用仍取决于每一步的具体实现；若某一步先 list(上游)，它仍会消费全部上游。

## 2. 开课预测：先推理，不运行

```python
def source():
    for index, text in enumerate([" A ", "   ", " B"], start=1):
        print("read", index)
        yield text


def clean(texts):
    for text in texts:
        cleaned = text.strip()
        if not cleaned:
            continue
        print("keep", cleaned)
        yield cleaned


stream = clean(source())
print("ready")
print(next(stream))
print("rest", list(stream))
```

### 初次批改：内部打印不会代替外层打印

## 3. 增量事件与中途失败

可以用事件描述流式输出。以下约定 type="delta" 表示新增文本片段，text 携带片段；type="done" 表示正常完成。这是我们设计的示例协议，不是 Python 自动提供的事件类型。消费者收到 delta 就累加或显示，收到 done 才确认正常完成。

生成器在推进时也可能抛出普通异常。与 StopIteration 的正常耗尽不同，RuntimeError 等异常会传到消费者。此前已经产生的修改和输出不会自动回滚；消费者可以保留部分结果并报告失败，但不能因此把失败当作正常完成。

### 预测：完整代码，判断全部终端输出

```python
def events(fail):
    yield {"type": "delta", "text": "Py"}
    yield {"type": "delta", "text": "thon"}
    if fail:
        raise RuntimeError("连接中断")
    yield {"type": "done"}


text = ""
try:
    for event in events(True):
        if event["type"] == "delta":
            text += event["text"]
            print("partial", text)
        else:
            print("done", text)
except RuntimeError as exc:
    print("failed", text, str(exc))
```

问题：完整执行时终端依次输出什么，会不会打印 done，text 最后是什么？如果只把 for event in events(True) 改成 for event in list(events(True))，同样保留外层 try/except，会有哪几行输出？说明原因。用户预测已通过，未运行。

list 只会在成功收集到迭代结束后返回列表；若中途抛出普通异常，list 调用抛出异常，外层循环拿不到成功返回的列表。比较两种写法时，分别跟踪“生成器已经产出”和“消费者循环体已经处理”，不能把这两件事等同。

### 预测评审

直接迭代的输出为 partial Py、partial Python、failed Python 连接中断，每项独占一行；不输出 done，text 保留为 Python。改成先 list 后迭代时，消费者循环体尚未执行就发生异常，因此没有 partial，text 仍为空；实际输出为 failed 后两个空格再接连接中断，空字符串不会显示引号。用户两种机制判断均正确，未运行。

## 4. 提前停止与资源释放

流式来源可能持有文件、连接等资源。生成器可把释放逻辑放进 try/finally；但 for 中的 break 只退出消费者循环，不保证关闭迭代器。生成器若还被引用，就可能仍暂停在 yield，finally 尚未执行。资源释放不应依赖垃圾回收的具体时机。

对于已经启动并暂停在 yield 的生成器，调用 close() 会请求其退出并执行 finally。它不会正常消费后续项来完成清理，也不会把下一项交给调用者。contextlib.closing(obj) 则在 with 退出时调用 obj.close()，把关闭时机绑定到明确的作用域；使用前须确认对象支持 close，普通迭代器并不保证具备该方法。

### 预测：判断完整代码的全部输出

```python
from contextlib import closing


def fragments():
    print("open")
    try:
        yield "A"
        yield "B"
    finally:
        print("close")


with closing(fragments()) as stream:
    for piece in stream:
        print("piece", piece)
        break
    print("inside")

print("outside")
```

问题：按顺序写出全部输出；close 发生在 break 时还是退出 with 时？B 会被产出吗？用户已修订通过，未运行。

### 初次批改：break 退出的是 for

用户正确预测B不会产出，但把 close 放在 inside 前，并认为 break 调用了关闭。需要按缩进区分作用域：break 退出 for，随后执行仍在 with 内的 print("inside")；离开 with 时，closing 才调用 stream.close()，生成器执行 finally 并打印 close；然后执行 with 外的 print("outside")。完整输出应为 open、piece A、inside、close、outside，每项独占一行。后续修订已通过，未运行。

用户已重新写出上述正确输出，并解释 break 只退出 for、closing 在退出 with 时调用生成器 close，修订通过。原答案与修订分开放在 notes；未运行预测代码。

## 5. 主练习：流式事件与来源生命周期

骨架见 [a05_stream.py](../a05_stream.py)。实现 stream_events(chunks)，本题约定 chunks 是产出 str 且支持 close 的生成器对象。转换层接管其关闭责任，消费者通过 closing 管理转换层。

关闭外层生成器不意味着任意上游迭代器都会自动关闭；本层必须明确管理自己的来源。消费者退出作用域时关闭外层，外层的清理逻辑再关闭来源，才能让提前停止的路径也完成清理。

具体要求：

- 只跳过空字符串 ""，其他片段原样保留，不能 strip 后丢掉空格；文本片段里的空格可能有意义。
- 每个有效片段产出 {"type": "delta", "text": chunk}。
- 正常耗尽并关闭来源后，产出一次 {"type": "done"}；空来源也正常完成。
- 来源发生普通异常时，异常向上传播，不产出 done；消费者提前关闭时也关闭来源。
- 按需拉取，不整体 list 输入，不提前缓存全部事件。

例如 Py、空字符串、thon 三个片段，事件应是 delta/Py、delta/thon、done。示例来源 finally 的 source closed 应在 done 事件被交给消费者之前打印。

### 首次实现与验证结果

用户以 with closing 管理来源，在 for 中对非空片段 yield delta，正常循环结束后 yield done。输入约定为 str，因此 if chunk 会跳过空字符串，同时保留只包含空格或换行的片段。普通异常从 for 的取值过程向外传播，不执行后续 done。提前关闭外层时，with 的退出逻辑关闭来源。

## 7. 通过验证的完整实现与运行

以下为用户完成的实现及示例，便于独立复习：

```python
from collections.abc import Iterator
from contextlib import closing


def stream_events(chunks) -> Iterator[dict[str, str]]:
    with closing(chunks) as chunks:
        for chunk in chunks:
            if chunk:
                yield {"type": "delta", "text": chunk}
        yield {"type": "done"}


def demo_chunks():
    try:
        yield "Py"
        yield ""
        yield "thon"
    finally:
        print("source closed")


with closing(stream_events(demo_chunks())) as events:
    for event in events:
        print(event)
```

实际输出：

```text
{'type': 'delta', 'text': 'Py'}
{'type': 'delta', 'text': 'thon'}
source closed
{'type': 'done'}
```

此实现以已启动的流式消费为课堂生命周期场景，输入契约为支持 close 的字符串生成器对象。正常耗尽、来源失败、消费者提前停止或失败分别要判断是否产出done和谁负责清理，不能用“最终都会结束”代替具体的生命周期管理。
