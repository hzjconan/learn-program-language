## 1. 项目目标与分步安排

实现读取 JSONL、校验、清洗、去重、输出 JSONL 的命令行工具。综合 P03～P10，不引入第三方依赖。先摸底并实现核心处理，再接文件读写与命令行；pytest 的系统学习和项目测试安排在 P12。本节仍使用必要断言和小样本验证，不启动训练。

练习目录约定为 `p11_docs/`，模块为 `__init__.py`、`processor.py`、`app.py`，用户按任务进展创建，不预先填入实现。课堂从课程根目录用 `python3 -m p11_docs.app --input 输入路径 --output 输出路径` 启动。CLI 参数解析在核心处理评审后讲解。

## 2. 数据处理契约

- 输入 UTF-8 JSONL，空白行跳过，但后续行号仍按文件物理行号计数。
- 每条非空行必须是可解析的 JSON 对象，且有字符串类型的 `text` 字段。缺失、非字符串、非对象和坏 JSON 记录为行错误，继续处理后续行。
- 对 `text` 只做 `strip()`，不转小写，不改变内部空白。清洗后为空字符串也是行错误。
- 按清洗后的文本去重，区分大小写；保留首次出现的有效记录，维持输入顺序。重复项跳过，不计为行错误。
- 保留其他字段，输出记录使用新字典，不修改原输入字典。没有修改嵌套字段的要求，不要求深拷贝。
- 输出每行一个 JSON 对象，使用 UTF-8；行错误保留原文件行号。
- 文件读取或写入失败属于整个任务失败，不能伪装成单行数据错误。CLI 层负责报告失败；先实现核心逻辑再讨论边界。
- 为避免截断输入，本项目拒绝输入与输出为同一个文件，且课堂输出使用新路径；具体检查在文件阶段落实。

## 4. 第一步：独立实现核心处理

创建 `p11_docs/__init__.py`（留空）与 `p11_docs/processor.py`。在后者实现 `clean_records(numbered_records)`。暂不读写文件，不解析 JSON，不处理命令行参数；调用者将已解析的值及真实文件行号传入，核心函数专注校验、清洗与去重。

输入是 `(line_no, value)` 的序列，value 可以是任意已解析 JSON 值。返回 `(records, errors)`：前者保存清洗去重后的新字典；后者保存 `(line_no, 错误说明)`。错误说明非空且能区分非对象、缺失/非字符串 text、清洗后为空即可，暂不固定措辞。

所有数据处理规则沿用第2节。每次调用的去重状态独立；空输入返回两个空列表；不修改输入字典。是否采用类由实际需要决定，这个核心函数不要求套用 P10 的类结构。

验证骨架：

```python
from p11_docs.processor import clean_records

source = [
    (1, {"id": 1, "text": "  Hello  "}),
    (2, {"id": 2, "text": "Hello"}),
    (4, {"id": 3, "text": "hello"}),
    (5, {"id": 4, "text": "   "}),
    (6, {"id": 5, "text": 123}),
    (7, {"id": 6, "text": "  再见  "}),
]
records, errors = clean_records(source)
assert records == [
    {"id": 1, "text": "Hello"},
    {"id": 3, "text": "hello"},
    {"id": 6, "text": "再见"},
]
assert [line_no for line_no, message in errors] == [5, 6]
assert source[0][1]["text"] == "  Hello  "
assert records[0] is not source[0][1]
```

这些断言可放在 processor.py 的 main 函数中，使用入口判断保护，并从课程根目录运行 `python3 -m p11_docs.processor`。除了骨架，请用户自行添加一个「JSON 合法但不是对象」的输入和一个「对象缺失 text」的输入进行验证。保留文件行号由调用方提供，不能在核心函数里重新按列表位置编号。

## 5. 初稿诊断：解释器与数据结构

本机系统 `python3` 为3.9.6，课程 `.venv/bin/python` 为3.12.14。项目要求 Python >=3.12；后续从课程根目录明确运行 `.venv/bin/python -B -m p11_docs.processor`，避免调用到系统解释器。

`f"text {record["text"]}"` 中复用双引号在 Python 3.12 起合法，旧版本会报 f-string 语法错误。可写为 `f"text {record['text']}"` 兼容旧版，但课程仍使用指定环境。参考：[Python 3.12 f-string 语法变化](https://docs.python.org/3.12/whatsnew/3.12.html#pep-701-syntactic-formalization-of-f-strings)。

初稿 errors 存字典，而调用方按二元组读取。迭代字典默认得到键，例如 `first, second = {"line_no": 5, "message": "invalid"}` 得到的是字符串 `line_no` 和 `message`，不会得到5和错误说明。数据生产方与消费方需要遵守同一约定，本题保持 `(line_no, message)` 契约。

此外必须先检查记录是字典，再检查 text 是否存在和为字符串，最后做 strip 与空文本检查。缺失字典键抛 KeyError，非对象下标访问可能抛 TypeError；JSONDecodeError 是 JSON 解析阶段的异常，当前核心函数没有解析 JSON，不能靠捕获它处理结构校验错误。

### 第二轮纠错：短路的保护范围

初次修订将非字典判断放在 or 条件最左边，但错误分支的 f-string 仍读取 `record["text"]`。当 record 是 None 时，条件左侧为真，or 确实跳过右侧；进入分支后构造错误消息是新的表达式，仍然发生不合法下标访问。因此程序仍抛 TypeError。

对字典 `{ "id": 8 }`，非字典判断为假，条件继续读取不存在的 text，抛 KeyError。可靠顺序是：先拒绝非对象并继续下一项，再检查字段存在与类型，随后清洗与空文本校验。诊断消息本身也必须能处理无效数据；非对象错误消息无需读取 text。

用户需补充非对象及缺失 text 的验证输入，检查它们记录正确行号且不会阻断后续有效记录。仅通过原来的混合输入不足以证明这些边界正确。

第三轮修订通过：用户拆分校验分支并 continue，补充了两个失败边界的断言。核心函数的混合输入、真实行号、继续处理、去重与输入隔离等检查全部通过。可清理未使用的 json 导入，并将 `not "text" in record` 改写为更惯用的 `"text" not in record`。

## 6. 第二步：JSONL 文件读写

在 `p11_docs/files.py` 实现两个函数，继续由用户编码：

1. `read_records(path)` 返回 `(numbered_records, errors)`。以 UTF-8、with、enumerate(start=1) 读取，跳过空白行。对每个非空行使用 json.loads，仅捕获该次解析的 json.JSONDecodeError，记录 `(文件行号, exc.msg)` 并继续。成功解析的值作为 `(文件行号, value)` 收集，包括 None、列表等合法 JSON 值；字段校验留给核心函数。文件打开、读取和编码错误向上传播。
2. `write_records(path, records)` 以 UTF-8 写出，每条记录一行，使用 `json.dumps(record, ensure_ascii=False)` 加换行。输出用 `"x"` 模式：只创建新文件，目标已存在时抛 FileExistsError。这样课堂尝试不会意外覆盖已有文件；CLI 后续还要拒绝输入输出同文件。文件错误不要转换为单行数据错误。

`json.loads` 将一段 JSON 文本解析成 Python 值，`json.dumps` 反向将 Python 值编码为 JSON 文本。ensure_ascii=False 使中文在输出中直接可读；若字符串值含换行，dumps 会转义它，JSONL 记录仍占一个物理行。

读写层不负责清洗、字段验证或去重。调用链由后续入口组织：read_records → clean_records → write_records。解析错误和字段错误分别收集，最终在 CLI 合并并按原行号排列。

用 TemporaryDirectory 创建输入和新输出路径。输入内容：

```python
sample = '{"id": 1, "text": "  你好  "}\n\n坏数据\nnull\n{"id": 2, "text": "你好"}'
```

读取后的行号应为 `[1, 4, 5]`，解析错误行号 `[3]`。核心处理应保留 `[{"id": 1, "text": "你好"}]`，字段错误行号 `[4]`。写出后逐行 loads 回读，结果应与 records 相等。再验证重复写入同一路径抛 FileExistsError、读取不存在的路径抛 FileNotFoundError。可在 files.py 的受入口保护 main 中放验证，通过 `.venv/bin/python -B -m p11_docs.files` 启动。

### 文件模块初稿：导入与职责纠错

`from files import ...` 是寻找顶层 files 模块，不会自动按当前包寻找 p11_docs.files。Python 标准库没有通用 File 类；使用已学的 Path 或内置 open。FileExistsError 是内置异常，不必导入。输出使用 open 的 x 模式时，会直接拒绝已有文件，不需要预先检查存在性。

包内调用核心处理使用 `from .processor import clean_records`，点表示当前包。从课程根目录运行 `uv run python -m p11_docs.files` 可保留包上下文。

read_records 应收集解析后的带行号记录，不在逐行读取时调用 clean_records。后者需接收整个记录序列，这样去重集合才能覆盖整批。main 先读取，再整批清洗，最后写入清洗后的字典列表。变量名 errors 需始终一致；append 接收一个项，收集一条带行号记录时该项是 `(line_no, value)`，不是用星号展开后的多个实参。

### 第二轮读写评审：编码与保留错误

用户已修正导入与分层，当前环境的读写、去重、异常传播检查通过。但两处 open 都必须显式指定 `encoding="utf-8"`；当前机器默认编码能够读中文，不能据此认为跨环境编码契约已满足。

main 中先接收读取错误，再用同一个 errors 名称接收校验错误，会丢失后续访问解析错误的入口。应分别保存 parse_errors 和 validation_errors，后续 CLI 才能合并、排序并报告两类问题。

逐行读取使用 `for line_no, data in enumerate(f, start=1)` 即可。`f.readlines()` 先读取全部原始行到列表再迭代，额外占用内存；即使当前仍返回全部解析记录，也无需保留这份原始行列表。

用户的 main 应补上清洗结果、字段错误行号、输出回读的断言，并自行验证 FileExistsError 与 FileNotFoundError。教师临时检查不能替代用户练习中的可重复验证。

### 第三轮读写评审：比较表达式与断言

单独写 `processed_records == records` 只计算 True 或 False，在普通脚本中丢弃结果，不会在不相等时失败；测试需要 `assert`。同时 read_records 返回的成功项是 `(行号, 值)`，例如 `[(1, {"id": 1, "text": "你好"})]`，而 processed_records 是字典列表。回读时先确认解析错误为空，再取出每项的值，与写入前字典列表比较，无需再次清洗，否则可能掩盖写入内容的变化。

第四轮用户修订通过：回读断言正确，两个文件异常用标记加断言验证，预期异常未发生会使断言失败。文件阶段验收通过。

## 7. 第三步：命令行入口

argparse 是标准库，用于定义参数、读取命令行并自动生成帮助。一个独立的演示（不属于项目完整实现）：

```python
import argparse


def main():
    parser = argparse.ArgumentParser(description="问候示例")
    parser.add_argument("--name", required=True)
    args = parser.parse_args()
    print(f"你好，{args.name}")


if __name__ == "__main__":
    main()
```

传入 `--name Alice` 后，args.name 为字符串 Alice；required=True 要求必须提供，缺少时 argparse 自动报告参数错误并以2退出。--help 自动显示帮助并以0退出。项目中可用 `type=Path` 将字符串转成 Path，这只转换路径表示，不验证文件存在。

命令行有两个输出通道：stdout 用于成功摘要，stderr 用于诊断。`print(message, file=sys.stderr)` 写标准错误。返回值只有交给 `sys.exit(main())` 或 `raise SystemExit(main())` 才成为进程退出码；单独 main() 返回1并不会让进程以1退出。

用户在 p11_docs/app.py 实现入口，使用包内相对导入已有函数：

- 必填 --input、--output；从课程根目录运行 `uv run python -m p11_docs.app --input 输入路径 --output 新输出路径`。
- 顺序执行读取、整批清洗、写入。解析错误和字段错误合并后按行号排序，每项打印到 stderr，格式 `line N: MESSAGE`。
- 文件任务成功时 stdout 输出 `written=N errors=M`，N 为写出记录数，M 为两类行错误总数。重复项不计错误。允许有坏行，仍写出有效记录并返回0；空输入也创建空输出，返回0。
- 输入输出 Path.resolve() 相等时拒绝操作，诊断到 stderr，返回1。现有输出仍由 x 模式拒绝，不能覆盖。
- 文件 OSError（含不存在、已存在、权限等）或 UnicodeError（含文本编码问题）报告到 stderr 并返回1，不输出成功摘要。不要捕获全部 Exception 来掩盖编程错误。参数错误交给 argparse，返回2。
- 入口使用 if __name__ 判断，导入 app 时不解析参数、不创建文件、不打印。

本节保留简单的直接写入方式，不实现临时文件加原子替换；写入中途失败可能留下部分输出，但必须报告失败，不能宣称成功。更完整的事务式输出留到后续需要时讨论。

参考：[Python 3.12 argparse 官方文档](https://docs.python.org/3.12/library/argparse.html)。最终将用独立子进程验证命令行输出、退出码、错误排序与文件内容，避免只在函数内验证。

### CLI 第一轮评审

最初 `No module named p11_docs.app` 是因为目录中还没有 app.py；`-m` 会寻找该包路径对应的模块，不会创建模块。用户创建入口后已经能够运行。

初稿把解析错误列表放在字段错误列表前面直接拼接，实际错误顺序是2、6、1、5。拼接只保留各列表内部顺序，不能恢复两类错误在文件中的交错顺序；应对合并结果按元组第一个元素（整数行号）排序，再打印。

成功摘要应严格按约定输出 `written=N errors=M`。摘要是命令行对外契约，不能因为含义相似就随意改名。

未捕获的文件异常虽然也导致进程退出1，但它提供的是 Python traceback；本项目要求 CLI 处理预期环境失败，向 stderr 提供简洁说明并返回1。把路径解析、读写等可能失败的操作放到合适的 try 范围，捕获 `(OSError, UnicodeError)`，不要把 argparse 的参数解析或所有编程错误都用宽泛捕获吞掉。

main 统一返回0或1，入口使用 sys.exit(main()) 传递退出码。成功摘要只在写入完成后打印，失败分支不得继续进入成功摘要。clean_records 应直接从 .processor 导入，不经由 .files 间接取得；导入来源应表达实际模块职责。

### 为什么在 CLI 层捕获，为什么建议 main 返回退出码

这里的 CLI 层就是 app.py 的 main：它接收命令行参数、组织文件操作，并面向终端用户报告结果。调用链为 main → read_records → open。缺失文件时 open 抛 FileNotFoundError，read_records 不把它吞掉，而是传给 main；main 能决定向 stderr 输出「读取失败」并以1结束。输出已存在、权限问题等也属于 OSError；无效 UTF-8 解码属于 UnicodeError。坏 JSON 的单行错误则已由读取层记录并继续，不应混成整个任务失败。

因此，「文件函数向上传播异常」与「入口捕获异常」并不冲突。文件函数保持可复用，不替调用者决定是否退出进程；CLI 根据任务需求处理预期失败。try/except 的示意：

```python
def main():
    # 此处省略参数解析。
    try:
        perform_file_job()  # 示意函数，代表需要用户实现的处理编排。
    except (OSError, UnicodeError) as exc:
        print(f"处理失败: {exc}", file=sys.stderr)
        return 1
    print("处理完成")
    return 0
```

main 内直接 `sys.exit(1)` 完全合法，也能满足本项目的退出码要求。建议返回整数并由入口 `sys.exit(main())`，只是为了把执行任务与退出进程分开：同一 Python 进程的测试可以直接断言 main 返回1，无需捕获 SystemExit。这里不要求为了风格单独返工。

### 排序 API 纠错：sort 与 sorted

`list.sort` 的 key 必须通过关键字传入，而且它修改原列表，返回 None；`sorted` 则返回新的排序列表。例如：

```python
items = [(6, "late"), (2, "early")]
ordered = sorted(items, key=lambda item: item[0])
# ordered 为 [(2, "early"), (6, "late")]，items 未修改。

items.sort(key=lambda item: item[0])
# items 原地排好；不要把 sort 的返回值赋给 items。
```

因此 `errors = some_list.sort(lambda e: e[0])` 有两层问题：位置参数不被接受；补 key= 后返回值仍是 None。这回访 P03 的原地修改与返回值区别。CLI 中也不应捕获 TypeError 来掩盖此类编程错误，应修正调用。

`sys.exit` 实际抛出 SystemExit，正常未捕获时结束进程；它会执行沿途的 finally 和 with 清理，不是立即强杀。SystemExit 不属于 Exception，因此 `except Exception` 通常抓不到。返回1则只是退出当前函数，若入口仅写 main()，正常返回后进程通常仍以0结束，所以需要入口将返回值交给 sys.exit。当前任务接受两种写法，重点是失败时 stderr 诊断、非零退出，且不打印成功摘要。

核心处理复用 P10 的 Pipeline 和 StripCleaner，读取层不在逐行读取时重置去重状态。CLI 最终使用 sorted(..., key=...) 排序，stdout 为 `written=N errors=M`，捕获 OSError 与 UnicodeError 后报告「文件处理失败」并返回1。

从课程根目录运行：

```bash
uv run python -m p11_docs.app --help
uv run python -m p11_docs.app --input input.jsonl --output output.jsonl
```

output.jsonl 必须是新路径。可重复运行用户已有的函数级验证：

```bash
.venv/bin/python -B -m p11_docs.processor
.venv/bin/python -B -m p11_docs.files
```

最终独立进程验证通过：参数错误退出2、帮助退出0；中文去重与错误顺序正确；同路径及已有输出拒绝且原内容不变；文件失败和编码/解码失败均简洁报告并退出1；空文件、全空白、全坏行均成功创建空输出；独立导入无输出。
