## 1. 从字典契约到对象建模

A01 的 TypedDict 描述字典结构，数据仍为普通 dict，通过 message["content"] 访问。dataclass 则用于定义数据对象，实例字段通过点号访问。二者使用不同的数据表示，选择取决于代码需要字典还是对象；dataclass 不会仅因字段上有类型标注就自动校验输入。

```python
from dataclasses import dataclass


@dataclass
class Task:
    name: str
    retries: int = 0


task = Task(name="summarize")
print(task.name)
print(task.retries)
print(task)
```

输出：

```text
summarize
0
Task(name='summarize', retries=0)
```

这里 Task 是类，task 是 Task 的实例，不是字典，不能直接照搬 task["name"] 访问。retries 的默认值为0，因此构造时可以省略；name 没有默认值，构造时需要提供。

## 2. dataclass 生成了什么

`@dataclass` 根据声明的字段为类生成常用方法。此处先理解其效果，装饰器机制留到 A03。

默认生成的初始化方法效果近似如下：

```python
def __init__(self, name: str, retries: int = 0):
    self.name = name
    self.retries = retries
```

因此调用 Task(name="summarize") 会初始化实例属性。默认还会生成 __repr__，让打印时显示类名及字段值；生成 __eq__，使同一个数据类的两个实例可以按字段值比较。值相等不等于同一对象，继续区分 == 与 is。

生成这些方法并不意味着自动检查 name 是否为 str、retries 是否为 int，也不意味着自动把字符串数字转换为整数。运行时类型校验需要另行实现或由校验库提供。

## 4. 可变字段默认值：每个实例分别创建

回访 P04/P05：普通函数的可变默认参数可能在多次调用间共享。标准库 dataclass 对直接使用列表等不可哈希对象作为字段默认值设置了检查，例如下面的定义会在处理类时抛出 ValueError，而不是等到实例共享后才失败：

```python
@dataclass
class Basket:
    items: list[str] = []  # 错误示例，不要与下方正确版本一起运行
```

常见列表字段写为 default_factory：

```python
from dataclasses import dataclass, field


@dataclass
class Basket:
    owner: str
    items: list[str] = field(default_factory=list)


a = Basket("A")
b = Basket("B")
a.items.append("apple")
print(a.items)  # ['apple']
print(b.items)  # []
print(a.items is b.items)  # False
```

field 用来配置字段，default_factory 接收一个无须参数即可调用的工厂。这里传入 list 本身；当创建实例且未提供 items 参数时，生成的初始化方法调用 list() 得到新列表。每次这样的构造分别调用工厂，所以列表独立。不能写 default_factory=list()，那样传入的是已经创建的列表，不是可调用的工厂。

可以近似理解为「省略 items 时，在这次初始化内部执行 self.items = list()」，不是在类定义时创建一个列表供所有实例共用。不要为了实现独立列表而直接套用可变默认参数写法。

default_factory 只处理未提供字段值的情况。如果调用者显式传入同一个列表，dataclass 默认直接保存该引用，不会自动复制：

```python
shared = ["apple"]
a = Basket("A", items=shared)
b = Basket("B", items=shared)
```

此时 a.items、b.items、shared 指向同一个列表。工厂不能保证显式传入的数据自动隔离，也不负责运行时元素类型校验。

参考：[dataclass 字段与默认工厂](https://docs.python.org/3.12/library/dataclasses.html#dataclasses.field)。

## 6. Pydantic：由库读取标注并执行校验

已执行 `uv add 'pydantic>=2,<3'`，更新 pyproject.toml 和 uv.lock。本课实际安装并验证 Pydantic 2.14.4、pydantic-core 2.50.5。安装是课程运行依赖，不是只供测试使用的开发依赖。

普通 Python 不会自动根据字段标注校验对象；Pydantic 则通过 BaseModel 等入口主动读取字段声明，提供校验与解析逻辑。检查行为来自库的实现，不是类型标注突然改变了 Python 的规则。

```python
from typing import Literal
from pydantic import BaseModel


class JobConfig(BaseModel):
    mode: Literal["fast", "safe"]
    retries: int = 0


config = JobConfig.model_validate({"mode": "safe", "retries": "3"})
print(config.mode)             # safe
print(config.retries)          # 3
print(type(config.retries))    # <class 'int'>
print(config.model_dump())     # {'mode': 'safe', 'retries': 3}
```

JobConfig 继承 BaseModel，而不是添加 @dataclass。model_validate 接收这里提供的字典，解析并验证字段，成功后返回 JobConfig 实例，通过 config.mode 访问。model_dump 则把本例模型导出为普通字典，不等于生成 JSON 字符串。未传 retries 时使用默认值0；mode 没有默认值，必须提供。

### 校验可以伴随转换

上例输入 retries 是字符串 "3"，输出字段变为整数3。Pydantic 默认会按规则进行部分类型转换，并非要求所有输入原本就完全符合目标类型。不要据此假设任意字符串都能转换，也不要假设所有字段类型都会任意互转。严格模式与额外字段规则稍后再展开。

### 校验失败用异常表达

```python
from pydantic import ValidationError


try:
    JobConfig.model_validate({"mode": "turbo", "retries": "abc"})
except ValidationError as exc:
    for error in exc.errors():
        print(error["loc"], error["type"])
```

实际验证输出：

```text
('mode',) literal_error
('retries',) int_parsing
```

turbo 不在允许的 Literal 值中，abc 无法解析为整数；同一次调用可以收集多个字段错误。model_validate 在失败时抛 ValidationError，而不是返回半个有效模型或 None。errors() 返回结构化错误列表，loc 表示字段路径，type 是错误类别。捕获异常后的程序行为由调用方决定，继续回访 P07 的异常边界。

参考：[模型与数据转换](https://pydantic.dev/docs/validation/latest/concepts/models/)。本节示例已在实际安装版本执行验证。

## 8. 输入规则：严格模式与额外字段

允许将 "3" 解析为整数有时方便，有时会掩盖外部数据格式问题。可以用模型配置启用严格模式，并独立设置额外字段规则：

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict


class StrictJobConfig(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")

    mode: Literal["fast", "safe"]
    retries: int = 0
```

model_config 是 Pydantic 识别的配置，不是要求调用者提供的业务字段。ConfigDict 在这里保存校验配置。

strict=True：本例 int 字段要求符合严格整数规则，拒绝字符串 "3"。不要理解成对任何字段都机械使用 type(value) is 标注类型；不同目标类型和输入入口有具体规则，本节先掌握这个整数例子。

extra="forbid"：输入多出未声明字段时抛 ValidationError。默认 extra="ignore" 会忽略多余字段，不因它们出现而失败；也可以选择 allow 保留，此处不展开。strict 与 extra 控制不同的行为，严格类型规则并不自动意味着禁止多余字段。

实际验证：StrictJobConfig 接收 mode=safe、retries=2；输入 retries="3" 产生 retries/int_type 错误；输入额外 debug=True 产生 debug/extra_forbidden 错误。普通 JobConfig 的额外 debug 则被忽略，model_dump 不包含它。

参考：[严格模式](https://pydantic.dev/docs/validation/latest/concepts/strict_mode/)、[额外字段配置](https://pydantic.dev/docs/validation/latest/api/pydantic/config/#pydantic.config.ConfigDict.extra)。

### 理解题：分别判断独立调用

1. StrictJobConfig.model_validate({"mode": "fast", "retries": "2", "debug": True}) 会成功吗？有哪两个字段问题，分别由哪条配置控制？
2. StrictJobConfig.model_validate({"mode": "safe", "retries": 2}) 与 StrictJobConfig.model_validate({"mode": "safe"}) 分别能否成功？后者的 retries 是多少？

先推理，不运行；随后进入 JSON 结构化输出解析与用户编码。

两题已通过：字符串 "2" 由 strict 规则拒绝，debug 由 extra="forbid" 拒绝；合法整数输入与省略 retries 均成功，后者默认0。

### model_config 的名称约定

课堂用户询问 model_config 是否为固定名字。它是 BaseModel 识别的配置属性名，不能任意改名来期待同样的配置效果。ConfigDict 是导入的工具，可以通过 as 起别名，但属性仍需叫 model_config。这是库约定，不是 Python 对任意类都提供的特殊配置语法。

## 9. 直接解析 JSON 字符串

模型或外部接口通常返回文本。在本课中先使用人工构造的 JSON 字符串，不调用真实模型接口。model_validate 接收本课之前使用的字典；model_validate_json 可以直接接收 JSON 字符串，完成 JSON 解析与字段校验：

```python
raw = '{"mode": "safe", "retries": 2}'
config = StrictJobConfig.model_validate_json(raw)
print(config.mode)  # safe
print(config.model_dump())  # {'mode': 'safe', 'retries': 2}
print(config.model_dump_json())  # {"mode":"safe","retries":2}
```

model_dump 返回普通 Python 字典，model_dump_json 返回 JSON 字符串，不要混淆二者的返回类型。字符串外层用单引号只是 Python 的书写方式，JSON 内部的键和字符串使用双引号。

model_validate_json 遇到非法 JSON 也抛 Pydantic 的 ValidationError，结构化错误类别为 json_invalid；已经是合法 JSON 但字段不合要求，也抛 ValidationError。不要在此入口误用 pytest.raises(json.JSONDecodeError)，后者是直接调用 json.loads 等标准库入口时可能遇到的异常。

## 10. Field：类型之外的字段约束

类型正确不意味着数值或内容符合要求。可以进一步用 Pydantic 的 Field 配置字段：

```python
from pydantic import BaseModel, ConfigDict, Field
from typing import Literal


class JobConfig(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")

    mode: Literal["fast", "safe"]
    retries: int = Field(default=0, ge=0)
```

default=0 提供默认值；ge=0 表示大于或等于0，因此整数-1即使类型正确仍会被拒绝。不提供 default 的 `Field(min_length=1)` 仍要求字段必填，用于限制字符串至少包含一个字符。它不自动 strip，单个空格长度也是1，不等同「至少一个非空白字符」。本次练习不额外要求去掉空白。

Pydantic 的 Field 与 dataclasses 的 field 是不同工具：前者为 Pydantic 模型配置字段，后者用于标准库 dataclass；注意首字母大小写。Pydantic 也支持 `Field(default_factory=list)`，在字段被省略时为每次构造提供新的默认列表。

教师已在安装版本验证 model_validate_json、两种导出方式、非法 JSON 的 json_invalid 以及负 retries 的 greater_than_equal 错误。

参考：[JSON 解析](https://pydantic.dev/docs/validation/latest/concepts/json/)、[字段定义与约束](https://pydantic.dev/docs/validation/latest/concepts/fields/)。

## 13. 最终实现与复习入口

用户最终实现核心如下；完整会话断言见 [a02_models.py](../a02_models.py)，解析与错误路径测试见 [test_a02_models.py](../tests/test_a02_models.py)。

```python
from dataclasses import dataclass, field
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field
from a01_message import Message


@dataclass
class Conversation:
    title: str
    messages: list[Message] = field(default_factory=list)


class Ticket(BaseModel):
    model_config = ConfigDict(strict=True, extra="forbid")

    title: str = Field(min_length=1)
    priority: Literal["low", "normal", "high"]
    tags: list[str] = Field(default_factory=list)


def parse_ticket(raw: str) -> Ticket:
    return Ticket.model_validate_json(raw)
```

Conversation 表达内部数据对象，标准库 dataclass 不自动检查消息字段类型；Ticket 用于外部输入边界，调用 Pydantic 的解析校验入口后才能取得符合声明要求的对象。parse_ticket 的失败由调用方处理，不吞掉异常也不返回伪造成功结果。

| 本课工具 | 数据表示与作用 |
|---|---|
| TypedDict（回访 A01） | 声明字典的静态结构；数据仍为字典，不自动运行时校验 |
| 标准库 dataclass | 定义对象，生成初始化、显示及比较等方法；默认不做字段类型校验 |
| Pydantic BaseModel | 通过模型构造和校验入口按声明的类型、约束、配置处理输入 |

本课使用两个工厂都写 list：dataclasses.field 用于 Conversation，pydantic.Field 用于 Ticket。它们配置的是不同系统的字段，不能交换使用。默认工厂在省略参数时创建新列表，不会替显式传入的共享列表自动隔离引用。

## 14. 结构有效不等于事实正确

title=" " 满足 min_length=1，因为当前没有去空白配置。若业务要求非空白文本，需要再声明或编写相应规则，不能从「至少一个字符」自动推导出来。

同样，原文是「我要退货」，提取结果 title="用户希望再次购买"、priority="low"、tags=[] 仍能通过当前模型。它满足字段、类型、枚举、长度及额外字段规则，但内容与原文不符。结构化输出解析能发现契约内的格式/字段问题，事实和任务效果仍需用原文对照、样本评测等方式验证。用户已在该换场景题正确区分二者。
