## 1. `try` 和 `except` 怎样改变执行顺序

Python 从上到下执行 `try`。某一行抛出异常时，`try` 中余下的语句会被跳过。如果当前有匹配该异常类型的 `except`，Python 会执行这个处理块。处理块正常结束后，程序继续执行整个 `try` 语句之后的代码。

`int("30")` 返回 `30`。`int("abc")` 收到的是字符串，但字符串内容无法转换成整数，所以会抛出 `ValueError`。捕获具体的 `ValueError` 可以让这里处理预期中的输入格式错误。

```python
def parse_timeout(raw):
    try:
        print("开始转换")          # ①
        timeout = int(raw)
        print("转换成功", timeout) # ②
    except ValueError:
        print("格式错误")          # ③
    print("继续处理")              # ④
```

先不运行，分别预测 `parse_timeout("30")` 和 `parse_timeout("abc")` 会执行哪些编号的 `print` 以及各自的输出。两次调用独立考虑。

`"30"` 走 ① → ② → ④，输出“开始转换”“转换成功 30”“继续处理”。`"abc"` 走 ① → ③ → ④，输出“开始转换”“格式错误”“继续处理”。

## 2. 用 `finally` 做退出前的清理

```python
def parse_timeout(raw):
    try:
        print("开始转换")           # ①
        timeout = int(raw)
        print("转换成功", timeout)  # ②
    except ValueError:
        print("格式错误")           # ③
    finally:
        print("结束转换")           # ④
    print("继续处理")               # ⑤
```

| 输入 | 执行顺序 | 调用方看到的结果 |
|---|---|---|
| `"30"` | ① → ② → ④ → ⑤ | 正常结束 |
| `"abc"` | ① → ③ → ④ → ⑤ | `ValueError` 已在函数内处理 |
| `None` | ① → ④ | `TypeError` 继续向外传播 |

`finally` 在正常退出、捕获后退出、异常继续传播时都会执行。`int(None)` 的 `TypeError` 与 `except ValueError` 不匹配，执行 ④ 后会传给调用方，⑤ 不会执行。这也是 `finally` 适合做资源清理的原因。

## 3. 用 `raise` 主动拒绝无效值

```python
def parse_positive_timeout(raw):
    timeout = int(raw)
    if timeout <= 0:
        raise ValueError("超时秒数必须大于 0")
    return timeout

def configure(raw):
    try:
        timeout = parse_positive_timeout(raw)
        print("配置成功", timeout)  # ①
    except ValueError:
        print("配置无效")            # ②
```

`configure("30")` 输出“配置成功 30”。`configure("-5")` 在转换成功后由 `raise` 拒绝，`configure("abc")` 在 `int(raw)` 中就失败，两者都执行 ②。数据能转成整数，还需要满足超时大于零的业务要求。

## 4. 用 `raise ... from ...` 保留底层原因

```python
def parse_positive_timeout(raw):
    try:
        timeout = int(raw)
    except ValueError as exc:
        raise ValueError("超时配置必须是整数") from exc  # ①

    if timeout <= 0:
        raise ValueError("超时秒数必须大于 0")           # ②

    return timeout
```

`as exc` 把原异常绑定到局部变量。`from exc` 把它指定为新异常的直接原因，调用方仍收到带上下文的 `ValueError`，traceback 能显示两层错误。`"abc"` 命中 ① 并保留转换异常，`"-5"` 命中 ②，没有显式直接原因。把 `try` 限在转换这一步，范围错误就能保留自己的消息。

## 5. 主练习：批量读取超时配置

在 `python/timeout_config.py` 实现 `parse_positive_timeout(raw)` 和 `load_timeouts(raw_values)`。前者按上面的规则转换一个字符串，后者逐个调用它，返回 `(timeouts, errors)`。`timeouts` 收集有效整数。`errors` 收集 `(原字符串, 错误消息)`，消息可用 `str(exc)` 取得。两个列表都保留输入顺序。

```python
load_timeouts(["30", "abc", "-5", "5"])
# ([30, 5], [("abc", "超时配置必须是整数"), ("-5", "超时秒数必须大于 0")])
```

批量函数能处理单项的 `ValueError`，记录后继续下一项。约定输入项是字符串，`None` 属于调用方用错类型，产生的 `TypeError` 继续向上传播。外部服务超时也应由能决定重试、回退或报错的调用层处理。

用 `main()` 验证上述混合批次和空批次 `([], [])`。再验证 `load_timeouts(["30", None, "5"])` 会向调用方抛出 `TypeError`。教学评审会额外检查原始转换异常是否保留。

本次实现的 `try` 位于循环内。`"abc"` 和 `"-5"` 分别被记录，后面的 `"5"` 仍会处理。`TypeError` 不匹配 `except ValueError`，因此调用者有机会看到类型问题。读取异常消息时，常用写法是 `str(exc)`，让 Python 调用对应的字符串转换方法。
