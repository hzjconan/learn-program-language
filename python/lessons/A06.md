## 1. 调用协程函数不会立即执行函数体

普通的 async def（本节不含 yield）定义协程函数，调用后得到协程对象。调用本身不执行函数体，也不会自动把它排入运行队列。可在协程中 await 它来运行并等待结果，或者后续通过任务调度执行。

与 JS 对照：调用 JS 的 async 函数时，函数体会立即执行到第一个 await 或结束，返回 Promise。Python 调用 async def 函数时先得到尚未开始执行的协程对象。不要把 Python 的协程对象直接套成已自动开始运行的 JS Promise。

在本课的同步脚本入口使用 asyncio.run(main())：main() 创建入口协程，run 管理事件循环并运行它直到完成。循环负责协调可运行的任务与等待中的操作；本课随后再展开任务调度。

await expr 等待可等待对象完成，成功时取得其结果；失败时异常在 await 处传播。等待期间可以给事件循环调度其他任务的机会，但写了 await 不等于创建了并发任务，也不表示代码自动在新线程运行。

asyncio.sleep(0) 在本例用于主动让出一次执行机会，不模拟真实网络，也没有启动额外工作。对两个尚未调度的协程对象逐个 await，第一个完成后才会开始第二个。

## 3. Task：把协程交给事件循环调度

asyncio.create_task(coro) 将协程包装成Task并提交给当前运行的事件循环调度。Task 也可以 await，等待其结果或异常；但它的启动不需要等到显式 await 该Task。必须在已经运行的事件循环中创建，本课放在 main 内。

本例使用 Python 3.12 默认任务工厂，未启用 eager_task_factory 等定制调度。创建任务后，main 先继续执行自己的代码；当main等待尚未完成的任务而让出控制权，事件循环再推进排队的任务。work 内的 sleep(0) 又明确让出一次执行机会。这里是同一线程中的协作调度，没有创建工作线程。

### 初次批改：提交调度不等于在调用处立即执行

用户正确判断a、b为Task，且B不必等await b才启动，但将created放在两个任务结束之后。默认任务工厂下，create_task先排队，不抢在当前main的下一条同步语句之前执行work。main会先打印created；await a发现A尚未完成时才暂停main，让事件循环推进其他任务。本例接着输出start A、start B、end A、end B，最后main打印a、b。

用执行位置理解三步：调用work创建协程；create_task提交运行调度；await task等待结果。已经完成的Task可以直接交回结果，await也并非每次都必然暂停或切换。这里main第一次等待A时，A尚未执行，才会实际让出。不能把本例的默认行为推广成所有自定义任务工厂的规则。后续修订已通过，未运行预测代码。

用户已修订为created、start A、start B、end A、end B、a、b，每项独占一行，并解释create_task提交调度后main继续执行，全部正确；预测题未运行。

## 4. 主练习：先启动任务，再按输入顺序收集结果

骨架见 [a06_jobs.py](../a06_jobs.py)。实现async def run_jobs(names, worker)，本轮约定worker是接收str并成功返回str的协程函数。先为全部输入创建Task，再按输入顺序await和收集结果。空输入返回[]，输入列表不修改，不在本函数内调用asyncio.run。

等待一个Task只暂停当前等待者；其他已经调度的任务仍可推进。因此，即使按输入顺序等待结果，也不等于按输入顺序逐个启动任务。相反，如果循环中每创建一个任务就立即await它，再去创建下一个，本例会退回逐项执行。

练习的demo_worker让A短暂等待0.02秒、B只让出一次；即使B先完成，返回列表仍应对应输入[A, B]，即['a', 'b']。无需通过总耗时判断并发；测试应观察执行事件。

测试由用户编写，放在tests/test_a06_jobs.py。普通def测试可在内部用asyncio.run运行异步场景，不需要安装额外pytest插件。在测试worker中记录start/end，使用await asyncio.sleep(0)让出；断言首个end之前全部输入的start均已出现，并检查结果顺序、输入未改与空输入。这样能区分“先启动全部任务”和“启动一项就等待一项”，不让返回值碰巧正确掩盖错误执行方式。

## 5. gather 与测试评审

用户自行采用先创建全部Task、再await asyncio.gather(*tasks)的实现。gather用于聚合多个可等待对象；成功时返回列表，结果位置对应传入顺序，而不是完成顺序。这里tasks已提前创建，因此gather接收的是这些Task，*tasks负责把列表展开为多个位置参数。该实现符合当前成功路径的要求。

用户测试记录start/end并找到首个end，断言此前所有start均已发生，能识别循环中启动一个就等待一个的串行实现；这项测试已通过。不过所有worker都只sleep(0)一次，完成顺序与输入相同，只检查返回列表不足以区分“按输入顺序返回”和“按完成顺序返回”。可让A多一次sleep(0)，观察B先结束，同时仍断言结果对应输入顺序；无需依赖时间阈值。

空输入测试调用run_jobs([], demo_worker)，但测试模块未定义或导入demo_worker。Python先求值调用参数，因此即使run_jobs会立即返回[]，也会先在读取demo_worker名字时抛NameError，根本进不到run_jobs。修订可采用测试本地的async worker，并让该worker一旦执行就令测试失败，以同时验证空输入不会调用worker。初次测试为1通过、1失败，后续修订后两项通过。

## 7. 通过验证的完整实现

以下为用户完成的实现与本节运行示例，供独立复习：

```python
import asyncio


async def run_jobs(names: list[str], worker) -> list[str]:
    if len(names) == 0:
        return []
    tasks = [asyncio.create_task(worker(name)) for name in names]
    results = await asyncio.gather(*tasks)
    return results


async def demo_worker(name: str) -> str:
    print("start", name)
    await asyncio.sleep(0.02 if name == "A" else 0)
    print("end", name)
    return name.lower()


async def main():
    results = await run_jobs(["A", "B"], demo_worker)
    print("results", results)


if __name__ == "__main__":
    asyncio.run(main())
```

实际运行输出：

```text
start A
start B
end B
end A
results ['a', 'b']
```

列表推导式在首次等待之前就创建全部Task；gather等待这些任务并将结果按传入顺序放进返回列表。输入顺序、任务启动顺序、完成顺序、结果排列顺序需要分别判断，不能看到返回列表正确就断言并发方式正确。

测试命令为 .venv/bin/python -B -m pytest -q -p no:cacheprovider tests/test_a06_jobs.py，最终2 passed in 1.02s。用户测试同时覆盖全部任务先启动、B和C先于A完成、结果仍按输入顺序、输入未修改、空输入不调用worker。普通同步测试通过asyncio.run运行测试场景；这是测试的脚本入口职责，不应将asyncio.run搬进已经运行的run_jobs协程内部。主练习按约定只验收worker正常完成路径，A07/A08继续扩展并发限制与生命周期。
