## 1. 信号量限制受限区域的进入数量

A06先创建全部Task，可以让它们交错推进。若同时发起的操作太多，需要给实际处理区域设并发上限。asyncio.Semaphore(2)可理解为两份可用许可：任务进入前获取许可，暂时没有许可则等待；离开时归还，其他等待任务才有机会进入。

```python
async with sem:
    await worker()
```

async with sem负责进入时等待获取许可、退出时释放；可以按await sem.acquire()配合try/finally中的sem.release()理解。即使在受限区域里await，许可也不会因此归还，要到退出该区域才归还。

信号量控制的是同时持有许可的数量，不是已创建Task总数；等待许可的任务依旧是已经创建的任务。共享同一个信号量才能共同受同一上限约束。本段控制同时进行的操作数量，不保证每秒调用次数，后续按实际接口要求再学习速率规则。

## 2. 开课预测：判断完整代码的全部输出

```python
import asyncio


async def work(name, sem):

    async with sem:
        print("enter", name)
        await asyncio.sleep(0)
        print("leave", name)

async def main():

        asyncio.create_task(work(name, sem))

```

### 初次批改：获取许可不必然暂停

Semaphore有可用许可时，获取可以直接完成，不需要暂停当前任务。A打印wait A后，计数从2减到1，立即进入区域打印enter A；到sleep(0)才明确让出。接着B打印wait B，取得剩下的许可并打印enter B，到sleep(0)让出。C打印wait C后，没有可用许可，才需要等待。不能先把三个wait都列出来，再让A、B进入。

A、B在sleep(0)期间仍然占用许可，因此C不能因它们暂停就立即进入。3个work任务已创建，最多2个在区域内持有许可；这个上限不等于Task总数，也不表示两个CPU线程并行。

最后gather返回的是按传入顺序排列的列表，外层print会显示['a', 'b', 'c']，不是分别打印a、b、c。回访A06：await和async with都不能简单理解成每次必然切换任务；是否真正等待取决于当时对象状态。本例用户许可占用判断正确，完整输出仍待修订，预测题未运行。

### 让出执行机会不等于归还许可

用户追问sleep(0)处“让出”是否表示让出信号量。这里让出的是执行机会：当前任务暂停，事件循环可以推进其他任务，但它仍然持有已获取的许可。许可到退出async with才归还。A、B都暂停时，C可以执行wait C，却会在获取许可处等待。

用户修订后的任务顺序为scheduled、wait A、enter A、wait B、enter B、wait C、leave A、leave B、enter C、leave C，全部正确；最后一行仍写a b c，教师再次批改为['a', 'b', 'c']。原答案与修订分开放在notes，预测未运行。返回列表形态将继续在主练习实际验证。

## 4. 共享状态：跨await的读改写

先前测试计数器的同步更新之间没有await。在本课单线程事件循环内，任务不会在这些普通同步语句之间主动交出控制权。但若“读取当前值”和“写回新值”之间发生await，其他任务可在这段间隙读取同一个旧值。之后各自用旧值计算再写回，可能互相覆盖；不需要多个CPU线程才能发生这种逻辑交错。

### 预测：判断完整代码的全部输出

```python
import asyncio


async def add_one(state, name):
    before = state["count"]
    print("read", name, before)
    await asyncio.sleep(0)
    state["count"] = before + 1
    print("write", name, state["count"])


async def main():
    state = {"count": 0}
    tasks = [
        asyncio.create_task(add_one(state, name))
        for name in ["A", "B"]
    ]
    await asyncio.gather(*tasks)
    print("count", state["count"])


asyncio.run(main())
```

问题：按顺序写出全部终端输出；本例只有一个事件循环线程，为什么仍可能丢掉一次累加？用户正确预测四行read/write并解释原因，仅漏最后一行count 1，教师已补充，未运行。

### 读到的旧值不会自动随共享对象更新

A和B先后读取0，分别保存在各自协程调用的局部before中。A写回1之后，B的before仍是它之前读到的0；写回before+1仍为1，覆盖了A的结果，而不是在共享对象最新值基础上累加。before不是指向字典字段、会随字段更新的动态引用。用户原因解释正确，完整终端输出应为read A 0、read B 0、write A 1、write B 1、count 1，每项独占一行。

## 5. Lock：保护完整读改写

asyncio.Lock用于互斥进入一段代码，一次只有一个任务持有锁。

```python
lock = asyncio.Lock()

# 在协程内：
async with lock:
    # 在这里维护共享状态的一致性
    ...
```

async with进入时获取锁，退出时释放；在内部await也不会自动释放。这与信号量许可保持到退出的机制相似，但这里的目标是让共享更新不互相穿插。各个任务必须共享同一把锁。

需要保护从读取旧值、经过等待、到写回结果的整个区间。仅锁住最后一行赋值，仍可能用先前在锁外读到的过期before写回，无法保证累计正确。若业务允许同步完成更新，也可以设计为更新区间不跨await；本练习刻意保留sleep(0)，学习锁如何维护这一段的一致性。

修订骨架见 [a07_counter.py](../a07_counter.py)。main已创建一把共享锁并传给A、B。由用户实现add_one(state, name, lock)，保留read/write打印和sleep(0)，用锁使最终count为2。用户写好后再评审和运行，不提前提供完整答案。

### 首次实现评审：with与async with的区别

用户已正确圈定完整读改写，但写成with lock。实际运行在该行抛TypeError，提示Lock不支持同步上下文管理协议。asyncio.Lock需使用async with，因为进入锁的过程可能要等待其他任务释放。

普通with使用同步的__enter__/__exit__协议；async with使用异步的__aenter__/__aexit__协议并等待进入与退出。这不取决于外层函数名字是否带async：在协程里管理支持同步协议的closing仍可用with；管理asyncio.Lock则需async with。当前只需用户修订获取锁那一行，保护范围和其余逻辑保持其正确实现。

## 6. 有界队列：让生产者等待消费者腾出容量

先前Semaphore限制实际worker区域的并发，但为全部输入创建Task仍会保留全部待办任务。另一种结构是固定数量消费者，从有界队列逐项取任务；生产者在队满时等待，避免无节制地提交待办项。这种由下游容量使上游暂停提交的机制称为背压。

参考 [Python 3.12官方队列文档](https://docs.python.org/3.12/library/asyncio-queue.html)：Queue(maxsize=1)最多保存一个尚未被取走的项；await q.put(item)在队满时等待；await q.get()取走并返回一项，队空时等待。get取走后，队列就腾出容量，不需要等待消费者完成后续处理。队列内排队项数和消费者手中正在处理的项数是不同指标。

### 预测：判断完整代码的全部输出

```python
import asyncio


async def producer(q):
    for item in ["A", "B"]:
        print("put begin", item)
        await q.put(item)
        print("put end", item)


async def consumer(q):
    for _ in range(2):
        item = await q.get()
        print("get", item)
        await asyncio.sleep(0)


async def main():
    q = asyncio.Queue(maxsize=1)
    p = asyncio.create_task(producer(q))
    c = asyncio.create_task(consumer(q))
    print("ready")
    await asyncio.gather(p, c)


asyncio.run(main())
```

问题：按顺序写出全部输出；producer把B放进队列，需要等消费者取走A，还是要等消费者处理完A？本例sleep(0)代表取走后仍有异步处理步骤。当前尚未使用join或完成记账，后续再展开。预测题尚待用户答案，未运行。

### 初次评审：先定位实际暂停的位置

## 7. 完成记账与消费者退出

get取走一项就腾出队列容量，消费者此时可能仍在处理。task_done()则用于处理结束后的完成记账，它是同步方法，不加await。await q.join()等待所有已put项的完成账，而不是仅等队列为空。每次成功get对应一次task_done，少记会使join等不到完成，多记会报错。

```python
item = await q.get()
try:
    # 处理本次取到的项
    ...
finally:
    q.task_done()
```

本课先约定worker成功完成；finally保证退出分支不会漏账，不应由task_done推断业务处理一定成功。失败与取消时如何管理其他任务，在A08系统展开。

持续等待get的消费者不会自动知道生产结束。本题约定None表示结束，一名消费者取到后退出；有几个消费者，就在全部数据后放几个None。结束信号本身也经过put/get，因此也须配task_done，不能在进入finally之前就直接返回。

若要保持输入顺序，可把(index, name)放进队列；消费者处理完后把结果写入results[index]。不同任务写不同索引，结果排列与完成先后分开；本例写结果是一条同步赋值，不跨await读改写同一个字段。预分配完整结果列表意味着输出内存仍随输入增长，有界队列只限制待办缓冲，不能将整个函数称为常量内存。

### join的未完成项计数与最终复测结果

用户追问join的含义后，补充如下完整过程：

| 操作 | 队列内排队项数 | 未完成项数 |
|---|---:|---:|

| put("A")成功 | 1 | 1 |

```python
import asyncio


async def run_limited(names: list[str], worker, limit: int) -> list[str]:
```

## 12. 通过验证的实现：固定消费者与有界队列

用户实际采用(None, None)结束信号，生产者与消费者两端一致。以下完整示例与源码逻辑一致：

```python
import asyncio


async def run_queued(names, worker, workers, buffer_size) -> list[str]:
    if type(workers) != int or workers <= 0:
        raise ValueError("workers must be a positive int")
    if type(buffer_size) != int or buffer_size <= 0:
        raise ValueError("buffer_size must be a positive int")

    q = asyncio.Queue(maxsize=buffer_size)
    results = [""] * len(names)

    async def produce():
        for i, name in enumerate(names):
            await q.put((i, name))
        for _ in range(workers):
            await q.put((None, None))

    async def consume():
        while True:
            i, name = await q.get()
            try:
                if name is None:
                    break
                results[i] = await worker(name)
            finally:
                q.task_done()

    consumers = [asyncio.create_task(consume()) for _ in range(workers)]
    await produce()
    await q.join()
    await asyncio.gather(*consumers)
    return results


async def demo_worker(name: str) -> str:
    print("start", name)
    await asyncio.sleep(0.01 if name == "A" else 0)
    print("end", name)
    return name.lower()


if __name__ == "__main__":
    print(asyncio.run(run_queued(["A", "B", "C", "D"], demo_worker, 2, 1)))
```

实际日志为start A、start B、end B、start C、end C、start D、end D、end A，最后打印['a', 'b', 'c', 'd']。固定消费者各自处理项，结果按不同索引写回；结束信号退出分支仍经过finally，记账不会遗漏。get在try前，保证仅对已经成功取得的项记完成账。

本例协调骨架与课堂契约保证worker正常返回；并未实现工作失败后的其他消费者取消、超时和完整故障恢复，这些是A08的后续学习内容。参数边界与成功路径验收不等于已验证失败生命周期。
